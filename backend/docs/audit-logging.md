# 管理写操作审计执行合同

正式业务事实与对应成功业务事件必须使用同一个 `Executor`，在同一事务中提交。业务代码提供明确动作与允许记录的结果投影；统一执行边界构造、校验并持久化事件。

## 身份、动作与事实

1. 认证入口从已验证身份构造 `AuditActor`。Handler 传递操作人、命令输入及已有请求关联，不接受客户端指定审计动作、目标类型或成功结果。
2. 普通动作必须在 `erp-audit::registered_actions` 以精确动作与目标类型配对登记。未知动作、错误目标类型及嵌入对象 ID 的动作代码必须失败关闭。类型化本域 Service 或命名 Process 登记 `AuditAction`，固定动作代码、中文名称、动作版本、目标类型及字段白名单。字段名、状态代码与中文含义必须显式登记，不得从权限、函数名或 HTTP 路径推导。
3. `BusinessEventContext::new` 在正式业务写入前验证动作与操作人。可选名称快照只接受当前命令已取得的安全名称；未取得名称时保留缺失，不得在展示时查询当前名称补成历史名称。
4. 目标 ID、业务编号快照、状态变化、数量和金额等结果事实由执行后的 `BusinessEventContent` 明确提供。上下文在审计写入前验证结果事实及允许字段。结果校验失败必须阻止本事务提交。
5. `BusinessEventResult` 表示命令执行结果。服务结果、审批决定及其他业务结果必须作为独立业务事实保存。确认服务失败事实可以对应一次成功执行的确认命令。
6. 可记录值限定为登记的状态代码与中文名称、精确 `Quantity`、精确 `Amount` 或“已变更”。不得提供任意实体、请求体、凭据、完整敏感值、密文或银行卡信息的通用序列化入口。
7. 审计关联 `command_id`、`request_id` 用于追溯。业务幂等结果、参与资格、创建人及终态判断必须读取拥有领域的回执和事实，不得解析审计 `message` 或结构化事件代替业务来源。
8. `event_sequence` 为 `NonZeroU32`，单事件默认1；上下文和日志 builder 必须拒绝0，反序列化不得接受缺失或零序号。一个命令的主、子事件共享 `command_id`，按原业务写入顺序分配序号。批次必须在首个业务写入前通过 checked 数量、乘法和加法验证全部序号容量，溢出明确失败，不得截断、饱和或写入后重新编号。
9. 请求关联只传递入口已经确定的安全追踪号。`AuditActor`、领域 Prepared 记录和 adapter 必须完整传递名称、请求编号及事件序号；内部调用没有请求号时保持 `None`，不得在事件构造时生成或用当前请求替换既有快照。

## 统一执行入口

| 入口 | 执行要求 |
| --- | --- |
| `erp-processes::audit::execute_audited` | 接收已验证上下文、`AuditedCommand`、`AuditEventSink` 及调用方的 `Executor`；不启动事务。首次成功执行完成结果校验后写一次事件；`AuditedWrite::Replayed` 直接返回原结果，不追加成功事件 |
| `erp-processes::audit::run_audited_event` | 在用例入口建立唯一事务，事务内调用 `execute_audited`；命令只包含必须原子的数据库规则与读写，外部 HTTP/S3/文件 I/O 位于事务之外 |
| `erp-processes::audit::execute_prepared` | 统一执行普通写闭包，先验证静态登记和成功语义，实际写入后在相同 Executor 保存一次安全事件；首错立即停止 |
| `erp-processes::audit::run_audited` | 接收领域已登记动作的准备记录，事务开始前校验目录、身份及目标；实际业务写入后经 `persist_log` 保存安全事件 |
| `erp-processes::audit::persist_log` / `persist_logs` | 普通写入的统一物理持久化入口。仅接受登记动作，重建安全中文模板，不复制自由说明。批量入口先校验全部事件再保序 `create_many_ordered`，不得改变业务批次与审计批次原顺序 |
| `erp-processes::audit::finish_attempt` | 必须在原事务返回之后执行。失败、拒绝及未知分别记录到 `audit_attempts`；成功不写尝试，失败写尝试也不得覆盖原命令错误 |
| `backend/scripts/audit-entrypoints.json` | 逐个生产入口声明实际边界阶段和 `Audited` / 带理由的 `Exempt`；动作目录数量、工厂调用或登记表不能代替实际命令执行及结果事实验收 |
| 身份策略事务 | 继续执行 `RbacService::run_authorized_audited_policy_transaction` 的授权 revision 重验、policy 写入、审计与提交后刷新合同，不得用普通业务入口替代其生命周期 |

`AuditEventSink` 的组合层实现仅将事件接到审计领域仓储。Repository 不决定哪些动作需要审计；业务规则、授权、版本、任务责任、事务边界和命令回放由拥有领域或命名 Process 维护。

业务执行失败不得继续审计成功事件。审计构造或持久化失败必须返回原错误并阻止正式业务提交。一个命令修改多个对象时，事件序号与共享命令身份由该动作合同规定；不得将每次仓储更新视为独立完整业务动作。

采购选源批次沿采购计划原循环顺序分配序号：第 `i` 张采购单（从0开始）的提交审批事件为 `2*i+1`，创建事件为 `2*i+2`，整批主事件为 `2*N+1`。库存独占、未创建采购子单的批次只记录序号1的主事件。独立依据建单沿原提交、创建顺序使用1、2。采购责任转交先保存采购单事件1，再保存工作项事件2；仅转交工作项时使用1。不得为符合事件名称的自然语言顺序调整实际业务写入顺序。

## 服务履约确认

`fulfillment_execution::service_confirm` 在事务开始前构造服务确认上下文。事务内依次执行原有版本、采购门槛、分配、图片凭证、资产登记、确认、任务、成本与验收步骤，最后经过统一边界保存结构化事件。

事件记录操作人账号快照、履约编号、草稿到已确认的状态变化、服务结果及精确服务数量。服务地点、交付对象、说明文本、密文及指纹不进入审计投影。失败服务确认仍记录成功的确认命令，且不执行仅适用于成功履约的成本与验收步骤。

此确认入口没有跨请求命令回执合同。调用方必须继续遵守当前状态与乐观锁规则；自动审计接入不新增幂等键、命令重试或回放语义。其他已提供命令身份的资金、销售、采购和工作流入口分别执行各自回执合同，不得用此局部限制否定其幂等要求。

## 事务、取消与失败分类

1. 普通 `run_audited`、`run_audited_event` 直接等待 `Transactional::with_transaction`，没有创建持有事务的独立 Tokio 任务。不得宣称 HTTP 超时或等待者被取消后仍由独立任务完成收尾。需要独立所有权的入口必须显式实现并验证。
2. 身份策略事务的独立任务、提交后刷新与一致性失败关闭继续按身份领域合同执行，分别验收。
3. `CommitOutcomeUnknown` 必须保留未知结果分类，不得误标执行失败或自动执行第二次业务写事务。已有命令身份时，仅通过原命令身份查证结果。
4. `TransientTransactionError` 保留现有冲突错误。当前 `FnOnce` 事务闭包不自动重跑；调用方沿该业务命令合同重读或查证后决定后续动作。
5. 成功业务事件与命令尝试分别保存。`audit_attempts` 固定 `event_kind=command_attempt` 和 `failed` / `rejected` / `unknown` 结果，只保存已验证动作、操作人、执行前已知目标、命令及请求关联；未知目标保持缺失。不得保存原请求、完整实体、错误正文或敏感字段。
6. `run_audited` 和 `run_audited_event` 在原事务返回后调用 `finish_attempt`。使用已有事务的入口必须在外层事务结束后执行同一独立尝试边界；禁止在仍可能回滚的执行器中保存尝试。工作项转交和关闭通过窄 `WorkflowAuditPort::persist_attempt` 接到同一尝试集合。
7. 独立尝试写入使用新的 `NoTransaction`；尝试持久化失败只输出固定、安全诊断，原错误对象和未知提交来源必须原值返回。独立尝试不是业务回执，也不构成重试、参与资格或终态依据。
8. 未知提交只允许查证同一领域命令；查证缺失或查证失败不得替换首次未知提交错误，不能再次执行业务事务。
9. 登录审计继续 best-effort，未鉴权的启动初始化不伪造业务操作人。敏感读取等独立事件沿各自合同执行。

## 查询与展示

审计列表保持 `items + total` 及单项字段，业务事件使用 `structured_event`。缺失的名称和业务编号必须展示缺失，不得查询当前对象补造发生时事实。独立命令回执不作为第二条业务事件展示；`audit_attempts` 与成功业务 `audit_logs` 分开保存。

业务列表以中文动作、操作人、业务编号、执行结果和业务字段变化展示。技术动作代码与关联编号放在详情。`event_result` 按结构化命令结果筛选，`resource_number` 按结构化业务编号字面筛选；模板与消息变化不得改变筛选、回执或业务执行。

业务 `audit_logs` 与身份治理 `audit_events` 分别登记及查询。审计可见性遵守审计查询授权；审计列表权限不授予关联对象读取、银行信息或客户敏感信息访问资格。

## 验证要求

实现阶段仅新增和执行内联库单元测试。测试必须执行真实统一边界和领域编排，验证同一执行器、首次记录一次、回放零新增事件、每步失败停止、命令结果与业务结果分离、中文白名单及敏感值隔离。

单元测试和编译不证明真实数据库事务回滚、并发唯一性、历史数据处理完整性、部署取消行为或最终浏览器体验。上述结论必须取得对应运行验收证据后核销。
