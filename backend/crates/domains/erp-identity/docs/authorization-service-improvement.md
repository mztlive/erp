# 权限系统重写方案

状态：第一至第五阶段已实现，待 review；第六阶段待实施。业务用例已接入统一服务，server 授权装配已绑定完整业务 Facts 和 Mapping，并通过不读取数据库的完整构造单元测试。HTTP、worker、应用工厂及前端按第六阶段切换。实施必须遵守本文规定的接口、职责边界和阶段验收条件。

本文规定公共接口、授权行为、数据接口和验收条件。内部临时类型、字段布局和函数拆分由实现确定，不作为兼容合同。

## 1. 重写原因与目标

### 1.1 现有接入方式的问题

现有系统已经具备 RBAC、DataScope、行级授权、任务指派和来源检查能力，但完整授权要求分布在 HTTP 中间件、identity 的资源动作规则、业务授权登记及查询调用中。接入一个业务用例时，需要同时维护权限资格、政策构造、事实读取、查询编译和服务构造，授权正确性依赖多个位置保持一致。

| 现有结构 | 维护问题 |
| --- | --- |
| HTTP 通过 `with_permission` 检查功能权限，业务用例另行执行数据授权 | HTTP 与 worker 等调用入口的授权责任分散，检查完整性需要逐入口核对 |
| identity 已有资源动作规则，业务又通过 `AccessRegistration`、`DataAccess`、`AccessPolicy` 组合要求 | 同一规则存在重复表达，变更时需要同时核对多个声明位置 |
| `ConsumerSpec`、`ActionSpec` 和 `AuthorizationPolicy` 同时承担范围规则、配置准入与展示分类 | 资源、动作与总策略分类相互关联，授权能力的职责不清晰 |
| 业务构造授权服务，并选择主体、查询模型及编译入口 | 用例承担服务装配和查询授权细节，同一权限的执行方式受调用方选择影响 |
| 权限值类型位于 identity，公共权限目录位于 server | 业务调用、目录展示和生成器缺少统一的公共权限定义来源 |

例如，修改询价必须同时确认“账号有修改询价的功能资格”和“这张询价在该账号可修改的范围内”。只检查其中一项不能证明操作被允许。列表查询还必须将相同的数据规则编译到数据库中，在分页和计数前执行，避免对象判断与查询结果采用不同的授权要求。

### 1.2 重写目标

重写后的系统必须满足以下要求：

1. **授权由统一服务执行。** `AuthorizationService` 是业务授权的统一入口，内部组合 RBAC、DataScope 和行级授权。
2. **一个权限对应固定要求。** 多个业务用例共用同一权限时，执行相同的基础检查；创建、归属变更和任务目标按固定合同追加目标检查。
3. **业务提供事实，identity 判断权限。** 业务负责读取真实归属、任务、来源和版本，并提供数据库映射；授权条件及其组合由 identity 确定。
4. **对象判断与查询采用同一规则。** 共同的数据条件只定义一次；创建、转交和任务办理的专有检查由固定函数执行。
5. **按实际需要执行。** 静态 Mapping 只描述字段和关系；事务内按快照授权，非事务读取按实际依赖复验，不重复读取同一事务快照来证明权限更新。
6. **接入缺失必须报错。** 缺少规则、事实或映射时终止操作，不得降级为只检查功能权限或全量读取。

### 1.3 重写范围

本次重写覆盖公共权限定义、identity 授权服务、业务授权调用、HTTP 与 worker 的共享装配，以及旧政策登记和路由鉴权入口的清理。现有 RBAC、DataScope、行级授权及有效的任务、来源规则接入统一执行流程；迁移必须保留既有授权条件、权限编码和存储数据。

## 2. 设计方案

### 2.1 总体设计

业务用例通过 `AuthorizationService` 的 `require`、`query` 和 `validate` 完成授权。服务按 `Permission` 取得固定处理分支，组合以下三项能力：

| 能力 | 判断内容 | 结果 |
| --- | --- | --- |
| RBAC | 账号、启用角色是否具备本操作的完整功能资格 | 资格证明及身份、角色版本 |
| DataScope | 当前账号对本操作拥有怎样的数据范围 | 本人、组织、仓库等范围条件及依赖版本 |
| 行级授权 | 当前记录是否有显式授权，是否满足指派、参与及真实来源要求 | 对具体记录和关系的条件及依赖版本 |

Facts 提供真实对象、任务、来源及版本；Mapping 将共享的数据条件映射到数据库字段和关系。`require` 执行对象条件及操作专有检查；`query` 生成数据库授权过滤；`validate` 在交付读取结果前检查使用边界、有效期，并按第 3.5 节决定是否重读依赖。

授权服务由 server 在启动时构造并注入业务用例。模块归属按第 2.4 节执行，装配接口见第 3.4 节。

### 2.2 三项能力的边界

RBAC 维护账号、角色与功能权限的授予关系。权限常量和启动绑定只描述系统能力，不向账号授予权限。规则要求同一角色具备入口与额外权限时，必须取得同角色证明；独立资格分别取证。

DataScope 负责范围配置、范围来源和当前账号的范围解析。静态信息集中在按权限查找的内部 `ScopeSpec` 中，字段和解析合同见第 3.3.3 节。公司共享、默认本人和范围条款复用均在此处理。

行级授权包含两类实际检查：

- 显式记录授权：读取现有授权记录、有效来源及修订版本。现有记录授权仍只按原动作补充读取资格。
- 记录关系检查：根据 Facts 判断实际指派、参与和真实来源；查询通过 Mapping 编译等价条件。关系直接从业务数据取证，权限检查不写入新的授权记录。

复用某资源的范围配置由 DataScope 处理；沿某张单据的真实来源判断访问资格由行级授权处理。前者不证明来源对象可访问，后者必须核对来源身份、完整性及版本。

### 2.3 固定组合与实现方式

`AuthorizationService` 使用 identity 内部按权限组织的普通函数完成处理选择。每个受保护权限必须明确支持的目标、所需功能资格、是否调用 DataScope，以及行级条件的组合方式。启动绑定校验和运行时处理复用同一份匹配关系；未知权限、未知动作或不支持的目标返回接入错误。

| 场景 | 必须成立的条件 |
| --- | --- |
| 仅功能资格操作 | RBAC 通过；仅接受明确支持无对象的权限 |
| 普通对象写入 | RBAC 通过，且 DataScope 命中，且满足该动作要求的行级条件 |
| 允许记录授权补充的读取 | RBAC 通过，且“有效数据范围或显式记录读取授权”成立；该动作另有必要关系条件时仍须满足 |
| 任务办理 | RBAC 通过，且实际任务指派或其他已确认办理关系成立；该权限有范围要求时同时满足 |
| 来源授权 | RBAC 通过，且真实来源满足该权限固定的任一或全部来源要求；独立来源资格分别取证 |

业务主流程只传身份、权限、目标和执行器。多个用例使用同一权限时基础条件一致。目标形态只能触发明确的附加检查：归属变更检查原对象与新归属，精确任务目标追加任务身份、版本和实际指派校验；调用方不能用普通记录目标绕过任务权限的必需检查。

对象判断和列表过滤共同使用的数据条件由 identity 生成一份内部条件表达，供对象执行和查询转换复用。修改询价使用询价范围，销售单读取按既有规则加入记录读取补充；不得分别手写两套授权条件。

创建候选、归属变更和任务办理由 identity 内的普通函数执行专有检查，不要求这些流程都能编译成列表查询。任务列表仍须使用实际指派和参与条件过滤；任务办理在此基础上核对精确任务身份、版本及该动作要求的关系。业务用例不能自行选择或删减这些检查。

迁移时逐入口核对原有条件。相同权限下已有的额外限制必须落实为所有入口共用的基础条件，或与明确目标形态绑定的附加条件；发现同权限、同目标但授权要求冲突时，必须先明确该权限的业务含义再迁移。

完整对象查询的成员判断必须与同权限、同目标语义的对象读取一致。历史参与、个人限制和显式记录读取授权的组合位置按第 3.6.2 节执行。

### 2.4 各模块的代码职责

新增 `erp-permissions` 一个独立 library crate。授权装配放在 server 现有的 `wiring` 模块。

| 位置 | 负责内容 |
| --- | --- |
| `backend/crates/foundation/erp-permissions/` | `Permission` 值类型、内置权限常量、资源标识、公共目录类型、分组及可复用说明 |
| `backend/apps/erp-server/src/wiring/authorization/` | 创建并连接身份设施、事实读取器和 Mapping，提供统一 `build` 入口 |
| `backend/crates/domains/erp-identity/` | 实现 RBAC、DataScope 和行级授权；维护内部范围定义与固定组合，执行绑定校验、对象判断、查询编译及复验 |
| 业务领域和 ReadModel 的事实、映射实现 | 读取对象归属与版本，将授权所需的事实映射到数据库字段及来源关系 |
| 业务 Service、Process、ReadModel | 接收共享授权服务，传入固定权限和本次目标，执行业务校验及读写 |
| HTTP、worker 运行时 | 通过 server 的授权装配入口构造共享实例，并注入业务用例 |

依赖必须遵守以下约定：

- `erp-permissions` 提供权限值类型及其纯校验、静态常量和目录信息，不依赖 identity、业务领域、ReadModel 或应用，不执行账号授权、数据库访问或 HTTP 路由逻辑。
- identity 依赖 `erp-permissions` 的 `Permission` 类型；业务模块依赖该类型、常量和 identity 的授权接口，不依赖 server，不自行构造授权服务。
- server 的授权装配模块依赖公共定义、identity 及业务实现，只连接实现，不定义授权政策，不启动 HTTP、worker 或外部连接器。
- identity 按公共权限调用已有规则，通过接口取得业务事实和映射，不反向依赖 server 或业务实现。范围定义和授权处理函数均归 identity。

HTTP 和 worker 使用共享装配。CLI 运维命令使用自身运行时，并可按需单向复用 `erp_server::wiring`，不挂载 HTTP 或启动 worker 常驻循环。

## 3. 实现细节

本节规定第 2 节设计对应的公共定义、调用合同、实现绑定、执行流程及旧结构清理要求。实施顺序按第 4 节执行。

### 3.1 公共权限定义与目录

#### 3.1.1 权限值类型与常量

将现有 `Permission` 值类型迁入 `erp-permissions`，由该 crate 统一实现构造、解析、格式化、序列化及权限覆盖关系。identity、业务模块、装配代码和目录生成器使用同一个类型和校验实现。

内置权限在所属模块中定义为 `const Permission`。例如，`erp-permissions` 的 `sales_inquiry` 模块定义：

```rust
use crate::Permission;

pub const COMMANDS_SALES_SAVE: Permission =
    Permission::new("sales_inquiry", "update");

pub const QUERY_SALES_LIST: Permission =
    Permission::new("sales_inquiry", "list");
```

两种输入使用以下构造约定：

| 输入来源 | 构造方式 | 校验时点 |
| --- | --- | --- |
| 代码中定义的内置权限 | `const fn new(resource: &'static str, action: &'static str) -> Self`，用于常量初始化 | 编译期；字面量必须已经规范化，非法常量使编译失败 |
| 数据库、配置和外部输入的动态权限字符串 | `Permission::parse(value)` | 输入边界；按既有规则规范化并校验，失败返回错误 |

业务调用和启动装配直接引用内置权限常量，不从目录字符串重新解析。反序列化动态权限时仍须经过 `parse`，不能绕过校验。

不单独分配菜单权限的内部业务入口统一在 `erp-permissions::internal` 定义常量，由 identity 固定映射到既有功能资格、范围和目标。此类派生入口不得要求账号获授内部编码，不加入角色配置展示目录。该模块中原有的隐藏功能权限仍按既有编码授予和检查，不因常量归属改变资格要求。审批类型的既有管理权限编码统一使用 `erp-permissions::approval_admin` 常量，不在业务流程中拼接。

客户详情保留历史参与补充；选择客户开展新业务使用独立的当前范围检查，沿用客户详情功能资格并关闭历史补充。文件转交只允许真实上传人执行。

审批定义创建、编辑、发布和退役必须同时具备对应 `approval_process` 动作资格及真实单据类型的定义管理资格，两项资格独立取证。业务用例从服务端类型政策构造候选目标；写入和收据回放前使用同一事务授权。定义详情允许该类型的定义管理或运行管理资格，定义期审批人候选只接受定义管理资格。

采购邮件发送使用 `purchase_order:send_email` 和真实采购单记录目标。identity 同时检查发送功能资格、独立的采购详情功能资格、公司范围及记录有效性；业务调用方不得另行拼接详情授权。

`Permission` 的 `resource`、`action` 字段保持私有，内部采用 `Cow<'static, str>`：常量借用静态字符串，动态解析结果持有规范化后的字符串。两种构造方式共用格式约束；相同资源和动作的权限，无论来自常量还是动态解析，其相等判断、哈希、排序和覆盖关系必须一致。

沿用现有权限格式、动态输入规范化、通配覆盖和 `resource:action` 字符串序列化语义。纯格式校验及解析错误由 `erp-permissions` 提供，不依赖 identity 的错误类型。

#### 3.1.2 公共权限目录的迁移

将原 server 权限目录中的权限编码、公共目录类型、分组和可复用说明迁入 `erp-permissions`，删除 server 的 `permission_catalog/` 和同名包装。HTTP 路由直接引用公共目录登记的权限主常量，server 不再维护第二份权限 `ENTRIES` 或 `MODULES`。

公共目录条目通过 `&'static Permission` 引用内置常量，保存默认分组和说明，不再维护独立的 `code` 字符串。多个接口复用同一主常量及公共元数据。server 只按方法和路径登记与默认值不同的接口说明、分组或既有展示权限差异；方法、路径及实际鉴权权限仍从路由取得。展示差异仅供构建生成器使用，不得改变运行时鉴权。

目录输出和前端生成统一通过 `Permission` 的格式化或序列化能力取得权限编码。差异引用不存在的受保护接口或同一字段重复登记时生成失败。既有编码、共享关系、展示分组和接口说明必须保持一致。

`erp-server/build.rs` 通过 build-dependency 读取 `erp-permissions`，运行时通过普通依赖读取同一份定义。前端权限生成、角色配置目录和权限漂移检查均使用这份公共定义，由 server 补充路由信息。

### 3.2 业务用例如何调用

#### 3.2.1 修改一张询价单

保存询价需求时，业务用例在写入前执行以下检查：

```rust
use erp_identity::AccessTarget;
use erp_permissions::sales_inquiry;

self.authorization
    .require(
        actor,
        &sales_inquiry::COMMANDS_SALES_SAVE,
        AccessTarget::record(inquiry_id)?,
        executor,
    )
    .await?;
```

四个参数分别是当前身份、`sales_inquiry:update` 权限、询价单 ID 和本次数据库执行器。`executor` 在事务内使用时承载同一事务的读写。

`require` 成功返回 `Ok(())`，失败立即终止本次操作。业务用例随后执行第 3.5.3 节规定的业务校验和写入。内部判断流程见第 3.6.3 节。写入授权必须使用第 3.5 节规定的事务执行器。

#### 3.2.2 查询询价列表

列表同样直接传入 `Permission` 常量。`query` 返回 `CompiledAccess`，其中包含可由仓储执行的数据库授权条件，以及当前读取阶段所需的边界、有效期和依赖信息。

```rust
use erp_permissions::sales_inquiry;

let access = self.authorization
    .query(actor, &sales_inquiry::QUERY_SALES_LIST, executor)
    .await?;

// 执行授权条件与业务筛选。
let page = self.repository.list(filter, &access, executor).await?;

// 检查读取阶段边界及有效期；非事务读取同时复验依赖。
self.authorization.validate(&access, executor).await?;
```

本例由授权服务使用 `sales_inquiry:list` 对应的固定 Mapping 生成 `CompiledAccess`。仓储按第 3.6.4 节执行，读取结果按第 3.5 节交付。

#### 3.2.3 业务授权接口

HTTP 通过 JWT 确认身份，Handler 调用受保护的 Service、Process 或 ReadModel；worker 调用相应的受保护业务用例。每个受保护的公共业务入口都必须在返回业务数据或执行写入前完成授权。

| 用途 | 调用 | 返回 |
| --- | --- | --- |
| 检查具体对象、创建或归属变更 | `require(actor, permission, target, executor)` | `Result<()>` |
| 只要求功能权限的操作 | `require`，目标为 `AccessTarget::Operation` | `Result<()>` |
| 列表、计数、汇总、查询式导出 | `query(actor, permission, executor)` | `Result<CompiledAccess>` |
| 读取结果交付检查 | `validate(access, executor)` | `Result<()>` |
| 单项功能资格查询、按钮展示 | `has_permission(actor, permission, executor)` | `Result<bool>` |
| 批量功能资格查询、按钮展示 | `permissions(actor, permissions, executor)` | `Result<Option<QualifiedPermissions>>` |

所有接收权限的接口使用 `erp-permissions` 提供的同一种 `Permission`；内置权限直接传常量引用。`AccessTarget::Operation` 表示本次没有对象目标。

`has_permission` 和 `permissions` 只查询 RBAC 功能资格，不证明账号有权操作某张单据。业务主流程必须使用 `require` 或 `query`。

### 3.3 业务如何提供事实和查询映射

业务通过 `AccessFactsPort` 提供对象事实，通过 `AccessMapping` 提供数据库映射，支持第 2.1 节的三项能力。

例如，询价的负责人取真实负责销售字段 `sales_owner_user_id`，客户的负责人取有效负责人分配。事实读取器和 Mapping 必须采用相同的业务归属定义，使相同规则下的对象判断和列表成员判断一致。

#### 3.3.1 对象事实

保留以下接口：

```rust
#[async_trait]
pub trait AccessFactsPort: Send + Sync {
    async fn load(
        &self,
        context: &AccessContext,
        ids: &ResourceTargets,
        executor: &mut dyn Executor,
    ) -> Result<Vec<ObjectFacts>>;
}
```

事实读取器返回对象身份、版本、负责人、所属组织，以及已有规则要求的任务指派和实际来源关系。必需事实由 DataScope 的维度要求、固定行级检查及本次目标共同确定。事实未加载、已加载但为空必须保持可区分，不能用空值掩盖缺失事实。

根对象及各层来源对象均按资源与身份视为无序集合。identity 在校验完整集合、重复对象及展开上限后固定比较顺序；非事务复验忽略排列差异，仍比较全部事实、版本和来源引用。

拥有领域的 repository 可以直接实现该接口；需要组合本域仓储时，由本域事实读取器实现。跨域事实通过窄 Port 获取，所需适配器在 server 的授权装配模块中连接。

所有读取使用本次调用的 `executor`。共享实例的状态限制按第 3.6.1 节执行。

#### 3.3.2 查询映射

`AccessMapping` 提供集合、主键、有效记录条件、事实字段和真实来源关系。元数据在启动时校验并保存为不可变描述；查询转换不得改变上层授权条件的与或关系。

Mapping 只提供静态描述，并按本次授权上下文将事实转换为数据库条件；不得在编译时执行查询外取数，也不登记映射修订。

数据库内需要先物化完整关系时，使用不可变的 `AccessMapping::stages()`。准备阶段只允许不改变根记录数量的只读关联与字段计算，不得提前过滤、展开、分页或写入。自然日等静态时间边界通过 `valid_until(context)` 提供，须按实际使用的最早时间边界限制凭证。

资金复合查询由一次 `query` 生成原根、固定来源和整账过滤，共用本次资格、范围及执行边界。`CompiledAccess::source_model`、`source_stages` 和 `whole_stages` 只公开固定计划的只读信息，不签发来源对象凭证。业务内部的来源读取只允许固定字段投影，禁止包装为通用销售单或采购单对象授权；交付前仍须校验原根凭证。只输出根身份的多来源查询使用 `Existence`，不得将多来源整根登记为单来源份额。

工作项列表和详情由同次 `query` 生成根读取和固定管理动作过滤。管理动作使用 `work_item:manage` 的合格角色与范围；无管理资格时只拒绝管理动作，不影响读取。`CompiledAccess::management_stages` 仅供当前展示批次计算可管理身份，不作为办理凭证。业务展示补齐后调用一次 `validate`，同时核对读取和管理动作的依赖、阶段及最早有效期。

工作项同次查询还提供固定执行和审批决定的展示资格。`execution_qualified` 按真实任务种类和业务对象类型使用 identity 内唯一的完整资格组合；`decision_qualified` 使用固定审批读取与决定组合。两项只读输出必须核对原执行器、读取阶段和有效期，业务不得传入权限列表或据此办理任务；展示补齐后仍须对原查询调用 `validate`。

任务接收者资格统一使用固定内部入口 `WORK_ITEM_RECIPIENT`。已有任务必须提供 `Task { id, version }`，identity 从持久化事实确定完整资格和真实来源；接收者不必已是当前负责人，转派操作人另行通过原任务的管理授权。任务形成前仅可用 `WORK_ITEM_EXECUTION_QUALIFICATION` 和服务端候选检查完整执行功能资格，候选只提供已验证的任务种类及业务对象类型，不代替已有任务、来源对象或管理操作授权。工作项领域和调用方不得重复维护任务权限组合。

同一集合管道中，集合、变量绑定和子管道完全相同的关联只生成一次；嵌套来源的别名作用域相互独立，不能因此改变来源完整性、与或关系或输出粒度。

查询中直接读取的负责人、仓库或来源字段由数据库条件判断，不要求为整个业务集合制造一个版本。非事务查询中，这些数据遵循数据库本次读取语义，不承诺返回前所有业务行均未变化。身份、范围和记录授权修订按第 3.5 节核对。

Mapping 不得使用请求传入的预筛选授权 ID 代替完整查询条件，不得把缺失来源过滤掉后宣称全部来源已通过。

同一仓储或适配器能够实现 Facts 和 Mapping 时，复用底层实现及实例。事实读取器不得依赖需要授权服务的业务 Service，避免形成循环依赖。

#### 3.3.3 DataScope 的内部范围定义

将原 `ConsumerSpec`、`ActionSpec` 中的范围信息合并为私有 `ScopeSpec`，以公共 `Permission` 常量为键。配置候选、保存校验、运行解析、初始化和授权文件导入导出使用同一份定义。仅功能资格或纯关系检查的权限由统一入口明确处理，不创建空范围定义。

| 字段 | 含义 |
| --- | --- |
| `permission` | 对应的公共权限常量 |
| `source` | 内部 `ScopeSource`：`Current` 使用本权限的人员配置；`Permission` 引用指定权限的范围配置；`Company` 在功能资格成立后产生公司范围 |
| `default_self` | `Current` 模式下，无人员配置时是否采用本人基础范围；为 false 时得到空范围 |
| `scope_types` | 本权限允许的范围类型，如公司、组织、本人、协作 |
| `supported_dimensions` | 可以配置和解析的组织、仓库、结算主体等维度 |
| `required_dimensions` | 必须提供的维度，必须是支持维度的子集 |
| `allows_history` | 本权限的读取是否接受已有历史参与补充 |

`ScopeSpec` 和 `ScopeSource` 均为 identity 内部静态定义，字段私有。`Permission` 来源直接持有 `&'static Permission`；非 `Current` 模式的 `default_self` 固定为 false，默认行为由来源定义或公司范围确定。`ScopeSource` 只表达范围取得方式；其他字段是配置与解析所需的直接数据。公共权限目录继续负责名称和分组，组织事实的加载由 DataScope 根据当前计算需要决定。

解析和配置遵守以下合同：

1. `Current` 允许独立人员配置；已有配置按原表达式解析，无配置时按 `default_self` 处理。原有超管范围继续在完成资格取证后由 DataScope 处理。
2. `Company` 不接受独立人员配置，不读取遗留人员范围及个人限制。仍须完成 RBAC、记录有效性及该操作要求的行级检查。
3. `Permission` 直接引用一个 `Current` 来源定义，使用来源配置和默认范围；本权限不接受独立配置。来源引用须有效且无循环。入口功能资格、目标归属及目标动作的读取补充要求仍按当前权限执行。
4. 配置保存逐动作校验 `scope_types`、支持及必需维度；运行时校验持久化表达式。复用来源配置时，目标必须支持来源条件所需维度，目标的额外必需事实仍须完整加载。配置能力不能由 Mapping 的字段支持情况放宽。
5. 定义缺失不等于仅检查 RBAC。要求范围的处理分支找不到定义时，启动校验和运行调用均报错。仅关系检查、仅功能资格操作在统一入口有各自明确分支。
6. `allows_history` 只用于读取。事实缺失、空范围、本人基础和个人限制的语义沿用第 3.6 节，不能由缺省值放行。

示例定义如下；表中的权限均引用 `erp-permissions` 的常量：

| 权限 | 范围来源 | 无配置时的范围 | 目标约束 |
| --- | --- | --- | --- |
| `sales_inquiry:update` | `Current` | 本人负责 | 内部组织维度必需；无历史读取补充 |
| `purchase_order:detail` | `Company` | 公司范围 | 仍检查详情资格、有效记录和适用的行级条件 |
| `contract:detail` | `Permission(customer:list)` | 使用来源配置的默认范围 | 用合同自己的归属解释条款；共同客户本身不授予合同访问权 |

#### 3.3.4 配置目录与权限检查接口

删除人员范围接口中的 `authorization_policy` 总分类字段。保留 `resource`、`actions`、`configurable_actions`、`dimensions`、`default_self_actions` 和说明文本；候选按资源分组只是展示组织方式。

`configurable_actions` 从 `ScopeSource::Current` 推导，`default_self_actions` 从这些动作的 `default_self` 推导；保留的汇总 `default_self` 仅在全部可配置动作均有本人基础时为 true。`dimensions` 展示可配置动作支持维度的并集，保存时仍逐动作校验。只有来源配置或公司共享、以及没有范围定义的权限，均不开放独立范围编辑。

`policy_description` 保留为展示文本，按权限的实际配置能力与处理方式生成；同一资源的动作要求不同，说明必须分别标注动作。前端按可配置动作和维度控制编辑，不从说明文本推断权限。

权限检查接口复用统一入口的功能资格、范围及行级检查。缺少具体对象或任务上下文时，只报告已完成的检查和仍需核对的条件，不能输出对象授权通过。已有对象检查范围及管理员入口资格保持原合同。

同步调整人员范围 DTO、配置候选、保存、退役配置说明、预定义范围、授权文件导入导出、权限检查 DTO 及前端调用。历史人员范围记录保留用于审计，不可独立配置的旧项继续列为退役项。

### 3.4 应用启动时如何构造共享服务

HTTP 和 worker 统一调用 `erp-server` 内 `wiring::authorization::build`，各自取得进程内共享的 `Arc<AuthorizationService>`。两个进程复用装配代码，各自持有服务实例。

构造顺序固定为：

1. 初始化 repository 和身份设施。
2. 创建事实读取器、Mapping 及所需跨域适配器。
3. 按资源绑定 Facts，按查询权限绑定根 Mapping，由 identity 的 Builder 校验绑定并构造服务。复杂查询所需来源映射在构造时连接。
4. 将共享服务注入业务 Service、Process 和 ReadModel。

#### 3.4.1 Builder 只绑定实现

Builder 的目标接口为：

| 调用 | 参数与职责 |
| --- | --- |
| `facts(resource, facts)` | `resource: &str` 为已有资源标识，`facts: Arc<dyn AccessFactsPort>` 为读取实现；返回 `Result<Self>` |
| `mapping(permission, mapping)` | `permission: &Permission` 为查询权限，`mapping: Arc<dyn AccessMapping>` 为查询实现；返回 `Result<Self>` |
| `build()` | 校验规则所需绑定，返回 `Result<AuthorizationService>` |

以下示例展示询价资源的绑定步骤，返回尚未完成的 Builder。参数中的两个 trait 实现由 server 使用业务仓储创建。调用 `build()` 前，必须补齐全部固定规则要求的 Facts 和查询 Mapping；仅绑定询价时不得构造生产服务。

```rust
use std::sync::Arc;

use erp_identity::{
    AccessFactsPort, AccessMapping, AuthorizationBuilder, AuthorizationService, Result, SharedRbacService,
};
use erp_permissions::sales_inquiry;
use mongodb::Database;

fn inquiry_bindings(
    db: Database,
    rbac: SharedRbacService,
    inquiry_facts: Arc<dyn AccessFactsPort>,
    inquiry_mapping: Arc<dyn AccessMapping>,
) -> Result<AuthorizationBuilder> {
    AuthorizationService::builder(db, rbac)
        .facts("sales_inquiry", inquiry_facts)?
        .mapping(&sales_inquiry::QUERY_SALES_LIST, inquiry_mapping)
}
```

`sales_inquiry:update`、`create` 等对象操作复用同一份资源 Facts，不逐权限重复绑定。同一个 Mapping 实例可以被多个查询权限引用。

每个查询权限绑定一个确定的查询入口，不要求该入口的所有来源共用一个集合或输出形态。普通入口使用一个根 Mapping；资金等复杂入口由固定实现连接所需分区及来源 Mapping，identity 决定授权组合和允许输出。来源映射可以有多个，不能被业务调用方替换或作为完整对象凭证使用。不要为分区另建可由调用方配置的政策树。

查询能力按公共权限常量显式声明，不按动作名称推断。`procurement_inquiry:internal_quote` 和 `purchase_payment_request:pay` 同时支持固定查询入口与精确任务检查；`supplier_fulfillment_order:submit` 支持原提交资格下的执行资料和命令结果查询，`supplier_api_connection:authorize` 支持原授权资格下的操作回放，两者均不追加详情菜单资格。支持查询不改变写入授权必须使用快照事务的要求。付款入口的 `pay` 与 `detail` 必须来自同一个启用角色，查询与任务检查均执行此资格要求。

Builder 按上述接口完成 Facts 和 Mapping 绑定，绑定在服务构造完成后保持固定。 `AccessMapping::relations()` 描述固定关系及来源 Mapping，默认返回空集合；有来源的实现必须提供完整描述。`relation()` 返回的来源实例必须与启动描述一致。多个权限或关系使用同一实例时，复用同一冻结包装。

构造时必须校验：

- 内部范围定义的权限唯一、来源引用有效、维度一致；第 3.3.3 节的定义校验必须先通过。
- 资源和权限引用有效，并有 identity 能执行的规则；权限目录条目本身不代表已接入授权。
- 每个资源只绑定一个根 Facts 实例，每个查询权限只绑定一个查询入口；重复绑定返回错误。内部来源与分区映射不作为该权限的重复入口。
- 按统一入口的固定处理分支及 `ScopeSpec` 确定所需能力，缺少必要 Facts 或 Mapping 时构造失败。仅功能权限操作不要求无用的对象或查询绑定。
- Mapping 的根资源、集合、主键、输出粒度及事实能力符合对应查询要求；描述在构造后不可变，不依赖请求状态。复杂入口同时校验全部来源和分区的绑定与输出限制；具体对象的必需事实在 Facts 返回后校验。
- `QueryOutput::Existence` 的输出字段必须且只能包含模型的 `id_field`；登记金额或内容字段时构造失败。

共享实例保存在 `Application`，`HttpState` 经 `Application` 取得它。`Application::authorization()` 只克隆 `Arc`。

### 3.5 业务调用合同

#### 3.5.1 不同目标的检查要求

`AccessTarget` 必须区分以下目标。identity 根据权限的固定处理分支校验目标形态，调用方不能通过更换目标形态绕过该权限的数据要求。

| 目标 | 调用方提供 | 授权服务必须检查 |
| --- | --- | --- |
| 无对象操作 | `AccessTarget::Operation` | 已有规则要求的功能资格；只有明确允许无对象的动作可以使用 |
| 已有记录 | 记录 ID 或完整目标 ID 集合 | 从持久化数据读取的当前归属、版本及操作资格 |
| 创建候选 | 业务模块从已验证输入生成的服务端候选事实 | 新对象的目标归属是否满足创建权限要求 |
| 归属变更 | 原对象身份和经服务端确认的目标归属 | 原对象操作资格和目标归属同时满足要求 |
| 任务操作 | 所要求的精确任务身份及版本 | 实际任务指派、关联对象及已有规则要求的事实 |

创建候选不能从 HTTP 参数直接反序列化为授权凭证，也不能代替已有记录的当前事实。任务目标不能只用关联业务 ID 代替。

#### 3.5.2 一致性与结果交付

本次重写采用以下一致性合同：

| 场景 | 授权依据 | 完成前检查 |
| --- | --- | --- |
| 事务内写入 | 当前事务快照中的身份、范围、业务事实与记录授权 | `require` 完成前检查目标和有效期；业务写入检查版本与并发冲突，不重新解析同一快照 |
| 事务内读取 | 当前事务快照；授权条件与业务查询使用同一事务 | 检查原事务、当前读取阶段和有效期；不重读同一批依赖 |
| 非事务读取 | 查询生成时的身份、范围及已使用的读取授权修订，加数据库查询中的实时字段与关系条件 | 返回前按原授权时点复验身份、范围和读取授权修订；变化时丢弃结果 |

事务快照内授权不承诺看见事务外随后提交的撤权。非事务前后复验只检测其覆盖的依赖变化，不构成多次读取之间的串行化保证，也不保证复验完成之后权限不再变化。本次重写不增加“并发撤权必须阻止在途事务提交”的承诺。

事务路径必须确认执行器处于同一活动事务并采用所需快照语义。现有 `Executor::session()` 只暴露会话，不能独自证明活动事务、事务身份或读取阶段。事务设施必须提供可核验的事务边界，或通过作用域封装保证凭证无法跨事务使用；完成该约束前不得启用省略依赖重读的路径。不得用会话 ID 或 `session().is_some()` 代替该约束。

事务回调使用 `Transactional::with_transaction` 签发的 `ExecutionBoundary`。非事务授权读取使用同一个 `ReadExecutor` 完成查询生成、仓储读取和交付检查。统一写操作在尝试写入前推进读取阶段；新查询和交付完成也结束旧阶段。仓储通过 `mongo_ops`、`aggregate` 或通用 Repository 执行数据访问；直接取得原始事务会话会撤销该执行器的边界证明。

`Executor` 只允许持久化设施实现，外部不能把旧边界重新挂载到自定义执行器。边界仅保留阶段弱引用；执行器退出、事务重启、阶段推进或原始会话暴露后，所有克隆凭证同时失效。

需要数据授权过滤的读取用例统一执行 `query → 仓储读取 → validate → 交付结果`。`validate` 按上表决定检查内容，调用方不能传入开关跳过复验。事务读取结果在同一事务内完成交付检查；事务失败时丢弃结果。列表和计数要求同一快照时必须使用同一事务，分页之间的一致性另按游标合同处理。

仅检查 RBAC 功能资格、没有数据范围依赖的读取，必须在同一快照事务内执行 `require(Operation) → 完整业务读取 → 事务成功后交付`。此类入口不绑定无用 Mapping，不重复读取同一快照中的身份资格；业务数据、分页和计数必须使用原事务执行器，禁止将授权结果带出事务后继续读取。

凭证只用于当前读取阶段。事务结束、发生业务写入或开始下一读取阶段后，必须重新授权；服务、身份、权限和目标查询不得替换。有效期在所有异步检查结束后再次核对。查询式导出必须在交付前完成检查；流式导出按有界批次授权和检查后交付，不得先发送未检查的数据再复验。

非事务读取必须记录所有已物化的授权依赖：账号及角色、实际使用的组织和人员范围以及允许读取补充的授权修订。修订号必须覆盖相应写入并避免变化后恢复成相同版本；无法可靠检测变化时，该入口只允许事务读取。

#### 3.5.3 写入和阶段内变化

业务用例在写授权前开启事务。授权读取、业务读取和写入必须使用同一事务执行器；创建、归属变更、任务办理也遵守此合同。

`require` 成功后，用例继续检查单据状态、金额、业务版本和幂等要求。决定写入的对象或任务版本必须受写入条件或事务冲突保护；涉及不同记录的指派、来源等约束，不得仅凭同一快照宣称已防止并发变化，必须沿用对应业务的并发保护。

如果本用例先改变了归属、指派、来源或权限，再执行后续受保护操作，后续操作必须重新授权。旧授权结果和已解析范围不得跨这次写入复用。

`require` 在全部异步读取及专有检查完成后核对最早到期时点，成功后释放本次检查数据。授权有效期保证到本次检查完成，不延伸为提交时仍有效的承诺；不为此新增提交钩子或长期授权凭证。

任一授权或业务检查失败，终止操作并按既有事务机制回滚；数据库故障及接入错误原样传播。

### 3.6 AuthorizationService 执行合同

#### 3.6.1 共享状态与单次解析

共享服务只保存身份设施、已校验的 Facts 与 Mapping 绑定及固定范围定义。绑定在启动后保持不变。账号、范围结果、对象事实、查询结果和动态依赖均属于本次调用，不保存在共享实例中。

单次授权按以下顺序执行：

1. 按权限取得固定处理分支，检查目标形态和必要绑定。
2. 读取有效账号与启用角色，取得完整功能资格；缺少资格时，在读取受保护业务事实前终止。
3. 按需解析 DataScope、记录授权和真实关系条件。
4. 执行对象流程或生成查询条件。
5. 按第 3.5 节检查使用边界、有效期及必要依赖。

同一次解析复用已取得的身份和合格角色。DataScope 使用满足本次完整资格要求的角色，不使用全部角色或权限并集代替同角色证明。独立来源资格分别取证；已满足的相同资格不重复查询。非事务复验重新读取依赖，不用原缓存证明自身仍有效。

内部结果只携带后续执行需要的数据。`Resolution`、`AuthorizedDataScope`、`AuthorizedQuery` 等中间包装没有独立职责时合并或删除，不要求沿用旧字段布局。

#### 3.6.2 共享的数据条件

对象判断和查询转换复用一份内部条件表达。只支持实际业务需要的归属、组织、仓库、结算主体、指派、参与、读取补充、与或组合和真实来源条件；不向业务调用方开放政策构造。

条件必须满足：

- 同一范围条款内，本人、协作和组织归属按并集组合；归属、仓库和结算主体等独立维度按交集组合。
- 多个正向范围按并集组合，个人限制只能收窄范围；空正向范围拒绝，不能等同公司范围。
- 历史参与按已有读取规则与正向范围合并后应用个人限制；显式记录读取授权按原有位置补充，二者不得授予写权限。
- 功能资格先成立，数据条件中的允许分支不能替代 RBAC。
- 必需事实未读取必须报错；已知空值或空集合正常参与判定。其他允许分支不能掩盖必需事实缺失及取证错误。
- 来源范围配置的复用不证明实际来源可访问。真实来源必须核对身份、有效性、完整引用及该来源要求的功能资格。
- 完整对象要求全部来源时，引用必须非空且全部通过；任一来源命中只能支持该权限明确允许的输出粒度。

`FactKind` 描述所需数据维度，`AccessFact` 表达具体条件，Facts 提供真实值，Mapping 翻译数据库字段。内部可沿用 `AccessRule`，但其节点只服务上述共享条件。创建、归属变更和任务办理的专有流程不增加通用查询节点。

采购任务内部资料要求当前指派给本人；已完成任务还须本人参与。完成标记使用 `ObjectFacts.completed` 和对应的 `FactKind::Completed`、`AccessFact::Completed` 表达，查询和精确任务检查共用这一条件。Facts 与 Mapping 必须完整提供指派、完成标记和参与事实；业务状态迁移仍由业务用例校验。

#### 3.6.3 对象与操作检查

已有记录按以下顺序处理：

1. 校验完整目标集合，读取对应 Facts。
2. 核对资源、身份、版本和必要事实；根目标不得缺失、重复或多出。来源展开遵守已有数量和深度限制。
3. 规则需要显式读取授权时，只查询本次目标及实际来源的授权记录，同时核对接收人、资源、读取动作、启用状态和有效来源；不预加载账号的全量授权 ID。
4. 执行共享数据条件，所有根目标均须通过。
5. 执行该目标要求的专有检查，并按第 3.5 节完成一致性检查。

| 目标 | 专有检查 |
| --- | --- |
| 无对象操作 | 只检查该权限要求的功能资格，不制造对象事实或空范围 |
| 创建候选 | 校验服务端候选归属和必要来源；只读取已经存在的来源，不读取尚未创建的对象 |
| 归属变更 | 原对象操作资格和目标归属同时通过；原对象来自 Facts，目标归属来自服务端确认的输入 |
| 任务办理 | 读取精确任务身份、当前版本、指派、参与及关联对象；按固定动作规则处理状态差异，普通单据 ID 不能代替任务身份 |

专有检查使用 identity 内的普通函数；任务列表只复用适用于列表的数据条件，不能用列表可见性代替办理资格。业务状态、金额和幂等校验仍由业务用例执行。

事务内不为检测事务外变化而再次读取相同对象及角色。非事务对象读取在 `require` 返回前重新核对实际授权依赖和对象事实；后续另行读取业务结果时，必须使用 `query → 读取 → validate` 或事务读取，不能把之前的 `require` 当作后续结果的授权凭证。写入禁止使用非事务对象检查。

#### 3.6.4 查询转换与仓储执行

`query` 按权限选择固定查询入口，取得共享条件后直接生成 `CompiledAccess`。业务用例不选择 Mapping，不调用独立的 `compile`。

转换必须遵守：

1. 使用启动时校验的集合、主键和事实能力。
2. 根记录及来源记录都应用有效记录条件，例如软删除过滤；范围为允许也不能省略。
3. 保留完整与或关系。准备关联数据时不得先过滤掉只满足其他并集分支的根记录，也不得展开关联数组放大根记录数量。
4. 显式读取授权在数据库中关联授权行和有效来源，不把全量授权 ID 读入应用。
5. 全部来源要求比较原始完整引用与通过集合；缺失和无权来源不能先丢弃。
6. 固定分区和来源查询保留各自资源与输出粒度。份额或存在性结果不能直接放行完整对象；复杂查询的合并、去重和计数使用同一完整授权条件。

`CompiledAccess` 只暴露仓储执行所需的只读查询信息。构造和修改权归 identity，内容包括查询条件、目标查询描述，以及当前阶段需要的边界和依赖信息；不强制保留中间 `AuthorizedQuery`、`Compiler` 或 `Fragment` 类型。

仓储执行前检查目标资源、集合、输出粒度及当前使用边界。全部授权过滤必须在分页、计数、汇总或导出之前执行，业务筛选不得改写授权依赖字段。`ensure_current` 只检查使用边界和有效期，不读取数据库；完整结果交付检查由用例调用一次 `validate`。

`CompiledAccess::version()` 可用于授权条件的游标一致性判断，但不代表所有业务行的数据版本，也不能替代结果交付检查。

#### 3.6.5 validate 与失败处理

`validate` 不重新执行业务查询，不更新旧凭证。执行要求：

1. 核对服务、事务或非事务读取阶段及有效期，拒绝跨边界复用。
2. 事务读取按原快照完成检查，不重新解析相同身份、范围和对象事实。
3. 非事务读取重新核对第 3.5.2 节规定的实际依赖；版本变化即拒绝，不用新条件重新认可旧结果。
4. 所有异步检查结束后，再次检查有效期。

静态 Mapping 的集合和主键描述由构造时固定，不参与每次依赖复验。共享 Mapping 不得保存请求数据或在运行中改变这些描述。

| 情况 | 执行结果 |
| --- | --- |
| 身份无效或功能资格不足 | 返回身份或权限错误 |
| 有功能资格，数据条件不允许 | 对象操作拒绝；查询生成空结果条件 |
| 未知权限、目标不支持、缺少绑定或事实、Mapping 能力不足 | 返回接入错误，不降级授权 |
| 根目标不完整、实际来源缺失 | 按对象或来源合同拒绝，不凭剩余对象放行 |
| 非事务复验发现依赖变化，或当前阶段已到期 | 返回既有 `DATA_SCOPE_CHANGED` 冲突，丢弃未交付结果 |
| 切换服务、事务或读取阶段 | 拒绝凭证复用 |
| 数据库或取证故障 | 原错误向上传播，不能伪装成空范围或授权成功 |

#### 3.6.6 功能资格查询

`has_permission` 返回有效账号是否至少有一个启用角色授予指定权限；`permissions` 返回逐项资格，允许不同权限来自不同角色。取证故障返回错误，不能当作无资格。

账号失效时，批量接口返回 `None`；有效账号未命中任何权限时，返回权限集合为空的 `Some(QualifiedPermissions)`。两个接口只处理功能资格，不加载业务对象、生成范围条件或查询凭证。

#### 3.6.7 询价示例

假定当前账号为 `user_1`，有询价修改和列表权限，两项操作的数据范围均为本人负责。询价负责人字段为 `sales_owner_user_id`，无额外范围、个人限制或读取补充。

修改时，事务内读取真实负责人和对象版本。负责人为 `user_1` 时授权通过；为其他人时拒绝；负责人事实未读取时返回接入错误。业务随后执行状态、版本及写入检查，无需再次读取同一快照的负责人来证明授权更新。

列表条件等价于：

```json
[
  {
    "$match": {
      "deleted_at": 0,
      "sales_owner_user_id": "user_1"
    }
  }
]
```

该 Mapping 只描述字段。事务列表在交付前检查原事务、当前阶段和有效期；非事务列表另行核对账号、角色及实际使用的范围依赖。两种路径都先在数据库中过滤，再分页和计数，不逐行加载 `ObjectFacts`。

| 查询凭证 | 保留不可伪造的查询条件、当前阶段边界及必要依赖；事务路径不携带仅为重读同一快照服务的数据 |

`Resolution`、`AuthorizedDataScope`、`AuthorizedQuery`、`QueryModelKey` 等内部结构按上述职责合并、删除或收为私有。不要求逐个保留旧类型，也不得仅改名后维持重复机制。移除结构时保留对应行为测试。

本节不删除账号、角色、人员范围和记录授权数据，不改变既有权限字符串。

#### 3.7.4 同步删除的接入代码

- 清理第 3.7.1、3.7.2 节涉及的业务构造和旧接口调用，删除重复动作白名单和临时 `AuthorizationService::new` 工厂。
- 业务访问器改为接收共享服务，移除为切换授权规则而持有的多个服务实例；业务状态检查和事实读取保留。
- 仓储统一消费 `CompiledAccess`，执行第 3.6.4 节规定的检查与过滤。
- 全部业务入口完成迁移后，删除 [`http/middleware/rbac.rs`](../../../../apps/erp-server/src/http/middleware/rbac.rs) 中的 `with_permission`、`RbacAuthorizeLayer`、`RbacAuthorizeService` 及对应路由包装。JWT 认证和路由权限目录信息按既有合同保留。

## 4. 实施计划与验收

### 4.1 实施顺序

按以下六个阶段实施。前四阶段完成底层改造，第五阶段迁移业务，第六阶段切换应用并完成整体验证。

每个阶段单独交付并停止，待 review 完成且明确要求继续后，再进入下一阶段。阶段交付必须列出改动文件、公共接口变化、代表性执行路径、已执行检查及尚未通过的检查；不得用后续阶段的计划代替本阶段验收。前四阶段的具体 review 内容见各阶段要求。

前五阶段允许尚未迁移的下游 crate 编译失败，不保留或新增兼容分支来维持中间状态的 workspace 编译。各阶段同步更新本阶段直接影响的内部引用，只按自身范围验收；完整 workspace 验证在第六阶段完成。尚未进入清理阶段的旧代码可以暂存，但不得新增双轨执行或默认放行分支。

| 阶段 | 交付内容 | 主要 review 内容 |
| --- | --- | --- |
| 一 | 公共权限类型、常量和目录 | 权限定义是否统一，编码和生成结果是否一致 |
| 二 | DataScope 与固定授权规则 | 每项权限实际检查什么，范围与关系如何组合 |
| 三 | Facts、Mapping 和执行边界 | 事实如何判断、条件如何转换、依赖何时复验 |
| 四 | 统一服务与启动装配接口 | 业务如何调用，启动时如何发现缺失接入 |
| 五 | 业务迁移和完整实现绑定 | 每个业务入口是否执行完整授权 |
| 六 | 应用切换和整体验证 | HTTP、worker、前端及全仓是否完成切换 |

#### 4.1.1 第一阶段：建立公共权限定义与目录

1. 创建 `erp-permissions`，按第 3.1 节实现权限值类型、常量、资源标识和公共目录。
2. 切换 identity 的权限类型引用，删除原值类型实现；迁出 server 的公共目录定义，删除权限包装目录和重复符号索引；路由直接引用公共常量，仅保留接口展示差异。
3. 完成 server 的普通依赖、build-dependency、前端权限生成器及权限漂移检查的目录接入。业务用例中的常量引用在第五阶段切换。
4. 同步 workspace 成员、`scripts/crate-layers.json`、依赖边界配置、README、`crates/README.md`，以及 `backend/AGENTS.md` 中权限定义与目录的归属。

Review 内容：检查 `Permission` 的构造、解析、序列化与覆盖关系；核对公共目录到 server 和前端生成结果的路径；确认没有第二份权限值类型或编码定义。

验收：`erp-permissions` 独立编译及单元测试通过；覆盖非法常量、动态输入边界、常量与动态值的等价性、既有序列化和覆盖语义。目录生成与权限漂移检查通过，且不依赖尚未迁移下游的编译。该 crate 不依赖 identity、业务实现或应用。server 全 crate 编译在第六阶段验证。

#### 4.1.2 第二阶段：统一范围定义与固定授权规则

1. 按第 3.3.3 节将范围信息合并为私有 `ScopeSpec`，完成范围来源、默认本人、支持及必需维度的校验。
2. 将配置候选、保存校验、范围解析、初始化和授权文件导入导出切换到同一份范围定义。
3. 按第 2.3、3.6.1、3.6.2 节，在 identity 内按权限组织固定授权函数。明确目标类型、完整功能资格、范围要求，以及任务和来源等附加检查；同次解析复用身份与合格角色。
4. 按第 3.3.4 节调整 identity 的配置目录和权限检查 DTO，移除总策略分类依赖；server 和前端调用在第六阶段切换。
5. 同步 identity 内直接受影响的引用，清理已经完成替换的范围定义及分类代码。统一服务、Builder 和执行管道的整体切换在第四阶段完成。

Review 内容：逐项检查权限对应的实际规则；用询价修改、记录授权补充读取、任务办理和真实来源检查展示规则输入及预期结果；核对同角色要求、个人限制和读取补充的位置。

验收：`erp-identity` 编译及受影响单元测试通过。覆盖范围来源缺失或循环、配置准入、无配置默认值、同角色资格、空范围、个人限制，以及任务和来源规则。测试执行实际范围解析与规则函数；规则声明测试不替代第三、四阶段的对象、查询及统一入口验证。

#### 4.1.3 第三阶段：简化事实、查询映射与执行边界

1. 按第 3.3.1、3.6.3 节整理 Facts 读取和对象判断，落实完整目标集合、必需事实及真实来源校验；实现创建、归属变更和任务办理的专有检查。
2. 按第 3.3.2、3.6.4 节接入静态 Mapping，使用第二阶段的共享数据条件完成对象判断和查询转换。
3. 按第 3.5 节完成事务边界识别和读取阶段约束，再移除同快照重复读取；保留非事务实际依赖复验及最后有效期检查。
4. 按第 3.7.3 节合并无独立职责的中间包装，调整 `CompiledAccess` 的只读执行信息及使用边界。底层接口变化导致的业务 Mapping 适配统一在第五阶段完成。

Review 内容：分别展示普通询价和多来源查询从条件到数据库过滤的结果；检查静态 Mapping 是否无需准备；对照事务与非事务路径，核对每次读取、依赖记录和有效期检查的必要性。

验收：`erp-identity`、受影响事务基础 crate 编译及对应单元测试通过。测试覆盖对象与查询成员判断一致、并集不提前丢弃根记录、来源完整性与输出限制、动态依赖变化、同会话跨事务、跨写入阶段复用和到期拒绝。事务路径不得仅凭会话存在就省略复验。测试替身验证执行合同，不能作为真实数据库事务行为已验证的证明。

#### 4.1.4 第四阶段：接通统一授权服务与装配接口

1. 将第二、三阶段的规则和执行流程接入第 3.2.3 节的公共 API。`require` 执行固定目标检查，`query` 直接返回 `CompiledAccess`，`validate` 按执行模式完成结果交付检查。
2. 实现第 3.4 节 Builder，启动时校验范围定义、权限引用、Facts、Mapping、目标能力和输出粒度；Builder 只绑定实现，不声明政策。
3. 在 server 的 `wiring/authorization/` 建立统一装配入口，明确所需实现依赖。完整业务 Facts 和 Mapping 在第五阶段补齐；不得用空实现或放宽校验构造不完整的生产服务。
4. 完成第 3.7.1、3.7.2 节的 identity 旧登记层与公开接口清理，删除调用方构造政策、选择授权主体及独立编译查询的入口。
5. 同步 identity 的调用示例和 `backend/AGENTS.md` 中装配职责。保留既有路由鉴权，应用服务工厂及中间件在第六阶段切换。

Review 内容：从 `require`、`query` 和 `validate` 各追踪一条完整执行路径；检查业务参数能否绕过必要条件；检查 Builder 对缺失、重复、错配绑定的拒绝结果，以及旧入口是否已删除。

验收：`erp-permissions`、`erp-identity` 和受影响事务基础 crate 编译及对应单元测试通过。使用测试事实与映射，经真实公共 API 验证允许、拒绝和依赖失效路径；Builder 测试覆盖完整绑定成功、重复绑定、未知引用、能力缺失及输出错配。server 装配结构完成 review；真实业务绑定、生产服务完整构造及 server 编译分别在第五、六阶段验证。

#### 4.1.5 第五阶段：逐 crate 迁移业务调用并补齐装配

1. 按第 3.1、3.2、3.5 节切换本 crate 的权限引用与业务调用。
2. 完成第 3.7.4 节的业务接入清理；HTTP 路由鉴权清理留到第六阶段。
3. 在 server 的授权装配模块中补齐该 crate 的事实读取器及 Mapping 绑定，可共用的实现及实例按第 3.3 节复用。逐个核对复杂查询的来源分区、输出粒度和动态依赖；静态实现删除空准备逻辑，非事务路径缺少真实依赖修订时改用事务读取。

验收：每个已迁移业务 crate 编译通过，并通过对应授权行为单元测试。第五阶段结束时，server 的授权装配代码覆盖全部所需 Facts 和 Mapping；业务不再重复声明权限政策。完整启动装配和 server 编译在第六阶段验证。已执行 `cargo test --lib` 的受影响 crate，不再重复执行 `cargo check`。

#### 4.1.6 第六阶段：切换应用入口并完成整体验证

2. 按第 3.2.3 节核对全部受保护业务入口，再完成第 3.7.4 节的 HTTP 路由鉴权清理。迁移期间不得出现缺少业务授权的接口；既有公开入口的认证规则保持不变。
3. 调整路由合同检查及生成器，移除对 `with_permission` 调用形式的依赖，沿用公共权限定义；同步 `backend/AGENTS.md` 的 HTTP 授权规则。
4. 按第 3.3.4 节同步 server 和前端的人员范围、权限检查与展示，验证旧分类字段移除后的请求和响应。前后端作为同一变更切换。
5. 按迁移清单清理剩余旧接口、临时工厂和业务侧重复权限判断。核对 CLI 的受影响调用及编译，保持其独立运行时和依赖边界。
6. 同步 `erp-permissions`、`erp-identity`、`erp-server` README 及根目录 [ERP 权限系统设计](../../../../../docs/authorization-system-design.md)。

验收：完整授权服务构造成功，全 workspace 和相关门禁通过，并满足第 4.2 节的交付条件。编译通过不能替代授权行为验证。

### 4.2 交付验收

交付时必须完成以下检查：

| 检查项 | 通过条件 |
| --- | --- |
| 公共权限与目录 | 第 3.1 节的类型、常量及目录迁移完成，前端生成与权限漂移检查通过 |
| 依赖边界与启动装配 | 第 2.4 节的依赖检查通过，HTTP 和 worker 按第 3.4 节成功构造完整服务 |
| 业务入口与内部执行 | 全部受保护入口符合第 3.2、3.5 节；第 3.3、3.5、3.6 节的事实、映射、执行及阶段边界合同由行为单元测试验证 |
| 配置与检查接口 | 第 3.3.4 节的 DTO、服务和前端同步完成；编辑能力、退役项和待检查状态正确，旧总分类字段及判断分支移除 |
| 旧实现清理 | 第 3.7 节清单全部完成，无旧 API 兼容分支 |
| 编译与文档 | 全 workspace 编译及第 4.1 节要求的门禁通过，README 和权限系统设计与实际接口一致 |

授权行为单元测试必须覆盖：

| 场景 | 预期结果 |
| --- | --- |
| 动态输入格式非法，或反序列化收到非法权限字符串 | 返回校验错误，不生成权限值 |
| 同一权限分别来自常量和动态解析 | 相等、哈希、排序和覆盖结果一致，使用相同规则与实现绑定 |
| 权限序列化及通配覆盖 | 保持既有 `resource:action` 表达及覆盖语义 |
| Facts 和 Mapping 已绑定，但 RBAC 未向账号授予该权限 | 授权被拒绝，实现绑定不授予功能资格 |
| 有功能权限，但不满足该权限的完整数据规则 | 对象操作被拒绝，查询不返回该对象 |
| 同一权限被多个业务用例共用 | 基础检查一致；附加目标检查由明确目标合同决定，不能削弱必要条件 |
| 普通范围未命中，但命中该动作允许的行级读取授权 | 功能权限仍须成立；按既有读取规则返回允许的数据 |
| 写操作仅命中历史参与或行级读取授权 | 不授予写权限 |
| 入口权限和额外必需权限分属不同角色 | 不能通过同角色要求；独立入口按各自角色分别验证 |
| 同一权限、同目标语义同时支持对象检查与完整对象查询 | 对象是否可读与列表是否包含它一致 |
| 查询仅证明某个来源份额或存在性 | 输出遵守对应粒度，不能据此放行整个对象 |
| 创建或归属变更 | 分别校验候选归属，或同时校验原对象资格与目标归属 |
| 任务身份、版本或指派与本次快照中的事实不符 | 旧任务目标不能继续办理；并发变更按业务版本及冲突合同处理 |
| 非事务查询的身份、范围或读取授权修订变化 | 交付检查失败，丢弃未交付结果 |
| 缺少规则、必要绑定或事实，资源错配、目标形态不支持或重复绑定 | 返回错误，不放宽授权条件 |
| 必需事实为 `Missing`，但其他并集分支可以放行 | 仍返回事实缺失错误；`Known(None)` 和已知空集合正常参与判定 |
| 数据范围为空但功能资格有效 | 对象检查拒绝；查询产生空结果条件，不退化为只检查功能权限 |
| 查询规则包含并集或多来源 | 保留完整逻辑关系，不在准备关联阶段提前过滤根记录或放大根记录数量 |
| 凭证来自其他服务、跨事务或跨读取阶段，包括同一会话开启下一事务 | 拒绝复用，旧结果不得返回 |
| 查询包含分页、计数、汇总或导出 | 数据库先执行完整授权过滤，交付前由读取用例执行一次模式对应的检查；流式导出按批次检查后交付 |
| 静态 Mapping 没有业务集合版本 | 正常生成条件；非事务身份和范围依赖仍须复验 |
| Mapping 的模型描述含请求状态或可在启动后变化 | 绑定或接口约束拒绝，不依赖每次复验补救 |
| 同一事务中执行授权和查询 | 按原快照判断，交付检查不重读同一批依赖；事务外后续撤权不宣称已经被观察 |
| 执行器不能证明当前活动事务及读取阶段 | 不启用省略依赖重读的路径 |
| 授权后本事务修改归属、指派、来源或权限 | 后续受保护操作重新授权，拒绝复用先前凭证 |
| 对象授权或查询交付检查过程中依赖到期 | 最后一次有效期检查失败，不返回授权成功或交付结果 |
| 完整对象、存在性或份额来源组合 | 保持输出边界、去重及计数，不因减少模型类型而扩大访问 |
| 范围定义权限重复、来源缺失、来源循环或维度不兼容 | 定义校验失败，不构造授权服务 |
| 没有人员范围配置 | 按当前定义得到本人基础、空范围或公司共享；任务权限不能因范围定义缺失变成仅 RBAC |
| 来源范围配置被复用 | 使用来源条款但检查当前入口资格和当前对象归属；范围复用不证明实际来源对象可访问 |
| 为公司共享、来源复用、纯任务或仅功能资格操作保存独立范围 | 拒绝配置；历史记录保留为退役项 |
| 一次配置覆盖多个动作，其中一个不支持类型或必需维度不完整 | 拒绝整次保存，候选维度并集不能替代逐动作校验 |
| 明确要求当前指派人的操作，账号有读取授权或普通范围，但任务已指派给其他人 | 办理检查拒绝；读取补充不能代替当前任务关系 |
| 权限检查缺少任务或来源对象上下文 | 返回已检查项和待检查项，不报告对象授权通过 |
| 同资源不同动作的配置能力不同 | 只允许编辑可配置动作，说明逐动作展示，前端不再依赖总策略分类 |
