# 项目 workflows

## simplify-backend-crates

在保持业务逻辑和对外 API 的前提下，精简 `backend/crates` 内部实现：去过度防御、去过度抽象、去死代码、去无意义包装，以及封装同语义重复逻辑。

### 运行

在仓库根目录启动：

```text
/simplify-backend-crates
```

也可使用 `/workflow simplify-backend-crates`。实际运行后在 `/workflows` 查看进度和报告。

默认动态发现 `backend/Cargo.toml` 登记的全部 `backend/crates` 成员。传给 workflow 工具的可选参数：

```json
{
  "crates": ["application-core", "erp-sales"],
  "parallelism": 2
}
```

| 参数 | 含义 |
| --- | --- |
| `crates` | 包名数组；省略或空数组时处理全部活动 crate |
| `parallelism` | 每批并发的执行者数量，默认 `4`，允许 `1..4` |
| `recovery_file` | 已获用户授权恢复的上一运行 `scratch/details.json` 路径；省略时要求后端干净 |

每个 crate 一个执行者，共享当前工作区并按互不重叠的 crate 目录分工。每批完成后独立复核；发现问题最多修正并复核一次。最终验证统一串行运行。

### 首批恢复

`recovery_file` 仅支持首批执行者已返回完整报告、因报告校验失败而停止的现场。原报告必须包含 `inventory`、`batch`、`results`，且 `completed` 为空。恢复前必须获得用户批准，并满足以下条件：

- 当前 HEAD 等于原始干净基线；暂存区为空，后端无未跟踪文件。
- 当前后端差异恰好匹配首批报告；所有修改均为分配 crate 内既有 `src/**/*.rs` 文件的内容修改。
- 原始报告完整导入；脚本校验 `completed` 为空、原 HEAD 和干净状态、`batch/results` 等长及完整有序前缀，仅规范化原 `results` 的路径。
- 恢复检查和独立复核前后必须保持同一 HEAD、暂存区、状态及 SHA-256 内容指纹；自动修正写入前再次校验快照。

恢复流程先导入报告，再独立复核首批并执行其完整定向门禁；全部通过后继续其余 crate。原运行记录保留，新运行独立记录恢复证据。其他阻塞格式、并发修改或归属不明的差异必须停止处理并保留现场。

### 执行边界

- 常规启动时要求 `backend/` 下没有既有修改或未跟踪文件；显式传入 `recovery_file` 时按“首批恢复”逐项校验。其他目录的用户工作保留。运行期间请避免编辑后端文件。
- 写入范围是目标 crate 的 `src/**/*.rs`，包括必要的内联行为单测。公开接口、错误语义、数据合同、权限、幂等、事务及必要副作用顺序保持。
- 证据不足、需要跨 crate 迁移、依赖变更或整文件删除的候选会保留并写入报告。
- 最终按 `backend/AGENTS.md` 执行受影响 crate 的格式检查、clippy、库单元测试，以及命中的条件门禁。测试使用隔离替身，真实数据库和外部服务保持关闭。
- crate 独立编译（`cargo test`、`cargo clippy`、`cargo check`）只把编译目录放在已挂载外置盘 `/Volumes/Kingston/rust-build-target`，并显式设置 `CARGO_TARGET_DIR`。外置盘未挂载时不创建该路径、不编译。`cargo fmt`、`git diff` 和边界脚本不产生编译目录。
- 修改留在当前工作区；workflow 不执行提交、推送、分支操作或自动清空工作区。遇到阻塞时保留修改与证据，并明确标注未验证范围。

报告记录逐 crate 的改动、五方向覆盖、等价性依据、跳过理由、实际命令与退出结果，以及生产代码净行数。

### 安全检查与限制

- 所有报告路径统一为仓库相对路径。脚本仅将当前实际仓库根目录下的绝对路径去除根目录前缀，再执行原有范围校验；其他绝对路径、路径逃逸和越界路径会阻塞。该规范化覆盖执行、修正和验证报告。
- 脚本通过宿主 `git_diff_since` 读取实际跟踪文件差异，在初始基线、每批复核前后、最终验证前后检查范围。后端差异必须落在已申报路径；后端以外的初始跟踪差异必须保持，删除、重命名、文件模式或二进制变更会阻塞。
- 写入执行者和修正者使用 `all` 能力模式；逐批复核者使用 `read-only`。清点和最终验证需要终端，使用 `execute`；该模式的终端仍可写文件。此 workflow 使用共享工作区，能力模式与差异检查提供审查和事后拦截，文件系统路径隔离需由宿主另行提供。
- `git_diff_since` 只覆盖跟踪文件。未跟踪文件、初始后端干净状态、真实命令执行结果与外部服务隔离仍由代理检查并提供证据；业务和 API 等价性由代码复核与定向行为测试确认。运行期间请保持仓库状态稳定。
- 结果字段 `status: verified` 表示验证通过，`status: blocked` 表示停止且可能留有未验证修改。宿主的 `complete` 会将两类结果都显示为运行结束成功，请按结果字段和报告判断验收状态。

### 调用预算

目标 crate 数量为 `N`，每批并发为 `P` 时，最大 agent 调用数为 `N + 3 × ceil(N / P) + 4`，已包含批次修正和最终修正重试。最大同时运行数量为 `P`。

以当前 50 个 crate、默认并发 4 计算，常规路径调用 65 次，最多 93 次，符合工具默认的 128 次预算。恢复模式额外预留 8 次调用预算，用于现场导入、快照、首批门禁及批次数差异，最多预留 101 次。降低并发或增加成员后，workflow 会在修改前检查预算；需要时可在工具调用中提高 `agent_budget`。

workflow 的 smoke check 验证元数据、编译和模拟主机选中的执行路径。真实仓库执行、Cargo 结果及业务等价性由实际运行的复核和验证阶段确认。
