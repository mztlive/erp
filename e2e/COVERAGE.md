# E2E 功能覆盖与执行合同

## 1. 验收口径

本清单适用于当前仓库已实现的管理端与公开选品功能。执行人必须按功能结果判断覆盖，不得以页面访问、API 成功状态或用例总数代替业务断言。

- **真实服务覆盖**：浏览器或正式 HTTP 命令调用当前后端，核对持久化结果、状态、金额、权限或文件内容。
- **浏览器模拟覆盖**：测试替换业务响应，只验收客户端请求参数、交互和渲染。不得计入真实数据库、授权或金额正确性验收。
- **前置未满足**：正式能力需要当前未装配的外部连接器、来源数据或尚未实现的入口。只能验收现有拒绝行为，不得登记完整成功链路通过。
- **未专项覆盖**：主流程可能经过该能力，但没有对应结果断言。必须保留本状态，直到专项测试进入清单并实跑通过。

flow-27 分别在个人提交触达后端前中断请求，以及使用当前 shard 的 `route.fetch` 取得真实提交成功结果后中断浏览器响应；两种场景必须分别核对原幂等命令、收件信息与方案唯一性。flow-28 和 flow-29 的响应丢失场景同样先调用真实后端完成写入，再中断浏览器响应。不得将注入的网络故障登记为真实网络环境验收。

任何新增或修改用例必须使用 `helpers/test.ts` 的隔离路由 fixture。所有写入、直接数据库 helper 与后端进程必须绑定本次 shard，禁止写入源开发库。

flow-27 的历史选品册 fixture 只允许移除本用例新建且未提交册的密码字段。执行时必须同时提供 `ERP_E2E_ISOLATED=1` 与 `ERP_E2E_CONFIG_PATH`，目标数据库必须符合当前 runner 的临时库命名；不得回退到开发配置或修改源库。提货券导出必须读取浏览器实际下载的工作簿，逐人核对提货码、方案编号、商品、数量、金额、姓名、电话和完整地址，不得只验收下载事件或文件名。

flow-27 的页面级路由拦截必须显式使用当前 `API_BASE`：放行请求使用 `route.continue({ url })`，取得真实响应使用 `route.fetch({ url })`。不得以共享前端构建中的源 API 地址执行写入。同码并发首发可返回原回执或 HTTP 409 版本冲突；每条原命令随后必须返回同一回执，后台仅有一份个人方案。

## 3. 未专项覆盖及前置要求

下列项目不得因本套件通过而登记完整覆盖：

| 范围 | 当前验收限制 | 补齐条件 |
| --- | --- | --- |
| 真实供应商 API 健康、商品同步、订单回调、售后和完整结算 | 默认装配不可用连接器与引用注册表；flow-25 只验收失败阻断 | 注入正式协议连接器及权威引用注册表，准备完整订单／账单／退款来源 |
| 供应商门户 | 当前只有专题合同，没有可执行入口 | 完成入口、鉴权及领域实现后另立真实流程 |
| 历史系统文件自动解析与实际搬迁 | flow-26 验收客户批次、确认、结果登记和重试；不验收库存／应收期初搬迁 | 接入实际解析 worker，准备可核对的历史输入、期初库存与往来余额 |
| 客户质量默认期间配置 | 旧默认期间接口尚未实现；flow-30 只验收故障提示保留及手动期间恢复 | 实现默认期间配置接口并验收保存、读取及默认查询；历史归属换任金额另需冻结订单 fixture |
| 银行回单直接接口的缓存 TTL 与撤权 | 现有流程验收任务上下文下载 | 固定缓存时钟或等待策略、权限撤销场景及直接接口字节核对 |
| 合并供应商付款及银行账号 CAS | 分次付款与退款已覆盖，合并与过期账号专项未覆盖 | 多任务、多应付和银行版本变化的确定性 fixture |
| 实物入仓／直发、部分履约及退款的实际成本 | flow-23 验收新增整笔成功的服务履约实际成本；电子交付金额由 flow-03 专项核对；不自动补记已确认历史履约 | 明确部分数量、零净额及退货成本纠正规则，补齐各履约入口与财务金额对拍；历史补记另设迁移与去重验收 |
| 导入／选品准备 worker 崩溃恢复 | 普通后台终态已覆盖 | 注入可恢复故障，验证租约恢复、已成功项保持及后续处理 |
| 分片上传降级、取消、超时恢复及极限文件 | flow-22 使用正常分片直传 | 固定上传故障、取消及大小边界，校验资源与任务不重复 |
| 公开链接 TTL、图片跨册访问及事务冲突重试 | flow-27 验收轮换、撤销、会话版本冲突及不同参与人并行提交；没有固定时间、跨册图片或确定性瞬态事务冲突场景 | 可控时间、不同册图片资源及权威结果核对；使用可控故障触发已明确回滚的瞬态事务冲突并核对重试次数和副作用 |
| 所有筛选组合及大数据跨页导出 | 当前只覆盖明确列出的业务查询组合 | 超过一页的独立数据及分页／汇总／导出一致性验收 |

基础资料历史版本要求以 `docs/erp-phase-1.md` §4.6.1 为准。商品分类与品牌当前的原地更新实现不得登记为“完整历史版本已验收”。仓库管理页面当前阻断建档／修订／停用操作；flow-30 的仓库生命周期属于正式 API 覆盖。

## 4. 执行与结果验收

全量验收必须从仓库根目录运行：

```bash
E2E_SKIP_BACKEND=1 bash scripts/ensure-services.sh
python3 scripts/run-e2e-parallel.py all
```

后端源代码变更后，必须先在 `backend/` 执行 `cargo build -p web-api --locked`。单流程使用同一隔离入口：

```bash
python3 scripts/run-e2e-parallel.py e2e/tests/flow-22-master-data-import.spec.ts
```

合同编号耗尽场景必须在隔离副本运行。不得通过共享库入口推进开发或正式流水至上限。

验收人必须核对 `logs/e2e/<run_id>/summary.json` 及逐 spec JSON，满足以下全部条件才能登记通过：

1. 计划中的每份 spec 恰好执行一次；全部预期测试执行，失败、flaky、skip 为零。
2. 当前源码对应的前端 `BUILD_ID`、静态资源及后端二进制已准备。
3. 每个 shard 使用独立数据库、配置、API、报告和 S3 前缀。
4. shard 数据库清理结果为 `dropped`；本次临时 Mongo 及数据目录为 `removed`，临时 API 进程和端口已经退出。
5. 源开发 API 健康、开发库没有本次流程写入。
6. 静态、单元测试、浏览器、真实数据库及外部供应商验收分别记录，不互相替代。

新增功能或修复必须同步维护第 2 节映射和第 3 节限制。不得删除尚未取得实际证据的限制项。
