# 工作台展示一致性核查与验收清单

核查日期：2026-09-08。适用范围：工作台列表、详情、审批跟踪和单据查看入口。

## 1. 验收口径

1. 同一业务对象、同一提交版本、同等数据阅读权限下，审批发起人与处理人必须读取同一组服务端摘要字段。金额、往来方和明细不得由角色名称决定。
2. 操作区必须服从服务端 `allowed_actions`。只读任务不挂载建单、付款、开票、导入确认或重放表单；履约责任管理独立于执行队列，仅在具有 `REASSIGN` 时保留。
3. 不同业务类型保留其业务字段。退款、回款、付款、冲正和应收未收余额不得被统一标为“含税金额”。不同含义的字段不得因数值相同而删除。
4. 审批跟踪必须按不可变提交读取。客户回款、两类退款、两类冲正和库存调整在提交事务内冻结公共展示；旧版本缺完整快照时仅返回已保存的基础事实并明确提示资料不完整。
5. 右上角文档图标用于查看。查看链接不得自动打开登记表单；变更单必须携带父单据与精确变更单身份，缺少父单据时不构造错误路径。
6. 审批概览明细保留现有最多 3 行与剩余行数提示；履约公共详情展示本次履约的全部业务行，不用订单总数量替代批次数量。
7. 代码核查、自动化检查与真实角色验收分别记录，不相互替代。工作台外完整对象中心的视觉验收不在本清单范围内。

## 6. 收尾合同

1. 四种履约对象（入库、发货、电子交付、服务履约）必须共用工作台公共详情。查看人与处理人均看到来源单据、来源金额、本次批次及实际业务行；收货显示合格/不合格数量，发货显示承运方和物流单号，电子/服务显示实际结果、期间、说明及受控凭证入口。
2. 仅 `PROCESS` 可显示“处理履约”，点击后打开原有正式作业表单；仅 `REASSIGN` 可显示责任转交。公共内容不得通过执行者队列查询。草稿默认的成功枚举与创建时间不得显示为履约成功事实。
3. 客户回款、客户退款、供应商退款、回款冲正、付款冲正、库存调整必须在正式提交事务内先持久化本次业务字段，再捕获展示快照并完成审批实例与任务的事务写入。任一步失败必须回滚整个事务；幂等重放不得追加快照。
4. 快照使用有界结构 `ApprovalDisplaySnapshot`；复用公共摘要字段定义，最多 128 个字段和 100 行，每项文本最多 8192 字符。审批概览原有 3 行上限及剩余行数必须随版本保存，不构造未保存的完整单据。
5. 旧快照缺少 `display` 时保持兼容。可证明当前同版本的业务内容按原规则读取；其他历史版本只显示当时保留的金额、数量和提交时间，必须标明“旧审批仅保留基础快照”。禁止使用当前往来方、原因或明细补成旧内容。
6. `MASTER_MAPPING_TASK` 无活动注册、工作台处理组件与导航。保留原始历史任务和审计数据；不得删除历史记录，不得为旧残留任务提供新处理入口。
7. 销售/采购变更未冻结的历史原因和类型仍不得从当前草稿补回；该限制不属于本次六类可变单据快照的可恢复范围。
8. 自动化验证与真实多角色业务验收分别记录。禁止把字段渲染测试表述为 MongoDB 事务集成验收；本仓库不执行集成测试。

## 7. 字段演进、部署与回滚

1. 部署前执行 `backend/scripts/migrations/20260908-approval-display-audit.js`，记录六类单据的旧快照数量、完整展示数量及缺失状态。脚本仅检查，不修改业务数据。
2. 本次为可选字段增量演进，无需给旧记录补空对象。旧记录不批量改写，禁止从当前单据回填历史展示。已有 `document_type + business_object_id + subject_version` 索引继续供批量查询使用，无新增索引。
3. 部署后新提交应同时具备审批实例、任务和 `display`；同一版本在发起人与处理人视角逐项比较公共字段。发现任一事务写入失败时按现有命令回执查询结果，不重建提交版本。
4. 应用回滚时保留所有已写入的 `display`，不得删除新快照或修改审批事实。旧程序按兼容反序列化忽略新增字段；重新部署后继续读取原冻结内容。
