## 1. 建设目标与强制边界

1. 系统必须支持公司管理层查看全公司经营情况，部门或团队管理者查看授权范围内的业务，业务人员查看本人负责、明确协作及按既有业务规则保留的历史参与数据。历史参与不构成永久、无条件的访问权。
2. 实现方案固定为：复用现有 Casbin RBAC，扩展现有 DataScope，补齐轻量组织成员关系，使用业务归属事实解析对象范围，使用现有 WorkItem 管理当前执行责任。
3. RBAC 决定资源与动作权限；DataScope 决定该资源、该动作的可访问数据；组织关系提供范围解析依据；业务归属提供对象责任事实；列表筛选只能收窄最终授权结果。
4. 部门成员身份不自动授予部门业务查看权。管理关系不自动授予编辑、审批、付款、开票、改派或敏感信息揭示权限。
5. 内部部门或团队、法人结算主体、仓库必须使用不同类型的身份和范围解释。禁止将部门 ID 直接写入现有 `settlement_party_id`、仓库 ID 或 WorkItem 的既有责任组织字段。
6. 每条开放人工任务仍必须属于一个具体用户。不得新增团队责任池、领取、抢单、开始处理或退回团队；审批节点仍按已发布定义指定到人。
7. 历史业绩归属与当前访问权限必须分别计算。历史人员、部门快照不构成访问授权；当前调岗不得改写历史业绩归属。
8. 本期不建设薪酬、考勤、职级、岗位编制或通用策略脚本引擎。不以部门名生成业务角色，不为每个团队复制一套销售经理角色。

## 4. 组织、成员与管理关系

### 4.1 组织单元

新增 `org_unit`，至少包含 `id`、`name`、`parent_id`、`kind`、`status`、`version` 及审计字段。

1. `kind` 固定支持 `department`、`team`；部门与团队共用一棵内部管理树。
2. 同一有效节点只能有一个父节点；不得自引用、形成环或跨越既定企业边界。父子关系调整必须原子校验并推进组织版本。
3. 组织节点只代表内部管理单元，不代表法人主体或仓库。Company 范围仅指现有 ERP 企业边界内的授权数据，不表示绕过未来租户或法人隔离。
4. 停用节点不得新增有效成员或管理关系；存在有效成员、管理关系或尚未结清且需交接的业务时，必须完成交接后才能停用。已结清业务和历史快照继续保留原组织引用，不阻止组织停用。历史节点不得物理删除。

### 4.2 成员关系

新增 `org_membership`，至少包含 `user_id`、`org_unit_id`、`valid_from`、`valid_to`、`version`、变更原因及操作人。

1. 首期每个用户同一时点只允许一个有效主属组织；跨团队协作使用业务协作关系，不通过多个主属组织隐式扩大数据范围。
2. 时间区间统一使用服务端 UTC 时点，按 `[valid_from, valid_to)` 判断；展示使用 Asia/Shanghai。客户归属原有自然日合同保持不变，按其既有业务日期规则解析。
3. 调岗必须结束旧关系并创建新关系。组织成员变化不得自动改写客户归属、单据负责人或开放任务。
4. 没有有效成员关系的用户不得被自动放入根组织。Company 授权仍可按自身规则生效；依赖本人组织的范围必须为空。

### 4.3 管理关系

新增 `org_management_assignment`，至少包含 `user_id`、`role_id`、`org_unit_id`、`include_descendants`、有效期、版本、授予人与原因。

1. 管理关系只在账号有效、指定角色有效且用户当前持有该角色时生效。不得用另一个角色的权限激活管理关系。
2. 同一销售经理角色可授予不同经理；每位经理通过自己的管理关系得到一组或多组组织目标，禁止通过复制角色区分团队。
3. 管理范围可以覆盖并非本人主属组织的团队；这种跨团队管理必须显式授予并审计。
4. `include_descendants` 必须显式设置，缺省为 `false`。组织挂接到某管理节点之下时，只有包含下级的既有管理关系才覆盖该新下级。
5. 成员变更、组织移动和管理授权页面必须提供变更前后影响预览。修改者须具备相应管理动作及目标管理边界，不得仅因是部门负责人而获得授权配置权限。
6. 组织、成员、管理关系及范围变更必须使用乐观锁，并在同一事务记录审计和版本变化。

## 5. DataScope 扩展与授权运算

### 5.1 模型要求

扩展现有 DataScope，不建立与其并行、互相兜底的数据授权服务。版本 2 至少表达：

| 字段 | 规则 |
| --- | --- |
| `schema_version` | 首次上线统一为 2；缺失或不支持的版本必须拒绝，不进入旧规则解释分支 |
| `subject_type` / `subject_id` | 复用角色／用户身份；角色范围为授权，用户范围为个人上限 |
| `resource` / `actions` | 明确业务资源和动作集合；使用已注册权限标识，缺失不得按全资源解释 |
| `scope_type` | 复用 Company、Organization、Team、SelfOwned、Collaborative 的业务含义 |
| `target_dimension` | 明确目标为内部组织、结算主体或仓库；由资源注册规则校验适用性 |
| `target_mode` | 组织／团队支持 `explicit`、`own_org`、`managed_orgs`；其他范围不携带该字段 |
| `scope_targets` | explicit 模式使用同一类型的明确目标 ID；动态模式不得混入静态目标 |
| `include_descendants` | explicit／own_org 的内部组织目标必须显式指定；managed_orgs 使用管理关系自己的设置 |
| `version`、有效状态及审计 | 用于并发控制、变更追溯和权限缓存失效 |

1. 动态组织解析仅适用于内部组织维度；不得将 `own_org` 或 `managed_orgs` 用于法人主体或仓库。
2. 范围规则不能授予 RBAC 中不存在的动作。未适配新范围模型的资源不得接受版本 2 规则并假装生效。
3. 同一主体、资源、动作可存在多条有效范围规则；同一维度的正向范围按并集解释。不存在隐式拒绝规则优先级。
4. 用户范围只作为对应资源、动作的上限，同时约束角色范围和合法历史参与读取；缺少用户上限表示不附加个人限制，不表示拥有 Company 授权。角色缺少有效范围表示不贡献角色范围授权，历史参与读取单独按第 5.2 节判断。
5. 用户 Company 上限表示不进一步收窄已有角色结果；禁止用其补齐没有范围的角色。首期不支持脱离角色的用户直接动作授权。
6. 既有多权限动作要求同角色提供完整权限集合时，继续执行该要求，不得拆成多个角色分别提供一部分。

### 5.2 计算规则

针对用户 `u`、资源 `r`、动作 `a`，统一执行：

```text
eligible_roles = 当前账号持有、启用且满足该动作完整权限要求的角色

role_scope(role) = 该角色对 r/a 的范围规则
                  + 与该角色匹配的组织、成员和管理关系解析

role_objects = UNION(
    domain_objects(role_scope(role))
    FOR role IN eligible_roles
)

participant_objects = 仅当 a 为资源允许的读取动作且 eligible_roles 非空时，
                      取 u 对该资源的有效历史参与对象；其他情况为空集

visible_objects = (role_objects UNION participant_objects)
                  INTERSECT user_limit(u, r, a)
                  INTERSECT mandatory_business_boundary(r)

result = visible_objects INTERSECT requested_filters
```

1. `domain_objects` 由业务对象规则将范围转换成对象集合或等价数据库条件；不得把全部模块简化成 `created_by IN users`。
2. 客户主责、协作和单据历史参与权按第 6 章解析。历史参与必须来自有效业务参与事实，不得由历史业绩快照推导。账号有效且至少一个有效角色提供该读取动作完整权限时，即使角色未配置数据范围，也可依有效历史参与读取对应单据；结果仍受个人范围上限和业务强制边界限制。历史参与不提供修改、审批或资金操作权限。普通客户交接保留合法历史查看权；明确撤销读取动作权限、收窄个人上限或依业务规则撤销参与资格后，历史参与不得绕过撤权。
3. 缺失范围、空成员集、停用角色、无效管理关系均不得退化为全量查询。账号停用或没有动作权限时拒绝访问；账号有效且有动作权限，但角色范围和合法参与均不产生可见对象时，列表返回空结果。没有动作权限返回 403；不可读详情按既有资源合同返回不泄露存在性的 403／404。
4. 不同维度是组合条件：仓库范围与内部组织人员条件必须分别校验后求交；不能将仓库 ID 和部门 ID 放入同一列表做并集。首期仅支持独立维度集合，不建设部门与仓库逐项配对的授权组或通用策略引擎；要求配对约束的配置必须拒绝，不得展开成任意组合后生效。资源须登记角色范围所需维度；除明确 Company 授权外，缺少必需维度时该角色不贡献对象。Company 覆盖该资源、动作适用的范围维度，仍受个人上限及业务强制边界约束。
5. 同时持有“全公司报表查看”和“本人订单修改”的用户，只能修改本人范围内的订单。权限和范围不得跨角色、跨资源或跨动作拼接。
6. 选择器只返回服务端允许的候选项；客户端提交候选项 ID 不构成授权证明。显式筛选越界时不得扩大结果，未知或类型不符的参数必须返回校验错误。

| 对象 | 权威来源与形成规则 |
| --- | --- |
| 客户 | 复用有效期内的 `customer_assignment`；主负责人与协作身份分别解释 |
| 合同 | 当前跟进负责人来自客户当前主负责人；签约／上传经办仅作历史事实，不参与当前负责人兜底 |
| 销售单 | 建立显式 `sales_owner_user_id` 与 `business_org_unit_id`；ERP 新单初始负责人取认证建单人，组织取其有效主属组织 |
| 采购单 | 复用显式采购负责人，补业务组织归属；创建与改派按既有采购责任合同执行 |
| 选品册／方案 | 册建立显式销售责任；方案关联该册；客户提交人不成为内部销售负责人 |
| 派生单据 | 保存来源单据关系；申请人、经办人分别保存；默认沿原单业务归属查询 |
| 任务 | 复用当前 `owner_user_id`；内部部门通过人员／业务关联解析，不覆盖原 `owner_organization_id` |

1. 当前客户团队查询按当前负责人所属组织解析；当前单据团队查询按单据 `business_org_unit_id` 解析。两种口径必须在页面摘要和接口元信息中明确。
2. 销售人员调岗后，历史未交接单据继续属于原业务组织；变更负责人或单据业务组织必须执行显式交接。当前负责人仍可依本人责任和权限读取，原团队管理者按业务组织管理。
3. 任意编辑人、提交人、审批人变化不得隐式改变单据负责销售。创建人和修改人字段继续保留原审计语义。
4. 首次开放正式业务前，必须启用各资源按自身规则要求的负责人和责任组织必填校验；不要求归属的公共字典和库存余额仍执行第 3 章。依赖主属组织的新建命令在人员缺少有效主属组织时必须阻断并提示维护。已建设并纳入本阶段的订单导入或商城同步入口必须使用明确责任映射；缺映射必须拒绝生成正式单据并提供可定位的异常反馈，不得把系统账号映射成销售人员。商城尚未建设，不属于当前 S2 交付或退出条件；后续建设时必须同步交付责任映射、缺映射处理及首次生效归属，不得先生成缺少必需责任事实的正式单据。
5. 销售单责任字段接入展示与查询时，必须同步列表、详情、打印、筛选和导出，不得因此重分配既有任务。验收责任来源由 `stable.created_by` 切换到显式销售负责人时，必须作为独立业务联动批次，同步修订履约合同并验证新任务形成与既有开放任务处理。未完成该批次验收不得开放销售责任改派，具体执行第 6.3 节。
6. 客户交接仅结束和建立客户归属，不自动转交全部历史订单。交接页面必须列出未结单据和开放任务，由显式命令确定是否转交。
7. 非审批任务改派继续执行原领域的级联与事务规则；审批任务禁止随客户、人员调岗或订单交接自动改派。

### 6.2 历史经营归属

1. 销售单首次生效时，必须在同一业务事务中冻结 `attribution_user_id`、`attribution_org_unit_id`、`attributed_at`、归属版本、姓名／组织名称快照及当时的组织祖先路径。人员与组织取该单首次生效时的负责销售和业务组织；缺少必需事实时不得生效。后续建设商城同步入口时，商城来源必须取正式来源映射及可证明的首次生效事实，不取同步执行人；该入口未建设期间不要求提供商城来源验收证据。
2. 已冻结归属不得随人员调岗、客户换任、单据交接或名称修改自动变化。确需纠正错误归属时，必须使用专门的版本化纠正命令，记录依据、原因、前后值及影响；普通编辑接口不得修改。
3. 部门历史分组必须使用首次生效时保存的组织祖先路径。部门移动后，历史部门汇总不得沿当前父子树重算。
4. 归属快照只冻结人员与组织口径，不冻结金额。实际盈亏仍按原合同取当前正式版本和查询时已分配的实际成本，不得宣称为历史封账快照。
5. 客户经营质量须明确区分“当前负责客户的经营情况”和“历史负责订单的贡献”；不得将两个口径混入同一排名或合计。实际经营盈亏默认使用历史订单归属。
6. 历史参与者读取复用 `document_participant` 等既有关系，并统一执行第 5.2 节。客户换任不自动撤销合法历史参与；明确撤权必须立即作用于后续请求，参与记录不允许绕过个人上限、停用账号、动作权限或资金敏感字段规则。撤销访问资格不得删除业务参与留痕或改写历史贡献。
7. 历史归属采集必须在第一张正式销售单生效前完成，报表页面与分组查询可以后续交付。禁止因报表尚未开发而暂不采集归属，禁止用日后的现任负责人或部门补写首次生效事实。开发测试中的缺失样本和异常检测不得成为正式单据缺失归属的放行依据。

### 6.3 工作台任务改派边界

1. 负责人筛选只改变查询条件，不改变任务负责人、可改派类型、执行状态或改派命令。新增部门管理可见权不得自动授予 `work_item:manage`，也不得提供审批、付款、开票等代办能力。
2. 非审批任务继续复用现有改派入口与领域命令。操作人必须具备任务管理权限、目标任务管理范围和对应对象访问权；接收人必须账号有效，并满足该任务要求的读取权、执行权限及岗位分离。任务开放状态、期望版本、转交原因、幂等键、事务内重验和审计要求必须保持。
3. `DocumentApproval` 继续禁止运行时改派、转交、转签和委托，通用 WorkItem 改派入口必须拒绝。人员资格失效时按审批合同进入或保持受阻状态，不得自动换人；长期换人通过新审批定义影响新建单据。
4. 按采购单责任键绑定的履约任务改派，必须在同一事务更新采购单当前负责人及同一 `purchase_order:{id}` 下的全部开放履约任务；接收人必须能够执行全部级联任务。已完成／关闭任务不变，仓库责任键任务不得被错误纳入采购单责任级联。
5. 组织范围接入可能改变操作人的可管理任务集合和接收候选集合。每次切换必须分别记录改派前后可管理任务、候选人员及变化原因；经核对的授权变化允许生效，禁止以“只增加筛选”为由跳过改派回归。
6. 改派候选必须使用任务专用资格查询，不得复用普通负责人筛选候选。不得仅因接收人与操作人或业务负责人不在同一部门而排除其资格，也不得因同部门就允许接收；跨部门财务、采购、仓储协作须按任务权限、对象范围及适用业务规则判定。
7. 人员调岗、部门移动、客户换任和管理范围调整不得自动改派开放任务。原处理人若因此失去读取或执行资格，必须保留任务责任与业务事实，按该任务现有规则阻断执行，在授权管理视图明确提示资格失效及处置入口；非审批任务由具备改派资格的人员受控处理，审批任务执行第 3 条。不得通过扩大权限、静默换人或自动完成任务消除阻塞。
8. 单次任务改派不得自动改变单据业务组织、客户归属、历史业绩快照或未来任务的默认责任配置；仅执行原领域明确规定的责任级联。业务组织交接必须是显式业务命令，不能随接收人所属部门隐式变化。
9. 销售负责人交接与验收责任联动必须单独实施、验收：列明已有开放验收任务是否随交接转交、原子更新的责任集合及后续新任务责任来源，保证任务与业务责任一致；不得改写开放审批任务、已完成验收记录或历史经营归属。该批次完成前，不得开放可能造成销售负责人和验收任务责任不一致的交接路径。

## 7. 金额分配与管理汇总

1. 人员与团队的成交、应收、回款、付款、发票和成本统计必须使用对应领域的权威金额与分配事实；禁止客户端按单据头金额重算。
2. 一笔回款核销张三订单 60 元、李四订单 40 元时，按销售归属统计分别记 60 元和 40 元；不得为两人各记 100 元。付款、发票、退款、冲正和成本遵守各自的关联分配与正反向事实。
3. 未核销或未分配金额归入“未分配业务归属”分区。若按当前客户负责人查看资金管理责任，必须另设清晰口径，不得算作该人员已实现业绩。
4. 多来源单据列表可因不同人员的关联份额被分别查询命中；人员汇总只计算匹配份额。结果必须区分单据总额、当前范围归属金额及单据数量口径。
5. 部分授权单据的列表、详情和导出只返回获授权且匹配筛选的份额，不得泄露其他人员／客户的分配明细。整单读取资格必须由服务端按该单据的读取动作、数据范围、个人上限及业务强制边界判断，覆盖完整单据、全部分配及未分配余额；仅命中某条分配、同属一个客户或具有财务／管理者角色名称，均不构成整单读取资格。未分配余额沿该资金单据自身的授权规则判断，不因可见某条订单分配而自动可见。各资金资源必须在接入时登记整单及余额的范围依据。
6. 多采购负责人共同服务一张销售单时，可筛选相关订单；采购人员成本汇总按实际分配事实计算。未定义收入分摊规则前，不提供按采购人员分摊整单销售收入或利润的排名。
7. 当前筛选条件下的明细、汇总、趋势、分组和导出必须复用同一授权条件和金额口径。原实际盈亏合同中覆盖率分母等明确例外继续执行，并在页面说明。
8. 分组必须提供未知归属分区，保证可加总指标与全范围结果核对；该分区仅承接资源允许的待定归属或已发现的数据异常，不得用于放行缺少必需归属的新正式单据。客户协作人数、关联单据数等非可加总指标必须标注去重口径。
9. 仅有部分读取资格时，整单金额、整单已分配合计、未分配余额、其他分配及完整凭证／附件不得返回；受限金额字段使用空值并注明权限限制，不得写零或通过差额暴露不可见金额。打印与下载执行同一限制；无法提供符合部分读取范围的内容时，必须拒绝该打印或下载请求。
10. 一笔回款分配给张三 60 元、李四 40 元时，仅获张三业务读取资格的账号只能读取其获授权的 60 元。具备整单读取资格的账号可查看整单 100 元与两条分配；其主动筛选张三时，范围归属金额仍为 60 元，整单金额须独立标注，不得纳入张三份额汇总。返回与展示必须区分授权限制和用户主动筛选。

## 8. 查询接口与前端合同

10. 任务管理范围必须按 `work_item:manage` 解析，并以任务当前具体负责人的有效内部组织成员关系形成条件；`owner_organization_id` 保留责任语义，不得用作内部部门授权事实。个人上限仍与角色正向范围相交；缺少正向范围时禁止回退公司范围。
11. 订单及变更审批的动作范围必须使用当前来源订单的 `business_org_unit_id` 和当前负责人；库存调整审批使用仓库维度。`responsible_org_id` 保留原责任语义：订单为结算主体，库存调整为仓库，不得改写为内部部门。绑定、升级、决定、恢复和管理读取必须使用公共解析器；订单详情读取须独立验证，绑定前按即将持久化的订单事实验证。

### 8.1 查询参数

各资源仅注册适用字段；未支持字段必须拒绝，不得静默忽略。以下为目标规范名，具体资源的 OpenAPI 必须在对应阶段同步：

| 参数 | 语义 |
| --- | --- |
| `owner_user_ids` | 本资源明确的当前业务负责人；使用去重后的稳定人员 ID |
| `sales_owner_user_ids` / `procurement_owner_user_ids` | 跨业务查询中的负责销售／采购负责人，不与通用 owner 参数重复表达同一条件 |
| `handler_user_ids` | 当前开放任务处理人 |
| `operator_user_ids` | 已发生动作的实际经办人；动作类型须由资源固定或显式选择 |
| `org_unit_ids` / `include_descendants` | 当前组织筛选；与资源定义的当前归属口径一致 |
| `attribution_user_ids` / `attribution_org_unit_ids` | 历史贡献人员／组织；使用冻结归属及历史组织路径 |
| `ownership_status` | `assigned`／`unknown`；仅用于资源明确允许的待定归属或异常排查，不表示可领取任务，不得放宽正式单据必填要求 |

1. 同一字段多值按 OR，不同字段按 AND。人员、部门和原有状态、客户、期间筛选共同求交。
2. 单次人员或组织条件各最多 100 个 ID；超限拒绝并提示缩小条件。服务端展开的组织成员不得受此前端参数数量限制而静默截断。
3. 不以姓名、角色名、部门显示名作为查询身份。当前／历史归属条件不得混用；不适用的组合必须返回结构化校验错误。
4. 负责人筛选属于普通查询能力，不新建“查看张三数据”这类人员级权限点；管理范围仍由授权服务决定。
5. 合同负责人筛选前后端统一使用人员 ID，不保留姓名参数的兼容解析。接口收到已废弃的姓名筛选参数必须返回校验错误，不得忽略后返回全部结果；姓名只用于展示和候选搜索。

### 8.2 选择器与页面

1. 提供资源和用途明确的人员候选查询；候选结果只包含 ID、显示名、必要组织标签和账号状态。使用该选择器不要求管理者具有系统账号管理权限。
2. 当前负责人筛选须包含仍有授权数据的离职／停用人员；新责任分派选择器只允许合格有效人员。历史归属选择器允许历史人员和历史组织，二者不得共用分派资格过滤。
3. 页面按“管理范围、组织、人员、业务条件”组织筛选。有效条件进入 URL 与 TanStack Query key，刷新、前进后退、清除条件必须一致。
4. 查询、清除和条件标签必须使用同一应用状态。禁止存在请求消费但页面无法查看、修改或清除的隐藏参数。
5. 查询响应必须提供 `scope_summary`、`ownership_basis`、`as_of` 和权限／组织版本标识；不得将内部授权证明、全量人员 ID 集合或其他不可见组织返回给客户端。
6. 无动作权限、无数据范围、筛选无结果、请求失败必须分别呈现。缺归属记录不得显示为“无人领取”。
7. 工作台管理筛选只能改变管理查询；任务动作仍由服务端 `allowed_actions` 和领域命令决定。查看他人待办不显示可代办按钮。

## 9. 后端实现与查询一致性

本章自动门禁、执行命令、规则边界及行为验证要求按 [第 9 章门禁执行合同](organization-data-scope-gate.md) 执行。自动检查通过不得替代本章查询一致性、事务、撤权及逐资源动作验收。

### 9.1 通用约束

1. 组织与范围基础归入身份域，通过 Port 向业务暴露类型化事实；业务 Service 使用公共解析能力与自身归属规则形成查询条件。不得把业务聚合或数据库句柄塞入通用组织模型。
2. 授权上下文必须按资源、动作解析；Repository 接收明确、不可混淆的授权条件与业务筛选。禁止 Repository 根据登录用户自行推断权限。
3. 列表、计数、分组和指标必须在同一查询快照中完成权限过滤和业务筛选；排序与分页在最终条件形成之后执行，稳定排序须包含 ID。
4. 详情、附件、打印、导出、报表下钻和人员候选均须独立重验当前权限；列表已授权不能作为详情请求的长期凭证。
5. 导出生成和下载须重验当前授权。异步任务若存在，必须保存条件及版本并在生成／下载时校验，不得在已撤权后返回旧的宽范围文件；同步导出继续使用本资源原有方式。
6. 跨页查询携带范围版本；版本不一致时返回可识别的范围变化错误并要求从第一页刷新，禁止悄悄拼接不同权限版本的结果。
7. 缓存键至少包含用户、资源、动作、策略版本、组织版本及适用业务归属版本。相关变更提交后，后续请求不得继续接受旧授权缓存；缓存有效期不得跨过已知成员、管理关系或授权的生效／失效时点。客户端必须清理范围相关缓存和已选无效条件。
8. 写命令仍在原领域事务内重验账号、动作权限、对象范围、当前责任、版本与岗位分离。授权事实和业务写入使用既有事务一致性规则；不承诺事务快照建立之后的墙钟级即时撤权。
9. 组织后代与人员展开必须批量执行；大范围采用服务端关联查询或可验证的查询索引，不得无限生成超大 `$in`，不得按当前页人员推导候选全集。
10. 新增查询索引由实际路径确定，至少评估当前负责人、业务组织、历史归属、状态／日期组合及稳定排序。不得为所有排列机械建立索引；上线前检查代表性数据的执行计划和超限行为。
11. 组织移动、成员变更、管理授权及责任交接必须具备并发重验、完整审计与幂等执行能力；唯一性和有效期不重叠等跨记录约束不得仅依靠前端校验。

### 9.2 公共解析与业务适配的唯一职责划分

本合同的统一引擎指身份域拥有的 DataScope 公共解析与授权组合能力。扩展现有 `DataScopeService`、`ScopeResolution` 及对应领域规则，不新增并行授权服务，不建设通用策略脚本引擎。

| 所属层 | 必须承担的职责 | 禁止承担的职责 |
| --- | --- | --- |
| `erp-identity` | 校验账号、有效角色和同角色完整动作权限；按资源动作解释规则；解析组织、成员和管理关系；确定角色条款、个人上限及固定授权组合关系；提供权限与组织版本 | 引用客户、销售等业务实体或仓库；按业务集合字段生成查询；以历史业绩推导参与资格 |
| 消费业务域的 `ports` | 定义本域所需的窄授权 Port、已解析事实和错误合同；按资源固定可用动作 | 暴露身份域实体、具体 Service、RBAC 实例或原始 DataScope 存储记录 |
| `erp-processes` 的消费方 adapter | 实现业务域 Port，调用身份域公共解析器，转换类型与错误，传递事务和版本；装配所需外域事实来源 | 自行解释原始范围规则，补 Company，改变角色、资源、动作或目标维度语义 |
| 业务域实体／值对象及 Service | 按第 6、7 章提供负责人、组织、协作、合法历史参与和业务强制边界；将解析结果映射为本域对象条件；编排范围校验与业务事务 | 复制账号与角色资格、动态组织解析、用户上限默认值等公共授权政策；直接依赖其他业务领域或组合层 |
| 命名 Process／ReadModel | 编排跨域命令或混合读取；复用身份域解析和业务域对象规则，组合各独立资源的授权结果 | 为报表、导出或写命令另建一套授权解释；让业务域反向依赖组合层 |
| 业务域 Repository | 将明确的对象条件转换为数据库查询，执行过滤、计数、分页和聚合 | 读取登录态推断权限，加载角色规则决定授权，承载创建／修改资格的纯业务判定 |

1. 业务领域的 normal、build、dev 依赖均不得引入其他业务领域或组合层。禁止通过重命名依赖、重新导出、公共 façade 或关闭检查绕过该边界。不得为共享 DataScope 将身份实体或授权算法迁入 `erp-core`、`application-core`、`persistence-core`。
2. 领域 Service 必须依赖本域 Port；具体 adapter 在组合层实现，由 HTTP、CLI 或测试组合根注入。命名 Process／ReadModel 可按仓库依赖方向调用身份域公共入口，但其本域对象规则必须复用，不得与领域 Service 各维护一份。
3. adapter 必须调用公共解析入口；只有返回类型称为“Fact”或实现了 Port，不构成合规。向业务域传递原始 `scope_type / scope_targets` 再由业务域解析，视为未完成公共解析接入。

### 9.3 Port 输入、输出与失败合同

各消费方 Port 必须满足下列语义；具体 Rust 签名、事实类型和 adapter 路径必须在对应阶段交付记录中登记。首个接入批次必须先形成符合本节的完整样例，后续接入复用其合同；不得以接口尚未存在为由增加跨业务域直接依赖。

| 合同项 | 强制要求 |
| --- | --- |
| 认证身份 | 接受服务端已认证身份；不得由客户端提供有效角色集合或已授权结论 |
| 资源与动作 | 资源由消费方固定；动作使用该资源注册的明确动作；需要同角色完整权限集合时一并传入，解析器必须包含目标动作自身 |
| 执行上下文 | 接受调用方 `Executor`；事务内的授权、业务归属读取及写入必须沿用该执行器。adapter 不得另开事务或换成 `NoTransaction` |
| 解析输出 | 返回已通过资格检查的范围事实，明确资源动作、类型化维度、角色条款与个人上限、解析时点及版本；全量、空集、缺少个人上限必须可区分 |
| 组织事实 | 通过窄事实操作取得指定组织展开、有效成员或本人组织；使用同一解析时点和执行上下文。不得将完整 `OrganizationState`、`OrgTree` 等身份域内部结构交给消费域自行重建组织解析 |
| 业务事实 | 客户归属、销售责任和有效参与等由其拥有领域提供；身份域不得查询业务集合。所需外域事实通过各自 Port 或命名组合用例取得 |
| 错误 | 未装配、未注册、维度不支持、无动作权限、版本变化必须明确失败；有效授权产生空范围时保留空集。禁止捕获错误后回退旧读取器或 Company |
| 对外输出 | 原始授权事实仅服务端使用；按第 8.2 节生成响应摘要，不暴露完整角色证明、组织关系或人员集合 |

1. 消费方事实类型只表达已解析结果，不包含可调用身份域内部实现的句柄。adapter 对公共结果的转换必须保留全部适用维度及限制；不支持的维度必须拒绝，不得静默丢弃。
2. 角色规则合并、个人上限、历史参与允许的动作及多维运算结构按第 5.2 节由公共能力统一确定。业务域只提供合法参与事实和本域条件，不得重新决定缺少角色范围或个人上限时的默认政策。
3. 数据库批量查询允许将公共授权结构编译为本域固定字段条件；该编译仅做等价映射，必须保留角色并集、参与读取与个人上限、强制边界及筛选的交集。不得先合并不同角色的不同维度再形成交叉授权。
4. 单对象纯范围判定由身份域公共规则拥有，经 Port／adapter 复用；业务域提供类型化对象事实，再执行自身责任、状态和岗位分离规则。在相同动作、事实、业务强制边界及筛选下，数据库条件编译必须与公共范围判定及业务条件判断得到相同对象集合，禁止另设独立默认值或例外分支。
5. 列表、详情、候选、汇总、导出和写命令必须共用本资源的事实映射与条件编译，各入口按自身动作重新解析。复用不表示可以将列表上下文作为写命令凭证；写命令按第 9.1 节在原事务重验。

### 9.4 客户域接入样例合同

客户接入必须满足以下调用关系；本节规定目标结构，不表示当前实现已经通过验收。

```text
组合根注入 erp-processes 的客户授权 adapter
  → CustomerService 依赖 erp-customer::ports 中的 CustomerDataScopePort
  → adapter 调用 erp-identity 的 DataScopeService
  → 身份域返回已解析授权事实，adapter 转换为消费方事实
  → 客户域按有效主责、协作、合法参与及主负责人所属组织映射对象条件
  → CustomerRepository 执行明确授权条件与业务筛选
```

1. `CustomerDataScopePort` 及客户所需事实类型归 `erp-customer`；其生产 adapter 归 `erp-processes`。客户域不得引用身份域的 `DataScopeService`、`SharedRbacService`、`AuthorizedDataScope` 或组织实体，不得在 manifest 增加 `erp-identity`。
2. 客户域保留客户归属有效期、主责与协作区分、历史参与资格及客户查询字段映射。组织展开与有效成员事实通过 Port 获取，客户域据此查询当前主责客户；不得用协作人员组织代替主负责人组织。
3. 其他领域按同样边界建立消费方 Port；销售单仍按单据业务组织解释范围，不照搬客户当前负责人组织口径。跨域读取与命令在既有命名 Process／ReadModel 中装配，不新增无业务边界的中央查询服务。

### 9.5 接入登记与实施顺序

1. 每个资源动作必须登记：拥有领域、公共解析入口、Port／adapter、适用及必需维度、历史参与允许动作、对象事实来源、条件编译入口、适用 HTTP／CLI／任务入口、接入状态及验证证据。身份域按该登记校验配置；不得以初始化清单中存在资源名代替接入完成证明，不得对所有资源硬编码同一组必需维度。
2. 范围配置、初始化和消费者准入必须引用一致的资源动作登记。未接入项不得作为已生效 v2 规则接受配置或初始化；验证器与初始化必须明确报告未接入，不得静默跳过后报告全量成功。完成批次接入检查后，才可登记其可配置能力；正式业务开放仍须满足第 10 章。
3. 每批依次完成：核对合同与当前调用链；确定 Port 及事实合同；装配公共解析；实现对象适配与全部适用入口；移除本批旧授权解释；执行功能和架构检查；登记证据。不得先复制旧范围算法完成页面，再将公共解析和边界修正记为非阻断优化。
4. 接入状态必须区分“尚未接入”“部分接入”“已接入但不符合合同”“本地检查通过”“已验收”。审查归因必须结合当前调用链和提交差异：尚未迁移的旧逻辑列为待接入项；已修改但违反 Port 或授权规则的实现列为整改项。两类均不得登记已完成，但不得混称为本批改错。
5. 本批接入完成后，其活动路径不得继续调用无资源动作和类型化维度的旧覆盖计算。未纳入当前批次的旧消费者必须登记依赖缺口并阻止其将 v2 配置作为旧语义消费；不得由某一资源接入完成推定所有消费者已迁移。

## 10. 首次初始化与上线准入

1. 首次上线统一使用本合同的数据模型、查询参数和授权规则。不交付旧业务数据回填、旧姓名参数兼容、旧范围映射或双版本授权读取机制；现有代码的 DTO、范围读取器、领域适配器、索引和种子必须同步适配新模型。
2. 上线前必须建立并核对组织树、有效成员关系、管理关系、角色动作权限及按资源／动作配置的 DataScope。部门、结算主体和仓库分别使用明确类型的身份，不得依名称或字符串相似度映射。
3. 初始化程序必须使用明确的预定义授权清单，具备幂等执行、失败定位和结果核对能力。缺少范围不得自动补 Company；重跑不得覆盖管理员调整，不得恢复已撤销、停用或软删除的授权。必要的全公司读取范围必须在清单中按资源和动作显式声明。
4. 数据库索引必须符合新模型允许的规则数量、主体身份及并发约束，不得保留阻止同主体按不同资源／动作配置范围的旧唯一约束。初始化验证必须同时检查规则写入、权限实际解析和种子重跑结果，不得以脚本退出成功代替验收。
5. 各首发资源必须登记负责人、业务组织及派生单据关联的创建来源、形成时点和允许变更的命令。本阶段已建设的 ERP 创建、订单导入、商城同步等适用入口必须全部校验；未建设入口须登记为不适用，不要求为完成 S2 新增该入口，也不得将其登记为已接入或已验收。后续新增入口必须在开放正式业务前完成本条校验。创建人、编辑人和系统执行人不得充当未经规则确认的责任人兜底。
6. 第一张正式销售单生效前，必须完成第 6.2 节的归属快照及组织路径采集，并验证其与单据生效原子提交。报表页面可以后续交付；不得先产生缺少必需归属的正式订单，再以当前人员或组织补写。
7. 首次上线必须列明实际开放的功能组、接口及关联任务。每个首发资源必须完成列表、详情、适用的汇总／候选／导出、命令权限和任务责任检查；未完成资源不得开放正式使用。分阶段开发不要求全部扩展功能同时上线，但不得通过遗漏后端入口绕过准入。
8. 上线验收必须记录初始化版本、授权清单、数据模型与索引版本、代表性账号及业务验证结果。上线后必须保留业务事实和审计记录；发现授权或责任错误时关闭受影响入口并受控修复，不得退回宽范围授权或依靠重新初始化清除正式业务数据。

## 12. 验收矩阵

### 12.1 验证层级

1. 静态检查必须核对注册权限、DTO、范围类型、参数消费、错误语义、版本与文档链接。
2. 单元测试必须覆盖组织集合运算、同角色授权、历史参与与撤权、人员归属、金额分配及部分读取、版本变化、查询归一化和初始化幂等性，不编写只复述实现的测试。
3. HTTP／浏览器验证须使用明确的账号、组织和业务数据矩阵，覆盖列表与直接详情访问、管理与执行边界、跨页及导出。仅按钮隐藏不构成权限验证。
4. 数据库一致性、查询计划、并发与真实集成验证按仓库现行门禁和各业务合同执行；受限制未执行的项目必须单列，不得以单元测试代替。
5. 首次上线验收必须核对真实组织、初始授权清单及第 10 章准入条件；生产业务验收必须核对实际权限和代表性业务汇总。本地静态、单元、浏览器或模拟数据结果均不得登记为生产权限和金额已验证。
6. 涉及接入的代码批次必须在 `backend/` 执行现有 `scripts/check-domain-boundaries.sh`，检查真实 Cargo normal／build／dev 依赖及源码边界；门禁必须包含能拒绝业务域直接依赖身份域的违规夹具。发现漏检必须补齐检查，不得增加白名单或放宽基线。仅修改本合同不要求执行代码构建或测试。
7. 架构审查必须核对生产 adapter 实际调用公共解析器、Port 不泄露身份域内部类型、事务执行器不被替换、已接入路径不再自行解释原始范围。依赖图通过不能替代调用链审查；记录必须包含检查命令、结果、代码基线和未执行项。
8. A34 的条件等价验证必须使用公共判定作为对象集合基准，覆盖代表性的本域责任事实；内存测试或查询结构断言不得登记为真实数据库执行等价性已验证。数据库验证仍按仓库允许的验证层级和第 10 章准入要求执行。
