# 人员开通与访问配置执行合同

版本：2.1
修订日期：2026-09-30

## 1. 授权边界

1. 角色只授予业务操作权限；人员数据范围决定该人员执行某个业务操作时可以处理的对象。范围不能授予操作权限。
2. 每个 `user_id + resource + action` 只保存一份有效人员范围。运行时只读取 `person_data_scopes`，不得叠加角色范围、个人附加授权或另一份个人上限。
3. 查询、详情、修改、提交、审批及其他已接线命令均须按自身动作解析范围。查看部门数据不授予修改部门数据的资格。
4. 既有命令要求同一有效角色提供完整动作集合时继续执行；审批节点仍须检查其指定角色资格。通过资格检查后，统一使用当前人员该动作的范围，不从资格角色取得另一份范围。
5. 未配置范围时保持无业务数据访问范围。不得在读取、角色保存、角色分配或服务启动时自动补本人或公司业务范围。内建超级管理员的组织配置权执行第 4 节的系统治理规则。
6. 账号、部门关系、角色操作权限和人员范围分别保存。后续配置失败不得重复创建账号或角色。界面摘要不得代替服务端鉴权。

## 2. 人员配置路径

1. 角色列表 → 编辑角色 → 选择业务 → 勾选操作 → 保存。此步骤只保存角色名称与操作权限。
   角色列表及角色有效权限查看不得请求人员范围，不得以人员范围配置权限阻断角色管理。
2. 组织与人员 → 人员账号 → 点击姓名 → 人员资料。列表仅承担人员查询和账号创建，不提供独立编辑弹窗、权限侧栏或操作列。
   人员资料固定为“基本资料”“角色与数据范围”两个页签。“基本资料”提供姓名修改和所属部门调整；“角色与数据范围”先展示已分配角色，再展示业务范围。密码修改与账号删除放在人员页“更多”菜单；系统角色账号不得删除。
   姓名、密码、角色分别提交对应字段，不得由某一表单覆盖另一分区的值。移除常驻开通进度卡；缺部门、缺角色和缺范围分别在所属分区提示。
3. 数据范围每个业务展示一行：业务名称、已有操作权限、当前范围及“设置范围／修改范围”。点击行内按钮固定当前人员与业务，不再重复选择人员或业务。业务和动作候选必须由服务端根据此人当前有效角色的实际权限计算；不得按角色名称猜测。
4. 选择业务后可以一次设置该业务全部已有动作，也可以展开“按操作区分”只设置所选动作。每个动作分别验证资格，允许所选动作由不同有效角色分别提供。
5. 普通内部组织业务使用本人负责、自己所属部门、指定部门、公司范围。部门模式必须明确是否包含下级。仓库和结算主体业务使用对应对象选择器，不得将对象 ID 当作部门 ID。
6. 审批支持的组织、仓库、结算主体是可选条件维度，不得要求每个审批对象同时具有全部维度。选择多个维度时必须明确各维度之间求交。
7. 同一业务的动作范围一致时汇总展示；不一致时显示“按操作分别设置”，展开后逐项展示当前已保存范围。没有记录显示“待设置”；迁移组合范围必须标明保留原条件及历史读取，不得伪装成普通本人或部门选择。不可见目标名称显示待确认，不显示内部 ID。
8. 新配置默认选择本人不代表已经授权，必须点击保存。已有统一简单范围应回填；动作范围不同或存在迁移组合条件时，须明确展示本次统一替换的影响。
9. 保存仅替换当前人员、当前业务、所选动作；其他动作、其他业务和其他人员不变。保存成功后后续请求使用新范围，仍须满足业务状态、责任、审批节点及岗位分离条件。
10. 未保存时取消、刷新或离开必须保护草稿。页签切换必须保留范围草稿；同一时间只允许编辑一个业务范围，保存或取消后方可切换业务。策略变化时保留用户输入及其原始版本，重新加载服务端资格；禁止静默将旧草稿改用新版本保存。成功或确认放弃后清除草稿。
11. 账号停用、角色停用、解绑或动作撤销后，已存范围不能单独提供访问权。恢复动作资格时尚未替换的人员配置可再次适用；永久收窄须显式保存目标范围，不能依赖暂时撤销角色。

## 3. 角色、部门与权限展示

1. 角色工作台按业务设置操作；不展示或写入角色数据范围。业务权限与系统权限共用同一编辑器，左侧选择模块、右侧勾选操作。不得提供简化版与完整版权限切换；复制权限、已选项、变更及特殊授权摘要须直接可达。
   角色列表侧栏仅展示角色名称、状态、关联人员数量及按模块汇总的操作权限；不得展示数据范围或查询范围区块。优先使用当前列表行的摘要，不为角色轻预览重复请求权限配置。修改入口统一为“打开角色资料”。
2. 新建角色成功后使用接口返回的 ID 进入编辑页。不得按角色名猜测 ID，也不得在保存角色时创建任何人员范围。
3. “全部操作”切换为“自选操作”时，按目录展开后移除指定动作；其他业务及目录外显式授权保留。全权和跨业务通配授权不得因单业务勾选被隐式撤销。
4. 变更摘要按操作授权前后结果计算，说明通配授权对今后新增动作的行为。搜索、模块切换和显示范围筛选不得丢失未保存的角色变更。
5. 关联人员加载失败须显示失败及重试，不得显示零人；当前可见人员数不得表述为公司总人数。
6. 部门页分别展示成员与管理人员。管理关系只表示组织管理事实，不授予业务操作或数据范围。需要处理部门业务时，进入对应人员资料设置业务范围。
7. 调岗预览必须说明原部门、新部门和“自己所属部门”范围的动态变化；指定部门配置、管理关系、单据责任和历史业绩不因调岗自动改写。
8. 人员资料中的部门管理关系与访问检查默认折叠，不得占用日常角色与范围配置主路径。权限与审计页按角色展示操作权限，按人员展示其唯一范围。不得将编译表达式内部的交集条件显示成另一个“个人限制”配置来源。跨人员汇总遇策略版本不一致必须重新读取。

## 4. 人员数据范围接口

| 方法与路径 | 输入 | 响应 | 路由权限 |
| --- | --- | --- | --- |
| `GET /admin/person-data-scopes/{user_id}` | 固定人员路径 | `items`、`businesses`、`policy_version` | `data_scope:list` |
| `PUT /admin/person-data-scopes/{user_id}` | `resource`、`actions`、`terms`、`expected_policy_version` | 空成功结果 | `data_scope:create` |

保存指定部门示例：

```json
{
  "resource": "sales_order",
  "actions": ["list", "detail"],
  "terms": [{
    "scope_type": "organization",
    "target_dimension": "internal_org",
    "target_mode": "explicit",
    "include_descendants": false,
    "scope_targets": ["已确认的部门ID"]
  }],
  "expected_policy_version": 12
}
```

1. 响应使用标准 `ApiResponse`。未知字段拒绝；客户端不得提交 `role_id`、原始迁移表达式或跳过校验的参数。
2. 读取要求同一有效角色提供 `admin:list`、`role:list`、`data_scope:list`、`org_unit:list`，并且读取人的有效组织读取范围为完整公司范围。
3. 写入要求同一有效角色提供 `admin:list`、`role:list`、`data_scope:create`、`org_unit:manage`，并且操作人的有效组织管理范围为完整公司范围。不得依赖已经删除的 `data_scope:delete` 入口权限。
4. 读取可展示停用后台人员的已存配置，但不得提供可保存的有效动作候选；写入必须重验目标账号启用、后台身份、业务已接线以及每个动作的实际资格。
5. 动作和目标必须规范化、去重；空动作或非法范围拒绝。支持维度、必需维度、动态模式和目标身份分别校验；明确部门必须存在且启用，外部对象通过拥有领域的窄接口校验。
6. `expected_policy_version` 必须来自本次完整读取。授权重验、版本校验、所选记录创建或替换、策略版本递增及 `person_data_scope.replace` 审计必须使用同一事务。
7. 失败不得部分替换。版本变化返回统一冲突；前端保留草稿，不自动覆盖。提交结果未知不得自动重放。
8. `(user_id, resource, action)` 建立唯一索引。保存覆盖同一记录的完整表达式，不通过增加平行规则表达修改。
9. `/admin/data-scopes`、`/admin/data-scopes/replace`、`/admin/personal-business-grants` 的旧写入及读取路由全部退出运行时调用；不提供旧接口回退。旧集合仅保留作显式迁移输入和回滚核对。
10. 内建超级管理员的 `org_unit:list/manage` 固定具有公司治理范围，不依赖人员范围记录，不受该记录收窄影响。必须先验证当前账号身份一致且有效、绑定的 `role-root` 为启用的内建系统角色，以及同一角色具备本次全部操作权限。普通角色或同名账号不得采用此规则；其他资源动作仍只读取人员范围。此规则不写库、不恢复被撤销的业务范围，用于组织维护、人员范围配置与访问检查的管理入口。

## 5. 访问检查

`POST /admin/access-check` 接收 `user_id`、`resource`、`action` 及可选 `object_id`。

1. 未指定对象时，只检查账号、动作资格和已解析的人员范围；不得宣称具体单据可执行。
2. 具体对象检查支持销售单 `detail` 与 `update`。检查人必须先通过该单据的详情读取授权，再计算目标人员的对应动作；不得泄露检查人不可读对象是否存在。
3. 路由要求 `data_scope:list`，服务端另按第 4 节读取资格检查公司组织边界。身份、组织和对象读取复用同一事务与公共范围解析器。
4. 响应 `steps` 每项包含 `layer`、`status`、`message`；状态为 `passed`、`blocked`、`review`。返回可取得的 `scope_version` 和 `checked_at`。
5. 无范围时引导到人员数据范围；无动作权限时引导到角色操作权限。不得继续要求用户修改角色范围或独立个人上限。
6. 销售修改检查复用首次提交工作副本可编辑规则；通过时仍须说明关联合同、客户、商品、版本及提交内容没有完成实际保存验证。
7. 配置、版本或数据库错误不能转换成无权限或检查通过。角色、组织或人员范围改变后撤下旧结果，重新读取；检查结果不能作为后续请求的授权凭证。

## 6. 初始化与迁移

1. 新建超级管理员时，在创建账号的同一事务中显式初始化公司人员范围。已存在、恢复或重新绑定角色的账号不得据此恢复缺失或收窄过的范围。
2. 开发种子在业务数据创建前按目标人员、资源、动作显式配置范围。角色模板仅用于生成经审核的初始化输入，不参与运行时范围解析。重复初始化不得覆盖既有配置或恢复撤权。
3. 旧范围必须先生成只读迁移报告，再按报告版本显式应用。报告包含 `user_id`、`policy_version`、`skipped_existing`、`configurations`、`blockers`、`applied`。
4. 迁移保留旧分支并集、维度交集、原条件和允许的历史参与读取；禁止把不同分支目标合成更宽的任意组合。新保存的普通范围不自动增加历史参与读取。
5. 依赖角色的管理部门、不同角色范围不能等价解耦、未完成旧版本绑定、非法规则或目标等情况必须报告阻断。不得猜测为本人、固定部门或公司范围。
6. 应用时在单个策略事务中按预览版本重新验证并重新生成配置；有阻断项整次拒绝，已有人范围不覆盖。写入与 `person_data_scope.migrate` 审计原子完成。
7. 在 `backend/` 执行预览；命令不得作为本地测试连接真实库运行：

```bash
cargo run -p cli -- --config-path ./config.toml migrate-person-scopes --user-id <人员ID>
```

8. 环境负责人审核候选及阻断项后，使用报告中的版本应用：

```bash
cargo run -p cli -- --config-path ./config.toml migrate-person-scopes --user-id <人员ID> --apply --expected-policy-version <预览版本>
```

9. 切换前暂停授权配置写入，逐人核对迁移结果，确认管理员可配置人员范围，再同时部署前后端。未经迁移或显式配置的动作保持关闭；不得以运行时双读旧集合维持访问。
10. 回滚须先停止范围写入，保留新旧集合及审计，核对切换后新增或收窄的配置。旧版本不读取人员新集合，直接回滚可能恢复旧宽范围；必须先确认旧配置不会违背已生效的撤权，再回滚配套前后端。不得宣称回滚代码会回滚数据库。

## 7. 验收要求

1. 张三、李四共用销售角色；分别设置本人范围。仅将张三销售单查看改为销售一部，李四、张三其他业务及销售单修改范围保持不变。
2. 张三查看列表与详情为部门、修改与提交为本人；直接访问他人详情按查看规则判断，直接调用他人单据写接口必须拒绝。
3. 角色只增加动作时，该人员新增动作显示待设置，不自动继承其他动作范围。范围保存不能增加没有授予的动作。
4. 公司范围收窄为本人后，旧部门范围不得残留；历史参与不能绕过新保存的本人范围。
5. 缺范围、停用账号、停用角色、解绑、动作撤销、无效部门及版本冲突分别验证；失败事务不得留下部分记录或成功审计。
6. 审批必须同时满足节点角色、人员动作范围、对象事实及岗位分离，不得借其他角色的旧宽范围通过。
7. 验证迁移的旧个人条件保留、多分支不交叉扩张、管理部门阻断、不同角色范围阻断及重复应用不覆盖已有记录。
8. 分别记录静态检查、库单元测试、前端构建、浏览器交互及真实事务验收；未执行项目不得登记通过。遵守仓库禁止真实库集成测试和前端单元测试修改的约束。
