# 人员开通与访问配置执行合同

版本：1.2
修订日期：2026-09-29

## 1. 适用范围与授权边界

1. 本合同约束人员账号、部门成员、管理关系、角色操作权限、数据范围和访问检查的页面交互。
2. 授权算法继续执行《组织架构、数据范围与负责人查询执行合同》。界面摘要不得代替服务端鉴权，不得通过引导隐式增加权限。
3. 角色动作和范围须由同一角色证明。个人范围仅作为上限。组织成员、管理关系、当前业务责任和历史归属分别维护。
4. 每项写入独立保存。账号创建成功后，后续部门或范围配置失败不得重建账号；角色创建成功后，继续使用返回的角色 ID。

## 2. 人员工作区

1. `/system/accounts` 的人员姓名必须进入 `/system/accounts/{accountId}`。部门成员入口必须进入同一人员资料页。
2. 人员资料页集中展示账号、所属部门、角色操作权限、管理关系、逐条范围与配置待办，并提供已有权限允许的编辑入口。
3. 新建账号后必须进入该人员资料页继续配置。账号列表读取失败时，必须告知账号已创建及继续操作路径，禁止提示再次创建。
4. 配置待办检查角色已授权且已接入范围控制的资源动作。缺范围时提示对应角色；依赖本人部门或管理部门时提示关系缺项。无权、加载失败、查询不完整不得判为已配置完成。
5. 配置待办无缺项只表示配置检查通过，不表示所有单据可访问。历史参与、命令内容与单据状态须继续按业务规则检查。
6. 角色选择必须展示从实际权限计算的业务操作摘要，不得按角色名称猜测权限。

## 3. 角色操作与范围

1. 角色编辑采用岗位权限工作台：左侧检索和选择业务，中间配置操作与查看范围，右侧展示本次调整和当前可见的关联人员。系统权限及未接入范围控制的业务从“高级授权与来源”进入。
2. 新建角色返回 ID 后进入该角色编辑页。修改角色后留在当前页，清除已保存的变更状态。底部“保存本次调整”只提交岗位名称和操作权限。
3. 新增范围只允许选择该角色已保存的操作权限。不得因选择范围自动补授动作。
4. 范围表单直接展示“自己负责、自己所属部门、自己管理部门、指定部门、公司范围”单选项。仓库与结算主体业务使用对应身份选择器；多维度业务明确选择本次替换采用的维度。当前多个维度或多个范围不能被默认为某个单选项。
5. 公司级范围不得作为普通角色表单默认值。协作参与不得作为客户、合同或销售单的推荐授权方式。
6. 工作台“保存数据范围”执行 §8 的原子替换，不得调用新增接口伪装成修改。只有所选操作的原有范围被替换，其他动作须保留。原始规则放入默认折叠的只读详情。独立规则管理页继续沿用叠加与移除语义。
7. 选择范围不写入；点击“保存数据范围”后独立保存并立即生效。页面须区分已保存范围与待保存选择。取消岗位编辑不能撤销已经保存的范围。
8. 业务“全部操作”允许切换为“自选操作”。取消其中一项时，须展开该业务当前目录中的全部操作，再移除目标动作；其他业务授权和目录外显式授权保留。全权及跨业务通配授权不得通过单业务勾选隐式撤销。
9. 变更预览按操作的授权前后结果计算。通配展开不得显示成新增全部勾选项；授权方式变化须说明今后新增操作的行为。
10. 范围摘要只汇总当前勾选且已接入范围控制的动作。无效协作规则不进入客户、合同及销售单的主摘要，原始规则仍可展开核对。不同动作或维度的差异不得伪装成统一范围。
11. 关联人员加载失败时显示失败和重试，不得显示零人。人员和部门仅依据当前可见接口结果展示，不得把当前可见人数表述为全公司总数。
12. 搜索业务、切换业务和进入高级授权不得清除未保存的权限。范围选择未保存时，禁止切换业务、操作及高级授权，提供“撤销选择”。返回及取消必须提示未保存的修改；浏览器刷新须触发离开提示。
13. “个别操作需要不同范围”展开逐项入口；单项保存只替换该项。统一保存会覆盖所选操作的个别范围，保存区须列明适用操作。后台重取数据不得无提示覆盖正在编辑的范围选择。

## 4. 权限展示与组织变更

1. 人员及角色权限预览必须保留每条范围的业务、动作、目标维度、目标模式、下级设置、启用状态和来源。
2. 角色授权与个人限制分区展示。个人限制不得命名为直接授权。不可见目标名称显示待确认，不得渲染内部 ID。
3. 跨页范围读取必须核对版本、总数和重复记录。跨主体汇总不得拼接已知不同版本的结果。
4. 部门页分别使用“部门成员”“管理此部门的人员”。人员侧使用“设置此人管理的部门”。
5. 调岗预览必须说明原部门与新部门、本人部门范围重算、既有管理关系保留、单据责任不自动转移及历史业绩不变。
6. 设置管理关系时须提示对应角色及“本人管理的部门”范围的依赖。无对应规则不得显示业务权限已开通。

## 5. 访问检查接口

### 5.1 请求与响应

`POST /admin/access-check`，请求体：

```json
{
  "user_id": "待检查账号ID",
  "resource": "sales_order",
  "action": "detail",
  "object_id": null
}
```

1. `resource`、`action` 必须为后端已接线范围消费者；未知字段、未知动作和非法目标返回校验错误。
2. 未指定 `object_id` 时检查账号、操作权限、实际解析范围及个人上限，不判定具体业务对象。
3. 具体对象检查支持销售单 `detail` 与 `update`。用户通过自己有权读取的销售单候选选择单据；其他资源动作仅提供配置检查。
4. 响应使用现有 ApiResponse 信封。`data.steps` 中每项包含 `layer`、`status`、`message`；状态为 `passed`、`blocked`、`review`。提供可取得的 `scope_version`、`checked_at`。
5. 不返回目标人员可见的业务内容，不创建代登录会话，不执行写命令。

### 5.2 服务端强制检查

1. 路由要求 `data_scope:list`。服务端另要求同一有效角色具备 `admin:list`、`role:list`、`data_scope:list`、`org_unit:list`，并提供公司组织读取范围；个人组织上限不得进一步收窄该边界。
2. 身份和业务读取在同一只读事务内执行，复用 DataScopeService 和 SalesAccess。
3. 具体销售单必须先通过检查人的详情读取校验，再判断目标人员对应动作。检查人不可读与单据不存在使用原业务的非泄露错误。
4. 销售修改检查复用实体的首次提交工作副本可编辑规则；通过时仍明确提示关联合同、客户、商品、版本与提交内容未作完整保存验证。
5. 数据库、版本或配置异常不得转换为“无权限”或“已通过”；必须返回错误并允许重试。
6. 修改身份、角色、组织或范围配置后必须撤下旧检查结果，重新读取；检查结果不是后续请求的授权凭证。

## 6. 角色创建响应

`POST /admin/roles` 保留原请求结构和权限校验，成功后 `data` 返回新角色 ID 字符串。前端必须使用该返回值继续配置，不得通过角色名称猜测新身份。

## 7. 验收要求

1. 普通销售：创建账号、分配角色、设置部门、核对角色动作和本人范围，在人员资料页完成配置核对。
2. 销售经理：共用经理角色，分别配置对应人员的管理部门；缺管理关系时显示待办，补齐后刷新待办。
3. 访问排查：无动作权限、缺角色范围、个人上限限制、合法历史读取、不可编辑销售单状态分别得到对应层结果；不可读对象不泄露业务内容。
4. 操作与范围不得跨角色拼接。新增窄范围不得抵消已有宽范围。个人范围不得增加权限。
5. 静态检查、库单元测试、前端构建、浏览器交互及真实多账号业务验收分别记录；未执行的验收不得标记通过。

## 8. 岗位数据范围原子替换接口

`POST /admin/data-scopes/replace`，请求体：

```json
{
  "expected_policy_version": 12,
  "scope": {
    "schema_version": 2,
    "subject_type": "role",
    "subject_id": "role-sales",
    "resource": "sales_order",
    "actions": ["list", "detail", "update"],
    "scope_type": "self_owned",
    "scope_targets": [],
    "target_dimension": "internal_org",
    "target_mode": null,
    "include_descendants": null,
    "enabled": true
  }
}
```

1. `expected_policy_version` 必须来自完整范围列表的 `policy_version`。不得猜测版本、默认填零或冲突后自动重试覆盖。
2. 路由要求 `data_scope:create`；事务内要求同一有效角色同时提供 `org_unit:manage`、`data_scope:create`、`data_scope:delete` 及公司组织配置范围，个人上限不得收窄该配置边界。
3. 仅接受有效岗位、已保存的完整动作权限及启用的新范围。个人限制、协作类型、未接线动作和非法目标拒绝。部门、仓库和结算主体目标复用原有身份校验。
4. 替换以岗位、业务和所选动作定位，覆盖这些动作的全部旧维度和规则。混合规则仅剥离所选动作，其余动作及启用状态保留；剥离后为空的规则软删除。其他岗位、业务、动作及个人上限不变。
5. 策略版本校验、授权与目标重验、旧规则更新、新规则创建、策略版本递增及 `data_scope.replace` 审计必须在同一事务内完成。失败不得产生部分替换。
6. 成功响应使用 `ApiResponse<DataScopeView>`。前端刷新范围列表及已保存摘要；不得将范围保存成功表述为岗位名称或操作权限也已保存。
7. 过期版本返回统一冲突错误；前端保留待保存选择并提供“放弃选择并重新读取”。提交结果未知时不得自动重放。
8. 现有 `POST /admin/data-scopes` 与 `DELETE /admin/data-scopes/{id}` 保留其独立管理语义。本次不变更集合结构或索引，不执行已有数据迁移。
