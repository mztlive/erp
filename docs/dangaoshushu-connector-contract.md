# 蛋糕叔叔接入合同

商品选品、公司资料同步与差异确认、正式采购触发及履约回写执行[供应商 API 商品与自动履约执行合同](supplier-api-product-contract.md)。本文保留供应商专用协议、配置与数据证据要求；运行时装配与状态处理按下列约束执行；实际交付须分别列明代码和单元验证、尚未执行的真实环境验收。

## 1. 所有权与启用范围

1. `erp-supply::ports::connector` 定义供应商无关协议；具体客户端由 `erp-processes::connectors::dangaoshushu` 实现。领域 crate 不得依赖该客户端。
2. Web API 通过 `SafeConfig` 登记技术配置及共享传输客户端。连接 ID、供应商、接口类型和业务启停只读取后台连接记录；自动使用当前部署配置并生成连接专属客户端，不从配置文件或回调正文取得 ERP 身份。部署环境由独立部署与数据库隔离；供应商测试或正式接口仅由该部署的地址和凭据决定，后台连接不得记录或选择环境。
3. 商品运行入口包含自动配置、连接测试、后台商品目录同步、目录筛选和选品确认。尚未选品的来源只保存目录观察；明确选品后，来源更新按合同应用到已关联供给与公司展示资料，采购价变化追加商业条款修订，不覆盖公司销售价。旧人工匹配不等于选品授权。
4. 客户端提供地址准备、配送方案、单组订单创建、独立支付结果通知和订单查询。正式采购执行通过持久化的 `SupplierApiOrderProcess` 装配这些能力，后台逐步执行并恢复；旧 `SupplierGateway` 继续失败关闭，不作为新链路入口。不得通过旧 `dispatch` 隐藏地址、创建与支付三个动作。
5. `catalog_page` 返回一页标准商品来源资料；`SupplierConnectionExecutionProcess` 负责保存目录、检查点与执行结果。订单回调由 `SupplierOrderTrackingProcess` 保存刷新意图、查询原单并应用正式履约；商品状态、属性、城市、价格回调保留刷新线索，商品更新由持续目录采集保证。只有目录记录与分页检查点已提交才计入已同步数量；不得将来源目录同步解释为正式供给可用或订单状态已生效。
6. 取消、单笔退款和结算流水能力保持未提供。订单累计退款金额不形成正式退款事实，不进行自动成本冲减。

### 接口类型与多供应商分派

1. 新建连接必须提交 `connector_type`。当前支持值为 `dangaoshushu`，展示名称为“蛋糕叔叔 API”。接口类型创建后不可修改；供应商主档、连接代码和接口类型分别表示业务归属、连接编号和调用协议，禁止互相推断。
2. `GET /admin/supplier-api-connector-types` 使用 `supplier_api_connection:create` 权限，返回当前程序已实现的类型及中文名称。该目录不包含地址或凭据，不代表部署已经登记技术配置。创建请求缺失、空值或未知类型返回参数错误；列表和详情返回 `connector_type` 与 `connector_type_label`。
3. 组合根把每种已配置协议登记到 `SupplierConnectorRegistry`。健康检查、目录同步、配置选项与引用解析均按连接类型精确分派；类型未登记时返回 `SUPPLIER_CONNECTOR_UNAVAILABLE`，禁止借用其它适配器。相同类型重复登记必须阻止启动。
4. 蛋糕叔叔专用只读目录、票据签发、业务客户端及回调入口仍须检查类型为 `dangaoshushu`。类型缺失或不符时拒绝技术调用；签名票据、技术引用和配送上下文同时绑定接口类型，禁止跨类型使用。
5. 旧连接缺少类型时保留 `null`，展示“未指定接口类型”，技术操作返回 `CONNECTOR_TYPE_REQUIRED`，仍允许在原业务约束下停用。不得把全部旧连接自动认定为蛋糕叔叔。旧数据补齐按本合同升级步骤执行。
6. 接入新协议须增加类型定义、协议适配器及组合根注册，并验证专用入口类型校验、配置隔离、失败分类与业务能力范围。仅新增供应商主档或填写另一接口地址，不构成新增协议接入。当前每种协议使用该部署登记的配置，本合同不声明同协议多渠道账号选择能力。

## 2. 配置合同

完整模板位于 [backend/config.toml.example](../backend/config.toml.example)。本地使用已忽略的 `backend/config.toml`；部署使用既有受控 Nacos 配置。禁止另建环境变量凭据通道或把真实密钥写入示例、业务表、文档、普通日志。

商品图片直接使用供应商返回的 HTTP/HTTPS 链接下载，无需登记图片域名，不限制目标主机、IP 或端口，允许 HTTP 客户端默认的有限重定向。单图最多 10 MiB、每商品最多 100 张，实际解码验证 PNG/JPEG/WebP 及尺寸，按内容摘要识别同 URL 换图；相同内容复用已归档资产。HTTP 和对象上传在事务外执行，素材元数据与业务变更由同一事务保存。

```toml
[dangaoshushu]
enabled = false
base_url = "https://dev.dangaoss.cn"
channel_no = ""
private_key = ""
user_id = ""
timestamp_unit = "milliseconds"
timeout_seconds = 15
callback_max_skew_seconds = 300
requests_per_second = 5
catalog_sync_interval_seconds = 3600
catalog_full_sync_interval_seconds = 86400
availability_validity_seconds = 7200

[dangaoshushu.spec_units]
# "<supplier-spec-id>" = "个"

[dangaoshushu.city_regions]
# "<supplier-city-id>" = "<company-region-code>"
```

| 字段 | 执行约束 |
| --- | --- |
| `enabled` | 缺省为 `false`；`true` 只登记可供后台选择的技术配置，不创建、不绑定、不启用业务连接 |
| `base_url` | HTTPS origin，不得含用户名、密码、接口路径、查询参数或片段；由部署配置确定测试或正式接口，不按后台连接标签限制主机 |
| `channel_no` | 启用时必填，使用供应商分配的渠道号；仅允许 1 至 128 个 ASCII 字母、数字、`-`、`_`、`.` |
| `private_key` | 启用时必填，不得含空白或控制字符，不得使用占位值；调试输出整体脱敏 |
| `user_id` | 只读查询可留空；准备地址前必须填写供应商允许使用的固定用户标识，仅允许 1 至 128 个 ASCII 字母、数字、`-`、`_`、`.` |
| `timestamp_unit` | `seconds` 或 `milliseconds`，缺省为毫秒；出站按该项生成，入站只接受 10 位秒或 13 位毫秒时间戳 |
| `timeout_seconds` | 1 至 30，缺省 15；连接超时为 `min(timeout_seconds, 5)` 秒 |
| `callback_max_skew_seconds` | 1 至 900，缺省 300；推送时间与接收时间差超限即拒绝 |
| `catalog_sync_interval_seconds` | 60 至 604800，缺省 3600；已有明确目录采集任务后按原发起人的当前有效身份和权限持续调度，首次采集前不自动启动 |
| `catalog_full_sync_interval_seconds` | 不小于同步周期，缺省 86400；在部分增量之外定期完整校对，仍不得据列表缺项推断下架 |
| `availability_validity_seconds` | ERP 可供缓存政策，缺省 7200 秒；仅实际成功观察产生有效期，来源时间仍可未知。不是供应商供货保证，下单须实时核验；过期投影转为待核验 |
| `requests_per_second` | 1 至 100，缺省 5；单进程实例限额，等待配额最多 `timeout_seconds` 秒，超时返回限流；不自动重试外部请求 |
| `spec_units` | `spec_id` 到公司 SKU 计量单位的明确映射；单位为 1 至 32 个字符，不得有首尾空白；缺项时保留来源单位未知，选品时明确确认公司单位映射；不阻止保存供应商结算价；目录显示“供应商未提供”，选品时选择公司单位，不要求为每个规格登记部署配置 |
| `city_regions` | 供应商 `city_id` 到公司标准地区编码的映射；键和值遵循 ID 字符限制，值必须唯一以保证可逆；缺少查询涉及的地区时拒绝映射 |

1. `enabled=true` 时加载校验 HTTPS 地址、凭据、限额和映射；配置错误须阻止运行时装配。关闭模板允许保留空字段。
2. 部署升级时须删除旧配置中的 `dangaoshushu.media_allowed_hosts` 和 `dangaoshushu.clearing_price_is_tax_inclusive_cny` 字段。技术参数按进程启动快照使用，修改文件或 Nacos 后须重启 Web API。后台新建连接、测试或停用连接不要求回填文件或重启；每次调用重新读取连接记录。
3. 调整端点、渠道、密钥及参与技术指纹的设置并重启后，下一次连接测试或商品同步自动更新内部绑定；旧健康证据失效，业务调用须重新通过连接测试。连接身份、供应商、接口类型和技术配置共同参与引用与配送上下文校验，禁止复制其他连接的引用。
4. `spec_units` 只确定计量口径，不建立公司 SKU 的外部身份绑定。正式供给必须单独绑定公司 SKU、连接、`product_id` 与实际订货 `spec_id`。

商品来源字段须按以下规则映射：

1. `specs[].clearing_price` 直接写入接口采购报价，金额使用定点十进制；允许零价，缺失时显示“暂无接口报价”，负值或非法金额按单项映射异常处理。`price`、`market_price` 不得替代采购报价；集采价和进项税率不得从结算价推断。
2. `images[]` 按原顺序写入商品轮播图；`content_images[]` 按原顺序写入商品详情图。SKU 默认主图取首张轮播图，轮播图缺失时留空，不使用详情图替代。`spec_img` 的非空格式未确认前不映射为 SKU 主图。`product.description` 作为文字简介保留，不将其解析为 HTML。
3. 图片未完成下载归档时显示“图片尚未同步”，选品须等待实际图片可用。商品预览与选品预览分别展示轮播图和详情图。
4. 同步检查点增加 `mapping_version`，旧记录缺省为零。旧映射检查点不得作为增量依据，升级后的新任务须完成一次当前版本全量同步，补齐既有目录分类、报价与图片。已在运行的旧任务即使完成，其检查点仍不得替代新版本全量同步。
5. `mapping_version` 为兼容新增字段，无需批量改库；回滚时保留该字段，旧版本忽略。恢复旧程序前须恢复其所需部署配置；不得回写或清空已同步的商品资料。

## 3. 连接建立与操作入口

1. 管理员在 `config.toml` 的 `[dangaoshushu]` 中填写端点、渠道、密钥和必要技术参数，设置 `enabled=true` 后重启 Web API。不得填写 ERP 连接 ID、供应商 ID 或环境字段。
2. 业务人员建立连接时只选择供应商、连接代码和接口类型。页面不得提供接口地址、凭据或引用选择器；不得让用户复制票据、填写密钥或重复绑定已有配置。
3. 新连接与旧连接均按自身 `connector_type` 自动使用当前服务端配置。配置不可用时必须显示缺失原因，禁止提供可成功提交的同步入口；类型不明时不得猜测为蛋糕叔叔。
4. 详情仅保留“商品同步”“连接设置”“运行记录”三个主分区，默认打开商品同步。原分区参数不再产生独立页面，无法识别的分区统一进入默认页。
5. 配置就绪后可直接执行“开始同步商品”；无需先启用业务连接、配置业务能力或匹配公司 SKU。停用仅阻止新的业务调用，不阻止明确授权的目录采集和连接测试。
6. “连接设置”显示服务端配置状态并提供“测试连接”。测试使用 `AUTHENTICATION` 读取品牌接口，不创建订单。测试受理不等于成功，界面须显示实际后台结果。
7. 业务连接启用继续要求能力、采购确认、当前技术健康证据及不同人员职责规则；商品同步不得替代这些证据。部署配置变化后旧健康证据失效，业务客户端须拒绝未通过当前配置检查的调用。
8. 地址与凭据的内部引用只用于配置变化检测、连接隔离与运行保护，不进入页面、响应和日志。既有技术票据接口不属于业务操作流程。

### 3.1 商品目录同步与匹配

| 操作 | 管理端接口 | 权限 |
| --- | --- | --- |
| 开始、继续或重新同步 | `POST /admin/supplier-api-connections/{id}/commands`，`action=START_CATALOG_SYNC` | `supplier_api_connection:detail` 及 `supplier_api_connection:catalog_sync` |
| 查询商品与最近二十次运行记录 | `GET /admin/supplier-api-connections/{id}/catalog?page=1&page_size=20` | `supplier_api_connection:detail` |
| 人工匹配公司规格 | `POST /admin/supplier-api-connections/{id}/catalog/{item}/match`，提交 `sku_id`、`expected_version` | `supplier_api_connection:catalog_sync` 及目标商品读取范围 |

1. 同步按有界上游商品分页读取，并逐规格保存。每页来源观察、检查点与任务心跳必须在同一事务提交；上游 HTTP 必须在事务外执行。单次扫描最多 10000 页，每页最多 5 个来源商品，按商品去重补查详情；每项素材准备前续写任务心跳。
2. 目录身份由连接、供应商商品编号和规格编号确定。重复同步更新最近观察并保留人工匹配和正式选品关联，不新增同身份目录行。只有明确选品关联允许同步正式供给价格；公司销售价不受覆盖。
3. 不报告单位时保留未知；供应商结算价直接形成采购报价，与单位未知分别保存。选品须明确选择并确认公司单位，不猜测“件”、零价或免税。来源更新时间缺失时必须保留缺失；读取时间只能作为观察时间。
4. 目录仅声明部分覆盖。列表缺项或结束不表示供应商已下架，禁止删除先前已同步记录。来源观察不是可采购、可售或库存保证。
5. 同一连接只能有一个正常运行的目录任务。连接记录的版本写入串行化任务登记与每页提交，配置变化必须阻断旧页面写入。
6. 一页失败不回滚先前已提交页面。最近失败任务尚未扫描完且技术配置一致时，“继续同步商品”从已保存游标继续，累计读取数包含恢复前已处理部分；配置变化或最近扫描已完成时从第一页重新读取。
7. 超过五分钟未更新心跳的未结束目录任务视为中断。下一次同步先结束旧任务：等待中任务取消并重新开始，执行中任务标记失败并按第 6 条恢复；旧执行者不得再写入或覆盖新任务结果。正常运行任务不得抢占。
8. 完成状态、页数、读取规格数和失败原因必须来自后端任务及检查点。刷新、切换分区或重新打开页面后须仍能读取；禁止固定显示“从未同步”或把命令受理显示为完成。
9. 人工匹配必须核对目录连接、预期版本、目标 SKU 与商品启用状态及商品数据范围。同一 SKU 重复确认保持幂等；其他版本冲突必须刷新，不按名称自动匹配。
10. 旧匹配只登记公司 SKU 身份，不得被展示为已可采购。采购选品预览与确认按新合同一次建立公司商品、供给与资料来源；报价、税率、配送及上架缺失条件须明确补齐，不得猜测。
11. 新版列表提供 `brand_id`、`brand_name`、`cat_id`/`cat_id2`/`cat_id3`，不提供完整商品详情。持久化同步须按商品定向查询新版详情，再读取 `product.description`、`images[].m_path`、`content_images[].m_path` 和规格及上级可供状态；同页同商品只补查一次。分类按 `cat_id3`、`cat_id2`、`cat_id` 顺序选取非空且非零的最末级编号，通过 `/dsapi/product/get_cats_info` 返回的 `id`、`name` 匹配名称并随目录保存；同页有效规格共用一次分类查询，无分类编号时不查询。单规格定向查询执行相同的名称匹配。分类接口失败不得推进本页检查点；字典未包含的编号保留未知名称，禁止把商品标签 `label_name` 当作分类名称。列表、轻预览和筛选选项使用已同步的分类名称，筛选仍提交来源分类编号；既有缺少名称的记录须通过完整商品同步补齐。来源图片 ID/URL 不构成内容不可变保证。
12. 首次完整读取后使用固定 `start_time`/`end_time` 窗口的部分增量；窗口按来源日粒度向外扩展并保留重叠。恢复沿用原窗口和游标；按部署完整校对周期重新完整读取。后台适配器复用既有连接命令、任务和检查点，不绕过任务授权，不与正常运行任务重叠。
13. 持久化同步遇到单个商品或规格的字段映射错误时，必须记录页码、页内商品和规格序号、错误码及脱敏原因，跳过该项并继续；同页其他有效规格仍须保存。商品规格列表缺失或为空按一个商品异常计数；详情找不到对应规格时不得用列表资料替代入库。分页按原始商品数推进，全页均为单项异常时仍须读取后续页。整页结构错误、鉴权、网络、限流及数据库保存失败必须停止任务，不得转换为单项跳过。
14. 检查点新增 `skipped_count` 与 `skipped_samples`，分别累计异常总数、保留最近 100 条脱敏原因；两者与有效来源及游标同事务保存，恢复任务继承原值。旧记录缺失字段按零和空列表读取，无需批量回填；回滚程序可保留新增字段，禁止删除既有目录记录。扫描完成不等于全部商品成功，界面须同时显示跳过数；存在跳过项的扫描不得建立新的增量起点，下一轮须完整读取以补齐修正后的来源。
15. 供应商品库的供应商筛选限定连接范围，关键词、分类、品牌、报价和选品状态只查询当前连接。切换连接须清除前一连接的筛选、分页、勾选和操作反馈；同步进度、异常及最近任务只在当前供应商的“同步记录”内展示。任务状态变化及手动刷新须更新连接可执行动作，失败或中断后不得继续使用旧的运行中阻塞提示。
16. 商品名称 `title` 与规格名称 `name` 在列表和详情映射时去除首尾空白，保留内部空白；缺失、空白名称或无法解析的类型须返回 `DGSS_MAPPING`。名称错误须指出字段，扫描规格映射错误须附页码及页内商品、规格序号，不包含原始响应。商品编号、规格编号、金额及状态字段继续执行原有严格校验，不得套用名称规范化规则。

## 4. 授权只读接口

入口为 `GET /admin/supplier-api-connections/{connection_id}/dangaoshushu/catalog`，需要 `supplier_api_connection:protocol_read` 权限。响应采用既有 `ApiResponse`，`data` 为供应商响应中的原始数据，尚未转成正式商品或供给。

| `kind` | 请求参数 | 上游接口 |
| --- | --- | --- |
| `brands` | 无必填业务参数 | `GET /dsapi/brand/brand_city_lists` |
| `catalog` | `page` 缺省 1，`size` 缺省 20、范围 1 至 50；可选 `brand_id`、`city_id` | `GET /dsapi/product/get_product_hot_lists`，固定 `sort_price_type=1` |
| `product` | 必填 `product_id`；可选 `city_id` | `GET /dsapi/product/get_product_details` |
| `cities` | 必填 `product_id`；可选 `city_id` | `GET /dsapi/product/get_product_cities_info` |
| `shops` | 必填 `brand_id`、`city_id` | `GET /dsapi/brand/get_shop_lists` |
| `delivery_map` | 必填 `product_id`、`city_id` | `GET /dsapi/city/get_rules` |

示例请求：

```http
GET /admin/supplier-api-connections/{connection_id}/dangaoshushu/catalog?kind=brands
GET /admin/supplier-api-connections/{connection_id}/dangaoshushu/catalog?kind=catalog&page=1&size=20
GET /admin/supplier-api-connections/{connection_id}/dangaoshushu/catalog?kind=product&product_id={product_id}&city_id={supplier_city_id}
```

1. 仅允许固定 `kind` 与查询字段，不接受任意 URL 或写动作。外部 ID 按字符串传递，保留复合品牌号及前导零。
2. 目录使用新版接口；不得用旧版列表、详情或品牌/城市标识补齐新版结果。响应中含小数或指数的 JSON 数值按完整词法字符串返回，防止精度丢失；整数身份只接受非负整数字面量，字符串复合 ID 保持原值。金额解析仅作用于供应商响应入口，不改变现有工作区的 JSON/BSON 数字序列化。
3. `stock=-9999999` 映射为未报告数量；其他负数拒绝映射。不得把该哨兵当作零库存或无限库存。
4. 来源未报告变更时间时保留缺失；接收、观察或签名时间不得填充 `source_updated_at`。来源版本保留 `Unversioned`，不可按接收顺序宣称上游新旧关系。
5. 目录扫描仅声明部分增量覆盖。列表缺项、扫描结束和单次不可见不代表删除。目录持久化按第 3.1 节执行；正式供给更新、上级对象变化展开和自动时效保障不由本次目录采集代替。

## 5. 下单与支付分步合同

支付结果通知是供应商履约接口确认。ERP 订单满足既有执行资格、外部创建成功且金额核验通过后，系统自动通知支付成功；不新增客户回款或真实采购付款条件，不创建财务事实。通知编号使用稳定的履约动作业务号，不表示银行流水。执行[产品合同第 6.1 节](supplier-api-product-contract.md#61-供应商支付结果通知)。

正式采购首次具备执行资格时建立持久化 API 执行意图，后台调用本节能力；不另建绕过采购审批的直接下单入口。每个采购明细及交付地址冻结独立意图、供给、金额与收件快照。缺少已核实的 BD-09 坐标、配送方案或入仓联系电话时，通过供应商订单的执行资料补齐入口处理；默认读取不得暴露完整收件资料。

| 独立步骤 | 上游调用 | 执行与恢复要求 |
| --- | --- | --- |
| 地址准备 | `POST /dsapi/addr/oprate_addr`，表单 | 先保存 `ActionKey` 和请求快照；要求 `user_id`、城市、区县及明确的 BD-09 百度经纬度；结果未知转人工，当前无法按动作号恢复地址，不得重建第二份地址 |
| 配送选项 | `POST /dsapi/order/get_distribution_rules`，multipart | 只读；按商品优先、品牌兜底的配送规则拆分，组内明细一致；提货额外读取门店 |
| 单组创建 | `POST /dsapi/order/submit_order`，multipart `order_data` | 每组独立 `out_order_no`；发送前核验地址、配送选项、明细、当前结算价和批准金额；每次调用至多发送一次创建请求 |
| 支付结果通知 | `POST /dsapi/order/order_pay_result`，JSON | 使用原外部单号、我方单号、交易号和金额；与创建分开保存意图与结果，创建方法不得自动调用支付 |
| 查单 | `GET /dsapi/order/order_details` | 支持我方 `out_order_no` 或外部 `order_no`；必须核对响应渠道及原查询单号 |

1. 商品行必须非空、最多 50 行，行号和规格号唯一，数量为正整数，批准单价非负。可选规格属性只接受至多一个非空且不含逗号的“口味”。
2. 收件地区必须有明确地区映射；坐标必须声明 `BD-09`，禁止将 WGS-84 或 GCJ-02 静默作为百度坐标发送。
3. 地址上下文及配送选项由服务端 HMAC 保护，绑定完整配置技术指纹、连接、收件资料、明细、方式和费用。配送选项本地有效期为 60 秒，创建前读价完成后再次核验有效期，HTTP 客户端取得配额后再次阻断过期请求并将请求超时限制到剩余有效窗口；过期后重新获取选项，不自行修改引用。
4. `clearing_price` 按人民币含税采购单价直接使用，同步、选品及下单共用该口径，不设置额外确认开关。尚未确认供给与公司 SKU 的单位映射时不得下单。来源报告单位时须匹配公司单位；未报告时使用选品已确认映射，不要求再次逐 SKU 填写 `spec_units`。预查结算价必须与批准单价一致；预查不能保证供应商创建时价格不变。
5. 创建返回外部单号、实付金额与下一步。返回金额超过批准值时仍须保存已创建外部订单，阻断后续支付并登记异常；不得丢弃回执后重新创建。
6. 未核实供应商幂等保护窗口，`ReplayProtection` 保持 `Unverified`。创建结果未知先按原我方单号查询；`NotVisible` 只表示当前不可见，不能作为重提证明。
7. 支付确认结果未知先查原订单的支付状态。支付确认成功只证明供应商侧履约确认，不证明 ERP 实际资金支付或供应商已接单。履约、取消、退款、支付分别保存，不由订单取消状态推断退款完成。
8. 供应商缺少单笔稳定退款身份及结算流水身份时，保留原始证据并人工核对；不得用累计退款金额生成多笔财务流水。

## 6. 推送接收合同

在供应商侧登记 HTTPS 公网回调地址，按消息类型使用以下路径。路径中的连接 ID 用于读取后台连接；该连接必须处于启用状态，并已绑定当前蛋糕叔叔端点和凭证引用。

| 路径 | 推送类型 | 保存的刷新目标 |
| --- | --- | --- |
| `POST /callbacks/dangaoshushu/{connection_id}/order` | 订单状态 | 原我方订单号 |
| `POST /callbacks/dangaoshushu/{connection_id}/status` | 品牌或商品可售状态 | 品牌或商品 |
| `POST /callbacks/dangaoshushu/{connection_id}/product` | 商品属性 | 商品 |
| `POST /callbacks/dangaoshushu/{connection_id}/cities` | 品牌或商品可售城市 | 品牌或商品 |
| `POST /callbacks/dangaoshushu/{connection_id}/price` | 价格变化 | `product_id` 与 `spec_id` |

1. 推送使用 JSON 原始正文，最大 256 KiB。路由限制同一接入键每分钟 300 次、全局每分钟 600 次、并发 8；过载不得发送成功应答。
2. 验签核对绑定 `channel_no`、时间戳、签名及接收时间窗口。供应商公式为对 `channel_no` 字面量、渠道号值、`timestamp` 字面量、时间戳值与私钥依次拼接，计算 SHA-1 的小写十六进制，再计算该文本的 MD5 小写十六进制。
3. 该签名不覆盖业务正文，认证范围始终标为 `EnvelopeOnly`。正文中的价格、数量、状态、变更时间不得直接应用为正式事实，只保存对象刷新线索。
4. 当前来源没有可靠事件号，`source_event_id=None`。本地接收 ID 使用 HMAC 绑定配置技术指纹、请求路径和原始正文字节；完全相同报文重放命中唯一索引后，须核实已有接收记录的连接才可应答。该身份只用于字节级接收去重，不能冒充来源事件号，不按对象或状态合并不同报文。
5. 接收层使用应用敏感数据加密器保存原始正文密文，连同刷新提示写入单文档；只有保存成功后才返回 HTTP 200 与 `{"code":200,"message":"success"}`。验签、绑定、加密或数据库保存失败均不返回该成功应答。
6. 供应商成功应答仅表示证据与待处理意图已接收。订单回调记录在原单补查及 ERP 履约应用成功后才能标记已应用；未匹配、查询失败和应用冲突保留待处理状态、错误及下次处理时间。采购变更已明确退役的执行不再被迟到回调唤醒，证据保留并标记 `ignored_retired`；混合应用和退役对象标记 `applied_with_retired`。商品类回调不得直接写入正式业务事实。
7. 验签时间窗口不提供上游单次使用保证。相同报文的重复成功应答只证明原接收证据已落库；路径、配置指纹或正文字节不同均使用不同接收身份。不得依赖接收顺序推断来源版本，正文未认证的限制仍适用。

## 7. 持久化、索引与兼容

1. 新增集合 `supplier_callback_receipts`，由 `erp-integration` 拥有。保存通用 `BaseModel`、连接 ID、来源事件号、认证范围、接收时间、消息类型、原始正文密文、刷新提示与处理状态；接收操作本身不修改供给、订单或财务集合，后台业务应用按独立事务处理。
2. 发布时先确认数据库账号具有既有启动索引登记所需权限。Web API 启动的 `erp-integration` 索引登记自动创建下列索引，执行幂等增量迁移；索引创建失败须停止发布，不跳过校验。

| 索引 | 键与选项 | 用途 |
| --- | --- | --- |
| `uk_supplier_callback_receipts_id` | `{id: 1}`，唯一 | 保护本地接收身份 |
| `ix_supplier_callback_receipts_order_queue` | `{status: 1, route_kind: 1, next_attempt_at: 1, received_at: 1, id: 1}` | 订单回调有界消费与延迟重试 |
| `ix_supplier_callback_receipts_pending` | `{connection_id: 1, status: 1, received_at: 1, id: 1}` | 按连接、接收时间及 ID 稳定读取最多 50 条待处理记录 |

3. 本次增量集合不回填既有业务文档，不给旧订单制造来源事件号，不修改既有来源时间口径。`source_updated_at` 允许缺失，旧标量时间按已知来源时间读取；ERP 观察时间与有效期独立保存，不回填伪造来源时间。
4. 接收证据不设自动 TTL，订单回调具备消费器；当前没有自动归档、容量告警或清理任务。登记供应商推送前，运营须在部署工单确定容量阈值、告警责任人和暂停入口处置；持续接收期间监控该集合的文档数量、存储/索引容量、按连接的 `received` 数量及最早待处理时间。待处理查询沿用连接与状态索引，分页有界，不用读取全部正文统计积压。
5. 容量或积压达到工单阈值时，先暂停供应商推送并按 §8 关闭运行入口，保留最后接收时间及待处理清单。未匹配或未应用证据不会自动消失；禁止人工将 `received` 改为完成、添加 TTL、删除记录或清空集合来消除告警。
6. 归档必须保存密文、接收身份、连接、时间、认证范围和刷新提示，并保留受控解密能力；先验证备份可恢复及对象数量一致，登记归档范围与位置。未经正式补查、业务处置或人工归档处置确认的未处理证据不得从在线集合删除；单纯导出副本不构成删除授权。
7. 加密证据保留既有应用敏感数据密钥政策。回滚保留能够解密历史证据的应用配置及受控备份，不把正文密文迁入普通日志。

### 7.1 目录集合升级与回滚

1. 新增 `supplier_catalog_items` 与 `supplier_catalog_runs`，由供应领域持有；组合根沿已有供应商 API 索引入口登记，启动时创建索引。
2. 目录记录 `id` 及 `(connection_id, product_id, spec_id)` 唯一；列表索引为 `(connection_id, name, id)`。检查点 `id` 等于任务 ID 并保持唯一。
3. 既有连接不执行批量改写；首次测试或同步时在命令事务内自动更新内部配置引用。旧连接缺少接口类型仍须按本合同指定的迁移补齐。
4. 前后端须配套发布。回滚使用上一制品，保留新目录、检查点、任务及审计数据，不删除集合或回退业务商品。新索引与旧版本数据不冲突。
5. 仅同步的来源目录与旧人工匹配均不构成正式采购供给；回滚不得将其转换成手工供给或改写公司商品。

### 7.2 选品、资料差异与订单执行升级

1. 选品预览、永久结果回执、商品来源同步关系、API 执行意图及跟踪观察由各自领域拥有，沿既有索引入口登记；发布不重写旧手工商品及历史订单。
2. `supplier_order_tracking` 与 `supplier_order_observations` 分别保存调度状态和不可变来源观察；业务应用冲突保留原观察。旧订单不因升级自动加入新的跟踪或发单队列。
3. 回调新增处理时间、错误和下次尝试时间提供缺省兼容。回滚停止 worker，保留新集合、索引和收件密文解密能力，不删除或补写业务发货事实。
4. API 仅提供一件代发报价时，正式供给集采报价及起订量为空；禁止补零或复制一件代发报价伪造集采能力。回滚旧制品前须停止新增 API 写入并完成此项兼容核对。

## 8. 停用与回滚

1. 停用前在供应商侧暂停或撤销推送地址，保留双方登记信息及最后接收时间；存在已创建或结果未知的外部订单时先登记人工跟踪清单。
2. 通过后台或既有连接治理 `DISABLE` 命令停用连接，后续业务客户端获取和新推送接收立即拒绝，不要求修改文件或重启。停用保留授权诊断查询和健康检查。要撤销该部署上的全部技术配置选项及诊断入口时，再将 `[dangaoshushu].enabled=false` 并重启。
3. 关闭技术配置并重启后，蛋糕叔叔运行时不再装配，授权协议查询返回未配置，回调返回非成功；已有 `supplier_callback_receipts`、连接引用、治理回执和后台任务均保留。
4. 程序回滚使用上一可用制品和对应配置，保留新增集合、索引与执行证据。新增 API 供给允许集采条款为空，旧制品不具备该业务语义，须先核对旧版读取与业务能力；禁止将删除集合或清空待处理记录作为常规回滚步骤。
5. 恢复接入时核对后台供应商及当前部署的技术配置，通过“测试连接”自动更新配置引用并完成只读健康核验，启用业务连接后再恢复供应商推送。保存的订单 `received` 记录按原单补查并应用成功后完成，其他记录继续等待明确处置，不直接标为完成。
6. 配置关闭及程序回滚不会撤销供应商已创建的地址、订单或支付通知；未知外部结果继续按原动作和单号调查，不自动补发写请求。

### 配置与连接结构升级及回滚

1. 从仍在 `[dangaoshushu]` 保存 `connection_id`、`supplier_id` 或 `environment` 的版本升级时，须移除这三个配置字段；保留端点、渠道、密钥及其他技术参数。新版本拒绝这些旧配置字段，ERP 连接身份只由后台记录持有。
2. 前后端须配套发布。连接创建、更新、列表查询、列表结果及详情均不再声明 `environment`；旧客户端携带的未知字段按既有反序列化规则忽略，不参与筛选或业务决策。新页面不得发送环境参数，也不得显示环境选择、列、徽标或环境专属提示。旧 URL 中的环境参数不参与查询。
3. 发布前停止该部署的 API、后台任务和供应商推送；备份受控技术配置并完成数据库备份。执行 `MIGRATION_MODE=check mongosh '<目标业务库 URI>' --file scripts/migrate-remove-supplier-connection-environment.js` 核对待处理数量，再以 `MIGRATION_MODE=apply` 执行同一脚本。脚本将旧环境值保存到专用迁移备份集合，移除业务集合字段，建立状态与健康索引并删除旧环境索引；允许断点重跑。不得删除迁移备份集合。
4. 新程序可读取仍带旧环境字段的连接，但不会返回或写入该字段。连接代码继续全局唯一，不合并历史连接，不更改供应商、连接 ID、能力、业务启停、订单、回调证据和审计记录。
5. 引用指纹已移除环境维度，旧蛋糕叔叔技术引用、选择票据及地址/配送上下文不得继续使用。发布后执行连接测试以自动更新配置，并进行业务启用核验，再恢复业务请求和推送；连接无需重新创建。配置文件无需增加环境字段。
6. 回滚前停止写入，执行 `MIGRATION_MODE=rollback` 的同一脚本，恢复备份环境值和旧索引；回滚不自动给升级后新建的连接猜测环境。存在无迁移备份的连接时，脚本须在恢复前停止，由发布负责人明确这些连接在旧版本中的环境并补齐迁移备份后重试。完成后回退配套前后端，重新绑定旧版本技术引用并核验健康。业务确认、订单和回调证据不得删除或伪造。

### 旧连接补齐接口类型

1. 发布前备份数据库及受控配置，明确每条旧连接对应的协议，不按名称、编号或地址推断。目标连接须先停用；存在活动业务阻塞时先完成相应业务处置。停止 API、后台任务与供应商推送后再迁移。
2. 在仓库根执行 `MIGRATION_MODE=check mongosh '<业务库 URI>' --file scripts/migrate-supplier-connector-types.js`，核对未指定类型的数量。
3. 通过 `CONNECTION_TYPES='{"<连接ID>":"dangaoshushu"}'` 明确指定连接与协议，再以 `MIGRATION_MODE=apply` 执行同一脚本。脚本先校验全部目标，再逐条备份字段存在性并执行版本条件更新；禁止更改已有类型。没有列入清单的连接保持未指定。脚本允许重复执行，不修改供应商、连接代码、订单或历史审计。
4. 迁移推进连接版本与技术配置版本，撤销地址/凭据的已绑定标记及当前健康证据有效性。发布后执行连接测试以自动更新配置，再进行业务启用核验，再恢复业务与推送。原始技术引用保留为后端历史值，不对外展示；缺少新绑定时不得调用。
5. 回滚使用相同 `CONNECTION_TYPES` 清单，以 `MIGRATION_MODE=rollback` 执行脚本。目标仍须停用且存在迁移备份；恢复原字段缺失或空值状态，推进版本并撤销绑定和当前健康有效性，不恢复已过期的健康结论。回退配套应用后按该版本重新绑定和核验，不删除业务证据。

## 9. 验收执行要求

1. 开发质量验证按后端规则执行受影响 crate 编译、库单元测试、Clippy、workspace 编译、领域边界及权限漂移检查。禁止新增或执行真实 MongoDB、S3 或供应商依赖的集成测试。
2. 单元测试验证签名公式、时间边界、映射失败、令牌绑定、单次写调用及创建与支付分离；替身轨迹只证明本地生产编排，不证明远端幂等或数据库保存效果。
3. 实际环境验收须区分只读认证/目录核验、回调持久化、正式供给应用与正式履约。只读核验不得创建地址、订单或支付通知。
4. 自动业务启用必须取得明确证据：ERP 对象身份绑定、单位与地区映射、价格口径、分步持久化及结果恢复、回调补查与领域应用、来源时间兼容。接口声明或本地通过不能替代这些证据。

### 商品来源身份核对与时间兼容

1. 已选品来源的规格描述或单位变化时，目录保存 `requires_identity_review`，关联供给先停止新增自动使用，持续同步不得自行解除。
2. `GET /admin/supplier-api-connections/{id}/catalog/{item}/identity-review` 展示来源原文、公司规格说明、基础单位及当前版本。读取须同时证明连接、公司商品及供给的访问资格，不返回采购成本。
3. `POST` 同路径须持有商品与供给维护权限，提交目录版本、公司 SKU 修订、供给版本、人工看过的来源原文、公司基础单位、同一实际销售项确认、核对依据及稳定操作号。来源单位不同于公司单位的代码、名称或符号时拒绝；尺寸、包装或单位含义实质变化不得通过本入口更换 SKU 或执行数量换算。
4. 确认在同一事务保存目录核对状态、仍有效的来源供给事实、审计及 `supplier_catalog_identity_reviews` 永久回执。回执以 `uk_supplier_catalog_identity_reviews_id` 唯一保护；同号异载荷拒绝，原成功回执不因后续来源变化而被重写。
5. 正式可供投影的 `source_updated_at` 允许为空；`received_at`、`verified_at` 与 ERP 策略 `valid_until` 分别保存。既有数字来源时间兼容读取为已知时间，禁止把接收时间填入供应商未提供的来源时间。缺少新字段的手工供给保留原行为。
6. 回滚保留新增目录、核对回执与素材证据。已经写入未知来源时间后，回滚制品须支持可空来源时间；不得通过伪造时间兼容旧版强制时间字段。
