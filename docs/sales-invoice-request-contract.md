# 销项开票申请执行合同

## 1. 生效范围

1. 销售单最终审批通过时，只建立应收及可申请开票额度，不生成开票执行任务。
2. 销项开票授权由独立单据 `SalesInvoiceRequest` 承担，必须采用统一审批引擎的已发布定义。未发布定义时，提交整体失败，不保留半张申请、不占用额度。
3. 一张申请固定关联一张已生效销售单的一笔应收。允许同一应收分次申请、同一批准申请分次开票；禁止跨应收执行和超额开票。
4. `Invoice` 保持无需审批。历史发票、开票金额、核销事实和红票事实不因本次切换改写。

## 2. 操作入口和责任

| 位置 | 操作 | 责任 |
| --- | --- | --- |
| 销售单详情 → 票款 | 查看可申请金额、审批中金额、已批准待开票金额；发起申请及查看记录 | 销售或获授权经办人 |
| 客户往来 → 开票申请 | 按客户、销售单、状态及申请单号/抬头/事由查询；新建、查看、撤回和重新提交 | 申请经办人 |
| 工作台 → 审批任务 | 按冻结开票资料审批 | 流程定义中绑定的审批人 |
| 工作台 → 销项开票执行 | 查看批准资料，登记真实发票 | 财务责任规则指定的当前个人负责人 |

申请必须填写含税金额、开票抬头、税号、开票内容和事由。申请金额必须大于零，最多两位小数。客户端不得指定流程定义或审批人。

## 3. 状态和额度

1. 申请依次进入 `draft → in_approval → approved → completed`。创建与首次提交在同一事务完成；撤回后保留为草稿。
2. 申请人只能撤回本人尚未最终通过的申请，必须填写原因和当前版本。撤回释放占用额度；修改后重新提交递增审批主题版本并产生新实例。审批驳回按统一流程回到入口节点，不自行修改业务资料或释放占用。
3. 最终批准只授予开票额度，不增加应收的已开票金额。实际发票登记、额度消耗、核销、任务状态、销售开票进度、审计和命令收据必须同事务成功或失败。
4. 可申请金额 = 应收未开票余额 − 审批中申请金额 − 已批准申请的未执行金额。已完成申请不再次占用；已登记金额已计入应收未开票余额，不重复扣减。
5. 所有申请提交、撤回、批准和开票操作均在同一应收子账上串行化竞争写入。销售减额后不足以覆盖现有申请占用时，销售变更必须回滚并提示处理占用申请。
6. 每次发票分配含税合计不得超过本申请剩余批准金额。财务只能操作当前任务绑定的应收，不得使用其他销售单余额填补授权。
7. 红冲恢复应收的可申请余额，不恢复旧申请已消耗的授权，也不自动生成新开票任务；需要再次开票时必须重新申请。
8. 已批准申请不得通过普通撤回释放授权。销售单关闭不豁免开票授权，也不关闭未执行的批准任务。

## 4. 审批与任务约束

1. 申请创建时绑定 `sales_invoice_request` 已发布流程；提交时冻结金额、申请人、客户、资料和独立 `approval_subject_version`。
2. 审批通过必须校验当前额度，并按 `SALES_INVOICE` 财务责任规则指定负责人；责任规则缺失或负责人权限不足时，批准事务不得部分生效。
3. 每张批准申请对应一个开票任务。任务业务对象继续使用应收，责任键附加申请身份；申请保存任务引用，发票保存所消耗的申请引用。
4. 只有找到与任务一一关联的批准申请，才允许登记销项发票。历史自动任务不能作为授权使用。
5. 任务转交沿用原任务身份和申请关系。剩余额度为零时完成该申请的任务，不按整张销售单余额决定任务终态。
6. 提交与撤回必须传入幂等键。结果未知时保留相同载荷和幂等键核对，不得换键重复申请。

## 5. 接口与权限

| 接口 | 权限 | 行为 |
| --- | --- | --- |
| `GET /admin/sales-invoice-requests` | `sales_invoice_request:list` | 同条件分页和总数，支持销售单、客户、应收、任务、状态及文字筛选 |
| `GET /admin/sales-invoice-requests/{id}` | `sales_invoice_request:detail` | 申请资料及真实审批进度 |
| `GET /admin/sales-invoice-requests/amounts/{accountId}` | `sales_invoice_request:list` | 服务端额度汇总 |
| `POST /admin/sales-invoice-requests/submit` | `sales_invoice_request:submit` | 原子创建并提交，或修改本人撤回草稿再提交 |
| `POST /admin/sales-invoice-requests/{id}/cancel` | `sales_invoice_request:cancel` | 校验申请人、业务版本与审批运行版本后撤回 |

销售、销售主管和财务预置角色纳入申请权限。流程管理员必须发布该类型定义；审批人须具备统一审批和该类型审批权限。财务执行人须具备既有开票执行权限，并具备申请列表和详情读取权限。自定义角色由权限管理员按职责配置。

## 6. 切换步骤

1. 停止旧版本业务写入并完成目标数据库备份，保留审批、任务和审计集合。
2. 在 `backend` 目录使用 `INVOICE_MIGRATION_DB=<业务库名> mongosh <连接参数> --file scripts/migrations/20260909-sales-invoice-requests.js` 预览目标库、历史开放任务数及索引状态，保存输出。
3. 核对预览后，增加环境变量 `INVOICE_MIGRATION_APPLY=yes` 执行同一脚本。脚本先建立申请责任键唯一索引，再逐任务以事务和版本条件关闭无申请授权的旧任务、追加审计，最后移除旧的应收唯一任务索引。禁止直接删除历史任务。
4. 部署新版本，由应用初始化创建申请集合索引并补齐预置角色权限。自定义财务角色补齐申请读取权限。
5. 在审批流程管理中发布 `sales_invoice_request` 定义；核对审批人和 `SALES_INVOICE` 财务责任规则。发布脚本中的示例定义仅用于已配置账号的环境，不得未经账号核对直接套用。
6. 开放新版本写入。历史未开票需求必须由经办人重新申请；不得批量伪造已批准申请。
7. 中断后重新执行预览并按剩余任务续跑。已关闭任务及对应审计不重复写入。

## 7. 回退与验收

1. 出现发布故障时先停写并保留新增申请、发票关联和审计事实。存在新申请或批准任务后，不得直接恢复旧自动派工版本；应修复后重新部署。没有新业务事实时，可在核对无重复开放任务后恢复旧索引及旧版本。
2. 合并前必须通过格式、编译、类型、单元回归、权限目录、BPM 边界、领域边界和前端依赖边界检查。
3. 页面验收覆盖销售入口、集中列表、必填资料、未知结果核对、撤回重提、批准资料及不同屏幕宽度。使用模拟接口取得的页面证据必须标明其范围。
4. 业务启用由目标环境负责人核对流程定义、角色和财务责任规则；本地代码检查和模拟页面验证不替代目标环境配置验收。
