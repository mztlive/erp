# 实际经营盈亏执行合同

## 1. 适用范围

1. 页面入口固定为 `/analytics/profit-loss`。
2. 本功能执行 `docs/erp-phase-1.md` 第 7.5 节的非卡券、不含税经营核算。卡券成交、消费成本及卡券利润不得进入本表。
3. 页面、查询接口和导出必须使用正式销售版本与正式成本分配事实。禁止使用草稿金额、预计采购价、未分配采购金额或客户端计算替代实际成本。
4. 本表提供订单经营分析，不替代现金收支表、法定利润表或已结账期间报表。

## 2. 期间与事实时点

1. 支持口径为 `sales_order_effective_date`。用户必须显式选择该口径；系统不得默认为收入确认日或成本发生日。
2. 起止日期按 `Asia/Shanghai` 自然日计算，包含开始日和结束日。单次查询最多 367 个自然日。
3. 订单归属取销售单首次生效日期；收入取查询时点的当前正式版本，按已舍入的销售明细不含税金额汇总，并校验与版本表头一致。
4. 成本取同一数据库快照中已分配到所选销售单、且发生时间不晚于查询时点的累计成本。不得只取期间内费用而遗漏所选订单的跨期成本。
5. 后补实际费用、冲减和正式销售变更必须反映到原订单分析结果。历史日期查询不得宣称为历史结账快照。
6. 缺少正式版本、版本归属错误或表头与明细收入不一致时，整次查询必须失败，不得返回零收入。

## 3. 金额与覆盖规则

1. 实际经营盈亏 = 不含税销售收入 − 不含税实际采购成本 − 不含税实际履约费用 + 不含税成本冲减。
2. `actual` 阶段的 `product` 费用计入实际采购成本；其他费用类别计入实际履约费用。`reduction` 使用已登记的正数金额加回一次。
3. `expected`、`confirmed` 只在阶段成本对照中展示，不进入实际经营盈亏。只有已明确分配到所选订单的阶段事实可展示。
4. 同一成本分配到多单时，各订单只使用本单分配金额，不重复使用整笔费用金额。
5. 完整覆盖须同时满足：销售单履约完成、当前每条销售明细存在已分配的实际商品或线下服务供货成本、关联成本事实存在、无已移除销售行供货成本缺口、冲减不超过实际成本。只有一条销售明细时，明确分配到整单的供货成本可覆盖该行；多行销售单不得按整单分配猜测行覆盖。
6. 完整覆盖表达正式成本记录的覆盖程度，不代表财务封账或承诺不会发生后补费用。财务必须完整登记实际采购成本与直接履约费用。
7. 未完整覆盖订单必须展示缺口；不得用缺少的成本值为零计算利润。缺少实际供货成本、履约未完成、成本事实缺失、移除行成本和超额冲减必须分别提示。
8. 订单行和分组行只有全部覆盖完整时输出盈亏。全局利润与利润率只汇总当前筛选中成本完整的订单；全局收入、已登记成本展示当前筛选订单全量，并在页面注明适用范围。
9. 覆盖率 = 完整覆盖订单不含税收入 ÷ 全部匹配订单不含税收入。覆盖状态筛选不得移除该比例分母中的未覆盖收入；客户、期间、关键词、场景和费用类别筛选必须作用于分子与分母。
10. 零收入订单允许产生亏损，但利润率必须显示不适用。所有金额累计与排序使用十进制定点数。

## 4. 筛选、分组和导出

1. 支持销售单、客户、福利场景、首次生效归属销售、首次生效归属组织分组。多场景订单按场景组合分组，收入不得重复计入多个场景。人员与组织按冻结的稳定 ID 分组；名称仅作展示，同名人员不得合并，缺快照单列“未知归属”。
2. 关键词只对销售单号和正式版本客户名称做字面量包含匹配。客户 ID 与销售单 ID 必须精确匹配。
3. 费用类别和福利场景用于选择订单。命中后必须保留整单收入与全部已登记成本，不得只扣所选费用而虚增利润。
4. 履约方式筛选及履约方式、费用类别分组不提供。客户端必须清理旧 URL 中对应条件，服务端必须拒绝不支持的参数。
5. 分页必须在筛选、全量汇总、分组和稳定排序完成之后执行。每页支持 20、50、100 行；空利润在两个排序方向均排最后。
6. 导出必须重新读取当前授权范围内的全部匹配分组，忽略页面分页限制，采用导出生成时的数据。文件不得使用客户端传入的金额、权限、行数或数据水印。
7. `attribution_user_ids`、`attribution_org_unit_ids` 接受最多 100 个稳定 ID。同字段按并集、不同字段按交集解释；组织条件匹配首次生效快照的祖先路径，不使用当前组织树。人员和组织条件必须同步作用于明细、金额、覆盖率分母、趋势、分组与导出。
8. 历史归属候选必须来自本次授权范围和期间内的完整有界订单集合，先于人员筛选、分组与分页产生。候选不得作为责任分派资格；人员离职、改名和组织移动不得删除原有历史贡献。
9. 读取事务必须使用 DataScope v2，按同角色完整的 `sales_order:list` 与 `cost_entry:list` 权限证明销售单当前访问范围；个人上限继续求交。历史归属快照不产生访问权，`customer_scope:detail` 不替代数据范围授权。
10. 跨页请求携带 `scope_version`；版本不一致必须拒绝并从第一页刷新。查询及同步导出返回前必须重验当前账号、动作和范围版本。响应提供范围摘要、归属口径、查询时点与权限及组织版本，不返回内部授权集合。
11. CSV 必须包含期间、口径、范围、生成时点、公式版本及覆盖缺口；文本字段必须防止公式注入。下载同步完成，不创建虚构的后台任务。
12. 查询最多处理 10000 张销售单、100000 条成本分配；超限必须提示缩小范围，不得截断后返回汇总。
13. 历史分组下钻使用 `attribution_group`，值为分组行 ID（`attribution_user:<ID>` 或 `attribution_org:<ID>`）；空身份后缀表示未知归属。下钻精确匹配直接归属，并保留其他已生效条件，不得以祖先路径筛选扩大原分组。条件必须可在 URL 恢复、独立清除，并同步传入导出。
14. `emptyReason` 必须区分确定的空授权 `no_scope`、期间没有授权订单 `no_data` 与已有授权订单但筛选无结果 `filtered_empty`；无授权范围不得提示清除筛选能够扩大权限。

## 5. 权限与接口

| 方法与路径 | 执行要求 |
| --- | --- |
| `GET /admin/actual-profit-loss/period-basis` | JWT 与 `cost_entry:list`；返回已实现的可选口径 |
| `GET /admin/actual-profit-loss` | JWT；同一有效角色提供 `cost_entry:list`、`sales_order:list`；事务内解析 DataScope v2 |
| `POST /admin/actual-profit-loss/exports` | 与查询相同权限；请求体使用同一筛选合同，返回 `csvContent`、`fileName`、`rowCount`、`generatedAt` |

1. 授权使用销售单当前负责销售、单据业务组织和有效客户协作关系。账号与同角色完整动作有效时，`document_participant` 记录独立补充合法历史读取；角色范围与参与读取求并集后，必须继续与个人上限求交。历史归属快照不产生访问权。显式客户筛选只能缩小授权范围。
2. 客户授权集合不得由客户端提供；`scope_id` 不构成权限证明，响应范围必须由服务端确定。
3. 成本详情可能包含跨客户分配，报表仅向具备销售单 Company 读取范围、个人上限未收窄且具备 `cost_entry:detail` 的用户展示整笔成本详情入口；其他用户仍可读取授权订单汇总。成本资源独立的详情授权与部分金额读取必须按组织范围合同 S3 批次完成接入，不得用入口可见性替代详情权限校验。
4. 页面、趋势、覆盖率、汇总和导出必须共用同一套授权范围与筛选规则。
5. 查询、成本下钻或导出返回 401／403／409 时，页面必须撤下旧报表、关闭成本明细及导出结果，并清除本功能非活动缓存。重新取得有效范围前不得以旧数据掩盖撤权错误。导出必须携带当前报表范围版本；成本缓存必须绑定范围版本。

## 6. 验证要求

1. 单元测试必须覆盖不含税收入、实际与预计阶段分离、冲减方向、缺成本、未来费用、卡券成本排除、版本归属与金额一致性、覆盖率分母、分页总额、分组不重复和全量导出。
2. 查询参数测试必须覆盖非法日期、非法期间口径、不支持筛选、空授权集合与显式客户交集。
3. 前端必须通过类型检查及本功能测试，并验证桌面和窄屏显示、显式口径选择、缺口展示与下载行为。
4. 按仓库测试约定执行单元与静态门禁，不通过真实 MongoDB 或外部服务执行集成测试。该验证不得登记为真实业务验收或生产数据准确性验收。
