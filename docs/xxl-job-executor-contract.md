# XXL-JOB 执行器接入合同

## 1. 协议与部署

执行器按 XXL-JOB 2.4.1 REST 协议实现，运行于独立 `erp-worker`，使用内部 ClusterIP Service。API 业务路由不提供执行器入口。仅支持固定 BEAN handler、单副本、丢弃后续调度（DISCARD_LATER）、无强制超时（executorTimeout=0）、非分片执行。其他运行模式、覆盖执行、任意脚本和参数必须拒绝。

部署继续使用 Recreate 和单副本。不得在旧 Worker 尚存活时强制删除并启动替代实例；首期不提供跨节点失联隔离保证。

## 2. 首批任务

| Handler | 业务范围 | 成功含义 |
| --- | --- | --- |
| supplier_tracking_scan | 最多一批到期订单查询与来源观察应用，沿用原有认领和业务错误记录 | 本轮扫描已完成；单单业务失败仍以 ERP 记录为准 |
| supplier_catalog_schedule | 扫描一页连接，按原同步授权和时间规则创建持久化目录任务 | 本页应创建的任务已可靠保存；不表示目录采集完成 |

目录采集、恢复、导入导出、批量采纳、媒体归档、outbox、自动发单等继续由 Worker 消费。订单回调的接收记录转换和完成确认继续由本地循环处理；实际来源查询使用同一订单跟踪执行流程。

## 3. 配置与切换

配置通过 SafeConfig/Nacos 的 `[xxl_job]` 读取。该节以及 admin_url、executor_url、app_name、access_token 全部必填。请求按固定 JobHandler 分发，不在 ERP 配置中绑定任务 ID。禁止 enabled 开关、缺省配置和单任务切换分支。

配置只在进程启动时生效。配置变化必须重启 Worker，禁止自动降级为本地调度；调度中心故障不得造成双重驱动。API 与 Worker 读取同一调度配置；`web-api` 固定提供业务 HTTP，`erp-worker` 固定提供执行器和常驻消费，不提供 embedded 模式或 ERP_BACKGROUND_MODE 开关。

发布顺序：在调度中心建立执行器，填写连接配置并发布 Worker，确认旧 Worker 已退出、新执行器注册成功。任务可随后在控制台创建，通过 JobHandler 选择能力；新增或重建任务不要求修改 ERP 配置或重启 Worker。首次运行先手动触发核对结果，再启用定时任务。回退必须先停止调度并排空或核实未完成回执；仅允许回退到同样要求 XXL-JOB 的版本，不恢复本地周期调度。

app_name 在同一业务库内必须稳定且唯一，测试、生产使用不同名称。不得直接改名遗弃待回报回执。access_token 与调度中心一致，仅存于受控配置，不写入 Git、日志或任务参数。

## 4. 接收、执行和回报

- `/run` 成功只表示调度请求已持久化，不表示业务完成。
- 同一 app_name + logId 唯一；重复请求必须核对 jobId、handler、logDateTime 等执行身份，一致则复用原回执，不一致拒绝。
- 同一 app 下，每个 jobId 同时最多一个待执行或执行中请求，按 DISCARD_LATER 丢弃后续触发。不同 jobId 即使使用同一 Handler 也独立接收，执行器不得基于 Handler 做额外互斥；重复创建调度任务由控制台配置管理负责。原有业务幂等和认领规则保持不变。
- 任务从 accepted 原子认领为 running 后才能执行业务；结束后先持久化 completed 和回报内容，再调用调度中心 callback。
- 回报失败只重试回报，禁止重放业务。回报每轮有界，失败退避 30 秒，未回报记录不自动删除；已确认回报记录保留 30 天。
- 新请求的 logDateTime 必须在当前时刻过去 24 小时到未来 5 分钟内；重复回执可继续查询和回报，保留期外旧调度不得重新执行。
- 重启后 accepted 请求可继续认领；上个进程遗留 running 请求转为中断失败并回报，不自动重跑其业务。实际业务结果沿原业务记录查询、核实或恢复。
- 不支持强制取消执行中的业务。`/kill` 明确拒绝；操作人必须等待当前有界轮次结束或通过 ERP 对应业务入口处理，不得把调度超时当作外部操作失败。

## 5. 生命周期与可观测性

注册周期为 30 秒。退出先停止接收和认领，再等待在途任务保存结果；注册注销及回报使用有界 HTTP 请求。未成功回报的记录由下一实例继续发送。

`/beat`、`/idleBeat`、`/run`、`/kill`、`/log` 必须校验 XXL-JOB-ACCESS-TOKEN。请求体有界、handler 必须为内置能力且 jobId 必须为正整数，日志接口仅返回脱敏执行摘要。管理端业务进度以 ERP 持久化状态为准。

## 6. 验证与交付

必须完成配置边界、协议路由、身份去重、繁忙拒绝、重启中断处理、回报重试不重跑业务、停止后不认领、目录调度与消费分离的单元验证，并完成 Rust 和离线 Helm 检查。

真实调度中心注册、Mongo 唯一约束并发、网络超时、Pod 重启和生产任务验收必须单独登记。仓库规则禁止本轮执行真实 Mongo 或外部服务集成验收，不得以单元替身结果代替。

`/idleBeat` 根据请求 jobId 查询活动回执；未知任务号视为空闲，是否执行仍由 `/run` 的 Handler 校验和该 Job ID 的活动槽位约束决定。jobId、logId 是调度协议事实，用于状态查询、身份去重和回报，不是部署配置。

新增 `scheduled_runs` 为技术回执集合，索引由应用启动入口登记；上线按配套迁移脚本预建索引。回退保留集合，不删除待回报证据。
