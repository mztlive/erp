# 销售减量后客户直退供应商执行合同

## 1. 适用范围

本合同适用于销售变更已生效、采购依据待更新、实物已由本采购供应商直发给客户，且客户实际直退原供应商的场景。原采购、发货、付款和发票记录必须保留。

公司仓收货、退仓验收、公司仓退供应商仍须履行库存手续，不得使用本入口代替。服务履约和电子交付不适用。来源无法关联到本采购的发货不得登记。

## 2. 经办顺序

1. 采购与销售落实客户退回数量、供应商接收地址及接收结果。货物尚未退回时，依据更新待办保持开放。
2. 采购在工作台或采购详情点击“登记供应商已收货”，填写实际数量、供应商收货回单或核实说明。允许分批、多商品登记；未退回的行填零。供应商尚未接收时不得登记。
3. 系统同事务追加销售退货处理单、采购退货单、全部实际退回明细及审计。采购退货状态为“已退货”，关联销售退货状态为“待财务处理”。不启动退货审批，不生成公司库存出入库，不重复调整销售应收。
4. 采购确认实物退回后，选择现金退款、供应商留抵或两者组合，填写供应商确认依据并提交。退款与留抵金额合计必须等于当前净已付款超过调整目标的部分。仅有票额差额时提交零款项方案并交接红票处理。系统保存方案和派发财务任务必须在同一事务完成；未提交方案不得派单。
5. 财务按方案办理实际退款或留抵审批，另行登记需要的进项红票。退款必须以实际到账为依据；留抵须经审批通过后形成余额，不生成现金退款。两类财务任务可并行，审批中不视为已结算。
6. 采购按最新销售目标提交采购改单。单地址可点击“按可调数量填入”同步数量与收件分配；多地址须人工核对。改单金额不得低于净已付款或净已收票。
7. 采购改单生效时追加唯一采购应付差额；同事务完成本采购已核实的直退处理单，并按原采购依据同步机制结束待办。任一步失败，整个生效事务回滚。已登记实际直退但尚未改单时，不允许以“维持原采购”跳过结算。

### 2.1 工作台职责与当前动作

- 采购依据更新工作面只展示当前退回数量、当前处理动作或当前阻碍，不平铺后续退款、红票与改单的操作说明。退回结果登记入口固定在工作台底栏。
- 供应商退款由财务经办中的出纳提交，采购提供退款依据；审批节点按已发布定义执行。预置演示链为出纳提交、采购确认依据、财务总监审批。采购确认退款依据使用独立审批待办，不在采购依据更新工作面登记资金到账。
- 尚有实物待确认退回时，仅显示退货处理。退回数量满足要求但款票未满足改单条件时，先显示采购确认处置方式，提交后显示财务经办人与办理状态；采购工作面不提供退款或红票登记入口。款票条件满足后显示原有改单动作。
- 实物退回登记只确认收货。采购提交方案后，按差额分别创建“退货款处理”和“退货进项红票”任务；无差额不创建对应任务，同采购同类型复用开放任务。采购面只显示当前动作、经办人和处理结果；财务面展示采购确认依据及本次可办金额。
- 退货款处理沿供应商付款责任规则分派给出纳；进项红票沿来源销售客户的开票责任规则分派给开票经办人。交接时同时检查对应操作权限，责任缺失或权限不足须明确失败，不得保存半份交接结果。
- 既有已发布退款审批链继续适用现金退款和留抵确认，不因采购选择方式跳过审批节点。审批详情必须明确展示现金退款或留抵及冻结供应商确认依据。若组织需要取消采购复核节点，须独立修订并发布审批定义，不改写在途实例。
- 采购可以调整尚未办理的剩余方案，旧方案保留历史。存在审批中款项时先由财务经办人撤回；已入账结果不可改写。财务提交和最终过账必须同时匹配当前方案身份、销售版本、目标金额和实物结果。
- 财务任务在相关净款或票额差额归零后自动完成；采购依据更新任务在采购改单生效且依据核对通过后完成。

## 3. 数量与金额

- 改单最低数量 = 原累计合格入库、直发与交付数量 − 具有已核实直退凭据的累计退回数量。原履约记录不修改。
- 本次可直退数量不得大于当前销售减量导致的多余净履约量，也不得大于本采购未退回的已直发量。只认当前采购版本行；空行、重复行、负数和越界数量拒绝。
- 原付款退款只回冲现金核销，不再次产生应付减少分录或减少抵销。采购应付差额由采购改单生效负责。此规则纠正此前退款回冲与采购改单可能重复冲减的实现。
- 示例：47 件 × 50 元 = 2,350 元，销售调整为 20 件，实际退回 27 件。原已付款 1,175 元，无额外费用且原价退回时，现金退款或经审批转为供应商留抵的金额为 175 元；改单应付减少 1,350 元，最终应付及净已付款均为 1,000 元，未付余额为零。未确认实际退回或实际退款时，系统不得将其当作已完成。
- 面板显示的调整后金额按原单价和原费用估算；最终以采购改单审批生效金额为准。退款或红票未核销到本采购时，不视为满足改单款票守卫。

## 4. 命令与授权

`POST /admin/purchase-orders/{id}/direct-returns`

```json
{
  "expected_version": 1,
  "idempotency_key": "12345678-1234-1234-1234-123456789abc",
  "reason": "销售减量，客户直退供应商",
  "receipt_reference": "供应商签收日期、回单号及核实说明",
  "lines": [{ "purchase_line_id": "原采购当前版本行身份", "quantity": "27" }]
}
```

- 沿用 `purchase_return_order:create`，在事务内按原采购当前负责人、业务组织重验写范围。无来源采购写资格时拒绝；关联销售退货只用于记录已生效销售变更对应的实物退回，不授予普通销售写权限。
- 同键同采购、同经办人、同完整载荷返回原采购退货身份；同键异载荷拒绝，不增加数量或重复写审计。结果未知时客户端保留原请求，使用原键核对。
- 首次登记校验采购版本及当前销售依据，并推进采购版本与销售采购串行化 guard；并发退货或改单冲突必须重读后重试，禁止按过期可退量提交。
- 采购改单数量、款票和来源守卫在提交及生效时继续执行；前端隐藏入口不替代后端校验。

### 4.1 采购方案与财务命令

- `POST /admin/purchase-orders/{id}/return-finance/sync` 接收 `idempotency_key`、`sales_revision_id`、`target_gross`、`refund_amount`、`credit_amount`、`supplier_confirmation`，沿用采购退货创建资格并重验原采购写范围。相同方案重复提交不追加写入；同键异载荷拒绝。更改方案必须使用新键，旧方案不得覆盖已入账结果。
- 供应商退款提交扩展 `settlement_method`（`CASH_REFUND` / `SUPPLIER_CREDIT`）、`source_purchase_order_id`、`settlement_decision_key`。缺省方法保持历史现金退款语义；留抵必须关联已确认采购方案。审批中与已入账金额共同占用该方案对应方式的额度。
- 指定来源采购的处理只反向核销本采购，不得消耗同一次合并付款中其他采购的分配。现金退款扣减原付款可用资金；留抵将该部分转为供应商余额，两者均不重复减少采购应付。
- 进项红票命令可传 `payable_account_id` 及本次 `amount`，只冲减指定采购的票额；不得使合并蓝票中其他采购一起红冲。原蓝票全部有效分配耗尽时才标为全部红冲。同键异载荷拒绝。

### 4.2 留抵使用

1. 留抵余额按来源审批单唯一建立，冻结原实际付款、供应商、我方付款主体和来源采购。
2. 出纳在已批准采购付款申请的本人付款任务中查询并选择余额。`GET /admin/purchase-payment-requests/{id}/supplier-credits` 仅返回同主体、同供应商的可用余额。
3. `POST /admin/purchase-payment-requests/{id}/supplier-credits/use` 接收申请和任务版本、余额身份、目标应付及分录、正数金额和请求键。金额不得超过余额、批准未付额度或应付分录开放额度。
4. 抵扣、原付款核销分配、申请已结算进度、占用释放、任务完成和审计须同事务提交。使用记录按请求键唯一，重复同载荷返回原结果，异载荷拒绝。现金付款只登记抵扣后的实际转账金额。
5. 示例：留抵 175 元抵扣下一次批准应付 500 元后，剩余现金待付 325 元；付款申请分别列示留抵记录和银行付款回单。留抵全部消耗时余额为零，不删除来源记录。
6. 已产生留抵关系的原付款禁止直接执行普通付款冲正，以免将后续采购抵扣错误恢复到原付款申请。需纠错时保留原事实，按对应采购的退货款流程处理；本合同不提供将未使用留抵直接提取为现金的独立功能。

## 5. 存储、发布与回滚

1. 新增可选采购处置方案、方案历史、财务记录的处置方式及依据字段。历史财务记录缺省为现金退款；不得自动生成历史留抵或推定供应商确认。`purchase_return_orders.direct_return` 缺省为空。
2. 新增 `supplier_credits`、`supplier_credit_uses` 集合和索引。执行 `backend/scripts/migrations/20261017-supplier-credit-indexes.mongosh.js`，或由新版应用启动登记同名索引；迁移不修改业务事实。已有付款现金退款累计字段缺省为零，首次新退款过账及每次留抵使用须在同事务按历史已过账现金退款重新核对，不把缺省值当作可重复使用资金。
3. 同批发布后端、前端和权限生成物。新增任务依赖对应财务责任人和操作权限。启用前检查既有审批定义可办理退款、岗位分离有效、经办人可读取所关联来源。
4. 回滚前关闭新交接和抵扣入口，暂停相关采购改单及付款。保留退货、方案、退款、留抵、使用记录、分配及命令回执；不得删除事实或让旧版付款冲正处理已产生留抵的原付款。恢复支持版本并逐笔核对后再开放。
5. 旧供应商退款产生的应付减少分录不自动删除。历史异常须逐单对账并通过独立纠错处理；代码变更不代表历史账已修正。

## 6. 验证边界

库单元测试验证净履约、分批与多行限额、异载荷重放、原付款退款回冲以及示例应付余额；前端执行格式、静态检查和构建。本合同不以静态检查代替真实数据库并发、事务回滚或实际收退货验收。
