# 组织与数据范围第 9 章门禁执行合同

## 1. 适用范围与放行条件

1. 本门禁执行上位合同 [第 9 章](organization-data-scope-contract.md#9-后端实现与查询一致性)，适用于组织、范围解析、业务授权适配、查询及相关入口变更。
2. 自动入口为 `backend/scripts/check-org-data-scope.sh`；Jenkins 的 `P0 质量门禁` 必须执行该入口。该入口包含原 `check-domain-boundaries.sh --cutover`，不得删除原领域边界规则。
3. 自动检查失败必须阻断提交批次的质量放行。待接入项与整改项分别报告，二者均不得豁免或登记完成。不得添加忽略路径、债务白名单或将失败改为警告以取得通过。
4. 自动检查通过仅允许登记“第 9 章静态门禁通过”。第 4 节的适用行为验证、调用链审查和阶段准入证据全部核销后，才允许登记对应资源动作符合合同。
5. 本门禁不修改业务数据、不启动服务、不执行数据库集成测试，不自动扩大实施批次。检查暴露的既有缺口须进入对应阶段交付记录。

## 2. 执行方式与退出合同

在仓库根目录执行：

```bash
bash backend/scripts/check-org-data-scope.sh
```

在 `backend/` 执行并保存机器可读结果：

```bash
./scripts/check-org-data-scope.sh --json > /tmp/erp-org-data-scope-gate.json
```

规则开发时执行纯工具自检：

```bash
./scripts/check-org-data-scope.sh --self-test-only
```

1. 默认执行顺序为：正反例自检 → 既有领域门禁 → 活动 Cargo 成员源码检查 → 汇总阻断结果。既有领域门禁失败后仍须输出范围检查结果，最终必须失败。
2. `--self-test-only` 仅验证检查器，不调用 Cargo，不得作为工作区质量放行依据。
3. `--json` 将检查结果写入标准输出，规则自检及领域门禁日志写入标准错误；记录包含状态、源码数量、规则编号、分类、路径、行号和未证明事项。

| 退出码 | 含义 | 处理要求 |
| --- | --- | --- |
| `0` | 静态检查通过；自检模式下仅为工具自检通过 | 核对输出状态及第 4 节，禁止推定功能或业务验收通过 |
| `1` | 源码规则或既有领域门禁存在阻断 | 按逐项诊断登记、整改或纳入待接入批次 |
| `2` | 参数、工具、自检、Cargo metadata、源码读取等失败 | 修复执行条件并重跑，不得视为未发现违规 |

## 3. 自动规则与检查边界

| 规则 | 合同依据 | 阻断条件 |
| --- | --- | --- |
| `ODS-DOMAIN` | 9.1.1、9.2.1、A33 | 原领域门禁失败；沿用真实 Cargo normal/build/dev 依赖、重命名依赖、源码引用及持久化边界检查 |
| `ODS-OWNER` | 9.2.1 | 范围实体、组织内部类型或解析实现进入共享基础 crate |
| `ODS-ENGINE` | 9.2 | 身份域之外定义第二份 `DataScopeService` 或 `ScopeResolution` |
| `ODS-PORT` | 9.2、9.3、9.4 | 消费领域 Port 引用身份域内部组织、授权上下文、RBAC 或具体解析器类型 |
| `ODS-RAW` | 9.2.3、9.3、9.5.5 | 消费业务域或组合层生产源码携带、解释 `scope_type` / `scope_targets` |
| `ODS-REPOSITORY` | 9.1.2、9.2 | 业务 Repository 引用公共解析器、RBAC、授权上下文，或读取原始范围/角色授权快照 |
| `ODS-ADAPTER` | 9.2.3 | 生产 `*DataScopePort` adapter 的 `resolve` 未在同一语句调用 `DataScopeService::new(...).resolve(...)` 或 `resolve_permissions(...)` |
| `ODS-EXECUTOR` | 9.3 执行上下文 | adapter 引用 `NoTransaction`、开启事务/会话，或未接收并直接转交 `executor` |
| `ODS-FALLBACK` | 9.3 错误合同 | adapter 使用 `unwrap_or*`，或显式构造 `company: true` / `authorized_customer_ids: None` 默认成功结果 |
| `ODS-REGISTRY` | 9.5.1—2、A35 | 公共解析入口使用 `predefined_data_scopes::RESOURCE_ACTIONS` 作为接入依据 |
| `ODS-DIMENSIONS` | 9.5.1 | 公共解析入口直接将单一固定维度数组传给 `required_dimensions` |
| `ODS-SAMPLE` | 9.4 | 客户 Port、生产 adapter、公共解析器或消费方注入结构缺失；注释和测试不能替代生产结构 |

1. 源码范围由真实 Cargo workspace 成员及目标确定；另行扫描其中的源码文件。字符串、字符、嵌套注释和标准 `#[cfg(test)] mod ...` 测试块不作为生产调用证据；独立 `tests`、`test`、`*_tests` 模块不参加范围源码扫描。原领域门禁仍保留其测试依赖与源码检查。
2. 其他条件编译分支保守检查；宏展开、任意别名链、跨函数数据流及动态调用不属于该词法检查器的证明能力。不得以更名、拆分语句、宏包装或修改配置条件规避规则。
3. adapter 当前按显式构造并直接调用公共解析器的结构检查。更换为字段注入、拆分实现或其他等价结构时，必须同步扩展规则及正反例，完成生产调用链审查，不得仅关闭检查。
4. 客户样例路径是必需结构锚点。合法移动文件时，必须同步更新检查器锚点与夹具，重新验证第 9.4 节完整调用链。
5. `ODS-RAW` 中已知工作流旧路径标为“待接入项”，此分类不改变非零退出码。其余命中标为“整改项”；实施负责人须结合当前提交差异与阶段登记复核归因，不得把旧消费者统一称为本批引入的错误。
6. `ODS-REGISTRY`、`ODS-DIMENSIONS` 检查已知违规结构；移除这些结构不等于逐资源动作登记已经完整，准入行为仍必须按第 4 节验证。

## 4. 行为与人工核验门禁

以下条款不能仅用源码关键词或函数存在性放行。实施批次须在对应 S1/S2/S3/S4 交付记录中逐项登记“通过、失败、未执行、不适用”；不适用必须给出资源动作边界及理由。失败或适用但未执行的项目不得登记完成。

| 条款 | 必须验证的行为 | 阻断条件与证据要求 |
| --- | --- | --- |
| 9.1.2—3 | 授权条件与业务筛选明确分离；最终条件先于排序分页；列表、总数、分组和指标同快照 | 用相同事实核对集合、总数及汇总；覆盖空页、尾页、同排序值和 ID 次序；独立多次查询不自动构成同快照 |
| 9.1.4、9.3.5、A36 | 列表、详情、附件、打印、下钻、候选、导出及命令各自解析当前动作，复用本域映射 | 按适用入口登记调用链；绕过列表直接请求仍须正确拒绝越权；列表读取证明不得用于写命令 |
| 9.1.5—6 | 导出生成及下载重验；跨页按范围版本拒绝拼接 | 覆盖请求期间撤权、组织变化、责任变化、第二页缺版本和版本冲突；异步文件存在时必须验证旧文件下载拒绝 |
| 9.1.7 | 缓存键包含身份、资源、动作、策略/组织及适用归属版本；期限不跨已知授权时点 | 覆盖成员或管理关系到期、权限变更及客户端缓存清理；无缓存的资源须登记事实依据 |
| 9.1.8、9.3 执行上下文 | 写命令在原事务重验账号、动作、范围、责任、版本和岗位分离 | 核对执行器从入口经 Port、adapter、归属读取到写入的传递；失败不得部分提交；不要求事务快照后的墙钟级即时撤权 |
| 9.1.9—10 | 组织/人员批量展开，有界大集合；索引覆盖实际过滤与稳定排序 | 核对查询次数、超限拒绝及代表性索引评估；真实执行计划未执行时必须单列，不得以索引声明替代 |
| 9.1.11 | 组织移动、成员变更、管理授权及责任交接并发重验、审计、幂等 | 验证冲突、环、有效期重叠、重复请求与失败原子性；真实并发未执行须单列 |
| 9.2—9.3、A34 | 公共单对象判定与本域数据库条件编译集合等价，保留全部维度和限制 | 使用公共判定作基准；覆盖空范围、缺角色范围、个人上限、历史参与、读写动作、多角色多维组合及业务筛选；内存集合/查询结构测试不得登记真实数据库等价 |
| 9.3 错误及输出 | 未装配、未注册、不支持维度、无动作权限、版本变化明确失败；空授权保留空集；响应不泄漏内部事实 | 覆盖各错误及独立动作权限；核对 DTO/序列化边界；禁止旧读取器或 Company 回退 |
| 9.4 | 客户按有效主负责人组织解释范围，主责/协作分开；销售按单据业务组织解释 | 使用业务事实验证，不能仅以 Port/adapter 文件存在判定符合对象语义 |
| 9.5、A35 | 逐资源动作登记、配置和初始化准入一致；未接入规则拒绝；已接入批次旧解释清零 | 每项登记拥有领域、解析入口、Port/adapter、适用/必需维度、历史参与动作、对象事实来源、编译入口、HTTP/CLI/任务入口、状态和证据；仅初始化条目不得取得准入 |

1. Rust 实现批次按 `backend/AGENTS.md` 执行格式、编译、Clippy、库单元测试、BPM 门禁及本门禁；只运行 `env -u ERP_TEST_MONGO_URI cargo test --workspace --lib --locked` 范围内的库测试，不新增或执行数据库集成测试。
2. 真实数据库、HTTP、浏览器及业务验收按仓库允许的验证层级执行。受限制的未执行项保持阻断相应验收状态，不得用静态检查或单元测试替代。
3. 证据至少记录代码基线、工作区差异、资源动作、命令与退出码、断言/样本范围、结果、未执行项及责任人。静态门禁成功、功能测试成功、真实集成成功和上线验收成功必须分别登记。
