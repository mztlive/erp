# 可测试契约

本文件是本次开发和测试的共同合同。实现若必须改变 P0 入口、权限、数据口径、稳定选择器或测试数据规则，应先更新已批准 PRD 和本契约。

## 1. 稳定业务标识

| 对象 | 稳定标识/代码 | 约束 |
| --- | --- | --- |
| 采购建单任务 | `PROCUREMENT_ORDER_CREATION` | 非审批任务，开放时必须有具体 `owner_user_id`，责任来源为系统规则或管理员转交。 |
| 业务对象 | `SALES_ORDER` | 任务指向销售单；责任范围由服务端冻结，不接受客户端自定义。 |
| 规则资源 | `procurement_responsibility` | 权限为 `list`、`manage`。 |
| 负责人资格 | `purchase_order:create` | 规则保存、销售提交和销售生效时均需验证。 |
| 派生采购状态 | `pending`、`partial`、`covered` | 仅为展示/查询派生值，不新增销售单主状态。 |
| 创建冲突文案 | `可采购数量已更新，请刷新后重试` | 并发或过期剩余数量统一提示。 |

## 2. 稳定接口与传输边界

实现应在现有 `/admin` API 体系内提供以下可定位能力；具体 Rust 类型名可调整，HTTP 语义不可静默改变：

1. 责任规则列表和维护：
   - `GET /admin/procurement-responsibility-rules`
   - `POST /admin/procurement-responsibility-rules`
   - `PUT /admin/procurement-responsibility-rules/{id}`
2. 销售行责任预览：`POST /admin/procurement-responsibility/resolve`，输入为销售草稿中解析所需的 SKU、服务区域等业务字段，输出逐行唯一负责人或可执行错误。
3. 采购创建依据：复用 `GET /admin/purchase-creation-bases`，每行必须返回销售数量、已覆盖数量和剩余数量，并按当前用户责任范围过滤。
4. 采购创建：复用 `POST /admin/purchase-orders`，请求必须显式携带本次选中的销售提交行及数量；系统重新校验最新剩余数量。
5. 销售详情：现有销售单详情返回采购单数量、销售总数量、已覆盖数量、剩余数量和派生采购状态。
6. 工作台：现有任务列表可返回并筛选 `PROCUREMENT_ORDER_CREATION`，详情路由指向采购创建页面并带服务端可验证的任务身份。

接口断言至少覆盖：成功结构、参数错误、未认证、无权限、跨责任范围、资源不存在、状态冲突和并发数量冲突。浏览器 E2E 不直接依赖内部字段名展示。

## 3. 数据一致性契约

1. `remaining = effective_sales_quantity - covered_purchase_quantity`，结果不得小于零。
2. 覆盖数量来源于关联同一销售提交/版本行的有效采购提交行或生效采购分配：草稿、审批中、生效、部分执行、完成占用；作废不占用。
3. 每次创建采购草稿前必须在最新数据库状态上重新计算并校验；成功写入采购单头、提交、行、审批绑定和审计记录，失败不得留下部分数据。
4. 销售单生效与采购任务派发不得留下部分负责人任务；同一销售单提交版本、负责人和责任范围最多一个有效任务。
5. 销售详情、创建依据和任务完成判断调用同一剩余数量规则或共享领域服务，不允许复制不同口径。
6. 采购作废或生效减量后同步重新计算任务状态；覆盖重新大于零时可重复打开同一责任范围。

## 5. 浏览器稳定入口与选择器

新增或修改的关键交互必须提供下列 `data-testid`，测试不得用易变 CSS 类或中文层级选择器代替：

| --- | --- | --- |
| 销售行责任 | `sales-line-procurement-owner-{lineId}` | 展示预计采购负责人或未解析提示 |
| 销售提交 | `sales-order-submit` | 提交审批并验证责任门禁 |
| 采购进度 | `sales-order-procurement-progress` | 展示总量、已覆盖、剩余和状态 |

| 任务入口 | `work-item-open-document-{workItemId}` | 打开采购创建页面 |
| 创建依据 | `purchase-basis-{basisId}` | 选择当前责任范围和供应商 |

移动端同一业务动作使用相同测试标识。

## 6. 可观察结果

- 责任解析：页面负责人名称、规则命中层级、逐行错误；接口返回唯一用户 ID。
- 任务派发：工作台任务数量、负责人、状态、销售单号、负责明细数和剩余数量。
- 采购创建：新采购单号、采购单列表数量、采购行数量与本次采购数量。
- 进度：销售详情、任务和创建依据三处剩余数量相同。
- 状态恢复：采购作废/减量后任务重新出现，已完成任务历史仍可查。
- 权限：入口隐藏与后端拒绝同时验证。
- 审计：操作人、动作、资源类型、资源 ID、时间和结果可定位。

## 7. 测试隔离与清理

1. Rust 单元测试不得依赖网络或全局可变状态。
2. 数据库集成测试使用唯一测试前缀或隔离数据库，测试结束删除本用例数据。
3. 并发用例使用固定屏障同时提交，不能依赖 `sleep` 猜测时序。
4. Playwright 测试串行执行涉及共享审批配置的主流程；每个场景开始前调用现有 reset。
5. E2E 不允许 `page.route`、接口 mock 或前端内联假数据。

## 8. P0 真实 E2E 完成条件

至少有一条 Playwright 测试完整证明：

1. 管理员建立 SKU 到 `caigou` 的责任规则。
2. `xiaoshou` 创建含数量 10 外采行的销售单，页面只读显示 `caigou`。
3. 采购确认不是最后审批节点；采购确认通过后没有采购建单任务。
4. 最后审批通过后 `caigou` 在“我的工作台”看到待采购建单任务。
5. `caigou` 第一次建立数量 4 的采购草稿，销售详情和任务显示剩余 6。
6. `caigou` 第二次建立数量 6 的另一张采购草稿，关联采购单数为 2，剩余为 0，任务完成。
7. 同一路径至少在桌面视口完成全部业务动作，并在移动视口验证进度和关键入口可达。

这条测试必须连接真实前端、后端和 MongoDB；仅打开页面或验证路由不算通过。
