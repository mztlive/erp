# ERP 页面布局与交互规范

本文定义 ERP 桌面端的统一布局、操作方式、状态反馈和防错规则。页面编号、菜单和路由以 [ERP 页面地图](./erp-page-map.md) 为准。

本规范同时覆盖两期。第一期和第二期使用同一套页面骨架、单据交互和状态表达；阶段差异通过业务性质、主责系统、功能启用状态和权限控制，不复制页面。

---

## 1. 交互目标

ERP 是公司内部的业务事实账本和单据流转系统。页面以快速处理、准确录入、跨部门交接和完整追溯为目标。

所有页面遵守以下规则：

1. **任务优先。** 首页先展示当前用户需要处理的事项，不用经营指标卡片替代工作队列。
2. **列表优先。** 高频查询和批量操作使用高密度表格，不把每条业务记录做成卡片。
3. **状态分离。** 主状态、履约、回款、开票、商城协同和异常状态分别展示，不合并成含义不明的综合状态。
4. **正式事实不可覆盖。** 已生效单据、收付款、发票、出入库和接口结果通过变更、退货、退款、冲正、红票、调整或补偿纠正，不提供直接改写和删除入口。
5. **责任动作明确。** 每条任务只有一个完成动作；业务单据允许履约、回款、开票和异常并行，页面展示当前用户主动作及各责任轨道。
6. **业务内容优先。** 接口页面先展示业务对象、金额和客户影响，技术尝试和响应摘要放在次级区域。
7. **键盘完整可用。** 高频录单、查单、逐条审核和表格操作无需依赖鼠标。
8. **不静默降级。** 无成本、映射失败、数据过期、商城未确认和结果未知必须明确显示，不能当作零值、成功或无变化。
9. **两期同页演进。** 一期商城主责卡券销售单和二期 ERP 主责卡券销售单使用同一销售单页面；主责变化不改变页面编号、路由、单号和历史。

## 2. 桌面应用壳

### 2.1 目标尺寸

- 基准宽度为 1440px，最低工作宽度为 1366px。
- 左侧导航展开宽度为 208px，折叠宽度为 64px。
- 顶部全局栏高度为 48px，内部任务页签高度为 36px。
- 标准列表行高为 36px，舒适密度为 44px，由用户偏好切换。
- 右侧快速预览宽度为 360～440px。
- 宽度不足时折叠左侧导航和右侧预览，不把单据明细表自动改成卡片。
- 手机端不承担正式录单、审批、核销、库存执行和异常补偿。

### 2.2 应用壳结构

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ ERP │ 全局搜索/命令 ⌘K │ 已打开任务页签… │ 待办 12 │ 后台任务 2 │ 用户 │
├────────────┬───────────────────────────────────────────────────────────────┤
│ 工作台     │ 面包屑 / 页面标题                   [刷新] [导出] [+ 新建]  │
│ 销售与客户 │───────────────────────────────────────────────────────────────│
│ 采购与供应商│                                                               │
│ 商品与供应 │ 页面内容                                                      │
│ 库存与履约 │                                                               │
│ 财务结算   │                                                               │
│ 卡券销售   │                                                               │
│ 异常与对账 │                                                               │
│ 经营分析   │                                                               │
│ 系统管理   │                                                               │
└────────────┴───────────────────────────────────────────────────────────────┘
```

顶部全局栏固定包含：

- 全局搜索和命令入口；
- 当前打开的内部任务页签；
- 我的待办数量；
- 后台任务数量及失败标记；
- 当前组织、用户和退出入口。

全局搜索覆盖客户、供应商、合同号、销售单号、采购单号、收付款单号、发票号、SKU 和条码。搜索结果按业务对象分组，只展示当前用户有权查看的对象。搜索不会返回卡号、卡密、卡实例绑定手机号或连接密钥。

### 2.3 内部任务页签

- 从列表打开详情时默认复用当前详情页签；按住平台标准修饰键时打开新页签。
- 页签保存筛选、分页、滚动位置、展开行和未提交草稿上下文。
- 有未保存内容的页签显示脏标记；关闭前必须确认。
- 正式提交成功后，页签标题更新为正式单号。
- 同一稳定业务对象重复打开时聚焦已有页签，不创建多个互相竞争的编辑页。
- 返回来源列表时恢复原筛选、页码、选择和滚动位置。

### 2.4 全局维护状态

维护窗口、主责迁移和关键链路冻结使用全局横幅：

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 维护窗口进行中：卡券销售新建、变更、制卡和商城关键事实已冻结。查看迁移进度 │
└────────────────────────────────────────────────────────────────────────────┘
```

横幅必须说明：

- 生效时间；
- 被冻结的业务动作；
- 当前执行阶段；
- 查看迁移或故障进度的入口；
- 当前用户是否仍可进行只读查询。

冻结动作在页面上保留位置并显示禁用原因，不通过隐藏按钮制造“不知道功能在哪里”的问题。

主责迁移的页面责任固定为：

1. 准备期由销售确认销售单商业清单，财务确认票款、应收和开票清单；
2. 任何清单、当前销售版本、卡实例或初始余额基线变化都会使原确认失效并重新产生任务；
3. 进入维护窗口并完成最后一次一期同步后，由上线负责人确认最终权威基线和最后水位；
4. 系统管理员执行迁移批次；执行前重新校验前三类确认、来源身份、唯一明细和基线版本；
5. 上线负责人不替代系统管理员执行，系统管理员不替代销售或财务业务确认。

## 3. 工作台与统一任务队列

### 3.1 工作台布局

```text
┌ 我的工作 ─────────────────────────────────────────────────────────────────┐
│ 待我处理 18 │ 今日到期 5 │ 已超时 2 │ 团队未分配 7       数据更新于 14:31 │
├──────────────────┬───────────────────────────────────────┬────────────────┤
│ 固定视图          │ 工作队列                              │ 快速预览       │
│ · 全部待办 18     │ 类型 │业务对象│客户/供应商│进入时间│时限│ 原因与影响    │
│ · 采购确认 5      │ ...  │ SO-... │ XX公司    │ ...    │... │ 下一动作      │
│ · 财务审核 3      │ ...  │ PO-... │ XX供应商  │ ...    │... │ 关联单据      │
│ · 票款复核 4      │                                       │ [开始处理]     │
│ · 异常 6          │                                       │                │
├──────────────────┴───────────────────────────────────────┴────────────────┤
│ ↑↓ 选择  Enter 打开  Alt+↑/↓ 上一条/下一条                               │
└────────────────────────────────────────────────────────────────────────────┘
```

工作台不展示无动作意义的长期状态。卡券销售单在履约期限到期前长期处于履约中属于正常状态，不进入积压待办。

### 3.2 任务最小信息

每条任务必须包含：

- 任务类型；
- 业务对象和单号；
- 客户或供应商；
- 进入队列时间；
- 截止时间或预警级别；
- 当前责任人；
- 产生原因；
- 对履约、库存、资金、客户或接口链路的影响；
- 唯一下一动作。

任务状态固定为：

```text
待领取 → 待处理 → 处理中 → 已完成
                ↘ 转交：原任务已转交 + 后继任务待领取
                ↘ 已关闭
```

业务单据状态和任务状态相互独立。关闭任务不改变正式单据；正式单据达到结果后由
系统完成对应任务。审批、确认、结果未知和未完成补偿任务不得人工关闭。只有重复、
误派或已由另一正式任务替代的任务可关闭，且必须选择结构化原因、关联替代证据并
记录审计。

转交是一次追加式审计动作，不是让同一任务停在无人处理的终态。服务端必须在一个
事务中校验受让角色、用户及其当前数据范围，令原任务进入“已转交”、立即失效原领取
租约，并创建继承业务对象、截止时间和处理上下文的“待领取”后继任务；校验失败时原
任务和租约均保持不变。页面显示完整转交链，受让人没有权限时不能被搜索或选中。

### 3.3 角色固定视图

| 角色 | 一期固定视图 | 二期增加 |
| --- | --- | --- |
| 销售 | 驳回销售单、待验收、履约超期、催回款、客户与合同映射差异 | 卡券销售审批驳回、执行投影失败、消费和经营下钻；迁移准备期增加销售清单确认 |
| 销售领导 | 团队销售、低毛利销售上级确认、票款和客户经营质量 | 卡券销售领导审批 |
| 采购 | 采购二次确认、采购单驳回、待履约、资质到期 | 外部商品变更、供货价变更、供应商订单异常 |
| 运营 | 卡券类目映射、商城同步差异 | 卡券销售运营审批、商品发布、投影接收、消费异常 |
| 仓储 | 待入库、待仓发、库存短少、库存调整 | 不增加卡号或单卡库存任务 |
| 财务 | 采购审核、卡券期初票款复核、卡券同步金额差额复核、核销、财务纠错 | 供应商结算复核、成本覆盖和对账差异；迁移准备期增加财务清单确认 |
| 客服 | 无独立一期队列 | 取消、退款、售后和人工补偿 |
| 系统管理员 | 同步失败、每日核对、导入导出 | 连接、迁移、消息、接口错误和对账 |
| 上线负责人 | 无独立一期队列 | 维护窗口、最终权威基线确认、主责迁移进度和切换结果；不替代业务确认或系统执行 |
| 研发运维 | 无独立一期业务队列 | 连接健康、签名鉴权、消息积压、技术重试和回调异常 |
| 管理层 | 客户经营质量、履约与票款快捷入口 | 实际经营结果和卡券经营快捷入口；下钻仍受数据范围限制 |

### 3.4 连续处理

- 审核和确认页面提供“处理并打开下一条”。
- 下一条必须来自当前筛选和当前用户有权处理的队列。
- 打开下一条前以原子操作领取任务并获得短租约；领取时再次校验角色、数据范围和当前状态。
- 已被他人领取的任务自动跳过；租约心跳续期，页面正常退出主动释放，超时后由服务端安全释放。
- 正式提交同时校验任务领取人和租约；租约丢失时保留输入并要求重新领取，不重复提交。
- 当前处理失败时不跳到下一条。
- 逐条处理后在原列表位置即时更新，不整页刷新。
- 正式审批默认不提供批量通过，用连续处理替代高风险批量审批。

## 4. 列表页

### 4.1 标准布局

```text
┌ 销售单                                        [导出] [+ 新建销售单] ┐
│ 视图：我的未完成 ▾ │ 单号/客户____ │ 状态▾ │ 更多筛选 │ 查询 │重置│
│ 已选 8 条： [分配负责人] [导出]                         取消选择     │
├────┬────────────┬────────┬──────┬──────┬──────┬──────┬───────────┤
│ □  │ 单号       │ 客户   │主状态│履约  │回款  │开票  │ 我的主动作│
├────┼────────────┼────────┼──────┼──────┼──────┼──────┼───────────┤
│ □  │ SO-...     │ ...    │生效  │部分  │未收  │部分  │待采购确认 │
└────┴────────────┴────────┴──────┴──────┴──────┴──────┴───────────┘
│ 共 2,341 条                            50 条/页              1 2 3 > │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2 筛选

- 单号、名称、客户或供应商等最高频查询常驻。
- 高级筛选进入抽屉，按“状态、时间、责任、金额、关联对象”分组。
- 点击“查询”或按 `Enter` 执行；输入过程中不对服务端连续请求。
- “重置”恢复当前保存视图的默认条件，不擅自切回系统默认视图。
- 日期区间明确包含起止边界和时区。
- 状态筛选允许多选，并显示状态口径说明。
- 非敏感查询条件进入 URL，复制链接后能够恢复业务筛选。手机号、邮箱、税号、
  银行账号、证件号等敏感筛选只保留在当前页面内存，不进入 URL、浏览器历史或访问日志。

### 4.3 保存视图

保存视图包含：

- 筛选条件；
- 排序；
- 显示列；
- 固定列；
- 列顺序；
- 列表密度。

个人视图只有本人可见。团队视图由有权限的负责人发布，用户可以复制为个人视图，不能直接覆盖团队视图。

### 4.4 表格

- 单号、名称等识别列固定在左。
- 状态、当前用户主动作和行操作固定在右；并行轨道用数量或摘要展开，不伪装成唯一动作。
- 金额右对齐，数量同时显示单位，文本左对齐。
- 表头支持排序、调宽、显隐和固定。
- 横向滚动时保留选择列和关键识别列。
- 单元格不通过截断隐藏关键状态；长文本使用摘要和悬浮完整内容。
- 列表默认服务端分页，不使用无限滚动代替准确页数和批量范围。
- 一页默认 50 条，用户可切换 20、50、100 条。

### 4.5 多维状态

销售单列表至少分别展示：

| 维度 | 状态示例 |
| --- | --- |
| 主状态 | 草稿、待二次确认、待审批、已生效、履约中、已关闭、已作废 |
| 履约 | 未开始、部分履约、已完成 |
| 回款 | 未收、部分回款、已结清、待复核 |
| 开票 | 未开、部分开票、已完成、待复核 |
| 商城协同 | 不适用、待接收、已接收、接收失败、版本差异 |
| 异常 | 无异常、待处理、处理中、已解决 |

状态必须同时使用文字、图标和颜色。禁止只用红、黄、绿圆点。

一期卡券销售单另外显示：

- 主责系统为福利商城；
- 商城快照状态；
- 最近同步时间；
- 当前同步版本；
- 票款复核状态。

商城快照状态不能代替 ERP 的回款、开票和履约期限口径。第一期由商城快照按已确认
状态字典推进 `source_status_code` 和允许映射的商业状态，ERP 页面不提供人工推进
来源状态的动作。即使商城显示已关闭，ERP 仍须分别判断履约期限是否到期、应收是否
结清；只有两者同时满足才显示 ERP 已关闭。商城关闭不会清空未完成开票或纠错轨道。

### 4.6 快速预览

- 单击行打开右侧快速预览；`Enter` 打开完整详情。
- 预览展示识别信息、多维状态、关键金额、阻塞原因、当前用户主动作和并行责任轨道。
- 预览内不放复杂编辑表单和正式审批。
- 列表切换行时，预览中未保存内容必须先处理。

### 4.7 选择范围

选择条必须明确区分：

```text
已选择本页 50 条
[选择全部符合当前筛选的 2,341 条]
```

选择全部筛选结果后，任何动作都再次显示筛选范围和预计影响数量。确认预览时生成
不可变选择快照，冻结目标稳定 ID、数据截止水位和逐项版本；后台执行逐项重验权限、
状态和版本，预览后新增或变化的记录不得被自动纳入。分配责任人还必须校验被分配人
的角色和数据范围。切换筛选条件会清空选择并明确提示。

## 5. 正式单据详情页

### 5.1 标准布局

```text
┌ SO-20260731-001  卡券销售单  [ERP主责] [已生效]                     ┐
│ 客户：XX公司 │ 合同：HT-... │ 负责人：张三 │ 当前版本：V4          │
│ 履约：部分履约 │ 回款：已结清 │ 开票：部分 │ 商城：接收失败          │
├──────────────────────────────────────────────┬─────────────────────┤
│ 基本信息 │ 明细 │ 履约 │ 票款 │ 关联单据 │ 版本 │ 操作记录          │
│                                              │ 我的主动作 / 并行轨道│
│ 当前生效快照                                  │ 商城接收失败          │
│ 明细表                                        │ [查看原因]           │
│ 关联票款、执行投影、消费和异常（按业务性质）   │ [进入错误处理]       │
├──────────────────────────────────────────────┴─────────────────────┤
│ [创建变更单] [登记回款] [登记发票] [更多操作]                       │
└────────────────────────────────────────────────────────────────────┘
```

### 5.2 页头

页头固定展示：

- 单据名称和单号；
- 业务性质；
- 主责系统；
- 主状态；
- 客户或供应商；
- 责任人；
- 当前版本；
- 多维进度；
- 关键异常。

动作顺序固定为：

1. 当前用户在当前任务中的一个主动作；
2. 履约、回款、开票、异常等并行责任轨道的高频相关动作；
3. “更多操作”中的低频动作。

单据本身不宣称只有一个全局下一动作。页面同时展示每条并行轨道的当前状态、责任人、
截止时间和入口；销售单业务关闭后，仍可继续展示尚未完成的开票或纠错轨道。

作废、退款、冲正和调整不能与普通查看按钮使用相同视觉权重。

### 5.3 内容页签

正式单据按以下顺序组织，并按业务性质裁剪：

1. 基本信息；
2. 明细；
3. 履约；
4. 票款；
5. 关联单据；
6. 版本；
7. 操作记录。

适用于该业务性质但当前没有内容的页签显示数量 `0`。不适用的页签不显示，并在基本
信息中说明履约边界；卡券销售单不出现采购确认、采购单、入出库或客户验收页签。
权限不足的敏感页签不显示；有页面权限但当前状态不可操作时显示只读内容和原因。

### 5.4 版本

- 默认展示当前生效快照，不把可变主数据当前值冒充历史单据值。
- 版本时间轴显示版本号、来源、产生原因、操作人和生效时间。
- 一期卡券版本标注“商城同步”。
- 二期迁移后的版本标注“ERP 变更单”。
- 主责迁移本身不产生销售单版本，在操作记录中单独展示。
- 两个版本可以并排比较；差异按表头、明细、金额、履约和票款影响分组。
- 已发生事实不因查看旧版本而提供编辑入口。

### 5.5 关联单据

实物与服务销售单按采购履约链分组：

```text
销售与合同
  └─ 销售单
      ├─ 采购确认任务
      ├─ 采购单
      │   ├─ 付款与进项发票
      │   └─ 入库、代发、电子交付或服务履约
      ├─ 客户验收
      ├─ 回款与销项发票
      └─ 变更、退货、退款、冲正和调整
```

卡券销售单使用独立关系树：

```text
销售与合同
  └─ 卡券销售单
      ├─ 回款与销项发票
      ├─ 商城同步版本或执行投影
      ├─ 二期商城订单、消费、余额和供应商履约
      └─ 销售变更、退款、冲正和其他纠错
```

卡券单不得挂接采购二次确认、普通采购单、公司库存、电子交付、服务履约或客户验收。
第一期卡券履约只展示履约期限，第二期仍不把制卡、绑定和激活建成 ERP 单据。

每个关联对象显示单号、状态、金额或数量、责任人和打开入口。不得只显示无上下文的 ID 列表。

### 5.6 责任动作

右侧区域先显示当前用户主任务，再列出并行责任轨道。每条轨道显示：

- 当前阻塞；
- 下一责任部门和责任人；
- 需要完成的动作或完成条件；
- 到期时间；
- 进入操作页的主按钮。

当前用户无权执行时仍显示责任人，但按钮不可用并说明权限原因。没有本人动作时仍显示
其他责任轨道和完成条件，不用一个“下一动作”覆盖并行工作。

## 6. 单据编辑页

### 6.1 标准布局

```text
┌ 新建实物与服务销售单                    草稿已保存 14:32            ┐
│ 客户与合同 ─────────────────────────────────────────────────────── │
│ 客户 [选择____]  合同 [选择____]  结算主体 [____]  开票要求 [____] │
│ 明细 ──────────────────────────────────────────────── [+ 增加明细] │
│ # │销售项目│规格│数量│单位│履约方式│履约期限│含税单价│税率│金额     │
│ 1 │ ...    │... │ 10 │件  │公司仓发│...     │100.00 │13% │1000.00  │
│ 附件与说明 ─────────────────────────────────────────────────────── │
├──────────────────────────────────────────────┬─────────────────────┤
│                                              │ 校验结果             │
│                                              │ 2 项待处理           │
│                                              │ 含税金额 ¥...        │
│                                              │ 不含税金额 ¥...      │
│                                              │ 税额 ¥...            │
├──────────────────────────────────────────────┴─────────────────────┤
│ [取消]                                      [保存草稿] [提交确认]   │
└────────────────────────────────────────────────────────────────────┘
```

### 6.2 表单组织

- 表头、明细、履约、票款约定、附件和说明分区展示。
- 首次进入时只展开必填和高频区，已经填写或含错误的区块不得折叠隐藏。
- 关联对象使用可搜索选择器，显示名称、编号、状态和有效期。
- 选择客户后只展示该客户有效且有权限使用的合同。
- 实物与服务销售只能选择启用且在有效期内的可销售项目；卡券销售选择启用的卡券类目，
  不走普通可销售项目的采购履约校验。
- 选中主数据后保存稳定身份和业务快照；后续主数据变化不静默改写草稿或正式单据。

### 6.3 明细表

- 支持 Excel 区域复制粘贴。
- 支持 `Tab`、`Shift+Tab`、方向键和 `F2`。
- 支持复制上一行的允许字段；单号、身份和审计字段不得复制。
- 行内错误固定显示在对应单元格和右侧错误汇总。
- 删除草稿明细需要确认存在的下游引用；正式明细不提供删除。
- 金额和税额按明细舍入到分，表头只汇总已经舍入的明细。
- 含税单价、不含税单价、税率、税额和金额的来源必须明确，不允许循环反算造成反复跳值。
- 单位随 SKU 基础单位带出，不能在单据中临时改成另一个基础单位。

### 6.4 卡券销售单唯一明细

卡券销售单采用专用的“唯一卡券明细”区，不使用可以任意增行的表格：

```text
卡券类目 [中国通____]        履约期限 [2028-07-31 23:59:59]
业务时区 Asia/Shanghai（固定）
面额     [500.00]           数量     [100]
成交单价 [480.0000]         卡形态   [电子卡 ▾]
成交金额 48,000.00（派生）   面值小计 50,000.00
配赠金额 2,000.00            配赠率   4.1667%
```

规则：

- 页面不存在“增加第二条卡券明细”。
- 卡券类目和履约期限位于销售单级区域。
- 履约期限使用“日期 + 时分秒”控件，业务时区固定显示为 `Asia/Shanghai`；持久化为统一
  时基的精确时间点。第一期来源时间按原精度展示，ERP 不擅自改成当日日终；第二期
  新建、详情、审批差异和执行投影均显示同一个精确时刻，系统达到该时刻后才判定到期。
- 面额、数量、含税成交单价、派生成交金额、配赠和卡形态位于唯一明细区域。
- 含税成交单价是可编辑的定价输入，最多 4 位小数；成交金额由
  `round(unit_price_gross × card_count, 2)` 唯一派生且只读，不能同时编辑单价和总额
  形成两个真相。第一期来源同时提供单价和总额但不符合该舍入关系时进入同步差异，
  不能静默选择其中一个。
- 同一生效结果需要不同卡券类目、面额、配赠条件、卡形态或履约期限**同时存在**时，
  使用多张卡券销售单。已生效单据通过销售变更单整体替换唯一明细时，仍沿用原销售单
  和稳定明细身份，不因新旧条件不同另开单。
- 一期及二期切换准备期不显示 ERP 卡券新建入口；只有全部迁移完成、一期轮询停止、
  P0/P1 完整链路就绪并登记 `T` 后才开放。
- 二期销售单生效后不能直接编辑，必须创建销售变更单。
- ERP 页面不包含玩法规则、卡号、卡密、手机号绑定和激活字段。

一期来源快照出现零条或多条卡券明细时，详情进入“唯一明细异常”只读态：保留并展示
清洗后的来源快照摘要、异常数量、来源版本和责任任务，禁止形成应收和经营结果，也
禁止 ERP 自动合并、丢弃或拆成多张销售单。修复来源后按原来源身份补拉并重放。

### 6.5 草稿与自动保存

- 草稿在用户停止输入后自动保存，并保留显式“保存草稿”动作。每次保存成功返回新的
  服务端版本和草稿内容指纹，后续自动保存与正式提交都使用最近一次服务端确认值。
- 页头显示“保存中”“已保存时间”或“保存失败”。
- 自动保存失败时保留本地输入，不清空表单；恢复后使用最近一次服务端确认版本重试，
  服务端已有他人变化时先进入差异处理。
- 附件单独显示上传状态。上传失败不丢失其他字段，但依赖附件的正式提交必须阻断。
- 离开存在未持久化内容的页面前必须提示。

### 6.6 校验

校验分三层：

| 层级 | 时机 | 示例 |
| --- | --- | --- |
| 字段校验 | 输入或离开字段 | 必填、格式、金额精度、日期顺序 |
| 行与单据校验 | 保存草稿、提交 | 明细合计、唯一卡券明细、客户合同关系、履约方式 |
| 业务与并发校验 | 正式提交 | 主数据有效性、资质、库存、单据版本、权限、岗位分离 |

错误汇总按页面顺序排列，点击错误直接聚焦字段。禁止只在页面顶部显示“校验失败”而不定位。

### 6.7 正式提交

`提交确认` 先打开影响摘要：

```text
本次提交将：
1. 销售单从“草稿”进入“待采购二次确认”
2. 为采购创建 1 条待办
3. 当前销售内容在待确认期间锁定

[返回修改] [确认提交]
```

摘要必须包含：

- 原状态和目标状态；
- 将锁定的字段；
- 将产生的任务、应收、采购草稿或执行投影；
- 下一责任部门；
- 无法自动撤回的影响。

键盘提交只打开该确认层，不直接执行正式动作。

## 7. 审批与采购二次确认

### 7.1 标准布局

```text
┌ 待采购二次确认：SO-...                         第 3 / 18 条           ┐
├──────────────────────────────────┬─────────────────────────────────┤
│ 销售单与合同摘要                  │ 本次处理                         │
│ 商品、数量、报价、参考成本        │ 供应商 [____] 最新成本 [____]    │
│ 毛利影响与履约期限                │ 可供数量 [____] 预计交期 [____]  │
│ 附件、版本和历史驳回原因          │ 履约方式 [____] 处理意见 [____]  │
│                                  │ ○ 通过  ○ 驳回                   │
├──────────────────────────────────┴─────────────────────────────────┤
│ [返回队列]                  [驳回] [通过并打开下一条]               │
└────────────────────────────────────────────────────────────────────┘
```

### 7.2 采购二次确认

- 采购二次确认是销售单上的任务和操作记录，不产生采购二次确认单。
- 页面左侧展示整张销售单和全部需外购明细；右侧为每条销售明细维护一条或多条
  “供应分配子行”，每条子行分别登记供应商、最新成本、供货数量、预计交期和履约方式。
- 同一销售明细可以按数量拆给多个供应商。每条供应分配必须为正，分配数量合计必须
  等于本次提交承诺数量；全部需外购销售明细都覆盖后才能整单通过。供应商、成本、
  数量或履约方式变化都会改变提交内容指纹并使旧确认失效。
- 处理结果按整张销售单提交。
- 通过后销售单生效，并允许按供应商、采购类型、付款条件和履约责任形成采购单草稿。
- 不通过时必须选择原因并填写说明，销售单退回负责销售。
- 销售选择“照原条件承接低毛利”时不能直接再次进入采购确认：必须填写承接理由，
  对比原提交并确认内容未改变，先进入 `LOW_MARGIN_MANAGER_CONFIRMATION`。销售上级
  只能通过或驳回；通过后才以同一提交内容再次进入采购确认，采购确认通过后方可生效。
- 销售改品或改价时原低毛利承接路径失效，按新内容重新提交采购确认；选择“不做”则作废草稿销售单。
- 驳回发生在销售单生效前，不创建销售变更单。
- 正式提交前显示最新成本对成交金额和预计盈亏的影响。
- 不提供批量通过。

### 7.3 采购单财务审核

- 审核页展示供应商、商品和物流费用、含税与不含税金额、税率、付款条件、履约责任和关联销售。
- 财务只能审核或驳回，不能在审核页修改采购内容。
- 驳回必须填写原因，采购修改后重新提交。
- 审核通过不等于付款完成；采购状态、付款状态和履约状态分别展示。

### 7.4 二期卡券销售审批

固定顺序为：

```text
销售提交 → 销售领导审批 → 运营审批 → 销售单生效
         → 形成首个不可变版本与应收 → 自动发送商城执行投影
```

规则：

- 销售领导审核客户商务条件、销售内容和合同一致性。
- 运营审核卡券类目和商城执行条件。
- 审批人只能通过或驳回，不能直接修改销售单。
- 驳回后，只要销售修改任何销售单内容，必须重新从销售领导审批开始。
- 销售单生效前不形成应收，不发送执行投影。
- 商城接收失败不回退已生效销售单和应收；页面另行显示“商城接收失败”并进入错误中心。
- 商城确认接收前，ERP 页面只显示“商城侧执行受阻”和接收结果；玩法配置、制卡、
  绑定和激活的实际入口及门禁均在商城，ERP 不提供或远程禁用这些动作。

### 7.5 卡券销售变更审批

- 运营在 ERP 查看变更前后差异，并自行进入商城核对执行可行性。
- ERP 只保存运营结论、意见、审批人和时间，不保存或自动判断发卡数、激活数。
- 运营通过后由财务复核金额、税额、应收和配赠影响。
- 运营和财务都只能通过或驳回，驳回原因必填并退回负责销售。财务只能复核运营已经
  通过的同一 `sales_change_submission.id` 和 `subject_hash`，不能复核页面当前可变草稿。
- 销售针对任一驳回修改后重提时，必须形成新的不可变 `sales_change_submission`；
  旧运营确认和财务复核全部失效并保留审计，新提交从运营确认重新开始，不能继承旧通过。
- 生效事务重新校验 `base_revision_id` 仍是当前有效版本、执行投影基线一致，
  且运营与财务均对当前提交的同一内容指纹通过；任一校验变化均阻断生效并重新提交。
- 生效后形成新销售单版本并发送新执行投影。
- 执行投影基线不一致时阻断提交并创建差异任务，不覆盖任一侧事实。

### 7.6 岗位分离

- 销售单创建人不得审批自己的低毛利承接；卡券销售创建人不得充当该单销售领导或运营审批人。
- 采购单提交人与财务审核人不得为同一人。
- 财务纠错的经办人与复核人不得为同一人。
- 库存调整的仓储经办人与仓储复核人不得为同一人。
- 供应商结算继续执行经办和复核分离。
- 权限管理员不得给自己授予新业务权限，也不得单独降低岗位分离规则；此类变更须由另一名授权管理员复核。
- 当前用户不满足岗位分离时，按钮保留但禁用，并显示“提交人与复核人不得为同一人”。

### 7.7 主责迁移确认与执行

主责迁移与商城级开放使用五段责任链；销售和财务确认可以并行，但后续三段严格串行：

```text
销售清单确认 ∥ 财务清单确认
→ 维护窗口内上线负责人最终基线确认
→ 系统管理员执行客户批次
→ 上线负责人执行商城级开放确认并登记 T
```

- 销售和财务只读查看商业事实，只能确认本角色负责的清单范围；两类确认分别留痕。
- 销售版本、票款、卡实例、初始余额、映射差异或迁移范围变化时，相关确认立即失效。
- 上线负责人确认最后同步水位、全量指纹、卡实例与初始余额基线和迁移执行投影基线；
  不替代系统管理员执行批次。
- 系统管理员执行前重新校验所有确认、来源身份、唯一明细、当前主责和基线版本。
- 每个按客户建立的迁移批次原子提交：任一销售单失败时，该批所有 `owner_system`
  变化均不提交。页面显示失败对象和原因，保持冻结并只允许使用原批次幂等续跑。
- 已完成的其他客户批次不回退；失败批次不得恢复商城主责、一期轮询或任一写入口。
- `ERP-MAL-022` 在全部客户批次成功前只显示禁用的“商城级开放”面板及逐项缺口。
  只有上线负责人可以提交该面板；系统管理员不能代提交。
- 提交商城级开放时，服务端在一个事务边界重新校验：迁移范围被成功客户批次完整覆盖、
  所有目标销售单已归 ERP、一期轮询已停止且水位封存、最终基线确认仍有效、维护冻结
  仍生效，以及商品发布、执行投影、五类事实、供应商下单/拒绝/未知结果、取消、退款、
  余额恢复、最终成本、周期结算、应付衔接、对账和历史回填程序等 P0/P1 门禁均通过。
- 校验通过时以服务端提交时间创建唯一 `mall_consumption_cutover` 并登记不可修改的 `T`；
  同一事务提交失败则不创建 `T`、不开放任何入口并继续保持冻结。成功后才开放 ERP
  卡券新建和商城员工业务，历史回填任务只能在此后运行。
- 成功结果固定展示操作者、`T`、范围摘要、检查项快照、关联全部迁移批次和“一旦产生
  ERP 新版本或下游事实不得回退商城主责”的确认；页面没有删除、改时点或回退按钮。

## 8. 多对多核销

### 8.1 核销工作区

```text
┌ 回款单 RC-...  到账 ¥100,000.00  待分配 ¥20,000.00                  ┐
│ 经营客户：XX事业部客户   往来/结算主体：XX有限公司                 │
│ 到账日：...             回单：[查看]                               │
├────┬────────────┬──────────┬──────────┬──────────┬───────────────┤
│ □  │ 应收来源   │ 应收余额 │ 本次分配 │ 到期日   │ 分配后余额      │
│ □  │ SO-001     │ 50,000   │ 50,000   │ ...      │ 0               │
│ □  │ SO-002     │ 80,000   │ 30,000   │ ...      │ 50,000          │
├────┴────────────┴──────────┴──────────┴──────────┴───────────────┤
│ 分配合计 ¥80,000.00              [自动建议] [清空] [确认核销]       │
└────────────────────────────────────────────────────────────────────┘
```

### 8.2 统一能力

同一工作区支持：

- 客户回款分配到一张或多张销售单应收；
- 一张销售单应收由多张回款核销；
- 销项发票分配到一张或多张销售单可开票金额；
- 供应商付款分配到一张或多张采购单或供应商结算单应付；
- 一张采购单或供应商结算单应付由多张供应商付款核销；
- 进项发票分配到一张或多张采购单或供应商结算单可收票金额。

### 8.3 核销规则

- 销售侧核销相等键是往来/结算主体 `counterparty_party_id`，不是经营
  `customer_id`。页头同时展示经营客户与往来/结算主体；候选应收和可开票金额只加载
  与来源回款或销项发票同一往来主体的子账。多个经营客户共用同一往来主体时可以在权限
  范围内核销，同一经营客户下不同结算法人之间禁止核销。
- 供应商侧只允许付款或进项发票的 `party_id` 与目标应付往来主体一致。
- 来源金额、已分配、待分配和本次分配始终同屏。
- 支持部分核销和保留待分配余额。
- “自动建议”只按确定规则预填，不自动提交。
- 提交前重新读取来源余额和目标余额，防止并发超分配。
- 服务端提交事务再次校验来源资金或发票的 `party_id` 与每个目标子账
  `counterparty_party_id` 一致；页面筛选不能替代该约束。
- 分配合计不得超过来源待分配金额，也不得超过目标可核销余额。
- 发票代码存在时按方向、代码和号码检查重复；数电票无代码时按方向和号码检查重复。
- 发票尾差单独记录，不修改销售或采购单价。
- 取消或纠错使用冲正或反向分配，不删除原核销明细。

### 8.4 卡券销售单票款复核

- 一期期初卡券销售单已收和已开票初始化为 0，必须逐单复核。
- `CARD_FUNDS_REVIEW` 任务的复核面板并排展示：当前销售版本及成交金额、往来/结算
  主体、派生应收、已过账回款及其有效核销、已登记销项发票及其有效分配、未分配余额、
  已收/未收和已开/未开差额、附件与复核证据。
- 复核面板不提供“填写已收金额”或“填写已开票金额”的捷径。历史事实缺失时，财务
  必须进入回款、销项发票和核销工作区逐项登记正式事实，再返回当前任务。
- 只有财务确认历史事实已经逐项登记，且不存在草稿资金/发票、超额分配、往来主体冲突
  或未处理差异，并提交受控复核证据后，服务端才按当前任务 `subject_hash` 原子记录
  `reviewed_by`、`reviewed_at`、证据和复核摘要，同时完成任务。复核过程中销售版本、
  应收、回款核销或发票分配变化时阻断提交并刷新任务。
- 复核完成只表示历史登记范围已核实，不表示应收已经结清、发票已经开足或销售单可以
  关闭；页面继续按正式余额展示未收和未开金额。
- `CARD_FUNDS_DELTA_REVIEW` 并排展示商城同步前后销售金额、应收差额、既有回款核销和
  发票分配影响。新同步版本使旧复核失效；若形成超额核销、超额开票或主体冲突，必须
  先通过反向核销、退款、冲正或红票等正式纠错闭环处理，才能按新 `subject_hash`
  重新复核完成。
- 页面突出“待复核”状态、复核进度、当前任务类型和因何失效。
- 不提供“批量置为已结清”。
- 复核前的应收、逾期、账龄和平均回款周期必须标注为不可直接参考。
- 客户经营质量支持“仅统计已复核数据”筛选。

## 9. 库存与履约

### 9.1 库存余额

库存页面同时展示：

| 指标 | 含义 |
| --- | --- |
| 在库 | 已形成有效入库事实的数量 |
| 预占 | 已锁定给来源销售单的数量 |
| 可用 | 在库减有效预占后的数量 |
| 待入库 | 有采购依据但尚未形成入库事实的数量 |
| 待出库 | 已形成发货责任但尚未出库的数量 |

库存余额和流水只读。任何变化必须来自入库、出库、采购退货、销售退货验收或库存调整。

### 9.2 先款后货履约门禁

采购单付款条件为“先款后货”时，入库、代发、电子交付和服务履约页在主操作区同屏展示：

- 付款条件和要求的最低付款金额或比例；
- 已过账付款中有效核销到该采购单应付的金额；
- 当前仍缺金额；
- 数据更新时间和进入付款/核销页面的入口。

未达到门槛时，“确认入库”“确认代发”“确认电子交付”和“确认服务履约”保留位置但
禁用并说明缺口。保存草稿不形成履约事实，可以继续；正式提交必须在同一业务事务边界
重新校验有效付款核销额，页面缓存或仅有付款单但尚未过账、尚未核销都不能放行。非
“先款后货”采购单不套用该门禁。

### 9.3 入库页

```text
┌ 采购入库 IR-...   来源 PO-...   仓库 [广州仓]                      ┐
├────┬──────┬──────┬────────┬────────┬────────┬────────┬──────────┤
│ SKU│采购数│已入库│本次实收│本次合格│本次拒收│入库后累计│自动预占  │
│ ...│ 100  │ 40   │ 60     │ 58     │ 2      │ 98       │ SO-... 58│
└────┴──────┴──────┴────────┴────────┴────────┴────────┴──────────┘
│ [保存草稿] [确认入库]                                                │
└──────────────────────────────────────────────────────────────────────┘
```

规则：

- 支持部分合格入库。
- 本次合格与拒收之和不得超过本次实收。
- 累计入库超过有效采购数量时阻断，必须先完成审核生效的采购变更。
- 合格入库后自动预占给来源销售单。
- 入库事实形成后不得回退；错误通过采购退货或库存调整处理。

### 9.4 仓发出库

- 页面同时显示在库、预占、本次出库和执行后余额。
- 默认只使用来源销售单的有效预占。
- 本次出库不得超过有效预占和实际可执行库存。
- 不允许负库存，不提供“继续提交并稍后补库存”。
- 支持部分出库，短少保留未完成数量，不允许把短少直接关闭为完成。
- 出库后形成追加式库存流水并进入客户验收。

### 9.5 代发、电子交付和服务履约

- 三种方式共用采购前段和客户验收后段，只在履约录入区显示各自字段。
- “先款后货”采购单先通过第 9.2 节付款门禁；每次正式提交都重新校验，不因曾经打开
  页面或保存草稿而绕过。
- 代发不影响公司自有库存。
- 电子交付登记对象、数量、时间、结果和凭证。
- 服务履约登记对象、时间、地点、完成结果和凭证。
- 不通过改变销售单主状态来代替履约记录。

### 9.6 库存调整

- 调整类型固定为盘盈、盘亏或损坏。
- 页面展示调整前、调整数量和调整后数量。
- 仓储经办提交，独立仓储复核，再由财务复核成本影响。
- 调整原因、实物依据和凭证必填。
- 原出入库记录保留，调整形成独立流水。

### 9.7 卡券库存边界

ERP 不展示和管理：

- 卡号；
- 卡密；
- 实体卡单卡库存；
- 卡号生产；
- 手机号绑定；
- 卡券激活。

第二期稳定卡实例引用只用于消费和余额追溯，不作为库存页面的 SKU 或序列号。

## 10. 异常、接口错误和对账

### 10.1 三类对象

| 类型 | 含义 | 正确处理 |
| --- | --- | --- |
| 业务异常 | 已发生业务需要变更、退货、退款、冲正或调整 | 从原单创建正式处理单 |
| 接口错误 | 消息发送、接收或供应商动作失败 | 查询、原幂等键重试、转人工或补偿 |
| 对账差异 | 两侧正式事实、快照或派生结果不一致 | 创建差异任务并人工确认，不自动覆盖 |

三类对象不能用一个“修复”按钮混合处理。

### 10.2 标准布局

```text
┌ 异常与对账 │ 我的待处理 18 │ 团队 43 │ 即将超时 6                  ┐
├──────────────────────┬──────────────────────────┬──────────────────┤
│ 队列                  │ 业务影响                 │ 处理记录         │
│ [结果未知] SUP-...    │ 商城订单 / 客户 / 金额   │ 自动尝试 3 次    │
│ [映射失败] SKU-...    │ 原支付事实已保留         │ 最近错误摘要     │
│ [投影失败] SO-...     │ 不影响销售单生效         │ 下次重试时间     │
│                       │ 推荐动作及阻塞原因        │ 审计时间线       │
├──────────────────────┴──────────────────────────┴──────────────────┤
│ [查询原结果] [使用原幂等键重试] [转交] [补充处理结果]              │
└────────────────────────────────────────────────────────────────────┘
```

### 10.3 业务异常

- 从原单、验收、票款或库存事实创建。
- 左侧展示原事实，右侧展示处理单和影响。
- 涉及金额、税额、应收、应付、成本或发票时必须进入财务复核。
- 已发生回款、付款、出入库和发票不随变更单回退。
- 原单与处理单双向关联。
- 完成条件由纠正结果决定，不能通过人工“关闭异常”替代正式处理单。

### 10.4 商城售后四段事实

商城取消和退款必须在同一详情中分段展示，不能合成一个“已退款”状态：

| 轨道 | 对象与责任 | 完成证据 |
| --- | --- | --- |
| 商城售后动作请求 | `mall_after_sales_request`；客服跟进请求范围和原因 | 请求已受理只代表开始处理，不代表取消或退款成功 |
| 商城取消/退款结果 | `mall_order_cancel_fact` 或 `mall_refund` / `mall_refund_allocation`；客服与财务 | 商城实际完成的结果事实；退款反向冲减原消费与原支付来源分摊 |
| 卡券余额恢复 | `mall_balance_restoration`；商城回流、财务核对 | 余额实际回补事实；不再次冲减消费、供应商成本或应付 |
| 供应商退款 | `supplier_refund_fact`；采购与财务 | 供应商实际退款事实，并据此追加冲减成本与应付 |

页面分别显示四条轨道的适用性、状态、金额、责任人、业务事实键和发生时间：

- 适用性由正式事实和固定规则计算为 `REQUIRED` 或 `NOT_APPLICABLE`；适用轨道的状态
  为 `PENDING` 或 `COMPLETED`。用户不能手工把轨道改成不适用。
- 卡券余额恢复只在原退款分配包含 `CARD` 支付来源时为 `REQUIRED`；没有卡券来源时以
  原支付分摊为证据显示 `NOT_APPLICABLE`。
- 供应商退款只在已形成需要退回的供应商成本、应付或付款时为 `REQUIRED`。`T` 前原
  人工链、供应商拒单且未计费/未形成应付等情况，由系统以支付时点、订单状态和账务事实
  计算为 `NOT_APPLICABLE` 并展示原因和证据。
- 整体只有在所有 `REQUIRED` 轨道均为 `COMPLETED` 时完成；任一适用轨道未完成时仍
  显示“退款处理中”。供应商已退款不能替代员工侧退款，适用的余额恢复也不能被其他
  轨道替代。

`T` 以前支付的历史订单始终显示“原人工售后链”，不提供 Supplier Connector 的取消
或退款动作。只有支付成功时间不早于 `T` 且已形成 ERP 供应商订单时，页面才允许驱动
对应供应商取消或退款；后续回流的商城结果仍按独立事实追加。

### 10.5 接口错误动作矩阵

| 错误类型 | 页面动作 |
| --- | --- |
| 能力不支持 | 查看商品能力、转人工；不显示自动重试 |
| 参数或映射错误 | 进入映射或数据修复；不显示重试 |
| 供应商业务拒绝 | 查看拒绝原因、通知业务、进入退款或恢复流程 |
| 网络超时 | 先查询原结果；确认无结果后使用原幂等键重试 |
| 结果未知 | 查询原订单或退款；供应商不支持查询时转人工 |
| 鉴权或签名失败 | 停止自动重试、立即告警、进入连接排查 |
| 限流 | 显示下次退避重试时间；不允许高频手工点击 |
| 重复回调 | 显示已幂等忽略，不产生业务任务 |
| 乱序回调 | 显示被拒绝的状态迁移和当前有效状态 |

人工重放必须使用原幂等键。页面不提供“把结果未知标记为成功”。

`RESULT_UNKNOWN` 查询后必须进入明确分支：

| 查询结果 | 页面结果与下一动作 |
| --- | --- |
| 已受理或已接单 | 追加受理事实，停止重复创建，等待或查询最终结果 |
| 已拒绝 | 追加拒绝事实，通知业务责任人，售后请求进入替代处理而非标记成功 |
| 明确无结果 | 经服务端确认可安全重试时，使用原幂等键重发 |
| 仍未知或不支持查询 | 转人工补偿任务，保留风险标记并进入对账，不能关闭原异常 |

接口错误任务只有在取得可验证终态，或已形成经复核的取消、退款、冲正、补偿事实并
完成相关对账后才能完成。普通“关闭任务”不能消除结果未知或未完成的资金、履约风险。

### 10.6 对账

- 对账中心按商品发布、销售投影、主责标记与商城商业字段只读状态、商城关键事实、
  支付分摊、卡券余额、供应商订单、退款和结算分组。
- 对账批次显示数据边界、开始与结束时间、比较数量、差异数量和结果。
- 差异详情并排展示双方值、来源版本和时间。
- 对账任务只创建差异，不修改正式业务事实。
- 修复主数据或补齐事件后重新归集或重跑查询模型，仍引用原业务事实键。
- 查询模型或对账任务失败不得改变正式事实。

### 10.7 技术信息

- 默认只展示脱敏请求摘要、响应摘要、统一错误分类、次数和时间。
- 原始报文仅在授权范围内查看，必须加密并受保留期限控制。
- 业务人员不需要理解供应商专用错误码；页面同时显示统一业务含义。
- 完整手机号、地址、银行账号、卡号、卡密和密钥不得进入接口尝试记录和操作日志。

```text
┌ 卡券经营分析                                      数据更新于 14:31 ┐
│ 期间 [____至____] 客户 [全部] 卡券类目 [全部] 成本口径 [全部] 查询 │
│ 销售金额(含税) │累计消费(含税)│实际成本(不含税)│成本覆盖率 92.4%   │
│ ⚠ 成本不完整，利润仅供参考                                         │
├───────────────────────────────┬────────────────────────────────────┤
│ 趋势与结构                     │ 客户 / 销售单明细表                 │
│ 简洁趋势图                     │ 可排序、可导出、可下钻              │
├───────────────────────────────┴────────────────────────────────────┤
│ 下钻：客户 → 销售单 → 商城订单 → 供应商订单 → 结算单              │
└────────────────────────────────────────────────────────────────────┘
```

### 11.2 共同规则

- 筛选区固定在顶部，支持保存视图。
- 指标区只展示核心结果，不堆叠大量卡片。
- 趋势图用于比较，明细表用于核对和下钻。
- 每个指标提供口径说明、数据期间和更新时间。
- 工作台与经营分析允许最多 1 分钟异步延迟，页面必须显示最近成功更新时间。
- 夜间重建期间继续展示上一次成功数据并显示“重建中”，不能清空为零。
- 下钻后保留上层筛选和面包屑。

### 11.3 含税与不含税

- 销售合同、应收、应付和实际收付款显示含税口径。
- 实际经营盈亏和利润类指标显示不含税口径。
- 指标名称直接带“含税”或“不含税”。
- 含税与不含税金额不得出现在同一个加减算式中。
- 消费金额换算使用销项税率，消费成本换算使用进项税率，二者不得互相替代。

### 11.4 一期卡券指标落点

- `ERP-ANA-001` 客户经营质量展示销售金额、面值、配赠金额、配赠率和客户复核口径。
- `ERP-ANA-003` 履约与票款展示履约期限、应收、回款、开票和期初票款复核进度。
- 销售单详情展示单据级面值、配赠和票款，不跳转到尚未启用的卡券经营分析路由。
- 卡券实际供货成本未覆盖时显示“成本未覆盖”。
- 不把缺失成本按零成本计算利润。
- 客户经营质量提供“仅统计已复核数据”。

### 11.5 二期 P1 经营结果与 P2 分析

- P1 在 `ERP-ANA-002` 实际经营结果展示卡券消费成本、未消费余额、当前经营贡献和成本覆盖率；
  销售按本人客户范围、销售领导按团队范围、运营和财务按授权范围查看。
- P2 再开放 `ERP-ANA-020` 的趋势、结构、多维筛选和跨订单下钻，不改变 P1 正式事实。
- 每笔消费标记 `ACTUAL`、`STANDARD` 或 `NONE`。
- 任何利润类指标必须与成本覆盖率同屏。
- 成本覆盖率低于财务确认阈值时显示“成本不完整，利润仅供参考”。
- `NONE` 消费只进入消费金额和消费率，不进入成本和利润。
- 当前经营贡献必须同时展示未履约余额。
- 履约期限到期前不得把当前经营贡献命名或展示为最终利润。
- 卡券全部消费不使销售单提前履约完成或提前关闭。
- 微信支付成本单列，不进入卡券实际消费成本和卡券利润指标。

## 13. 批量操作与导入导出

### 13.1 操作分级

| 级别 | 允许动作 | 处理方式 |
| --- | --- | --- |
| 直接批量 | 导出、分配责任人 | 明确选择范围后执行；责任人必须满足角色和数据范围 |
| 预校验批量 | 主数据导入、商品映射、同步补拉、生成草稿、可重试技术消息 | 先校验和预览，再进入后台任务 |
| 禁止批量 | 正式收付款成功、结果未知标记成功、直接覆盖正式单据、卡券票款复核结清、绕过审批、主责任意切换 | 页面不提供入口 |

正式审批默认逐单处理。采购二次确认、卡券销售审批、库存调整复核、财务纠错复核和供应商结算复核使用“处理并打开下一条”，不使用批量通过。

### 13.2 批量预览

批量执行前显示：

- 当前筛选；
- 选择范围；
- 预计处理数量；
- 可处理数量；
- 跳过数量和原因；
- 失败不会影响的对象；
- 是否产生后台任务。

执行结果按成功、跳过和失败分组。正式单据以单据为事务边界，一张失败不得形成半张单据。

主责迁移不适用上述逐单部分成功规则。一个按客户建立的迁移批次是原子事务，任一对象
失败时该批主责变化全部不提交；保持冻结并使用原批次幂等续跑。其他已完成客户批次
不回退。

### 13.3 导入

导入流程固定为：

```text
下载模板 → 上传到隔离临时区 → 安全清洗与结构校验 → 业务预校验
→ 查看成功/失败预览 → 确认导入 → 后台执行 → 下载结果
```

规则：

- 错误定位到工作表、行、列和业务原因。
- 正式导入前不修改业务数据。
- 同一原文件重复提交必须有明确重复提示和幂等处理；原始来源只以
  `HMAC(原始文件字节)` 的带密钥指纹及 `key_id` 关联，不持久化普通哈希，密钥轮换后
  通过仍受保护的旧密钥验证历史指纹，不回存原始文件。
- 期初迁移必须先在验证环境完成校验和业务确认，再进入生产。
- 原始 SQL、商城原始导出和含禁止字段的文件只在隔离临时区使用，完成清洗、带密钥来源
  指纹和审计摘要后
  按批准期限销毁，不进入长期附件或普通下载。
- 成功形成正式数据时长期保留重新生成的白名单导入包、manifest、规则版本和映射审计；
  失败的合规清洗包保留 30 天，页面显示到期日。
- 文件位于加密受控对象存储。每次查看或下载重新校验当前角色、责任域和数据范围，
  使用短时链接并记录下载人、用途、对象范围和时间。

### 13.4 导出

- 导出使用当前筛选、排序和选择范围。
- 导出前显示预计行数和敏感字段范围。
- 大数据量导出进入后台任务。
- 导出文件保留 7 天，任务中心显示到期日。
- 用户没有完整敏感字段导出权限时，导出内容沿用页面遮罩规则。
- 下载后台任务结果时重新执行当前权限和数据范围校验，不能沿用任务创建时的旧权限。

## 14. 状态反馈

### 14.1 普通操作

筛选保存、列宽调整等低风险操作使用轻提示。提示包含结果，不遮挡主操作区。

### 14.2 正式状态变化

提交、审核、生效、作废、入库、出库、核销、退款、冲正、结算和迁移完成后，必须在页面固定区域展示：

- 新状态；
- 产生的正式单号或版本；
- 下游任务；
- 下一责任人；
- 查看结果入口。

不能只显示短暂 toast。

### 14.3 后台任务

后台任务状态固定为：

```text
等待执行 → 执行中 → 部分成功 / 成功 / 失败 / 已取消
```

任务显示总数、已处理、成功、跳过、失败、开始时间、预计剩余或最近进展。失败后提供错误明细和允许的续跑入口。

主责迁移批次不使用“部分成功”终态；只能显示执行中、成功或失败。失败表示该客户批次
没有提交任何主责变化，并提供原批次续跑入口。

### 14.4 数据新鲜度

- 库存、票款和正式待办提交成功后立即刷新。
- 工作台和经营分析显示“数据更新于”，允许最多 1 分钟延迟。
- 商城同步、商品同步、执行投影、消费事件、供应商回调和余额快照分别显示来源时间、ERP 接收时间和当前处理时间。
- 数据超过业务新鲜度阈值时显示“数据已超过新鲜度阈值”，依赖新鲜数据的动作禁用并提供刷新或排查入口。

## 15. 防错规则

### 15.1 通用防错

1. 关键按钮使用具体业务动词，如“提交采购确认”“审核通过”“创建回款冲正”，不得使用含义不明的“确定”。
2. 禁用按钮显示原因和下一责任人。
3. 作废、退款、冲正、调整和迁移使用独立确认层，显示业务影响。
4. 正式单据不存在删除按钮。
5. 生效后的金额、数量、商品和供应商变化只通过变更单。
6. 已付款、已回款、已入库和已出库事实不回退。
7. 所有金额同时显示币种；比例显示精度和计算口径。
8. 销售和采购金额按明细舍入，表头不再次按未舍入值重算。
9. 同名客户、供应商、商品和卡券类目在选择器中同时显示稳定编号和状态。
10. 失效资质控制对应供应商能力，不允许用于新的可销售项目和采购单。

### 15.2 状态与动作防错

- 草稿允许编辑和作废。
- 已提交等待下一责任部门时锁定申请内容。
- 已生效关键字段只读。
- 部分执行继续处理剩余数量，不提供“整体重置”。
- 已完成和已作废为终态，只允许查看或创建纠错事实。
- 一期商城主责卡券销售单在 ERP 不提供商业变更、作废或补写状态动作。
- 二期迁移后卡券销售单仍不能直接编辑，只能创建销售变更单。

### 15.3 跨系统防错

- 一张销售单同一时刻只有一个主责系统。
- 执行投影未被商城确认时，销售事实保持生效；ERP 只展示“商城侧执行受阻”，真正
  玩法、制卡、绑定和激活入口由商城侧禁用。
- 投影版本、商品发布版本和供应商订单动作重复发送使用原幂等键。
- 网络超时或结果未知必须先查询原结果，不能直接重复下单。
- 对账差异不自动选择任一系统覆盖另一系统。
- 映射失败先保存原始事实并进入待处理，不形成错误的应收、成本或经营归属。
- `T` 以前支付成功的历史事实只回填台账，不触发供应商下单，也不通过 Connector
  发起取消或退款；该类订单沿用原人工售后链。
- 只有支付成功时间不早于 `T` 且已形成 ERP 供应商订单的业务，才允许驱动供应商取消或退款。

### 15.4 卡券防错

- 一张卡券销售单恰好一条卡券明细。
- ERP 不出现玩法规则、卡号、卡密、手机号绑定和激活字段。
- 卡券履约完成只按履约期限，不因已发卡、已激活或已全部消费提前完成。
- 一期卡券成本未覆盖不得显示零成本利润。
- 二期 `NONE` 成本不得进入利润指标。
- 卡券余额恢复只记录余额回补，不重复冲减消费、供应商成本或应付。
- 微信支付金额和成本单列，不归入企业客户卡券消费和利润。

## 16. 并发、幂等与草稿冲突

### 16.1 并发版本

- 所有可编辑主数据和草稿携带版本。
- 正式提交使用最近一次自动保存或显式保存后由服务端确认的版本及内容指纹，不使用
  刚打开页面时已经过期的初始版本。
- 服务端版本已变化时阻断提交并展示差异。
- 用户可以重新加载、复制本地内容到新草稿或逐项合并允许合并的主数据。
- 正式单据和追加式事实不执行最后写入覆盖。

冲突提示必须说明：

```text
该销售单已由李四在 14:35 提交为“待采购二次确认”。
你的草稿基于 14:21 的旧版本，不能覆盖当前状态。

[查看差异] [保留为新草稿] [重新加载]
```

### 16.2 编辑占用

- 页面显示正在查看或编辑同一草稿的其他用户。
- 占用提示是协作提醒，不替代服务端版本校验。
- 长时间打开页面不锁住业务对象。
- 普通后台任务不得持有跨整个任务的业务锁，按单据事务边界提交。主责迁移是明确例外：
  按客户批次在一个原子事务中提交，失败时整批回滚并保持冻结。

### 16.3 幂等

- 连续点击正式提交只产生一次结果。
- 页面提交中禁用重复点击，并显示正在处理的业务对象。
- 请求超时后查询原提交结果，不直接生成新单号。
- 接口人工重放使用原幂等键。
- 实时消费和历史回填按业务事实键去重，不以商城订单号单独去重。

## 17. 敏感信息

### 17.1 页面展示

- 客户和供应商银行账号默认遮罩，有完整查看权限的用户可以临时查看。
- 客户和供应商联系人手机号、邮箱、税号和证照附件按字段权限展示，列表默认遮罩或不展示。
- 二期供应商履约所需的收货人、手机号和地址默认遮罩。
- 查看完整值必须通过字段权限，并记录查看人、业务对象和时间。
- 列表默认不展示完整敏感值；快速预览沿用相同遮罩。
- 导出权限与页面查看权限分开控制。

### 17.2 禁止进入 ERP 的数据

- 卡号；
- 卡密；
- 卡实例绑定手机号；
- 商城玩法规则中的个人执行数据。

稳定卡实例引用是不可反推卡号和卡密的不透明标识，可以用于授权的消费追溯。

### 17.3 连接密钥

- API 供应商连接页只显示密钥管理系统引用。
- 不提供查看、复制或导出密钥正文的入口。
- 连接测试只显示成功、统一错误分类和脱敏摘要。

### 17.4 日志和审计

操作日志和接口日志不得记录：

- 完整手机号；
- 完整邮箱和税号；
- 完整地址；
- 完整银行账号；
- 证照正文或未授权附件链接；
- 卡号和卡密；
- 连接密钥；
- 未脱敏的完整请求或响应。

原始报文确需保留时必须加密、限制权限并设置保留期限，普通业务页面只展示排障所需摘要。

## 18. 加载、空态和失败

### 18.1 加载

- 首次列表加载使用与最终列结构一致的骨架，不使用遮挡全页的无限旋转图标。
- 翻页和刷新保留表头、筛选和已有内容，并在表格内显示加载状态。
- 详情各区块可以独立加载；一个次级区块失败不能让整个详情空白。
- 正式提交期间锁定提交按钮，但允许查看当前输入。
- 超过正常响应时间时显示正在处理的阶段和“可安全离开，结果将在后台任务中更新”。

### 18.2 空态

空态必须区分：

| 空态 | 文案与动作 |
| --- | --- |
| 尚无业务数据 | 说明数据来源，提供有权限的新建或导入入口 |
| 当前筛选无结果 | 展示当前筛选摘要，提供清除筛选 |
| 当前角色无数据范围 | 说明数据范围限制，不显示新建诱导 |
| 尚未同步 | 说明来源系统和首次同步状态，提供任务入口 |
| 无待办 | 显示“当前没有待处理事项”，不把长期履约单当作待办 |
| 无异常 | 显示当前筛选范围内无未解决异常 |
| 功能未启用 | 生产菜单不展示该页面，不使用页面空态代替阶段控制 |

### 18.3 失败分类

| 失败类型 | 页面处理 |
| --- | --- |
| 字段错误 | 定位字段并说明修复方式 |
| 业务阻断 | 说明当前状态、阻断规则和下一责任人 |
| 权限限制 | 说明缺少页面、动作或数据范围权限 |
| 并发冲突 | 展示当前版本和用户本地版本差异 |
| 系统失败 | 保留输入，显示错误编号和重试入口 |
| 一期商城同步失败 | 保留来源快照和正式事实，进入商城同步任务、同步差异或每日核对页面 |
| 二期外部接口失败 | 保留正式业务事实，进入接口错误中心 |
| 查询模型失败 | 展示上次成功数据和失败提示，不修改正式事实 |

失败信息不得只写“操作失败”。错误编号用于排障，但不能向普通用户暴露堆栈、SQL、密钥或完整外部报文。

### 18.4 部分成功

批量、同步、回填和对账任务允许显示部分成功。页面必须分别列出：

- 成功数量；
- 跳过数量及原因；
- 失败数量及原因；
- 是否可以使用原批次续跑；
- 是否已经形成正式事实。

已成功的正式事实不得因同批其他记录失败而回退。

主责迁移不允许部分成功：一个客户迁移批次失败时，该批次没有任何主责变化可保留，
页面显示整批失败、冻结状态和原批次续跑；其他已完成客户批次属于不同原子批次。

## 19. 可访问性与可读性

- 状态不只依靠颜色，必须包含文字和图标。
- 键盘焦点清晰可见，焦点顺序与视觉顺序一致。
- 所有图标按钮提供可见名称或辅助文本。
- 表头、金额汇总和关键动作保持足够对比度。
- 错误信息与对应字段建立可访问关联。
- 表格支持放大，不因浏览器 125% 缩放丢失固定操作列。
- 动效只用于状态过渡，不延迟录入和逐条处理。
- 数量、金额、税率和日期使用等宽数字，便于纵向核对。

## 20. 两期关键页面行为

| 场景 | 第一期 | 第二期 |
| --- | --- | --- |
| 新建实物与服务销售单 | ERP 创建 | 不变 |
| 新建卡券销售单 | ERP 不提供入口，商城创建后同步 | P0-A 与维护窗口仍关闭；全部迁移完成、一期轮询停止并登记 `T` 后由 ERP 创建，固定两级审批 |
| 卡券商业字段 | 商城主责，ERP 只读 | 单据迁移前仍由商城主责；迁移后 ERP 主责，生效后通过销售变更单调整 |
| 卡券版本 | 商城快照变化形成同步版本 | 迁移前版本保留，迁移后由 ERP 变更单形成版本 |
| 卡券票款 | ERP 登记和核销，期初逐单复核 | 不变 |
| 商城执行 | ERP 不下发控制 | 生效版本自动下发执行投影；商城确认前由商城侧阻断受影响执行，ERP 只展示结果 |
| 卡号、卡密、绑定、激活 | 商城闭环 | 仍在商城闭环 |
| 商城消费 | 不进入 ERP | 关键结果事实回流，处理中间态不进入 |
| 供应商订单 | 人工采购和履约单据 | `T` 以后符合固定供应关系的消费自动创建；`T` 前订单的取消和退款仍走原人工链 |
| 卡券成本 | 标记成本未覆盖，不计算实际利润 | 逐笔标记成本口径并展示成本覆盖率 |
| 一期商城同步 | 运行基线、轮询和每日核对 | 主责迁移后停止并转历史只读 |

## 21. 页面验收清单

每个业务页面上线前必须满足：

1. 页面编号、菜单和路由与 `erp-page-map.md` 一致。
2. 当前角色、数据范围和动作权限均有明确结果。
3. 主状态与履约、票款、商城协同和异常状态分开。
4. 空态、加载、失败、部分成功和无权限均已实现。
5. 键盘可以完成查询、录入、保存草稿和逐条处理。
6. 正式动作具有影响确认和持久结果反馈。
7. 已生效事实没有直接编辑和删除入口。
8. 并发冲突不会最后写入覆盖。
9. 批量范围明确，失败可以定位和下载。
10. 敏感信息在页面、导出、操作日志和接口日志中执行相同边界。
11. 一期与二期状态下使用同一稳定业务路由。
12. 卡券销售单保持唯一明细，不出现 ERP 不负责的玩法、卡号、卡密、绑定和激活字段。
13. 利润类指标与成本覆盖率、含税或不含税口径同屏。
14. 接口结果未知时先查询原结果，不允许直接重复下单。
15. 对账和查询模型失败不修改正式业务事实。
