# 履约收货安排执行合同

## 范围与入口

1. 生效且未关闭的销售单提供独立「收货安排」入口。首次补充地址不创建销售变更单，不修改生效销售版本、采购版本、商品数量、价格、费用或付款条件。
2. 手工供应商直发、仓库发货任务提供「补充收货地址／调整收货安排」入口。当前任务处理人只能修改该任务的真实商品与数量；销售入口按销售单写权限与数据范围授权。
3. 草稿销售单继续使用原「收货安排」编辑器。采购入库、电子交付、服务履约不因缺少客户收货地址增加确认限制。
4. 供应商 API 子单使用下单时冻结的收件资料。有 API 子单的销售单不得通过本操作覆盖地址，须按供应商订单变更流程核对。

## 地址与数量

1. 收货安排按稳定销售商品保存。每条地址必须包含收货人、联系电话、最末级行政区和详细地址；地区名称由服务端生成。
2. 每项商品地址数量之和不得超过生效销售数量。未分配数量表示「待补收货地址」，不补造默认地址，不使用客户主档地址静默代替。
3. 当前任务入口按真实发货行限定范围。客户端提交品名、商品总量、已发数量或额外身份字段无效；可分配量由服务端读取。
4. 同一商品相同收件信息合并数量。一次输入最多200项商品、100条地址分配，数量最多6位小数。
5. 已发包裹的收件信息和数量冻结。调整后的完整安排必须覆盖已有冻结发货数量；地址删除、替换或减量不得侵占已发部分。已冲正的历史发货快照同样保留，不自动转成可重新分配数量。
6. 先保留仍被完整安排覆盖的现有任务地址，再按稳定发货身份为待补及调整部分分配剩余地址数量；已发快照优先占用原地址数量。禁止多个任务重复领取同一份分配数量。

## 操作与包裹

1. 销售入口展示完整安排及已发只读摘要；履约入口只展示当前任务安排。地址信息可以用于其他待补商品，不得覆盖其他商品已经登记的地址。
2. 修改已有地址须填写原因。保存影响已有包裹时，必须确认重新核对包裹；仅清除地址或商品分配数量变化的包裹，原物流号保留作为核对资料；同一任务内其他包裹和本次发货数量保持不变。来源商业版本变化时全部包裹重新核对。
3. 履约页的「待补收货地址」分组只展示商品和待补数量，不提供包裹录入。该分组本次发货数量固定为零。
4. 已有完整地址的商品允许先发。确认后，待补地址及其他未发商品进入原部分发货流程生成的后续任务，保持来源分配、预占和数量守恒。
5. 全部商品均未发时不得确认；缺地址商品的正数发货或任何包裹登记均须拒绝。
6. 取消编辑不写入。版本冲突保留输入并要求重新读取，不自动覆盖其他人的修改。保存后刷新销售安排、履约任务、工作台和相关采购查询；当前履约页重新加载本任务。

## 持久化、权限与并发

1. `fulfillment_address_arrangements` 为履约领域拥有集合。当前记录 `id` 等于销售单身份，保存生效销售版本、加密安排、更新人和原因；每次成功写入同时保存 `history:<销售单>:<版本>` 加密历史记录。
2. 集合须存在 `uk_fulfillment_address_arrangements_id` 唯一索引。收件资料只在授权接口解密；调试输出、普通审计描述及迁移输出不得包含收件人、电话或地址。
3. 销售接口复用 `sales_order:detail` 读取和 `sales_order:update` 写入权限，并在命令事务内重验销售数据范围。履约接口复用 `delivery:update`，重验当前开放任务、冻结责任身份、当前处理人和完整履约执行权限。
4. 查询和保存接口分别为 `/admin/sales-orders/{id}/delivery-arrangements`、`/admin/deliveries/{id}/delivery-arrangements`，使用 GET、PUT。PUT 接收完整 `lines`、`expected_version`、`reason`、`reset_packages`；身份、数量和已发信息由服务端决定。
5. 地址安排、受影响发货草稿、开放任务版本、销售主表并发锁、加密历史及成功审计须使用同一事务执行器。任何失败均不得形成部分成功。
6. 客户端版本同时绑定销售生效版本、销售主表版本、安排版本及当前任务版本。保存草稿、确认发货与地址修改共用销售主表写锁。旧页面不得覆盖新地址或新的发货进度。
7. 新生效销售版本不得静默沿用旧版安排。必须读取当前商品后重新核对；已发快照仍须通过覆盖校验。旧发货记录缺少可核对的地址分配时拒绝自动猜测。

## 上线与回滚

1. 发布前执行 `backend/scripts/migrations/20261105-fulfillment-address-arrangements.mongosh.js` 默认只读核对；批准发布后设置 `APPLY_MIGRATION=true` 创建唯一索引。禁止回填历史收件资料。
2. 新字段 `DeliveryDestination.pending_address` 缺省为 false，旧完整地址快照保持可读。
3. 前后端配套发布。开发验证不连接真实 MongoDB，不运行迁移。
4. 产生独立收货安排或待补地址快照后，禁止回退到忽略这些资料的旧写入端。回滚只能停写并前向修复，或先提供兼容读取、数量保护及地址校验版本；禁止删除安排或历史来模拟回滚。

## 验收

1. 销售未填地址，分别从销售和当前履约任务补齐；原任务不重建即可登记包裹和确认发货。
2. 两商品中一项缺地址，先发另一项；后续任务保留缺地址商品，补齐后可继续发货。
3. 同商品两个任务不得重复占用地址数量；同任务多个地址、同地址多个商品均保持数量守恒。
4. 已发部分不得删除、改址或减量；剩余部分允许调整，正式详情和客户验收仍读取原已发快照。
5. 权限不足、非当前处理人、跨任务伪造行、重复身份、超量、负数、无效地区、缺收件资料、过期版本及缺少包裹重核确认均拒绝。
6. 发布验收须覆盖真实事务回滚、并发保存与确认、源版本变更、销售与采购任务联动以及桌面窄窗口操作。静态构建、领域单元测试和编排测试不得替代真实环境验收。
