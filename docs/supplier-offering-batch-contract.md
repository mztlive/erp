# 供应商供给批量配置合同

## 1. 适用范围

1. 批量操作分为追加价格与条款修订、更新可供状态与数量两类。两类命令不得混用。
2. 每批必须包含 1–100 条已有供给。列表勾选后打开批量维护 Dialog，不提供新增行、供应商切换或文件导入。
3. 批量维护不得创建商品或供给，不得修改供给关联的供应商、SKU 或供应商订货编码。
4. 价格、费用、税率、数量使用十进制字符串。数量空白表示未提供，`0` 表示明确为零。
5. 批量建立供给统一使用商品页的 16 列联合导入，执行 [商品与供给导入合同](product-import-contract.md)。该入口按显式供应商字段原子建立商品、SKU 与供给，行数和文件限制独立执行。单条添加供给继续保留。
6. 询价内部报价和反馈不执行本合同的通用条款修改。限定询价及需求行的专项报价独立保存、按精确版本被关联采购消费，不进入其他客户的通用推荐。更新通用供给必须显式执行本合同规定的维护命令。

## 2. 入口与权限

| 入口 | 操作 | 权限 |
| --- | --- | --- |
| 供应商供给列表勾选当前页记录 | 批量调价与条款 | `supplier_offering:update`；界面另要求 `supplier_offering_cost:detail` |
| 供应商供给列表勾选当前页记录 | 批量更新可供情况 | `supplier_offering_availability:update` |

- 勾选只作用于当前页记录；列表结果集合或顺序变化时不得沿用上一页勾选。
- 不提供商品列表或供应商供给页头的批量添加入口；商品列表不保留仅用于批量添加的勾选栏。
- 供应停止核对任务模式不提供批量操作。
- 服务端逐行复用单条用例的数据范围、维护责任、供应商资格、来源和版本检查；界面权限不能替代服务端授权。

## 3. Dialog 操作要求

1. Dialog 必须保留固定标题和操作区，正文独立滚动。宽表仅在表格容器内横向滚动。
2. 公共设置只应用于勾选且可编辑的行。默认操作为补齐空白，已有值保持不变。
3. 覆盖已有值前必须显示确认。未填写的公共字段不得清空行值。
4. 可供状态默认保持每行当前值；数量默认保持当前值。明确选择“数量未提供”后，确认覆盖才可清空数量。
5. 两种价格相同可逐行或对勾选行设置。启用后集采价跟随代发价；取消后允许独立编辑。
6. 条款生效与失效日期在行内展开，可供数量在可供更新模式维护，不打开第二层编辑 Dialog。
7. 提交前必须显示本次实际处理行数。异常行只能由用户明确取消勾选；不得静默跳过。
8. 服务端版本冲突时，用户可确认重新读取异常行。重新读取必须替换为最新内容，重新校验后才可保存；不得仅替换版本号而保留未经核对的旧条款。
9. 成功行必须锁定。失败行保留输入、提示原因，后续提交只包含尚未完成的勾选行。

## 4. 粘贴与结果导出

- 表格支持从当前单元格开始粘贴 TSV 多行多列；保留引号内的分隔符和换行。
- 超出当前表格范围或包含锁定行时，整次粘贴必须拒绝，不得截断数据。
- 粘贴仅作用于当前模式可编辑的价格、税率、起订量或数量单元格，不新增行，不改变供给身份。
- 日期使用 `YYYY-MM-DD`，失效日期留空表示长期有效。配送范围继续通过供应商配送模板设置。
- 不提供供给专用 Excel/CSV 模板下载、文件解析或 SKU 匹配导入。
- 未完成明细可导出为 CSV；导出必须防止单元格内容被表格软件识别为公式。

## 5. 批量接口

| 方法与路径 | `rows[].input` |
| --- | --- |
| `POST /admin/supplier-offerings/batch/revise` | `{ offering_id, command: 单条修订请求 }` |
| `POST /admin/supplier-offerings/batch/availability` | `{ offering_id, command: 单条可供更新请求 }` |

公共请求结构：

```json
{
  "validate_only": true,
  "rows": [
    { "row_id": "稳定行标识", "input": { "单条命令字段": "按对应写入合同提供" } }
  ]
}
```

- `validate_only=true` 只校验并恢复已有成功回执，不执行新写入。
- `validate_only=false` 仍须重新校验整批；只要存在预检失败行，就不得开始新的写入。已完成命令的回执仍须返回。
- 容器内禁止重复行标识、重复命令键和重复供给身份；修订与可供更新禁止同一目标出现多次。
- 不注册批量新增路由；`supply_batch` 后台任务仅接受 `revise` 和 `availability`。原 `create` 模式不得提交、执行或恢复写入。
- 每行复用单条用例的独立事务，供给事实、审计和成功回执维持原原子性。批次整体不提供全部回滚语义。
- 条款修订必须携带 `expected_revision_no`；批量可供更新必须携带 `expected_version`。
- 商业条款修订不得修改可供数量；可供更新不得追加商业条款修订。
- 批量命令键须按当前操作人隔离。原请求内容及键相同的重试必须恢复原成功结果，不得重复写入。

响应为标准 API 信封，`data.rows` 按请求顺序返回 `row_id`、`status`、`message`、`result`：

| `status` | 行语义 | 客户端操作 |
| --- | --- | --- |
| `READY` | 当前校验通过，未执行新写入 | 可编辑；提交时再次检查 |
| `INVALID` | 预检失败，整批未开始新写入 | 保留输入并修正，或明确取消勾选 |
| `SUCCEEDED` | 写入完成或恢复到持久化回执 | 锁定，不再次提交 |
| `FAILED` | 单行操作明确失败 | 保留输入，修正后重新校验 |
| `UNKNOWN` | 无法确认提交结果 | 锁定原命令，仅允许原内容、原键重试确认 |

## 6. 中断与恢复

1. 发出写请求前，客户端须在当前账号、当前操作类型的浏览器会话内保存本次完整提交内容。无法保存恢复记录时不得发起写入。
2. 网络中断、响应丢失及无法确认的服务错误不得直接显示为“未保存”。受影响行必须进入待确认状态。
3. 待确认行不得更改内容或生成新命令键；点击“确认待定结果”必须复用原命令，服务端优先恢复已有成功回执。
4. 待确认行可以关闭并保留记录。同一浏览器标签页重新打开对应操作时必须恢复；页面刷新可恢复，关闭整个标签页、清理会话数据或更换设备不在客户端恢复保证范围内。
5. 存在待确认行时，不得因其他勾选行完成而自动清除恢复记录。
6. 仍无法确认的行保持锁定，不得通过忽略错误自动重建。完成全部勾选行且没有待确认行后，清除恢复记录、提示成功并刷新供给和商品查询。

## 7. 发布与验收执行要求

- 发布前须处理完旧批量新增任务及其待确认结果；旧新增草稿须改用商品导入或单条添加，禁止将原新增输入转换为修订命令。已有供给、条款、可供数据与审计记录不得删除。
- 后端仅执行库单元测试；覆盖容器限制、主体隔离、整批预检阻断、成功回放和部分失败保留。
- 前端执行 lint、类型检查和构建，使用隔离样例检查粘贴、公共设置、异常提示、失败重试、网络中断恢复和窄窗口。
- 真实服务恢复后，使用授权业务数据分别验收修订和可供更新的写入、审计、版本冲突及成功刷新。商品导入与单条新增按各自合同验收。隔离样例结果不得代替真实接口验收。
