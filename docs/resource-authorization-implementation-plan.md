# 统一资源授权实施规划

版本：1.4　日期：2026-11-06　状态：待实施

本规划规定[统一资源授权设计合同](resource-authorization-design.md)的实施顺序、代码责任、阶段交付与验收门槛。业务规则以设计合同及[98 项 Q&A 执行清单](resource-authorization-qa.md)为准；数据范围适用性以[设计合同第 3.6 节](resource-authorization-design.md#36-数据范围适用表)为准。

当前仅交付规划文档，不表示代码、数据库迁移、业务接入或生产切换已经完成。P1–P7 均为待实施；必须先完成 P1 的接口与判定内核，再按依赖推进后续阶段。

## 1. 实施边界与现有基础

### 1.1 强制执行规则

1. `erp-identity` 负责唯一的访问权限判定、授权存储及统一查询约束。业务调用统一能力，不自行解释角色、部门、所有者、审批人等放行规则。
2. 业务领域继续维护当前所有者、固定部门、关联、版本、业务状态及历史事实；工作流维护任务分配、状态、代次与职责分离。授权处理器不得修改这些业务事实。
3. 各业务领域通过本域窄 Port 消费授权能力，由组合根装配到 `erp-identity`。编排与 ReadModel 按既有依赖规则调用；不得新增业务领域间依赖或恢复跨层转发 façade。
4. 保留现有账号、认证、角色、Casbin 与显式功能目录基础，按目标规则调整功能合并及失效机制。不得另建一套功能权限目录。
5. P1–P5 可交付代码及未切换的接入能力。生产访问路径只能在 P6 验收完成后由 P7 切换；不得为提前使用未完成的新能力合并新旧授权结果。
6. 每个资源必须登记全部访问入口和来源生产者，按完整资源边界切换。不得按页面、单一路由或部分人员拆出含义不同的权限规则。
7. 阶段验收须区分规则单测、静态检查、真实数据库与并发、浏览器、迁移和生产证据。缺少证据的项目保持未验收，不以“代码已完成”代替。
8. 仅单据类、客户资源类启用人员数据范围。供应商、商品、供给、仓库及其他公共资料和系统配置只接统一功能检查，不新增所有权、个人公司/部门/单对象授权或范围事件。任务、文件、外部会话等保留登记上下文；普通业务附件具有独立所有权及指定附件授权入口，不开放通用公司/部门范围。
9. 自动授权按设计合同第 2.2–2.3 节落实到 `crates/orchestration/erp-resource-grants/`。Rust 策略实现授权语义，数据库保存登记、版本与运行状态；业务参数来自所属领域配置，第一版不建设脚本、表达式语言或通用规则编辑器。策略计算不得替代 `erp-identity` 的统一访问判定。

## 2. 统一接口交付合同

### 2.1 调用入口

下列名称是接口职责标识，不表示现有方法已实现。P1 必须确定实际服务入口、类型、签名、错误和可见性，并同步更新本表。后续业务只能使用已交付接口或指向这些接口的窄 Port。

| 接口职责 | 调用输入 | 必须输出及约束 |
| --- | --- | --- |
| 单资源及创建入口授权 | 已认证主体、服务端登记的入口、目标资源定位、调用方 `Executor` | 返回绑定主体、入口、资源、动作及事实版本的判定结果；创建不存在的新对象时按入口检查功能与必要已有容器，不要求新对象已有授权 |
| 复合操作授权 | 同上，附本次业务目标定位 | 入口登记确定全部必需功能、资源与动作；可信关联经事实 Port 核实，调用方不能删减资源检查项；任一必需条件失败即拒绝 |
| 集合访问约束 | 已认证主体、登记的集合入口、必要上下文、`Executor` | 根据资源分类返回受限范围或明确的公共资料无人员过滤结果；区分资格不足、受限空范围与公共访问，不以公司 ACL 模拟无范围；分页前约束 |
| 输出字段资格 | 已获资源访问结果、登记的输出投影、`Executor` | 返回当前允许的字段集合及版本；敏感功能不生成独立数据范围，附件仍是独立资源动作 |
| 授权解释 | 有权查看解释的主体、目标判定或来源定位 | 返回受控的允许/拒绝原因、来源与版本；不能泄露无权业务内容，不能作为执行凭据 |
| 来源治理与进度 | 治理主体或有权查看关联进度的主体、来源定位、登记命令 | 支持个人配置、来源终止、重算及受控进度；治理权限不隐含业务读取范围，终止保存成功与撤权收敛分别表达 |

服务端入口登记必须明确功能集合、是否需要数据范围、适用的数据动作、目标解析规则、必要关联资源、输出字段和即时约束；公共资料不补造数据动作。调用方不得用任意权限字符串替换入口要求，不得提交自行拼装的所有者事实或授权成功标志。

资源目录必须登记 `requires_data_scope` 及上下文约束；只有单据和客户资源可开启数据范围。公共资料无需数据授权并不等于任何未知资源默认公开；未知分类拒绝。涉及公共资料和受限单据的复合操作按目标分别判断。

### 2.2 事实与查询边界

1. `erp-identity` 消费的事实 Port 按资源分类返回身份、必要关联及可比较版本；受限单据/客户统一返回 `owner_id`、`business_org_unit_id`、`ownership_version`，字段与迁移执行第 5.2 节。任务返回当前分配；公共资料不要求授权所有权事实。普通业务附件返回当前所有者、归属版本、内容版本及绑定关系；材料与历史资源返回固定版本；外部会话返回当前有效范围及凭证代次。
2. 事实读取由资源拥有领域的窄查询能力实现，跨域事实在允许的组合层接线。事实 Port 不重复执行同一授权查询，不通过公开详情接口取事实，不直接泄露完整业务对象。
3. 授权内核决定查询范围及来源组合；业务仓储或 ReadModel 仅编译、组合并执行查询。涉及授权存储的查询协议必须通过拥有领域公开能力接入，不得直接读其私有集合。
4. P2 按第 5 节实现权限感知查询：统一约束编译、公司/部门规则、逐来源对象授权、查询计划、索引及一致性上下文。必须验证单资源判断与查询结果等价，不得以业务层先取一页再过滤或无限拉取授权 ID 替代。
5. 写入授权重验与业务读取复用同一 `Executor`。所有权移交和任务办理必须通过条件写入或等效并发控制检测责任、版本及分配变化；移交还须覆盖原所有者名下绑定附件，并检测任务/附件绑定集合变化及共享附件归属冲突；只在事务开始检查一次或只检查已读任务版本不满足要求。
6. 查询结果、缓存、游标及导出产物必须绑定必要的身份、功能、组织、归属及授权版本。版本失效后按设计合同重算或重验，不永久复用此前授权结果。

### 2.3 授权与业务条件分工

| 检查 | 唯一负责方 | 业务调用方职责 |
| --- | --- | --- |
| 身份有效、功能并集、资源数据依据、字段资格 | `erp-identity` 授权模块 | 调用接口并遵守结果，禁止自行补放行 |
| 所有权、任务分配是否提供已登记访问依据 | `erp-identity`，经可信事实 Port | 所属领域维护事实与版本，不自行将关联关系解释为权限 |
| 当前办理人、分配代次在提交时仍有效 | `erp-workflow` 的条件校验与写入 | 使用当前分配提交，拒绝转派、完成或取消后的旧请求 |
| 状态、金额、业务版本、职责分离、流程迁移 | 所属业务与工作流领域 | 授权通过后继续检查，失败时停止命令或整体回滚 |
| 查询、分页、统计和实际输出 | 所属仓储、ReadModel、输出入口 | 消费统一范围及字段结果，不扩权、不遗漏重验 |

### 4.2 必须验证的规则

1. 角色甲有创建、角色乙有提交，合并后可满足两项功能；撤掉其中一个角色时按其他有效角色重新判断。
2. 普通角色不产生数据范围；个人部门来源不得作为所有权或其他授权的上限；不同来源不能跨资源拼接动作。
3. 当前所有者无需额外 ACL，移交后创建人身份不提供残留权；其他独立来源继续成立。
4. `update` 包含同选择器 `read`；普通导出检查 `read`，任务转派检查任务 `read` 加独立功能，均不生成额外数据动作要求。
5. 单据读取支持登记的任务基本信息查看，不扩展到任务办理、材料或附件；内建 `root` 不能绕过功能及任务办理资格。
6. 不存在的新对象按登记的创建要求判定；未知入口、动作、资源类型或缺失必需事实必须拒绝或返回可追踪错误，不默认全公司范围。
7. 同一稳定单据身份覆盖当前与全部历史版本；固定快照仅覆盖明确版本；新版本不能恢复已终止来源。
8. 有供应商/商品查看功能但没有任何个人范围时，可读取公共资料；无维护功能不能修改。相同账号读取无依据的采购单仍拒绝，公共资料访问不能传播到关联单据。
9. 公共资料授权判定不依赖所有者、部门或个人授权集合，不生成全员公司 ACL。任务、附件、通知及外部会话即使不设人员范围，仍须满足分配、指定内容及身份绑定约束。

10. 授予与撤销须具备对应治理功能及当前资源、动作资格，禁止自授；授出期限可超过自身期限，授权人后续失权不终止合法授出的独立来源。
11. 任务派生查看走任务上下文，不把任务误标为需要人员范围；普通附件绑定后保留所有权，单据所有者不能读他人附件，内建 root 的普通附件读取特例仍检查功能。

### 4.3 退出门槛

上述规则通过调用真实生产内核的库单测；接口、事实来源及依赖方向明确；无直接跨业务领域依赖。尚未完成的持久化、策略消费和真实业务查询必须明确标为 P2 以后工作。P1 不以改造全部业务调用方为完成条件，也不得以仅新增空接口和数据结构声明完成。

## 5. P2：授权存储、治理与查询

### 5.1 工作包与实施边界

本阶段交付面向已登记 ERP 资源的权限感知查询能力。`erp-identity` 决定授权语义；所属仓储或 ReadModel 通过公开查询协议编译、组合并执行 MongoDB 查询；数据库负责索引访问、关联、排序及聚合。不得新增独立权限内核、允许客户端提交可执行条件，或建设任意资源及脚本可扩展的通用查询语言。

1. 在 `erp-identity` 为受限单据及客户建立个人公司/部门/指定资源来源，并建立必要上下文授权、稳定来源、终止事实、版本、审计及进度的实体、仓储与索引。公共资料不保存人员数据范围；归属不生成重复 ACL，独立审批来源不因所有权重叠而删减。
2. 交付管理员个人授权、撤销与来源终止的用例，按设计合同第 3.3 节检查治理功能及操作者当前资源/动作资格、禁止自授，并保存授出时资格证据。涵盖指定附件授权及 A50 历史来源终止；期限可超过操作者权限期限，已合法授出来源不依赖授权人后续资格。配置事实保存与访问集合生效分别记录；运行期发布和撤销接入 P3，不以直接改集合绕过来源处理。
3. 实现单资源授权、集合约束、复合检查与字段资格；查询编译仅做存储映射，统一范围用于列表、数量、汇总及导出。销售单先交付第 5.4 节语义基准及第 5.5 节查询计划，通过有界数据用例比对单资源结果和集合结果。
4. 部门范围使用固定部门 ID 与当前组织树；个人配置部门不随调动改变。组织、角色、账号、来源及授权版本变化必须进入缓存和游标失效合同。
5. 输出数据库字段、索引及迁移设计，明确唯一键、来源差异清理、有效期主动检查和大范围查询路径。TTL 不承担即时失效语义。
6. 身份域提供接收来源完整应有集合的差异应用能力，校验资源动作、事实版本、来源终止及策略启用代次，计算与本来源实际集合的差异。下层步骤接收 `Executor`，由授权用例控制独立事务，原子保存授权、批次、审计及成功进度；普通业务接口不取得写授权集合的能力。
7. 通用人员范围 API 和页面只接受需要范围的资源；指定附件授权按独立登记上下文入口执行，不开放附件公司/部门范围；拒绝供应商、商品、仓库等资料的个人范围配置。公共资料查询不得因无范围而返回空集，也不得保留旧部门/仓库范围过滤。

### 5.2 统一所有权与 MongoDB 存储

#### 5.2.1 业务归属字段

需要所有权授权的单据、客户必须统一保存并输出下列事实；字段所属领域继续负责写入，授权领域不得成为业务归属的另一份事实来源。

| 字段 | 必须语义 |
| --- | --- |
| `owner_id` | 当前所有者的账号 ID；类型为统一账号 ID，不能存员工名、部门 ID、创建人或任务办理人 |
| `business_org_unit_id` | 按创建入口确定的固定部门 ID：人工创建取创建人、导入取发起时部门；应收/应付及供应商履约订单取生成时指定责任人的部门；调动、移交均不修改 |
| `ownership_version` | 当前对象的单调所有权版本；与 `owner_id` 在同一业务事务中更新，不能替代业务内容版本 |

事实 Port 同时返回稳定资源类型和 ID。数据库字段同名不授权 `erp-identity` 直接读取其他领域集合，单资源事实仍经可信 Port 获取；列表直接编译统一字段条件，不先读取全部对象的所有者。

销售单的 `sales_owner_user_id` 等存量字段必须逐资源核对语义：确实表示当前所有者的，迁移为 `owner_id`；表示独立销售责任、创建人或历史归属的，保留其业务含义，不自动作为所有权依据。目标实现只保留一份权威所有者；迁移期间的读写兼容、回填、索引与切换步骤须显式登记，禁止长期双字段分别决定权限。

公共资料不因统一字段规范新增所有权授权。任务继续使用实际分配事实及分配代次，不能将办理人改名为 `owner_id` 后套用单据规则。

普通业务附件另存 `owner_id`、`ownership_version` 及上传历史，由文件资产领域维护；不新增附件部门字段或范围配置。多单引用同一附件身份，移交由编排在原业务事务中条件更新唯一所有者，并使所有引用入口缓存失效。冻结引用固定内容版本，归属版本不改写内容。

应收、应付和供应商履约订单的创建命令按设计合同第 1.5 节落实指定责任人及生成时部门。责任解析失败阻止本次触发操作；应收/应付与触发业务原子提交，供应商外部调用保持事务外。其他自动对象保持逐类型待登记，不用统一默认所有者填补缺口。

#### 5.2.2 核心集合及记录粒度

以下名称为目标存储协议；业务集合仍由所属领域维护。公司/部门与对象授权在逻辑上均属于 `ResourceGrant`，物理拆分不得产生两套授权规则。

| 集合 | 记录粒度与用途 |
| --- | --- |
| `sales_orders` 等业务集合 | 一条稳定业务对象；保存统一归属字段、业务筛选字段及业务版本，不嵌入无限增长的可见人员数组 |
| `auth_scope_grants` | 一个来源向一个主体授予某资源类型的一个动作、一个公司或部门范围；大范围不展开为逐单授权 |
| `auth_object_grants` | 一个来源向一个主体授予某资源的一个动作、一个明确选择器；管理员指定与审批来源分别保存，查询时按有效来源取并集 |

两类授权均须保存 `source_id`、`subject_id`、`resource_type`、单值 `action`、`valid_from`、`valid_until`、`state`、`constraint_kind` 及结构化约束、`batch_id`、`applied_version`、`policy_epoch`。来源与 checkpoint 保存对应的事实版本组合。`ACTIVE` 只表示已完整发布的授权，未就绪批次不得进入有效查询。

`valid_from`、`valid_until` 使用统一 BSON Date 精度；无截止时间须显式保存 `valid_until: null`。集合校验及发布校验必须保证必需字段和类型完整，`constraint_kind = none` 时约束必须为空。缺少起止字段、未知状态、未知选择器或未知约束不得解释为无限期、全范围或无条件允许。有效时间统一为 `valid_from <= evaluated_at < valid_until`，无截止时间只省略右侧比较。

| 集合 | 专属字段与唯一约束 |
| --- | --- |
| `auth_scope_grants` | `scope_kind` 取 `company` 或 `department`；`scope_id` 分别为固定标识 `*` 或明确部门 ID。唯一键为 `(source_id, subject_id, resource_type, action, scope_kind, scope_id)` |
| `auth_object_grants` | `resource_id` 为稳定对象 ID；`selector_kind`、`selector_key` 区分完整对象、固定版本及已登记子资源选择器。完整单据使用 `resource / all_versions`。唯一键为 `(source_id, subject_id, resource_type, resource_id, action, selector_kind, selector_key)` |

完整销售单读取的两种记录示例：

```javascript
// auth_scope_grants：一个部门即使包含百万张单据，仍只保存一条范围。
const scopeGrant = {
  source_id: "ADMIN_SCOPE_001", subject_id: "U1",
  resource_type: "sales_order", action: "read",
  scope_kind: "department", scope_id: "D10",
  valid_from: ISODate("2026-11-01T00:00:00Z"), valid_until: null,
  state: "ACTIVE", constraint_kind: "none", constraints: {},
  batch_id: "B1", applied_version: 3, policy_epoch: 1
};

// auth_object_grants：同一人同一单据的不同审批、管理员来源分别保存。
const objectGrant = {
  source_id: "APPROVAL_EXECUTION_88_U1", subject_id: "U1",
  resource_type: "sales_order", resource_id: "SO1001", action: "read",
  selector_kind: "resource", selector_key: "all_versions",
  valid_from: ISODate("2026-11-01T00:00:00Z"), valid_until: null,
  state: "ACTIVE", constraint_kind: "none", constraints: {},
  batch_id: "B2", applied_version: 5, policy_epoch: 1
};
```

稳定来源键不得包含会随重算变化的状态版本。重复处理按来源唯一键及版本幂等；撤销只处理本来源。不得因当前所有权或公司范围已覆盖而删除独立审批记录，也不得以一个不可解释的布尔值覆盖不同有效期、不同约束的来源。

在线集合保存已发布查询所需记录；已终止来源的历史差异保留在审计及终止存储中。仍然有效的长期审批授权必须保留，不能仅按年龄归档出可见集合。TTL 只承担获准清理，不承担有效性判定或终止事实保留。

#### 5.2.3 组织关系与配套存储

| 记录 | 必须合同 |
| --- | --- |
| `org_closure` | 当前组织树的可重建查询投影，保存 `org_version / ancestor_id / descendant_id`，包含部门自身；三字段唯一 |
| 组织版本发布记录 | 新组织树及闭包准备完成后整体发布；禁止新树已声明生效而查询仍使用旧闭包，禁止混用两个版本 |
| 授权来源及终止记录 | 稳定来源身份、事实版本、策略代次、终止版本与原因；A47 与 A50 独立终止，快照事实不删除；终止保存成功不等于授权已收敛 |
| 管理员配置事实 | 授出人及授出时资格/版本证据、接收人、选择器、动作、期限与原因；操作提交时重验资格，之后不以授出人失权撤销接收人来源 |
| `auth_subject_versions` | 按 `(subject_id, resource_type)` 保存已发布额外授权的单调版本；来源差异、审计、checkpoint 与版本在同一授权事务发布 |
| Outbox、授权任务及审计 | 复用设计合同第 4–5 节的可靠投递、进度、幂等、对账和历史保留约束 |

部门授权按固定单据部门与当前组织闭包匹配；组织调整不重写历史单据部门，不将祖先路径作为每张单据的授权事实。授权部门可在受控组织规模内展开为部门 ID；必须登记展开上限，超限使用组织关联计划或显式拒绝，不能截断后声明范围完整。禁止展开全量销售单 ID。

### 5.3 集合约束与查询编译

接口须使用类型区分 `Denied`、受限集合及公共资料访问。受限集合至少表达以下语义，具体 Rust 类型由 P1 交付：

| 内容 | 生产与消费要求 |
| --- | --- |
| 主体、入口、资源类型、数据动作 | 来自认证及服务端登记；调用方不能用请求参数改写 |
| 所有权条件 | 按登记资源动作确定是否启用 `owner_id = subject_id`，不能无条件为所有动作添加所有者放行 |
| 公司、部门范围 | 合并当前有效来源并保留必要约束；部门展开绑定组织版本，公司完整覆盖必须有明确证明 |
| 对象授权存在性条件 | 指定主体、类型、动作、完整对象/固定版本选择器、状态、有效期及本来源约束，不能仅检查存在任意授权行 |
| 输出字段 | 来自当前字段资格；无资格的金额或敏感统计不得进入输出 |
| 查询上下文 | 主体/功能版本、授权版本、组织版本、必要归属与业务查询版本、`evaluated_at`、下一有效期边界、数据库快照、筛选与排序指纹 |

业务调用方只提交已规范化的客户、状态、日期等筛选与允许的排序分页参数。排序白名单、页大小上限、游标校验及执行时限由服务端入口登记，不能由客户端覆盖。授权约束与业务筛选必须通过 `$and` 或等价关系组合；各允许来源通过 `$or` 或去重并集组合。用户筛选中的 `$or` 不能覆盖授权 `$or`，业务筛选只能缩小授权集合。

`erp-identity` 负责来源组合与条件含义；存储适配层仅进行已登记选择器及字段的机械编译，不重新解释“审批人可读”等业务关系。涉及 `auth_*` 集合的名称、字段及查询片段由授权域公开读取协议提供，组合层按仓库边界装配；业务仓储不得硬编码身份域私有集合协议。权限查询不实时遍历审批实例、任务历史或审计流水。

普通受限单据、客户的完整读取计划必须满足同一等式；任务及受限内容按各自登记上下文编译，不能漏掉已登记的任务查看关系，也不能借该关系加入完整源单据读取。公共资料使用明确的无人员范围约束，不套用下列读取集合：

```text
Readable = CurrentOwnership UNION EffectiveScopeGrants UNION EffectiveObjectGrants
Matched = Readable INTERSECT RegisteredResourceBoundary INTERSECT BusinessFilter
Page = StableSort(Matched) 后的游标页
Count = CountDistinctResource(Matched)
Amount = SumBusinessAmountPerResource(Matched)
Export = Matched 的受控分批输出
```

`RegisteredResourceBoundary` 包含所属资源登记的软删除等边界，不引入本项目未定义的租户过滤。单条详情使用相同数据动作和上下文，对目标稳定 ID 判定；不带列表业务筛选。列表、详情、导出仍分别检查各自入口功能，不以数据范围等价取消入口差异。

### 5.4 销售单 MongoDB 基准管道

本节为“无完整公司范围、当前所有权与部门范围及多个对象授权同时存在”的语义基准。查询先证明身份、列表功能和输出字段资格，再在同一查询上下文解析有效范围。部门 ID 只能来自该上下文中的有效范围与当前组织树，不接受客户端提交已授权部门。

以下模板仅适用于本次完整单据读取来源无额外动态条件的情况，`constraint_kind = none` 必须由统一模块确认。存在其他已登记约束时，编译器必须生成覆盖全部有效来源的条件，并在关联内 `$limit` 前判定；不能直接套用模板而漏掉有效来源，更不能忽略约束。未知或无法执行的约束必须返回受控错误。

代码展示编译后的 MongoDB 结构，不是现有数据库可直接执行的迁移脚本。`businessFilter` 是已规范化业务筛选，`resourceBoundary` 是所属领域提供的强制边界；创建时间、删除标记等按实际 BSON 类型编译。`amount` 为业务定义的一单一行精确金额投影，`itemProjection` 为已获准输出字段。实施必须登记实际金额来源、版本、精度和币种口径，不能临时改用浮点、对授权行求和或将缺失金额默认为零。

```javascript
// queryContext 由服务端建立；范围解析与下列查询共享其数据库快照。
// access 示例：subjectId=U1，company=false，departmentIds=[D10,D11,D12]。
// 本模板已证明所有者可提供 read，且存在性查询只针对完整单据读取。
const pipeline = [
  { $match: { $and: [resourceBoundary, businessFilter] } },
  {
    $lookup: {
      from: "auth_object_grants",
      localField: "id",
      foreignField: "resource_id",
      pipeline: [
        {
          $match: {
            subject_id: access.subjectId,
            resource_type: "sales_order",
            action: "read",
            selector_kind: "resource",
            selector_key: "all_versions",
            state: "ACTIVE",
            constraint_kind: "none",
            constraints: {},
            valid_from: { $lte: queryContext.evaluatedAt },
            $or: [
              { valid_until: { $type: "null" } },
              { valid_until: { $gt: queryContext.evaluatedAt } }
            ]
          }
        },
        { $limit: 1 },
        { $project: { _id: 1 } }
      ],
      as: "_readGrant"
    }
  },
  {
    $match: {
      $or: [
        { owner_id: access.subjectId },
        { business_org_unit_id: { $in: access.departmentIds } },
        { "_readGrant.0": { $exists: true } }
      ]
    }
  },
  { $unset: "_readGrant" },
  {
    $facet: {
      items: [
        // 首次查询使用空条件；后续页使用已校验游标的严格边界。
        { $match: pageCursorFilter },
        { $sort: { created_at: -1, id: -1 } },
        { $limit: pageSize },
        { $project: itemProjection }
      ],
      statistics: [
        {
          $group: {
            _id: null,
            total: { $sum: 1 },
            total_amount: { $sum: "$amount" }
          }
        },
        { $project: { _id: 0 } }
      ]
    }
  }
];

// 事务外查询示意；事务内执行须由调用方在事务级设置 snapshot。
const options = {
  maxTimeMS: queryContext.maxTimeMS,
  readConcern: {
    level: "snapshot",
    atClusterTime: queryContext.atClusterTime
  }
};
db.sales_orders.aggregate(pipeline, options);
```

执行必须满足：

1. `$lookup` 内 `$limit: 1` 只证明存在至少一个有效来源，必须位于完整来源筛选之后。不得在主管道授权 `$match` 前添加销售单分页或以“先取一页再补齐”替代。
2. 存在性数组不得 `$unwind` 成业务行。一个人同时命中所有权、部门、管理员及多个审批来源时，主管道仍是一单一行；完整详情也用相同的数据依据。
3. 页游标只限制 `items`，不限制全量计数和金额。创建时间相同必须以唯一 `id` 决胜；排序白名单变化必须生成对应游标比较，不能只变 `$sort`。
4. 无匹配时将空 `statistics` 规范化为精确数量 0 和同精度金额 0；列表为空但统计非零可以表示游标已到尾部，不能重置真实总数。
5. 金额如果来自正式版本或明细，须按登记口径在同一快照加载，并先归约到一单一行，再进入金额聚合；不能因关联多行放大数量或金额。无金额字段资格时不生成该聚合及输出。
6. 导出复用同一授权与业务筛选定义，替换结果输出步骤；不复用只含当前页的 ID，也不将查询过程中关联出的授权记录输出给业务调用方。

`$lookup` 支持关联内筛选，但关联索引与候选量必须验证，不能假设所有者已匹配就自动跳过关联。[MongoDB `$lookup`](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/)

`$facet` 只保证分支消费相同输入，不单独保证授权与业务数据的读取时点一致。该阶段存在 100 MB 限制且不能通过 `allowDiskUse` 溢写，最终输出还受 BSON 文档大小限制；不得收集全量结果为数组，也不得将此模板认定为所有规模下的唯一计划。[MongoDB `$facet`](https://www.mongodb.com/docs/manual/reference/operator/aggregation/facet/)

### 5.5 查询计划与索引

#### 5.5.1 必须支持的执行方向

| 计划 | 适用条件 | 必须执行的步骤 |
| --- | --- | --- |
| 完整公司范围 | 当前有效来源无额外限制地覆盖目标类型、动作与完整资源 | 保留强制业务边界、筛选及字段控制；省略所有权/部门/对象授权关联，不删除其他来源记录 |
| 业务集合驱动 | 客户、日期等业务筛选可有效缩小候选量，或该主体可见比例较高 | 业务索引获取候选，数据库中完成授权存在性判断，再分页或统计；第 5.4 节为语义基准 |
| 对象授权驱动及混合合并 | 对象授权稀疏、业务候选量大 | 从有效对象授权按主体/类型/动作查起，去重资源身份并关联业务筛选；与本人/部门分支合并，在全局分页、计数和求和前去重 |

计划选择只能使用受控统计及已验证规则，不能改变授权语义。必须记录计划类型、候选量、授权匹配量、扫描与返回量；阈值通过第 5.7 节容量验收确定。不能仅因主体拥有某条带条件的公司来源就省略该来源约束。

多分支输出必须按稳定资源身份去重，或证明各分支经过排除条件已互斥后再合并；禁止直接相加所有权、部门、管理员、审批四类来源的计数和金额。应用侧不得无界收集候选 ID、执行页后权限过滤或用固定超取倍数声明结果完整。

使用 `$unionWith` 时，其结果包含重复项且顺序未定义，必须执行后续去重与全局排序；该阶段不能在多文档事务内执行。实施须按部署版本、拓扑验证事务外同快照读取或其他等价计划，不能将 `$unionWith` 直接塞入现有事务包装器。[MongoDB `$unionWith`](https://www.mongodb.com/docs/manual/reference/operator/aggregation/unionwith/)

#### 5.5.2 索引交付

唯一约束按第 5.2 节实施。下表以销售单为例给出查询索引候选；其他资源使用统一归属字段，并按登记协议映射各自业务状态、时间等字段。方向未标记的字段使用升序；不得不经测量为全部筛选排列组合创建索引。

| 集合 | 字段顺序 | 验证的查询形态 |
| --- | --- | --- |
| 业务集合 | `(owner_id, deleted_at, created_at desc, id desc)` | 本人范围、创建时间游标 |
| 业务集合 | `(business_org_unit_id, deleted_at, created_at desc, id desc)` | 部门范围、创建时间游标 |
| 业务集合 | `(deleted_at, created_at desc, id desc)` | 公司范围、创建时间游标 |
| 业务集合 | `(customer_id, deleted_at, commercial_status, created_at desc, id desc)` | 客户、状态、期间组合；缺少前缀等值条件时另行验证排序成本 |
| `auth_scope_grants` | `(subject_id, resource_type, action, state)` | 人员有效范围解析；有效期与约束仍须检查 |
| `auth_object_grants` | `(subject_id, resource_type, action, state, selector_kind, selector_key, resource_id)` | 已发布完整单据授权存在性与人员授权反查；有效期字段位置按测量调整 |
| 两类授权集合 | 来源唯一索引的 `source_id` 前缀 | 独立来源清理、幂等及修复；避免重复创建等价索引 |
| `auth_object_grants` | `(resource_type, resource_id, subject_id, action)` | 单资源治理反查，不能替代人员查询索引 |
| `org_closure` | `(org_version, ancestor_id, descendant_id)` 唯一 | 指定版本的部门及下级查询；反向匹配按实际计划补索引 |
| 主体授权版本及来源终止记录 | 主体/资源类型唯一键、稳定来源唯一键 | 查询失效及终止防恢复 |

每种允许排序须有索引支持或明确、经容量验证的排序成本。有效期包含两个方向的边界，不得假定一个复合索引消除所有剩余过滤。关联条件、类型与索引必须一致；不能只检查索引已创建便声明查询达标。

常用宽范围计数、金额聚合可使用精确增量投影，但必须证明业务筛选、授权并集去重、金额口径、版本和收敛时效一致。没有相应证明时，使用完整精确查询或显式返回受控失败，不得改用估算总数、缓存旧金额或静默收窄日期。异步统计如需提供，必须另行登记入口与快照合同，不默认改变同步接口行为。

### 5.6 版本、有效期与输出一致性

1. 查询入口建立受控上下文，在同一数据库快照中解析范围、组织关系并执行业务及授权查询。`atClusterTime` 使用 MongoDB 的快照时间戳，不能用 `evaluated_at` 的墙上时钟代替；缓存范围只有在版本与有效期均验证后才能复用。
2. 事务外同快照读取按部署版本与驱动支持使用 `snapshot / atClusterTime`，不得混用与之冲突的会话选项；事务内在调用方事务级配置读取语义。`$facet` 不是快照替代品，拆成多次列表/统计查询时仍须共享快照和授权定义。
3. 当前身份、功能及字段资格按即时合同检查，当前所有权按业务提交事实生效。输出前验证必要版本与时间边界，当前版本重验不得在原有旧快照中自证有效；须登记并验证授权变更与访问判定的并发顺序。已生效撤权、所有权变更或资格失效使旧上下文失效时，拒绝或重新查询，不能以旧快照继续放行。
4. 普通额外来源撤销按设计合同允许的时限收敛。来源差异、授权版本及进度同事务发布；撤销某来源不删除其他来源。账号、会话、功能失效不得等待该事务或 worker。
5. 已发布授权仍主动检查 `valid_from / valid_until`；授权版本未变也可能到达开始或结束时间。查询上下文和缓存必须登记下一相关时间边界，跨界后重新解析；不能只等 TTL、事件或版本变化。
6. `auth_subject_versions` 只证明额外授权状态，不能证明所有权、组织或业务金额未变。资源拥有领域须提供有界的集合归属/业务变更版本或等价可验证机制，覆盖尚未出现在当前页的资源变化。单条 `ownership_version` 仅供对象重验；禁止枚举全部命中 ID/版本计算列表指纹。销售列表现有一万条匹配版本上限不得作为目标查询能力或一致性机制保留。
7. 游标绑定主体、入口、资源动作、授权/组织/必要归属与业务版本、筛选、排序及有效时间边界；客户端不能自行更改。上下文变化后要求重建查询，不能把不同范围的页面拼接为一次完整导出。详情数据依据与同快照列表数据依据保持等价，入口功能仍分别检查。
8. 长作业不得假设数据库永久保留快照。导出与异步作业必须登记快照期限、分批策略及重启/重新生成规则；快照失效或权限变化时整体失效或按新上下文重新生成，不得删除部分行后沿用旧统计。发布与下载重新检查实际单据及字段资格。

MongoDB 快照只能在可用历史窗口内读取，长读取可能因窗口限制终止；实际版本、拓扑、驱动及会话配置必须纳入验收。[MongoDB `snapshot`](https://www.mongodb.com/docs/manual/reference/read-concern-snapshot/)

### 5.7 迁移、验证与退出门槛

P2 交付字段与索引迁移方案；P4/P5 接入对应资源，P6 核实和回填，P7 按完整资源切换。迁移须同时更新归属写入、可信事实 Port、查询字段映射、移交条件写入、索引及旧字段退出步骤。禁止以创建人、当前部门或当前待办猜测缺失的历史所有权与审批来源。

| 验收场景 | 必须结果 |
| --- | --- |
| 所有权、部门、管理员与多个审批来源重叠 | 同一单据只出现一次，数量与金额只累计一次 |
| 部门外的有效指定/审批授权 | 进入业务条件匹配的列表；不得被先执行的部门上限排除 |
| 撤销其中一个来源、重复及乱序事件 | 其他来源继续有效，旧事件不能恢复已终止来源 |
| 授权开始或到期但版本未变化 | 按时间边界重新判定，列表、详情、缓存和导出一致 |
| 所有者与审批人相同，处理器暂停后移交 | 当前归属立即变化，原审批来源持续有效 |
| 人员调动、部门移动及闭包版本切换 | 固定部门不改写，个人指定部门不随人员调动替换，查询不混合组织版本 |
| 固定版本或材料授权 | 不能通过完整单据存在性查询混入管理列表 |
| 同一快照逐条判定与集合查询对拍 | 数据依据等价；业务筛选及入口功能差异单独记录 |
| 相同排序值、跨页、空结果和游标尾页 | 稳定排序，无重复遗漏；总数和金额不被页游标截断 |
| 不同执行计划及拆分列表/统计 | 集合、计数、精确金额、导出范围一致，无来源重复累计 |
| 当前页外发生移交、撤权或业务变化 | 集合上下文按登记版本失效，不依靠全量版本枚举 |
| 治理授予/终止超出操作者范围或动作、批量自授 | 拒绝；操作提交与资格变化可检测冲突，保留审计证据 |
| 授出期限超过自身期限、授出人随后失权 | 按授出来源自身期限执行，不截断、不级联撤销 |
| 附件绑定、混合所有者移交及跨单共用 | 保留唯一附件所有权；只移交原所有者附件，所有引用共同失效，第三人附件不自动可读 |
| 非审批取消及 A50 终止并发重算 | 固定快照可恢复，来源可终止且不恢复，实体与审计保存，其他来源保持 |
| 授权查询失败、未知选择器、失效快照 | 受控失败，不回退到全公司、不返回部分结果冒充完整结果 |

容量验收至少覆盖 100 万、1000 万张销售单；人员可见范围覆盖几十张、约 1%、约 50% 和全公司；组合覆盖窄/宽日期、客户/状态筛选、允许排序、深游标页、重叠来源、长期审批增长、到期清理滞后及并发授权变更。数据分布必须记录每人有效授权量、每单来源数、组织规模、历史记录比例及读写并发，不能只用均匀随机样本。

每个查询形态须登记业务要求的响应时间与资源预算，并记录实际计划、索引、扫描键/文档数、返回数、排序/去重内存及溢写、P95/P99 延迟、统计与导出耗时、撤权收敛时限。缺少预算或实测证据保持未验收；不得以第一页快速、索引存在或库单测通过声明精确统计及千万级查询达标。真实 MongoDB 验证仍受第 11 节环境授权约束，本规划不授权执行。

P2 退出要求：来源独立建模、撤销和解释；统一字段、持久化、查询编译、字段控制、计划选择及版本协议完成；规则单测覆盖上述行为并交付可复核的索引、迁移与容量验收材料。真实数据库计划、并发和性能缺口单列，必须在 P6 对目标批次补齐后才能进入 P7。

## 6. P3：异步授权与恢复机制

### 6.1 工作包与代码归属

1. 建立授权事实事件协议和可靠 outbox。业务事件记录与业务事实共用事务；既有通知机制仅复用合适的技术能力，不承载业务授权策略。
2. 新建 `crates/orchestration/erp-resource-grants/`，同步 workspace、层次与依赖登记、边界门禁及 README。`src/policies/` 放独立纯策略类型，`src/ports/` 放本库消费的窄事实接口，`src/process/` 组织事实读取、策略计算和身份域提交。各业务领域与 `erp-identity` 不得反向依赖该库。
3. 处理器读取当前与有效历史事实、业务参数、管理员终止版本及当前策略代次，以显式时间基准计算来源完整应有集合。通过 `erp-identity` 的 P2 接口原子应用差异、审计、消费进度和必需资源发布；策略自身不得执行 I/O，不能将读取失败作为空集合。
4. 实现重复消费、旧事件迟到、事实变化、策略切换、来源终止并发的冲突处理。查询失败不能解释为空集合；管理员终止后任何重试、回填或对账只能保持该来源为空。
5. 实现待处理、处理中、重试、隔离、已收敛状态；进度查询受控，投递成功不等于授权就绪，已收敛也不等于获得权限。
6. 实现按资源、来源和策略重算、批量续跑与定期对账。遍历业务来源和已保存授权来源的并集，兼顾补漏与清理；不得重放业务命令。
7. 登记每项策略的收敛时限、退避上限、隔离条件、告警和人工恢复入口。完成崩溃点与并发故障用例设计，并分别记录库单测与真实运行证据。
8. 在 `erp-identity` 实现 `GrantPolicy` 登记与版本治理，代码显式登记可执行实现，数据库仅保存不可变内容版本、启用代次、依赖说明和状态。启停与回退同事务保存审计及重算事件；执行设计合同第 5.5 节的部署能力检查、停用清理和回退约束。
9. `apps/erp-server/src/wiring/` 装配事实 Port、策略目录与身份域服务；`src/worker/` 启动和监督投递、消费任务。通用投递机制不得依赖 ERP 业务，接线层与 worker 不承载策略。逐项登记业务 outbox 存储及其拥有方，不由授权库直接访问业务私有集合。

### 6.2 策略接口交付

P3 必须交付下列实际类型、公开方法和可见性，落点遵守设计合同第 2.2 节；通用应有集合及差异提交协议复用 P1/P2 身份域合同，不在编排库复制同义结构。

| 接口职责 | 必须交付的合同 |
| --- | --- |
| 事实加载 | 来源定位转换为类型化事实、完整版本组合及明确时间基准；当前、历史、配置与终止事实齐备；错误可分类，不泄露完整业务对象 |
| 纯策略计算 | 输入事实与策略版本，输出规范化完整应有集合及解释依据；相同输入同结果；空集合有证据，事实失败不发布部分结果 |
| 策略目录 | 稳定 ID、内容版本到 Rust 实现的显式登记，关联 A01–A50 与资源范围；未知 ID、未知版本及登记与实现不一致均拒绝执行 |
| 来源处理 | 事件、显式重算、回填和对账调用同一流程；由身份域校验版本并提交差异，冲突后重读重算，不重放业务命令 |
| 发布与清理 | 先部署支持版本，再受控启用；停用可不运行业务算法而清空本策略来源；回退使用当前部署支持的旧版本和新启用代次 |

每条规则按设计合同第 6 节登记实现位置、配置参数、事实依赖、事件生产者、来源遍历、收敛时限及验收证据。责任、组织、附件、历史分配或业务配置变化均须能定位受影响来源；不能只登记任务创建事件。A04–A06 仅保留迁移和清理登记，不生成公共资料替代授权。

### 6.3 验证与退出门槛

| 场景 | 必须结果 |
| --- | --- |
| 相同事实、策略版本、时间基准重复计算 | 集合与摘要稳定；重复应用不重复授权、不延长有效期、不重复发放审计 |
| 事实证明责任结束，或管理员终止来源 | 按生命周期输出应有集合；须清空的来源有明确原因，其他来源保持，终止来源不可恢复 |
| 事实查询失败、不完整、配置错误或版本不支持 | 分类重试或隔离，不清空已有集合、不发布部分结果、不默认放行 |
| 旧事件迟到、计算中事实或策略代次变化 | 重读当前与有效历史事实；旧结果不能覆盖已应用新结果，冲突按同一流程恢复 |
| 所有者同时为审批人，随后移交 | A47 输出完整独立来源，已有审批读取在处理器暂停时仍连续有效 |
| 策略停用且当前业务事实已无该责任 | 仍遍历已持久化来源并清理，不依赖停用算法或当前待办；事实与审计保留 |
| 混合版本处理器、回退或移除旧实现 | 不支持版本不能执行；启用前满足部署条件；回退增加代次，旧实现移除前无活动或回退依赖 |
| 事件、重算、回填和对账分别处理同一来源 | 共享真实策略和差异应用行为；对账可修复同版本缺失或多余记录，已终止来源仍为空 |

退出门槛：真实处理逻辑的规则、幂等、版本及上述发布生命周期单测通过；策略接口、版本治理、停用清理、恢复入口和登记台账交付；运行依赖和未完成的环境验收明确。库单测不得冒充真实事务原子性、并发及混合部署验证；没有真实故障恢复证据时只能标记代码交付，P6 仍须完成验证后方可切换。

## 7. P4：首条业务闭环

首条闭环固定为“客户 → 销售单 → 审批 → 开票类非审批任务 → 材料、附件及导出”。以该链验证通用能力，其他资源不得为接入方便复制授权内核。

1. 客户与销售单保存当前所有者、创建人和创建时固定部门；新增、详情、列表、编辑、提交及移交调用统一授权接口。创建销售单前核实客户查看资格，销售责任建立和结束分别驱动客户读取来源。
2. 工作流提供当前和历史正式分配事实。节点激活形成完整审批来源；转派、或签完成、撤回、驳回和取消保留读取，管理员可整体终止；后续附件变更按同一来源更新。
3. 开票类非审批任务使用受限材料；完成、取消或未办理即转派时保存固定任务信息、已有记录、材料与附件版本，异步发布不得读取后来变化的内容冒充快照。
4. 所有权移交与原所有者在该单下全部未完成任务转派、原所有者名下绑定附件移交使用同一业务事务。覆盖并发新增任务、绑定变化和共享附件移交冲突，不移交第三人的附件。不能只处理本轮选取的审批和开票类型；未接入的任务类型必须补齐，才可验收该资源的移交。任一职责分离冲突整体失败，接收人缺功能不阻止接收。
5. 接入本人待办、单据任务监督、完整详情、独立材料、历史版本和历次审批。明确当前提交与历史冻结内容，旧任务不恢复办理，历史折叠不省略权限检查。
6. 接入字段控制、附件独立所有权、管理员指定附件授权、内建 root 访问及导出清单重验；保存成功后的额外授权进度只影响缺少依据的区域，不让用户重复提交。

退出门槛：覆盖多来源叠加、同角色限制移除、处理器暂停时归属立即生效、已有审批来源在移交后连续可读、来源终止不恢复、分配并发及受限输出。该闭环必须有端到端验收用例清单；未覆盖的资源消费者仍登记到 P5，不能据此提前整体切换。

## 8. P5：按批次完成全量接入

| 批次 | 必须覆盖的范围 |
| --- | --- |
| P5.1 主数据与销售剩余入口 | 客户、合同、选品、询价按范围接入；供应商、商品、供给、仓库、公共主体目录仅接功能与字段规则，退出旧人员范围，不生成资料授权 |
| P5.2 采购、供货与履约 | 采购、供应商目录及结算、需求处理、履约、交付、库存及全部相关任务；供应商履约订单按指定执行责任人及其生成时部门归属，缺人阻止本次下单 |
| P5.3 财务与逆向业务 | 应收应付、付款、开票、对账、资金、退货退款、红票、冲销及相关材料与任务；应收应付按指定财务责任人及其生成时部门归属，缺人阻止触发业务 |
| P5.4 公共与后台入口 | 个人会话、供应商门户、回调、服务身份、导入、作业、通知、文件及导出；后台导入保留发起人和发起时部门 |
| P5.5 治理与前端收口 | 人员授权页面、角色功能配置、授权 JSON 校验/预览/应用/导出、来源终止、进度、解释与恢复页面；各业务页面错误和可见字段 |

各批次必须更新 P1 台账中的事实 Port、事件生产者、自动来源策略、全部消费者、Q&A 对应项和验收状态。共同依赖的任务、文件及关联资源随批次一并接入；不得因被列在后续批次而遗漏本批次的必要依赖。

退出门槛：设计合同的全部类型与 A01–A50 有明确实现或退出归属，Q01–Q98 有对应验证项；Q05 不实现已废止的转派撤权规则。公共资料无人员范围配置、无 ACL 生成及范围过滤；单据和客户仍受控。旧配置入口不得继续生成角色数据授权或人员上限；冻结的未知历史类型不恢复执行。

## 9. P6：影子、回填与整体验收

1. 按资源核实当前所有者、创建时部门、自动生成责任人、附件上传与移交及共用关系、历史正式分配、含取消的非审批快照、来源终止及导入发起事实。缺乏证据进入治理清单，不用当前部门、当前待办或当前对象内容猜测历史。
2. 交付可预览、分页、续跑、幂等、逐项记录失败的迁移工具。授权回填复用正式处理器，既补应有来源，也清应撤记录；迁移期间事件持续处理至收敛。
3. 影子判定只比较和记录差异，不改变运行授权结果。逐项解释新增和收缩访问，不为消除差异恢复受限客户/单据的创建人特权、同角色要求、人员上限或普通角色数据范围。公共资料退出范围过滤单列为预期变化，不回填全员公司授权；已有范围配置退出运行并保留审计。
4. 完成设计合同第 11 节的相关业务、事务、崩溃恢复、重复/乱序、版本与策略并发、查询性能、文件和导出重验。前端必须通过实际页面检查验证进度、错误、待办与历次审批展示。
5. 为每个切换批次列出全部入口、事件生产者、事实版本兼容性、缓存失效、监控阈值、迁移结果、回退步骤与执行责任。回退保留历史及终止事实，不能恢复已知越权路径。

退出门槛：目标批次未决数据、越权差异和关键验收缺口已处理；回填与实时事件收敛；实际运行证据齐备，回退可执行。未取得允许的环境验证条件时保持该项待验收，不得仅凭单测进入 P7。

## 10. P7：切换与清理

1. 按资源整体切换列表、详情、历史、工作台、材料、文件、导出、写命令及后台入口；所有来源生产者同时使用新事实与事件合同。
2. 执行版本和缓存失效，核对访问变化、授权延迟、错误原因、任务办理及导出下载；记录生产结果，不以部署成功代替访问验证。
3. 删除已切换资源的旧同角色要求、创建人放行、岗位共享、角色数据范围、个人上限、接口审批特判及重复授权路径。确认零调用后再删除共享旧能力；未切换资源不得被破坏。
4. 同步身份域、业务领域、权限配置及运行维护文档。记录每个批次的切换与回退验证状态，全部批次完成后关闭旧运行路径。

退出门槛：统一模块成为全部登记入口的唯一权限判定实现；各领域业务约束和职责分离保持有效；生产观测、旧路径清理及运行文档全部完成。
