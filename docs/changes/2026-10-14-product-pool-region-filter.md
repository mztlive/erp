## 一、需求背景与目标

配送模板上线后，同一 SKU 能否送到某地由其全部有效供给的配送模板决定，但公司商品池只能按供给"区域"自由文本筛选，销售和采购无法回答"哪些商品能送到广东省深圳市"。上线后商品池将录入几万个 SKU，筛选不能在每次查询时逐个 SKU 现算。

目标：

1. 商品池可按省、市或区县筛出能送到该地区的商品，区分全部可送与部分可送，可选是否把需另付运费的地区算作可送；
2. 几万个 SKU 下筛选仍按索引直接匹配，不随 SKU 数线性计算；
3. 筛选口径与销售地址提示、采购供给分配一致，结果允许短暂滞后但不影响下单判定。

## 二、目标用户与使用场景

- **销售**：客户在某地，先在商品池筛出能送到当地的商品再报价或选品；
- **采购**：维护模板后核对某地区的可售商品覆盖。

## 三、用户可见方案

1. 商品池"更多条件"新增"配送地区"：地区可选到省、市或区县；范围为"全部可送"（默认）或"部分可送"；可勾选"包含需另付运费的地区"（未选地区时范围与勾选不可用）。
2. 判定口径：一个地区"包邮可送"指 SKU 至少一条有效且当前可供供给代发配送或集采包邮；勾选运费另计后，集采运费另计也算可送。"全部可送"要求所选地区内全部区县可送；"部分可送"要求有可送也有不可送的区县，两者互斥。虚拟商品、线下服务和卡券不受配送范围限制。
3. 勾选运费另计时，所选地区内有只能集采并另付运费才能送到的地方的商品，列表标"需另付运费"。
4. 已生效条件标签、表头说明、导出筛选说明显示"配送地区：广东省深圳市 · 全部可送 · 含需另付运费"；地址栏记录 `deliveryRegion`、`deliveryExtent`、`freightExtra`，移除标签一并清除三项。
5. 按配送地区筛选时，"发起选品"只能从勾选的商品发起，按钮提示原因；按筛选条件生成选品册暂不支持配送地区。

## 四、边界与非目标

1. 筛选按后台预算结果匹配，通常数秒内反映供给、可供状态、配送模板变化及条款按日期生效失效；大批量变更按每轮约 1000 个 SKU 依次重算。筛选结果只作选品参考，采购供给分配与销售地址提示仍按实时事实判定。
2. 资格业务日期（`eligibility_as_of`）只影响原销售资格；配送覆盖始终按当天计算。
3. 销售选品 Dialog、选品册按筛选生成不支持配送地区。
4. 本期不改变商品池列表一次取全部结果的加载方式（见十、实施说明中的性能风险）。

## 五、验收标准

1. 模板设"深圳市南山区不配送"的 SKU：选广东省"全部可送"不命中、"部分可送"命中；选深圳市福田区"全部可送"命中；选南山区两者都不命中。
2. 两条供给分别只送广东与北京时，选广东省"全部可送"命中，选上海市两种范围都不命中。
3. 代发不送新疆、集采运费另计的 SKU：选新疆维吾尔自治区不勾运费另计时不命中，勾选后"全部可送"命中并标"需另付运费"。
4. 虚拟商品有有效供给时任何地区"全部可送"都命中；没有有效且可供供给的 SKU 任何地区都不命中。
5. 改模板、改供给指定模板、停用供给、可供状态变化或条款到期后，筛选结果在后台刷新后随之变化，无需重启。
6. 地区代码不存在或格式非法时接口返回校验错误；只传范围或运费另计、不传地区时不筛选。

## 六、方案与取舍

- **预算存 MongoDB，不用 Redis 或 Meilisearch**：难点在于何时重算而非存储；同库可共享运维、备份与 E2E 隔离，Redis 只能按键取值、无法与其他条件联合分页，Meilisearch 适合整体接管商品池搜索，应另行立项。
- **按 `updated_at` 扫描发现变化，不在各写入点埋点**：供给写入分散在后台、门户、批量导入和接口同步，集中扫描不会遗漏新写入路径；延迟复扫补上开始早、提交晚的事务。
- **压缩存储**：每档只存整片可送的最大地区与部分可送的省、市，全国可送只存一个标记，典型 SKU 只有几十个代码，可建多键索引直接匹配。

## 十、实施说明

### 实现落点

| 能力 | 位置 |
| --- | --- |
| 逐地区合并与压缩 | `erp-core` `delivery_coverage.rs`：`delivery_reach`、`DeliveryCoverage`、`RegionCoverage`、`DeliveryCoverageQuery`；销售地址提示改用同一合并规则 |
| 预算投影 | `erp-supply` `sku_delivery_coverages`（每 SKU 一条，主键为 SKU）与 `sku_delivery_coverage_state`；`SkuDeliveryCoverageStore` 提供变更扫描、待重算标记、保存与地区匹配；索引含四个地区集合、供应商、待重算与到期日，以及供给、可供状态、模板的 `updated_at` |
| 事实读取 | `erp-read-models` `catalog_center::delivery_coverage::sku_delivery_inputs`：有效且可供供给的去重政策、供应商、下次按日期变化日与商品类型 |
| 后台刷新 | `erp-processes` `DeliveryCoverageRefreshProcess` 经 `DeliveryCoverageRefreshAdapter` 接入统一后台执行器（每 2 秒一轮）：首次或口径版本升级时全量重建；即时扫描与提交余量 120 秒后的延迟复扫；到期日标记；每轮最多 5 批、每批 200 个 SKU，同批相同政策组合只算一次；保存时比对标记序号，多实例并发不会留下过期结果 |
| 商品池筛选 | `GET /admin/sellable-skus` 新增 `delivery_region_code`、`delivery_extent`（`FULL`/`PARTIAL`）、`include_freight_extra`；按投影匹配出 SKU 后并入原资格聚合的首个 `$match`，返回行带 `delivery_freight_extra` |
| 前端 | `features/master-data`：`sellable-delivery-filter-fields.tsx`、`lib/sellable-delivery-filter.ts`、筛选 Hook、条件标签、表格与卡片"需另付运费"标记、按地区筛选时发起选品须勾选 |
| 开发重置 | `reset-dev-business-data` 清目录主数据时一并清除 `supplier_delivery_templates` 与两个覆盖集合，由后台重建 |

### 未完成与后续

- **性能风险（存量）**：商品池页面按每页 100 条顺序取回全部结果在浏览器分页，且每页请求都对全部 SKU 重新执行资格聚合；几万个 SKU 时需要数百次请求。地区筛选只缩小命中集合，不解决该问题，需改为服务端分页并实测聚合耗时。
- 供给条款有效期结束日：采购与销售提示按"结束日当天仍有效"，商品池资格聚合按"结束日当天失效"，存量口径不一致；配送覆盖沿用前者。
