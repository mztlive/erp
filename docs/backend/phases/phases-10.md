## 1. 分支与职责

| 项目 | 约定 |

| 分支名 | `codex/backend-p1-10-integration` |

当前仓库没有后端工程，也没有 git-tracked OpenAPI/Swagger。`erp-client/features/**/api.ts`
和 `queries.ts` 是前端 mock/session 证据，不是后端契约或运行时实现。

## 2. 所有 worktree 的共同创建规则

创建任何 worktree 前，协调者必须先在 `main` 记录并提交统一的后端语言/版本、包命名、
格式化/静态检查基线。这个决定只解决 Phase 1～9 能否编写同一种代码，不预先确认数据库
产品或共享运行时实现。决定缺失时所有 phase 都停止，不能各自选栈。

然后把本组文档提交到 `main`，保持工作区干净，并只冻结一次基线：

```zsh
BACKEND_PHASE_BASE_SHA="$(git rev-parse main)"
git worktree add -b codex/backend-p1-01-platform-governance ../erp-backend-p1-01 "$BACKEND_PHASE_BASE_SHA"
git worktree add -b codex/backend-p1-02-partner-contracts ../erp-backend-p1-02 "$BACKEND_PHASE_BASE_SHA"
# Phase 03～10 使用同一个 BACKEND_PHASE_BASE_SHA；不得使用前一 phase 的 HEAD。
```

硬规则：

1. Phase 1～9 不能 merge/rebase 其他 phase，只能从冻结基线继续提交。
2. 每个 phase 只修改自己文档写明的独占目录。
3. Phase 1～9 不修改根构建、锁文件、入口、正式 migration、全局 API、CI 或前端。
4. 不新增临时 `common` / `shared` 作为跨 worktree 依赖；跨域只用本模块自有端口。
5. 每个分支交接前执行
   `git diff --name-only "$BACKEND_PHASE_BASE_SHA"...HEAD`；出现越权路径即不接收。
6. 每个分支交付 commit、路径清单、领域不变量、端口、测试结果、未决项和未验证层级。

## 3. 合并顺序与冲突处理

Phase 10 自身也从 `BACKEND_PHASE_BASE_SHA` 创建，按下列审查顺序 `--no-ff` 合并：

1. Phase 1 平台治理；
2. Phase 2 伙伴与合同；
3. Phase 3 供应商目录与商品池；
4. Phase 4 销售与二次确认；
5. Phase 5 采购；
6. Phase 6 履约、库存与验收；
7. Phase 7 财务；
8. Phase 8 导入与商城同步；
9. Phase 9 分析投影。

这是集成审查顺序，不是前置 phase 的开发依赖。按目录隔离设计，文件冲突应为零；出现
冲突先判断是否有分支越权，不得用“最后写入者”覆盖业务规则。

语义冲突的裁决顺序：

1. `erp-phase-1.md` 的第一期范围、主责和业务规则；
2. `erp-data-model.md` 的聚合、实体、状态和事务不变量；
3. `erp-mall-data-mapping.md` 的旧商城防腐、安全和同步规则；
4. `ui-workspaces/*.md` 的查询/命令/交互所需语义；
5. 前端现有类型和 mock 只作为调用方差异证据，不能反向改业务规则。

## 4. 技术与物理设计硬门

后端语言/版本已经在冻结基线中确定。开始真实 DDL 和接线前，还必须在本分支记录并通过
评审：

- Web 框架、异步运行时和最终项目布局；
- 目标数据库产品/版本、隔离级别、锁模型、连接池和迁移工具；
- 检查约束、部分唯一、有效期不重叠、延迟约束和并发锁的实现方案；
- 金额/单价/数量定点类型与统一舍入函数；
- 外部身份规范化、内容指纹、业务事实键和请求幂等键算法；
- 文件/密钥/敏感字段加密、HMAC、日志脱敏与配置来源；
- 后台任务、outbox 投递、重试/死信、结果未知恢复和监控方案；
- 部署运行方式、健康检查、备份恢复和环境隔离。

`erp-data-model.md` §13 明确要求这些能力在具体数据库 DDL 前完成。当前文档没有确认某个
数据库产品，Phase 1～9 的 `persistence-spec` 不能直接当生产 migration。

   供应商 SPU/SKU、SKU 映射、多供应商供给和公司商品池全部属于一期；一期不对接 API
   供应商。二期仅增加 API 连接、自动同步和 API 变化处理，并复用一期同一套目录、映射、
   供给与商品池实体。该决策已同步到 `erp-data-model.md` 表目录与阶段矩阵、
   `erp-ui-design.md` W21 阶段矩阵、W21 工作面和 `erp-phase-2.md` 增量范围。
2. **outbox 阶段归属**：`erp-data-model.md` §5.4 将 outbox/inbox 列为二期扩展，§10
   又要求一期启用 outbox 基础。必须明确一期所需表、事件类型、投递范围和调度器；
   二期 inbox、双向事实和通用对账保持关闭。
3. **W18 任务登记自相矛盾**：正文称正常导入确认类型未登记并 blocker，验收项又有已完成
   表述。未真正写入权威任务注册表前按未登记处理。
4. **W21 SPU/SKU 粒度**：入池命令必须使用 supplier catalog SKU 或逐 SKU 明细，不能只
   传 SPU；必须补 `supply_mode` 来源，移除目录修订中的进项税率。
5. **采购确认供给引用**：补精确 `supplier_offering_revision_id`，校验供应商、SKU、
   业务日期和有效期一致。
6. **商品池启用 guard**：固化“至少一条有效供给 + 有效销售可见价 + 有效 SKU”的
   服务端原子校验。
7. **W05 合同修订字段**：统一 `contractRevisionId` 与
   `requestedContractRevisionId` 的含义和唯一正式字段后再生成 OpenAPI。
8. **W14 伪默认值**：进项税率 `0.13`、区域“全国”、当日生效及由底价推导确认成本

9. **W05 撤回与 W07 转交**：撤回策略未确认时不注册撤回写操作；W07 角色池直转个人
   未确认时 handler 拒绝，不能被通用任务转交能力绕过。
10. **库存调整任务链**：必须注册同一 `INVENTORY_ADJUSTMENT_REVIEW` 在仓储复核、财务
    确认两个阶段的顺序、subject 版本/指纹和唯一完成动作；未接线时调整全链关闭。
11. **开账与领域导入所有权**：Phase 8 只拥有 `legacy_import_batch/row` 的治理编排，
    Phase 3 等对象 phase 是正式领域事实唯一写者；禁止双批次各自重复写同一对象。

## 6. 真实持久化、API 与安全接线

### 6.1 数据库与事务

- 将各 phase 逻辑约束编排为唯一、可顺序执行的真实 migrations；以统一模型表名为准，
  不增加同义通用表。
- 提供统一 Unit of Work、稳定锁顺序、乐观版本、幂等结果持久化和提交后 outbox。
- 从空库执行全部迁移，并提供上一发布版本到当前版本的升级验证；首版也要验证重复执行
  和失败恢复。
- 数据库约束、事务校验和每日复核共同覆盖跨行断言，不能只依赖 ORM 校验。

### 6.2 API 与前端契约

- 建立仓库当前第一份权威 OpenAPI 和错误码目录；所有 operation ID 唯一、引用可解析。
- Command 使用稳定资源 ID、`idempotencyKey`、预期版本/指纹；不提供泛化 PATCH/DELETE
  绕过业务命令。
- 结果未知可按原幂等键或 operation ID 查询最终结果，不能以列表状态猜成功。
- Query 返回权限/范围版本、数据水位、`allowedActions`、`actionBlockers` 和安全字段投影。
- 对照 W01～W19 建立前后端契约测试；前端 mock 类型只有在与业务事实一致后才能更新为
  生成/适配客户端。

### 6.3 认证、权限、任务与敏感数据

- 服务端实现模块/动作、数据范围、字段、对象状态和业务 blocker；不得仅靠前端按钮。
- 注册固定 `work_item_type → handler → completion action`；未登记类型一律拒绝，禁止用
  `BUSINESS_EXCEPTION` 冒充普通业务任务。
- `claimToken`、密钥、卡密、完整敏感字段和签名 URL 不进入 URL、日志、审计正文或
  长期缓存。
- 正式导出冻结范围/字段/遮罩，执行和下载时均重新鉴权并留审计。

## 7. 必须同事务完成的跨域动作

| 动作 | 原子写入 |
| --- | --- |
| 采购二次确认通过 | 确认事实、销售正式版本/状态、应收、采购创建依据、审计、当前任务完成、必要 outbox |
| 采购财务审核通过 | 采购正式版本/状态、应付、确认成本、审计、当前任务完成、必要 outbox |
| 销售变更生效 | 新销售版本/当前版本、应收差额、影响确认、审计、任务完成、必要 outbox；不回退已发生事实 |
| 采购变更生效 | 新采购版本/分配、应付与成本差额、审计、任务完成；不覆盖已付款/入库/开票事实 |
| 合格入库 | 收货事实、库存流水/余额、销售预占、实际成本、采购进度 |
| 仓发 | 发货事实、预占消耗、库存流水/余额、履约进度 |
| 客户验收 | 验收头行、APPLY/REVERSE 分配、履约/销售进度、审计；若为任务入口再同事务完成任务 |
| 库存调整过账 | 财务确认、当前任务完成、库存流水/余额、适用预占和审计；任一失败不留半过账 |
| 采购退货 | 正式退货处理单、库存流水/余额、预占变化、采购进度和必要成本/财务后续意图 |
| 供应商 SKU 入池 | SKU 映射、供给修订、必要商品池修订、审计、outbox |
| 商城快照归集 | 快照引用、映射校验、统一销售版本、应收首笔/差额、当前版本、对应 `CARD_FUNDS_REVIEW` / `CARD_FUNDS_DELTA_REVIEW`；安全持久化后才推进游标 |
| 导入单项应用 | 来源身份、正式对象/期初事实、逐项结果、审计；批次可部分失败，单项不能半写 |
| 权限变更 | 权限事实/策略版本、审计、权限版本失效；若需复核再同事务完成任务 |
| 财务核销/纠错 | 资金/票据、账户、分录、APPLY/REVERSE、offset/纠错、审计和幂等结果 |

外部 HTTP 调用不得包在本地业务事务中。先提交业务事实和 outbox，再由持租约投递器调用；
超时先查询原操作结果，仍未知则进入错误处理，不能盲目重复。

## 8. 最终验证矩阵

### 8.1 编译与静态门禁（必须全部通过）

- 创建唯一入口命令 `backend/scripts/check.sh`（或目标平台等价脚本），串行执行格式、静态
  检查、全量单元/契约测试和生产构建。
- 根工程和所有模块在干净环境编译；锁文件已提交且依赖可复现。
- OpenAPI lint、引用解析、operation ID/错误码唯一性和客户端契约测试通过。
- `git diff --check` 和越权路径审计通过。

### 8.2 数据库门禁

- 空库 migration、重复执行保护、失败回滚、升级 migration 和约束/索引检查。
- 真实数据库并发测试：任务双领取、双提交、库存/预占竞争、核销超额、验收超额、
  重复/乱序商城快照。
- 事务任一写失败时无半完成销售/采购变更、退货、库存调整、票款复核任务或游标；
  上述动作均有并发竞争、旧版本/旧指纹和幂等重放测试。

### 8.3 第一期 E2E

1. 基础资料/供应商目录 → 映射/供给 → 公司商品池。
2. 实物/服务销售草稿 → 提交 → 采购二次确认 → 销售生效/应收。
3. 采购单 → 财务审核 → 应付 → PREPAY/POSTPAY 门禁。
4. 入库/预占/仓发、直发、电子交付、线下服务 → 客户验收。
5. 客户回款/发票核销、供应商付款/进项票核销、退货/冲正/红票。
6. 商城卡券基线 → 映射 → 销售版本/应收 → 逐单票款复核 → 每日全量核对。
7. 期初实盘库存和基础资料导入的验证、确认、生产应用和幂等重跑。
8. W01/W02/W19 的权限、租约、任务完成、导出和审计安全路径。

### 8.4 故障恢复与安全

- DB commit 后 outbox 未投递、消费者崩溃、重复投递和死信重放。
- 商城分页中断、同刻记录、停机恢复、迟到快照和 A→B→A。
- 导入取消、部分失败、结果未知、成功行重跑。
- 权限在请求中途收回、短时下载过期、字段遮罩、敏感日志/错误扫描。
- 二期 feature gate 关闭时不产生 API 供应商订单、商城消费事实、主责迁移或执行投影。

## 9. 编译成功与业务可上线必须分别报告

### 9.1 可以报告“最终代码可编译”的条件

- 第 8.1 节全部通过；
- 真实 migration、应用入口、路由、认证中间件和任务注册均能构建；
- 未决功能使用明确的编译期/运行时 capability gate 和结构化 blocker，不存在空实现成功。

### 9.2 只有满足下列条件才可报告“一期可上线”

- 第 8.2～8.4 节全部通过；
- 真实数据库、真实商城样本、验证环境/生产导入演练和业务确认完成；
- 监控、告警、备份恢复、密钥管理和人工异常处置演练完成；
- 所有阻断第一期主链的未决事项已有书面决议并同步到业务文档、模型、API、代码和测试。

特别是：

- W09 Q1 未决时可以编译，但正常履约入口必须关闭，不能声称一期履约可上线。
- W05 撤回、W07 角色池直转、库存调整任务链未按第 5 节接线时，对应入口保持关闭。
- W06 Q2 未决时可保留 `DIRECT_OBJECT` 验收，但 W01/W02 验收任务入口关闭。
- W18 Q6 未决且生产确认矩阵未落地时，生产期初导入不能放行。
- W19 Q1～Q4 未决时核心服务端鉴权仍必须上线；高风险授权、角色时间策略、字段策略写入
  和审计导出按各自 blocker 关闭。
