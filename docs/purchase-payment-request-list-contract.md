# 采购付款申请列表查询合同

## 1. 适用范围

1. 本合同约束 `/procurement/payment-requests` 的「有效」「草稿」「可申请」三个列表。申请单列表使用 `GET /admin/purchase-payment-requests`；可申请采购来源使用第 6 节接口。
2. 新建及编辑申请弹窗继续使用原候选数组接口 `GET /admin/purchase-payment-requests/candidates`。列表分页不得改变申请创建与提交规则。
3. 查询须继续执行申请列表动作授权和全部采购来源范围校验。部分来源可读不得返回整份申请，不得将未授权申请计入总数。

## 2. 分类与独立条件

| 参数 | 规则 |
| --- | --- |
| `view` | `effective` 包含审批中、待付款、部分付款、已付清、已关闭；`draft` 包含草稿、已驳回、已撤回。不传时不增加分类条件。 |
| `request_no` | 按申请单号包含匹配。 |
| `supplier_id` | 从可搜索供应商下拉框选取，按申请供应商身份精确匹配。 |
| `payer_party_id` | 从可搜索我方主体下拉框选取，按申请保存的付款主体身份精确匹配。 |
| `applicant_name` | 按申请人当前账号姓名包含匹配；姓名缺失时与列表的「未记录姓名」保持一致。 |
| `purchase_order_no` | 任一冻结采购来源单号匹配即可；返回整份申请。 |

1. 五个条件同时生效，条件之间使用 AND。去除首尾空格；空值不增加条件。文本包含匹配忽略英文大小写，正则元字符按普通文字匹配；身份使用精确匹配。
2. 每个条件最多 200 字符，超限拒绝，不得静默截断。
3. 供应商和主体选择器展示目录中的名称，查询使用身份，不因名称变化而漏查历史申请。同名但身份不同的对象不得混合匹配。采购单号仍查询冻结来源；尚无冻结来源的草稿不匹配采购单号条件。
4. 原有名称包含条件 `supplier_name`、`payer_party_name` 以及 `created_by`、`purchase_order_id`、`payable_account_id`、`work_item_id`、`status`、`q` 参数保持兼容；独立条件与这些参数叠加，不扩大权限范围。页面不再发送混合关键词 `q` 及旧名称条件；旧 URL 中的名称条件不参与查询，下一次更新查询时清除。

## 3. 分页、排序及总数

1. 页面只请求当前页，不得循环拉取后续页后在浏览器分页。页面默认每页 50 条，可选 20、50、100 条。
2. 接口 `page` 从 1 开始，缺省为 1；`page_size` 缺省为 20，范围为 1 至 100。小于下限时使用下限，超过每页上限时使用 100。
3. 返回 `items`、`total`、`page`、`page_size`。`total` 为授权、分类及全部筛选生效后的申请总数，不得使用当前页长度代替。
4. 缺省按创建时间倒序、内部身份倒序排列。`sort_by` 仅允许 `request_no`、`supplier`、`applicant`、`amount`、`paid`、`unpaid`、`date`、`status`；`sort_desc=true` 表示倒序，否则正序。同值使用创建时间倒序、内部身份倒序稳定排列。
5. 排序须在分页前作用于完整授权筛选结果。金额按精确数值排序；有效已付为明细净已付之和，剩余待付为申请金额减去净已付及关闭金额。
6. 数据读取、授权、总数及当页资料使用同一读取事务。沿用候选 10,000 条上限，超过时返回「付款申请查询超过上限，请收窄筛选」。候选上限在数据库条件生效后、逐来源授权及申请人姓名过滤前检查；不得静默截断。
7. 当前实现仍在服务端完成逐来源授权及内存分页。本合同不将其声明为 MongoDB 直接分页，也不取消上述候选上限。

## 4. 页面执行规则

1. 供应商和我方主体使用支持远程搜索、清空和已选名称回显的下拉框，选项来自有权访问的对象目录，不得从当前分页记录提取。清空表示不限制该条件；输入搜索词只查找选项，须选择对象才形成身份条件。输入或选择条件只修改表单草稿；点击「查询」或按回车统一应用，并回到第一页。
2. 「重置」清空五个条件并回到第一页。分类切换清空条件；排序变化、每页条数变化回到第一页。
3. 分类、已应用条件、页码、每页条数及排序保存在 URL，刷新及返回列表时按 URL 恢复。修改查询参数保留新建入口与其他导航上下文。
4. 查询失败必须显示错误，不得显示为无匹配数据。空结果回到第一页；非空结果的越界页回到最后一页。
5. 查询控件与表格列设置分离。窄窗口允许筛选控件换行，不得隐藏新建申请等页面动作。

## 5. 索引与发布

1. 新增非唯一索引 `idx_purchase_payment_requests_list`，键顺序为 `deleted_at: 1, created_at: -1, id: -1`，支持未删除候选的稳定倒序读取。包含匹配条件仍须执行文本过滤；不得将本索引声明为所有模糊条件的直接索引查找。
2. 应用启动时由财务领域索引入口幂等登记。需要提前登记时，在目标数据库执行 `backend/scripts/migrations/20261015-payment-request-list-index.mongosh.js`；具体执行参数见脚本头部。
3. 索引回滚先部署不登记该索引的版本，再以 `ERP_INDEX_ROLLBACK=1` 执行同一脚本。不得删除其他索引或修改业务文档。
4. 前端与后端同时发布。后端字段均为可选扩展，原调用方仍可按原参数调用；旧后端会拒绝新增查询字段，不得先单独发布新前端。

## 6. 可申请采购来源

1. 「可申请」须展示采购单号、采购内容两个文本条件，以及供应商、我方主体两个可搜索下拉框。参数依次为 `purchase_order_no`、`purchase_summary`、`supplier_id`、`payer_party_id`；条件之间使用 AND，每项去首尾空格且最多 200 字符。文本忽略英文大小写并按字面量包含匹配；身份精确匹配。两个下拉框执行第 4 节规则。接口保留 `supplier_name`、`payer_party_name` 的名称包含条件兼容，页面不读取或发送旧名称条件。
2. `GET /admin/purchase-payment-requests/candidates/page` 返回 `items`、`total`、`page`、`page_size`。前端只请求当前页，缺省每页 50 条，允许 1 至 100 条；页面提供 20、50、100 条选项。筛选先于计数、排序及分页。
3. 两个新增候选入口均要求 `purchase_payment_request:create`，复用现有候选资格检查：采购范围、已生效状态、当前采购及销售版本、付款主体、应付来源及正可申请余额。不得通过分页或全选绕过资格检查。服务端沿用原有候选快照及上限，未改为数据库直接分页。
4. `sort_by` 允许 `purchase_order_no`、`supplier_name`、`payment_term_name`、`total_amount`、`paid_amount`、`reserved_amount`、`available_amount`，`sort_desc=true` 表示倒序。金额使用精确数值比较；付款条件使用名称，缺少名称时使用条件代码。缺省按采购单号倒序；同值按应付身份正序稳定排列。
5. 翻页、调整排序与筛选不得丢失已勾选身份。工具栏须展示全部已选数量，允许明确清空。表头勾选只操作当前页。
6. 「全选筛选结果」调用 `GET /admin/purchase-payment-requests/candidates/ids`，传当前四项条件，合并接口返回的全部匹配身份。该接口忽略页码，不得用当前页记录冒充全部筛选结果；不得返回无申请资格的身份。
7. 点击「发起申请」须重新查询当前全部候选身份并核对勾选。失效身份须取消勾选并告知数量，暂停打开申请弹窗，要求重新核对。核对失败须保留选择并提示重试；不得静默提交失效来源或自动缩减申请后继续。
8. 切换分类、离开页面或应用新的筛选条件后，迟到的全选或复验响应不得修改勾选或打开申请弹窗。创建与提交接口仍须执行事务内最终资格及余额检查。
9. 可申请列表条件、页码和排序使用 `candidate_` 前缀保存于 URL，刷新恢复；分类切换清除这些参数，保留新建入口及其他导航上下文。查询与重置回到第一页；空结果和越界页处理沿用第 4 节。
10. 新前端须与新增候选接口配套发布。原数组接口保持不变，不影响新建与编辑弹窗的候选读取。
