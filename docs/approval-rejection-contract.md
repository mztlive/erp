# 审批驳回与重新提交执行合同

## 1. 适用范围

本合同适用于下列 13 类必须审批的业务单据，审批生命周期不得按单据类型分叉：

| 类型 | 单据 |
| --- | --- |
| `sales_order` | 销售单 |
| `voucher_sales_order` | 卡券销售单 |
| `sales_change_order` | 销售变更单 |
| `purchase_order` | 采购单 |
| `purchase_change_order` | 采购变更单 |
| `stock_adjustment` | 库存调整单 |
| `sales_invoice_request` | 销项开票申请 |
| `customer_receipt` | 客户回款单 |
| `purchase_payment_request` | 采购付款申请 |
| `customer_refund` | 客户退款单 |
| `supplier_refund` | 供应商退款单 |
| `receipt_reversal` | 回款冲正单 |
| `payment_reversal` | 付款冲正单 |

供应商付款单、采购收货单、仓发单、电子交付单、服务履约单、客户验收单、发票、销售退货单、采购退货单继续执行各自的无审批业务规则。

本合同取代现行需求文档中“驳回自动增加轮次、回到首节点、业务状态保持审批中”的规则。历史审批记录不得按新规则改写。

## 2. 驳回命令

1. 仅当前合法审批人可以对当前实例、当前执行和当前有效审批任务提交驳回。服务端必须在写入事务内重验身份、责任、操作权限、实例状态及版本。
2. 驳回原因必填。接受决定后，当前节点执行记录为 `REJECTED`，本次实例进入 `REJECTED` 终态并记录结束时间；不得增加轮次、创建新节点或重开实例。
3. 必须关闭该实例全部未完成审批任务。或签节点中实际决定人的任务记为已办理，其他参与人的任务按统一终结规则关闭；不得留下可再次批准或驳回的任务。
4. 必须调用该类型登记的驳回领域动作，使业务单据显示“已驳回”，并释放本次审批持有的临时占用。
5. 必须为原提交人建立一条“驳回待处理”任务，关联原单据、本次被驳回实例及提交版本；重复命令不得创建重复任务。
6. 节点决定、实例终结、审批任务关闭、业务状态更新、占用释放、驳回待处理任务和审计记录必须使用同一事务。任一步失败，全部回滚；提交结果未知时按原幂等键查证，不得换键重放。
7. 已驳回实例不接受新的审批决定、恢复或撤回。原驳回命令同载荷重试只回读已提交结果，不重复释放占用或产生任务。

## 3. 单据状态与修改

| 当前状态 | 允许的处理 | 结果 |
| --- | --- | --- |
| 审批中 | 合法审批人驳回 | 已驳回，原提交人收到处理任务 |
| 已驳回 | 有修改资格的人编辑并保存 | 仍显示已驳回，审批历史保留 |
| 已驳回 | 有提交资格的人填写说明并重新提交 | 新版本、新审批实例，显示审批中 |
| 已驳回 | 原处理责任人填写原因并放弃本次办理 | 关闭驳回待处理任务，单据仍显示已驳回 |
| 已驳回 | 具备作废资格的人执行单据作废 | 按单据作废规则处理，不复用“放弃办理”动作 |

已驳回单据直接按服务端修改资格编辑，不要求再次撤回。销售单采用商业主状态与审核轨组合时，必须以审核轨的已驳回结果正确显示状态；不得仅凭可编辑商业状态把单据显示为普通草稿。

放弃办理必须填写非空原因，最多 512 个字符；前端与后端使用同一限制。该操作只结束本次处理责任，不删除或作废业务单据，不解除其他业务占用，不伪造审批通过。放弃后，有权人员仍可重新打开单据编辑并重新提交，重新提交说明仍必填。

审批中单据仍需按既有撤回规则回到可编辑状态；最终生效或实际执行后的事实按变更、退货或冲正规则处理。

### 3.1 独立保存接口

以下接口只保存编辑内容，不提交审批。保存成功必须保持原 `DRAFT` 或 `REJECTED` 状态，不递增审批提交版本、不创建审批实例、不关闭驳回待处理任务。重新提交说明只在提交审批时必填。

| 单据 | 接口与请求 | 返回与授权要求 |
| --- | --- | --- |
| 销项开票申请 | `PUT /admin/sales-invoice-requests/{id}`；请求为 `{ expected_version, data }`，`data` 为完整开票申请资料 | 返回 `InvoiceRequestView`；必须为原申请人，账号有效，具备提交权限及对象读取资格；使用当前乐观锁版本 |
| 采购变更 | `POST /admin/purchase-change-orders/{id}/draft`；请求为 `{ expected_lock_version, payment_term_code, reason, lines, idempotency_key }`，`lines` 为非空完整目标明细 | 返回 `PurchaseChangeDraftView`；必须同时具备来源采购单的更新和提交资格，校验当前版本及生效基准；同键同请求回读原保存结果，同键异请求拒绝 |

开票申请保存不得取得待审批开票额度。采购变更保存必须写入独立编辑内容，保留旧冻结提交及原生效版本，不调整询价数量占用；新增占用只在提交审批时按当前可用资源重新取得。保存失败不得留下部分明细或改变原状态。

开票保存结果未知时，必须保留原输入和请求版本，通过只读查询核对服务端返回的同一申请、有效版本及当前状态。不得用客户端缓存补齐缺失结果，也不得因当前字段与原输入相等就判定旧保存已成功。服务端版本已前进且申请仍可编辑时，用户可明确选择“采用最新版本并保留输入”，再以新编辑意图保存；申请已不可编辑时，须允许查看原输入并明确退出，禁止自动覆盖或继续使用旧版本保存。

### 3.2 编辑内容与审批历史隔离

采购变更独立保存形成的 `DRAFT-*` 编辑目标只用于展示自身内容，不得分配或继承旧 `approval_subject_version`，不得计入正式 `CS-*` 提交序列。连续保存必须保持既有正式提交与审批版本的对应关系；重新提交后仍可读取各旧正式提交的冻结摘要。

草稿或已驳回状态下修改的原因、目标行及其他可变内容，不得补写到旧审批摘要。历史审批缺少冻结展示快照时，只能使用能够证明对应审批版本的正式冻结提交补充展示；缺失相应正式历史时应保留缺失结果，不得用当前编辑内容冒充历史审批依据。编辑页面可以同时展示当前目标和真实旧审批记录，但必须保持各自身份及版本。

## 4. 重新提交

1. 曾被驳回的单据重新提交时，`resubmission_reason` 必须为去除首尾空白后的非空说明，最多 1000 个字符；前端与后端使用同一限制。业务内容可保持不变，不得强迫修改无关字段以绕过重提限制。
2. 保存修改不得修改旧提交快照、旧审批依据或旧实例；新提交必须重新冻结当前内容、附件和重提说明。
3. 每次重提必须取得新的审批提交版本并创建新审批实例。旧实例永久终结，旧节点通过结果不得继承。
4. 新实例从当前绑定定义的首节点开始，执行既有流程绑定规则；提交资格、审批人有效性、来源版本、金额数量和额度必须重新校验。
5. 需占用的资源必须按本次新提交重新取得；额度或来源已被其他业务使用时，提交必须失败并说明原因。
6. 新提交、资源占用、新实例启动和原驳回待处理任务关闭必须在同一事务内完成。启动失败时原处理任务保持待处理，单据不得单独进入审批中。
7. 重提说明必须纳入命令载荷身份及冻结记录。同键异说明不得被视为同载荷重放。

### 4.1 未知结果与精确回放

提交请求发出后，客户端必须保留本次完整请求，包括业务对象、请求版本、业务内容、重新提交说明及幂等键。超时或服务端返回提交结果未知时，重试必须发送同一份冻结请求，不得以当前表单、刷新后的版本或新填写的说明重建载荷，也不得更换幂等键发起第二次提交。

客户退款、供应商退款、回款冲正及付款冲正的列表重提必须保留未确认命令，关闭对话框后仍提供“继续核对”入口；列表已经不显示提交动作时，该入口仍应可用。核对期间重新提交说明只读，同类新建或其他单据提交不得覆盖原命令。一次重试明确失败不能证明此前未知请求未提交，必须继续保留原未知状态和冻结请求，直至查证结果或按已定义的受控恢复流程处理。

上述四类单据可由用户选择“读取最新单据”。只能接受本次显式查询返回且 ID 匹配、版本为正安全整数、状态属于草稿、已驳回、审批中、已过账或已冲正的服务端结果。最新版本严格大于冻结请求版本时，方可显示“结束本次核对，查看最新单据”；用户明确选择后刷新当前详情并清除本地旧待核对命令。该操作不判定原提交成功或失败，也不直接重新提交；后续办理遵循最新状态，不可编辑状态仅允许查看或退出。读取及结束核对期间必须锁定原请求重试和关闭操作，防止并发覆盖恢复结果。

服务端必须以原请求身份及完整载荷判定回放。同键改变原请求版本、业务内容或重提说明必须拒绝；命中已提交的精确回执时只回读原命令确定的对象或提交结果，不创建新审批版本、实例、任务或占用。当前业务状态已推进时，不得用当前可变内容替代原请求或推定原提交已成功。历史回执缺少证明原请求版本所需事实时，必须拒绝无法证明的回放，并要求刷新核对结果。

销售变更提交回执必须绑定操作人、变更单、幂等键、原 `source_version` 及规范化重新提交说明，并冻结提交 ID、提交序号和审批实例 ID。正常重试、事务内竞争及提交结果未知后的恢复使用同一回执规则，按回执中的提交 ID 校验冻结事实；后续版本已经提交时，仍须能够证明先前命令的原提交。HTTP 返回的当前变更详情仅用于刷新当前状态，不得标注为旧提交快照。旧数据缺少完整命令回执时必须拒绝无法证明的回放，不得扫描历史猜测原版本或回填旧 `source_version`。该回执复用 `sales_command_receipts` 及其既有 ID 唯一索引，采用独立 `sales-change-submit` 命令前缀，无需新增索引或批量回填。

新请求、成功回放和未知结果恢复均必须校验当前账号、操作权限及业务来源资格。拥有原幂等键或曾经提交成功，不授予继续读取或操作来源对象的权限。决定业务写入或回放结果可见性的授权读取必须使用所属命令的同一事务执行器；资格失效时不得返回该业务结果或继续写入。

开票申请提交、保存、撤回及其结果读取必须按当前动作重验有效账号、操作权限、原申请人和真实销售及应收来源范围。回放须先校验账号及动作权限，再匹配精确财务回执，随后核验原申请人和当前来源范围，在同一只读事务中读取详情，并在读取前后校验授权策略版本。回放及结果读取不得推进授权策略版本；写事务内发现并发命令已形成精确回执时，必须回滚该次写事务，再经只读恢复返回结果。原审批绑定不能替代当前来源授权；未知提交恢复时若无法获准读取结果，应保留原未知结果，不得泄露详情或将其报告为确定未提交。

### 4.2 已提交但结果不可读

事务已确认成功，或精确命令回执已证明提交成功后，如果当前授权、结果读取或策略版本后验失败，必须返回 `CommittedResultUnavailable`，HTTP 使用 `503`、错误码 `COMMITTED_RESULT_UNAVAILABLE`、`retryable: false`。对外提示固定为“操作已提交，但当前无法读取结果，请稍后查询处理状态”，不返回未授权业务详情或内部错误原因。原成功审计保留，不得因提交后的结果读取失败追加一条声称该业务命令失败的审计。

该结果已有提交成功证据，不得伪装成 `CommitOutcomeUnknown`、普通失败或未提交。客户端必须保留原请求和幂等键用于核对，不得自动换键重提或清空原输入。再次核对失败时保留已提交证明；原始结果确为未知且恢复仍不能查证时，继续保留原未知结果。核对和结果读取始终执行当前授权，不因已有提交证据放宽权限。

## 5. 资源释放边界

| 资源 | 驳回时要求 |
| --- | --- |
| 本次审批的开放任务和当前执行资格 | 全部关闭并失效 |
| 采购付款申请的未付额度占用 | 释放；实际付款及核销事实保留 |
| 客户回款单的待审批应收分配占用 | 释放；重提重新争取可分配余额 |
| 销项开票申请的待审批开票额度占用 | 释放；重提重新争取可开票余额 |
| 采购变更提交时新增的询价数量占用 | 恢复原生效采购数量及地址，释放本次增加量；重提重新校验并取得增加量，原生效采购数量不得释放 |
| 供应商退款的采购结算方案额度 | 同一采购、结算方案及结算方式下，审批中和已过账退款计入占用，排除本单、草稿、已驳回、已冲正及已删除记录；驳回后不再计入，重提按当前占用重新校验，保留采购单并发守卫 |
| 单据创建或草稿阶段取得、且仍由保留单据持有的来源数量及费用归属 | 销售来源数量、采购来源覆盖、询价采用及费用分摊按拥有领域的来源规则保留；不得把草稿持有量当作审批临时占用释放 |
| 最终通过时才产生的应收应付、资金核销、退款冲正和库存流水 | 驳回不创建、不冲销、不删除 |
| 原单号、单据内容、附件、冻结提交、审批历史、命令回执和审计记录 | 保留 |

各领域必须通过登记的驳回动作执行资源处理，不得在 BPM 引擎中直接访问业务集合。释放必须受当前状态、提交身份和版本约束，重复命令不得重复增加可用余额。没有审批阶段独立占用的类型，只更新驳回状态并保留业务事实。

## 6. 界面与待办

- 列表、详情、工作台和审批材料必须一致显示“已驳回”，展示驳回原因及本次审批历史。
- 驳回确认文案必须说明本次审批结束、退回提交人处理；不得提示自动进入下一轮。
- 驳回待处理任务详情必须返回由任务固定责任关联解析的 `approval_process_instance_id`；不得从当前单据的最新审批或前端任务编号推断。列表未携带该关联时，进入任务必须读取独立详情。
- 驳回待处理必须复用该单据的审批详情组件、字段区、行明细、附件入口和审批历史，不得另建通用材料页或纸质预览页替代审批工作面。销售、采购、付款及其他登记类型执行同一规则。
- 展示资料必须绑定被驳回的审批实例、单据类型、单据 ID 和提交版本。历史付款申请及审核材料必须按提交版本读取，不得补读当前申请替代历史提交。缺少关联、读取失败或身份不一致时停止展示对应内容并提供重试。
- 原发起人读取已结束实例的资料、历史和附件沿用审批实例授权；任务关联字段不授予额外读取资格。
- 详情正文上方展示本次驳回原因、驳回人、审批节点和时间，来源为该实例的真实审批记录。未取得意见时显示读取状态或错误，不得将通用影响说明冒充审批意见。完整历史沿用审批详情入口。
- “待我处理”和“我发起的审批”必须展示同一审批详情，并使用同一条开放驳回待办。实例详情的 `rework_task_id` 只向原提交人返回身份和版本完全匹配的开放待办引用，其他情况返回 `null`；前端不得拼接任务编号或依赖列表筛选查找关联。
- 修改或重新提交、放弃本次办理集中在审批详情底栏，按实际待办允许动作展示。任务命令仍校验原提交人、任务版本及权限；编辑入口携带返回当前详情的地址。
- 查看审批或保存修改不得结束待办。重新提交必须填写说明，内容不变时仍可提交；重新提交成功或放弃办理后关闭本次责任。
- 已重提、已放弃或未持有开放责任的旧审批详情只读，不得仅凭实例状态为已驳回展示办理按钮。原单据仍可按自身业务权限再次办理，历史审批不得被新内容覆盖。
- 审批实例版本、业务提交版本和历史轮次须分别按真实含义显示，不得用旧轮次模拟新提交。

## 7. 存量实例清单与处置

### 7.1 只读清单

切换前必须运行 `backend/scripts/migrations/20261103-approval-rejection-audit.mongosh.js`，按状态和更新时间范围分批读取。该脚本仅读取 `approval_process_instances`、`approval_node_executions` 和 `work_items`，不得写入、补索引或修改历史。

输入必须明确目标数据库、实例状态、起止时间及单页上限。`RUNNING` 与 `BLOCKED` 分别执行。使用返回的游标逐页继续，直至 `has_more=false`；超时或超限不代表清单完整。输出文件只保存业务对象引用、实例/执行/任务身份、版本及分类，不保存驳回原因全文或人员姓名。

执行示例（连接串由执行环境提供，命令从仓库根目录运行）：

```bash
APPROVAL_AUDIT_DB=erp \
APPROVAL_AUDIT_STATUS=RUNNING \
APPROVAL_AUDIT_FROM=0 \
APPROVAL_AUDIT_TO=1793635200 \
APPROVAL_AUDIT_LIMIT=50 \
mongosh "$ERP_MONGO_URI" --quiet --file backend/scripts/migrations/20261103-approval-rejection-audit.mongosh.js
```

执行前必须将 `APPROVAL_AUDIT_TO` 替换为本次核查截止时刻的 Unix 秒；不得直接沿用示例日期。后续页同时设置 `APPROVAL_AUDIT_AFTER_TIME` 和 `APPROVAL_AUDIT_AFTER_ID` 为返回游标，其他筛选条件保持不变。对 `BLOCKED` 另起第一页。清单不提供跨集合一致性快照，读期间有写入时须复核并重新扫描相同窗口；不得以单次分页结果证明并发环境下已无遗漏。

| 清单分类 | 处置要求 |
| --- | --- |
| `RESTARTED_UNTOUCHED` | 历史驳回后只有新轮次活动或受阻执行，且未再产生决定；核对单据和当前责任后，由当前合法审批人按新规则重新驳回 |
| `CONTINUED_AFTER_REJECTION` | 首次历史驳回后已有后续通过或驳回决定；逐笔核对办理事实，确认继续办理或由当前合法审批人重新驳回 |
| `REVIEW_REQUIRED` | 历史超过上限、版本变化、缺少执行、存在替换执行、身份或状态不一致；补充证据后逐笔处置，禁止直接批量变更 |

清单是只读时点证据，执行处置前必须由应用重新读取并校验当前权限、版本和状态。清单分类不授予审批或管理权限。已通过、已驳回、已撤回的终态实例不参与清理，历史保持原样。

### 7.2 受控处置

1. 不提供数据库批量 `$set`、删除或自动终止脚本。
2. 运行中实例需要结束时，由当前合法审批人使用正常驳回命令，说明存量处置原因；原始历史原因不得覆盖。
3. 受阻实例先按现有授权恢复或取消规则处理；管理员不得冒充审批人提交决定，不得为清理数据跳过资格校验。
4. 驳回执行后核对实例终态、全部审批任务关闭、业务已驳回、审批临时占用释放和唯一驳回待处理任务。
5. 已继续处理的实例必须记录逐笔处置结论。决定继续办理时后续新发生的驳回仍执行本合同，不恢复自动重启语义。
6. 切换后禁止回滚到不认识新增已驳回状态或驳回待处理类型的旧应用版本；回退方案须保留已落库状态、历史和占用结果，并采用兼容修复版本。

### 7.3 销售变更唯一索引切换

销售变更集合 `sales_change_orders` 必须以 `(sales_order_id, base_revision_id)` 约束同一生效基准下唯一进行中变更。已驳回变更仍占据该编辑资格，不允许绕过原单另建并行变更。

| 项目 | 值 |
| --- | --- |
| 旧索引 | `uk_sales_change_orders_active_per_order_base` |
| 新索引 | `uk_sales_change_orders_active_per_order_base_v2` |
| 键 | `{ sales_order_id: 1, base_revision_id: 1 }` |
| 唯一性 | `unique: true` |
| 新部分过滤 | `status` 为 `DRAFT`、`IN_APPROVAL`、`PENDING_IMPACT_CONFIRMATION`、`PENDING_FINANCE_REVIEW`、`REJECTED` 之一 |

按以下顺序部署：

1. 暂停销售变更的创建、编辑、提交及审批写入，保持读入口可用。
2. 使用 `backend/scripts/migrations/20261103-sales-change-active-index-audit.mongosh.js` 按明确的销售单 ID 分批读取，覆盖全部待切换销售单。该清单只证明本批指定对象，不代表全库验证。部分索引没有软删除过滤，清单必须包含软删除行。
3. 发现同一销售单及生效基准下存在多个匹配变更时，先按业务命令逐笔处理；禁止删除历史或直接改状态以绕过唯一约束。查询超时或超过单销售单 500 条上限时不得继续切换。
4. 由部署索引入口创建上述 v2 唯一部分索引，保留旧索引。若创建失败，停止部署；不得删除旧索引后重试。
5. 读取索引元数据，确认 v2 键、`unique` 和完整部分过滤均正确且构建成功，再由数据库维护人员删除旧索引。禁止用旧索引未覆盖的 `IN_APPROVAL` 数据推定全量无重复；新唯一索引成功构建是最终约束检查。
6. 部署兼容新状态及新索引的应用版本，完成驳回、直接编辑、重提及同基准并发检查后恢复写入。
7. 回退使用兼容新状态的修复版本，并保留 v2 索引；不得恢复遗漏 `IN_APPROVAL` 的旧唯一性规则。

## 8. 验收要求

- 13 类审批类型的登记必须具有驳回领域动作，普通驳回全部终止实例。
- 单人及或签节点驳回后无开放审批任务，且恰有一条原提交人的驳回待处理任务。
- 已驳回单据可编辑；保存保持已驳回；无说明重提失败，内容不变且说明有效时可新建提交和实例。
- 重提重新校验并取得资源；资源不足时不创建新实例，也不关闭原处理任务。
- 驳回、重提、放弃的同载荷重试不重复改变状态、占用或任务；异载荷同键冲突。
- 未形成成功回执的旧请求遇到版本变化必须拒绝；精确成功回执按原请求回放。权限或责任变化必须按当前资格拒绝不再获准的操作或结果读取。
- 未知结果重试保留原请求版本、内容、说明及幂等键；重复请求不得读取当前编辑内容重建原载荷。
- 财务列表未知命令关窗后仍可恢复核对，其他单据操作不得覆盖；开票未知保存只能依据有效服务端结果核对，采用新版本必须由用户明确选择。
- 已知提交成功后结果不可读必须返回 `COMMITTED_RESULT_UNAVAILABLE`，客户端保留原请求；只读回放与结果读取不得推进授权策略版本。
- 采购变更连续保存编辑目标不得新增审批历史或覆盖旧提交摘要；缺失正式历史时不得将当前草稿映射为旧审批版本。
- 事务失败不得留下部分业务状态或资源变更；纯函数和替身测试通过不能替代真实数据库原子性验收。
- 清单工具须通过语法与离线分页/分类验证；真实环境只读核查和逐笔处置须单独记录，不得把静态检查标为存量迁移完成。
