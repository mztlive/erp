# 列表筛选候选独立查询执行合同

版本：1.4

制定日期：2026-09-23

状态：R0—R5 代码、用途复核及本地检查已完成；生产构建受外部字体下载阻塞，真实环境验收待执行。第 11 章是当前实现、配置和验证状态的权威清单；第 10 章定义必须持续满足的行为。不得将本地检查通过登记为真实业务验收通过。

适用范围：管理端列表、查询型报表、目录页面中的人员、组织、客户、供应商、结算主体、仓库及字典筛选。覆盖后端随列表返回候选、前端从查询结果反推候选两种实现。

实施入口：后续 agent 必须先读本文件、根目录规则和目标子项目 `AGENTS.md`，按第 11 章未完成项及第 8 章文件边界执行，并更新第 11 章验收状态。不得将本文的目标状态登记为已实现。

## 1. 产品规则与完成边界

1. 普通筛选器展示当前用户有权选择的对象；对象在当前业务列表中没有匹配记录，仍须允许搜索、选择。选择后列表正常返回空结果。
2. 销售人员候选由销售人员资格、人员查询 DataScope 和人员搜索条件决定；不得要求其拥有客户、合同、销售单、收付款或选品册。
3. 候选不得取自当前页、业务列表全量结果、业务汇总、已选择 ID 集合或导出结果。将当前页改成全量业务记录去重，不构成本合同要求的整改。
4. 候选接口与业务列表分别解析自身资源、动作的 RBAC 和 DataScope。候选可见不授予相关业务记录的读取权；选中 ID 不构成授权凭证。
5. 业务查询继续执行 `业务授权范围 ∩ 用户筛选条件`。不得在拆分候选时删除列表、总数、指标、详情或导出的授权校验。
6. 普通候选查询不接受消费页面的页码、业务关键词、业务状态、金额、日期等条件。候选自身的关键词、分页、状态，以及明确登记的组织等级联条件可以收窄候选。
7. 业务列表不再承担普通筛选候选的生产和传输。列表保留行、分页、授权元信息及原有业务指标；指标是否另拆接口不属于本次强制要求。
8. 改造不改变合同当前客户主负责人、销售单负责销售、采购负责人、实际经办人、任务处理人和历史归属的业务含义。
9. “无候选权限”“无候选范围”“候选搜索无结果”“候选加载失败”“业务筛选无结果”必须分别处理。读取失败不得伪装成请求成功后的空候选。
10. 本项目尚未上线，按批次直接切换目标接口、调用方及当前合同；不新增双读、旧字段回退或按错误自动调用账号管理接口的兼容路径。未迁移批次维持原行为，并明确登记未完成。

### 1.1 必须成立的示例

经理可查询销售甲、乙；甲有合同，乙无合同。销售候选必须同时包含甲、乙；选择乙后合同返回 `items=[]`、`total=0`。合同的翻页、状态、关键词变化不改变销售候选。经理失去乙的人员查询范围后，候选及已选项回显必须重新授权；合同本身仍按 `contract:list` 独立授权。

### 1.2 与既有合同的效力

1. 本文替代既有文档中“普通候选随列表返回”“从可见业务对象反推普通候选”“候选必须保证能筛出业务记录”的要求。替代范围仅限本次候选查询职责与接口拆分。
2. [组织与范围主合同](organization-data-scope-contract.md) 的授权组合、个人上限、历史参与、业务事实归属、事务和版本规则继续有效。候选与业务列表共用公共授权机制，各自使用其拥有对象的事实映射。
3. [S1](organization-data-scope-s1.md)、[S2](organization-data-scope-s2.md)、[S3](organization-data-scope-s3.md)、[S4](organization-data-scope-s4.md) 的既有完成登记不证明本文已完成。新增批次使用独立状态，不重写过去的验证结果。
4. `organization-owner-query-openapi.yaml`、`organization-data-scope-s2-openapi.yaml`、`organization-data-scope-s3-openapi.yaml`、`organization-data-scope-s4-openapi.yaml` 在对应代码切换批次同步更新。文档准备阶段不得先删除仍被实际接口返回的字段，制造虚假的已切换状态。
5. [列表搜索执行合同](../backend/docs/api/list-search.md) 中的业务搜索、排序与指标规则继续有效；普通候选规则以本文为准。

## 2. 分类与禁止混用

| 类型 | 数据源与授权 | 执行要求 |
| --- | --- | --- |
| 当前人员查询候选 | 独立人员目录资格及该目录的 DataScope | 允许零业务记录；保留查询需要的停用人员；不得复用分派资格 |
| 当前客户、供应商、结算主体、仓库候选 | 被选择对象的目录、资格及对应 DataScope | 优先复用符合本合同的对象查询；不得从消费业务记录去重 |
| 当前组织候选 | 组织目录及明确的组织查询范围 | 不从业务记录出现过的部门反推；业务页组织筛选仍按其业务归属解释 |
| 状态、类型、动作等固定字典 | 领域枚举、正式动作注册表或权威字典 | 使用完整合法集合，不从列表或统计中出现的值生成；不为常量新增 HTTP 请求 |
| 历史人员／组织归属候选 | 历史身份及冻结归属语义、当前查询授权 | 单独登记历史接口；不得用当前销售资格、当前部门覆盖历史身份和标签 |
| 命令、交接、改派、审批恢复候选 | 具体业务对象、动作、资格及岗位分离规则 | 保持专用资格接口；不得使用普通查询目录代替命令授权 |
| 当前对象内部选择 | 当前单据明细、选品册套餐档位等对象内事实 | 可保留局部选项；必须证明不承担跨对象目录筛选 |

历史候选允许从授权历史事实识别历史身份，是显式例外；历史候选接口必须独立于报表分页和当前结果集。拆分时必须登记其时间范围、快照名称及授权依据，不得把例外扩展到当前销售人员候选。

行展示名称与筛选候选必须分离：业务行已经授权时，按本域展示合同返回负责人／处理人名称；不得通过是否能读独立人员目录决定已授权业务行的基本可读性。页面不得依赖候选全集充当行名称字典。

## 3. 候选资源、资格与 DataScope

### 3.1 首批销售人员资源

目标接口固定为 `GET /admin/salespeople`，授权固定为 `sales_person:list`，拥有领域为 `erp-identity`。该资源为轻量业务人员查询，不是系统账号管理接口，不暴露密码、联系方式或账号管理操作。

| 事项 | 强制规则 |
| --- | --- |
| 销售资格 | 由身份域统一解析账号与正式销售资格关系；优先复用已存在的权威规则；不得按角色显示名、创建过单据或客户归属记录判断 |
| 资格登记 | B0 必须登记确切的资格来源、稳定角色／类别标识、停用与撤销含义及对应代码入口；不存在权威规则时，先补齐身份域规则再接入页面，不得各页面各自猜测 |
| 查询与分派 | 查询资格不能直接等同于 `sales_order:create` 等命令权限；具有筛选资格不等于可接收责任或可建单 |
| 停用与历史人员 | 账号停用不自动删除查询资格；离职、撤销销售角色与资格终止必须有独立约定。原系统可筛选的存量负责人不得因角色变化静默消失；需要保留的身份由资格历史／人员目录保存，不得再次依靠消费列表推导 |
| 本人范围 | 候选人员 ID 等于当前操作人，且符合该目录资格；没有业务记录也可出现 |
| 组织／团队范围 | 使用候选人员在授权时点的有效主属组织；复用显式组织、本人组织、管理组织及下级展开规则 |
| 公司范围 | 覆盖符合资格的人员；仍受个人上限、账号类型、软删除等边界约束 |
| 无组织 | 不视为属于任意组织；本人／公司范围是否允许按公共判定及资格规则执行，不补造部门 |
| 协作与历史参与 | 人员目录不从某张业务单的参与权扩张出人员读取权；未定义的范围类型必须在配置入口及解析边界拒绝 |
| 多角色与个人上限 | 复用同角色权限证明、角色正向范围并集、个人上限交集；不得自行把部门和人员条件拼成更宽的权限 |
| 空范围 | 无有效角色范围返回空候选及 `no_scope`；缺动作权限拒绝；不得回退公司范围 |

资格是目录对象集合的定义，DataScope 是操作人可读范围，两者必须分别建模。B0 未完成资格登记时，仅阻断该人员类别的接入，不得以随意加入全部管理员完成批次。

### 3.2 其他人员与对象资源

1. 采购、维护人、能力负责人、制单人、经办人、任务处理人分别登记候选语义。销售／采购属于明确的岗位类别；维护人、经办人、申请人等字段在普通查询中使用第 10.1 节的后台人员目录，无需逐个新建岗位资格记录。具有单独历史语义或明确限定资格的字段另行登记。不得因同处一个页面就将所有人员字段接入销售／采购目录。
2. 新增人员类别前先登记“接口、资源动作、拥有领域、资格来源、组织映射、状态规则、默认授权”。禁止每个页面新增一套人员目录，也禁止客户端传任意 `resource` 或 `permission` 绕过服务端固定注册。
3. 销售、采购混合筛选必须按页面字段语义登记允许的类别；服务端或前端组合均须保留每一类自身授权，不得以有销售查询权获取采购候选。
4. 客户、供应商、仓库已有列表接口符合轻量、分页、资格及授权要求时直接复用；若绑定管理权限、强制启用状态或携带沉重候选聚合，则在拥有领域提供独立轻量查询。不得为了选择器授予账号／主数据维护权限。
5. 结算主体按主体身份与有效业务资格查询，不能用客户 ID 或供应商 ID 代替。现有接口没有接入所需 DataScope 时，先完成资源注册与范围映射，再供合同页调用。
6. 人员目录范围与业务范围独立配置。禁止直接复制任意角色既有 `contract:list`、`sales_order:list` 的授权为人员目录授权。默认配置须明确发布；没有配置保持关闭。

### 3.3 权限及初始化交付

每个新增候选资源必须同时完成：

1. `erp-identity/src/service/access_control/consumers.rs` 的真实消费者登记、支持维度、范围类型限制及对象判定。
2. Handler 权限标注、管理端认证路由、权限生成物及角色权限管理界面的登记。
3. `service/iam/predefined_roles/`、`predefined_data_scopes.rs` 和相关开发种子的显式初始化规则；更新资源动作总目录及管理界面合法选项。
4. 发布一张角色默认授权表，逐项填写资源动作、Company／SelfOwned／组织目标模式及个人上限处理。不能以“所有能看合同的角色默认 Company”代替该表。
5. 重跑初始化不得恢复已撤销范围、覆盖人工配置或默默扩大现有账号权限。本文不授权执行真实库种子、清库或批量权限写入。

## 4. 查询接口合同

### 4.1 分页搜索

销售人员接口采用以下参数；其他新建普通目录接口复用相同基础语义，业务专用字段另行登记。

| 参数 | 规则 |
| --- | --- |
| `q` | 可选，去首尾空白，最多 200 字符；姓名、登录账号字面量搜索，不执行用户正则 |
| `page` / `page_size` | 从 1 开始；默认 1／20，页大小上限 100；过滤、授权先于分页 |
| `org_unit_ids` | 可选稳定 ID 集合，最多 100 个；与候选授权求交 |
| `include_descendants` | 只在指定组织时使用；由后端展开，不能扩大授权 |
| `scope_version` | 后续页携带第一页的候选授权版本；版本变化使用现有 `DATA_SCOPE_CHANGED` 语义 |

1. 按显示名、稳定 ID 排序；同名人员可通过登录账号和允许显示的部门区分。
2. 返回现有 `ApiResponse` 信封，`data` 含 `items/total/page/page_size`、`scope_version/policy_version/organization_version/as_of/empty_reason`。人员项只含 `id/name/account/status` 及允许显示的组织标签。
3. `total` 与 `items` 使用相同资格、搜索及授权条件。不得先分页全量账号后在内存过滤权限。
4. 同一请求的授权、资格与组织读取保持一致；复用调用方事务执行器，不在下层开启嵌套事务。
5. 候选版本独立于业务列表版本，不传合同版本给人员接口，不要求两个独立请求共享同一数据库快照。候选授权、组织及资格变化必须使相关候选结果失效；不能只依赖人员数量变化。
6. 候选版本不构成数据快照令牌；跨页发生目录数据变化时重新搜索，前端按 ID 去重，不把多页候选用作正式导出。业务导出继续执行原业务快照合同。
7. 所有普通候选 API 的未知参数、非法 ID、空 ID 片段和超限必须校验；不接受消费列表的 `owner_user_ids` 来预先缩小人员全集。

### 4.2 已选项回显

1. 销售人员回显固定为 `GET /admin/salespeople/selected?ids=...`，复用 `sales_person:list` 与同一资格、DataScope 判定，不要求账号详情管理权限。
2. `ids` 必填、去重、最多 100 个。回显不受搜索词、候选页码及当前搜索结果限制；组织搜索条件也不删除已选值。
3. 返回当前可读项及授权元信息；不存在和无权读取的 ID 均不返回名称及组织信息，不提供可用于区分存在性的额外字段。
4. 回显成功但未返回的已选 ID，前端标为“已选人员（当前不可用）”，允许移除。网络失败、403、版本变化分别处理，禁止统一 `catch → null`。
5. 不因候选搜索、分页、权限变化或回显失败自动清除业务 URL 中的筛选 ID。用户移除或重新应用条件后才能改变业务查询。
6. 业务列表独立校验输入并与自身授权求交；不得因不在候选当前页而忽略筛选，也不得把整个候选目录再次当成业务授权集合。

## 5. 前后端职责与改造边界

### 5.1 后端

1. 单域候选放拥有领域 Service／Repository；跨域只读组合放 `erp-read-models`。Handler 只适配协议，禁止直连数据库。业务域之间不新增直接依赖。
2. 复用现有 `DataScopeService`，不建立并行人员权限服务。Repository 接收明确授权条件，不按登录用户自行推断权限。
3. 合同删除 `ContractListView.owner_options`、`settlement_options` 及专用候选聚合。保留 `apply_list_filters`、当前客户主负责人事实、关键词搜索、排序、行名称、业务版本和授权指纹所需读取。
4. 其他资源采用相同步骤：沿字段追踪生产、序列化、前端消费、行显示、导出及测试，再删除仅服务候选的查询。共享类型仍有未迁移消费者时不得提前删除字段。
5. 不顺带拆分统计、不重写金额算法、不改变历史参与、不修改责任交接、不扩大当前迁移批次。
6. 人员或对象查询必须评估搜索、组织、资格与排序索引；禁止加载全公司账号或全部业务记录后在内存完成授权和分页。

### 5.2 前端

1. 共用 `features/entity-selectors` 的 API、Query hook 和选择器；组件只消费 hook。多选负责人增加远程搜索、加载更多及已选项回显能力。
2. 候选 Query key 包含对象类别、明确用途、候选搜索、组织级联和候选分页；不包含业务列表页码、合同状态、业务时间范围或业务搜索词。
3. 账号切换清空旧缓存；权限、组织、资格变更接入 `features/data-scope/cache.ts` 及 `QueryProvider` 现有失效机制。已选项缓存也必须失效。
4. 授权变化时不能用 `placeholderData` 或旧页继续展示已撤权人员信息。搜索条件变化时是否保留旧结果须与授权失效区别处理。
5. 列表与候选并行、独立加载。候选失败不抹掉已成功的业务列表；业务列表失败不抹掉有效候选。局部权限失败不得被错误地解释为整页业务权限丢失，需核对全局 Query 错误处理。
6. 保持稳定原生 DOM id、显式应用筛选、URL／前进后退／刷新一致性、已选 chip、清除与导出条件一致性。
7. 仅当用户明确选择组织级联时，将相应组织条件传给候选。未在控件上表达的条件不得偷偷影响候选集合。
8. 行名称放在业务行 DTO，或专用且经过业务授权的行展示补充读取中。筛选候选加载失败时，行负责人姓名不得全部退化为 ID。
9. 不固定取前 20／100 条充当完整目录；不让用户必须知道精确姓名才能找到后续页。已选对象跨页时保留名称，清空搜索不会丢失选中值。

### 10.1 后台人员目录与字段映射

### 11.3 资格管理与初始化合同
