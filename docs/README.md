# 员工福利 ERP 文档首页

本文是员工福利 ERP 文档体系的统一入口，说明各文档的职责、事实优先级和阅读路径。本文只负责导航，不定义业务规则、数据约束或页面行为。

---

## 1. 文档体系

文档体系分为五类。其中，建设方案类由第一期和第二期两份文档组成。

| 类别 | 文档 | 职责 |
| --- | --- | --- |
| **建设方案** | [第一期建设说明](erp-phase-1.md) | 约定第一期系统边界、业务单据、部门职责、采购与履约流程、卡券销售单同步、票款和纠错规则 |
| **建设方案** | [第二期建设方案](erp-phase-2.md) | 在第一期基础上约定销售单主责迁移、商城商品与消费协同、API 供应商接入、卡券经营核算和跨系统治理 |
| **规范数据模型** | [两期数据模型](erp-data-model.md) | 统一定义覆盖两期的稳定身份、实体关系、字段、版本、快照、状态、约束、索引、审计和迁移规则 |
| **商城兼容映射** | [商城数据映射](erp-mall-data-mapping.md) | 定义商城现有数据到 ERP 规范模型的识别、转换、校验、同步和历史数据兼容方式 |
| **页面地图** | [页面与导航地图](erp-page-map.md) | 定义两期统一菜单、页面编号、页面职责、角色入口、启用阶段和页面之间的跳转关系 |
| **交互规范** | [页面布局与交互规范](erp-interaction-spec.md) | 定义 ERP 全局框架、工作台、列表、表单、详情、单据动作、批量操作、快捷操作和异常恢复交互 |

## 2. 事实优先级

不同文档只在各自职责范围内作为事实源，不得跨层替代。

| 事项 | 事实源 | 约束 |
| --- | --- | --- |
| 业务范围、系统主责、单据性质、部门职责和业务流转 | 第一期、第二期建设方案 | 第二期只在明确写出的衔接点扩展或修订第一期；其余第一期规则继续有效 |
| ERP 规范实体、关系、字段、状态、版本和技术约束 | 两期数据模型 | 必须实现建设方案，不得用技术设计改变业务规则 |
| 商城旧表、旧字段、历史数据和接口到 ERP 的转换 | 商城数据映射 | 只处理兼容，不得为了照搬商城结构而改变 ERP 规范模型 |
| 菜单、页面编号、页面职责、角色入口和阶段可用性 | 页面与导航地图 | 不得新增建设方案范围外的业务能力 |
| 页面布局、操作方式、反馈、校验和异常处理 | 页面布局与交互规范 | 不得改变页面地图的职责，也不得绕过数据模型和业务状态约束 |
| 文档入口和阅读顺序 | 本文 | 本文不是业务或实现事实源 |

同一事项出现不一致时，按以下顺序处理：

1. 先确认事项属于第一期还是第二期，并以对应建设方案为业务依据；
2. 数据结构问题以两期数据模型为实现依据，商城数据映射只能适配该模型；
3. 页面范围和入口以页面与导航地图为准，具体操作方式以页面布局与交互规范为准；
4. 下层文档与上层事实冲突时，修改下层文档，不得静默改变上层规则。

## 4. 第一期、第二期与详细设计的关系

第一期建设说明建立 ERP 的业务基线。第二期建设方案在该基线上增加跨系统自动化，并只在明确列出的衔接点改变第二期生效后的规则。

详细设计同时覆盖两期，不为两个阶段建立互不相干的模型或页面：

- 两期数据模型使用同一套稳定业务身份，通过阶段适用范围、状态和扩展实体表达能力演进；
- 商城数据映射把一期商城主责数据和第二期迁移数据接入同一规范模型，不建立商城专用 ERP 业务模型；
- 页面与导航地图使用统一菜单和页面编号标识一期可用、二期新增或二期增强的能力；
- 页面布局与交互规范复用同一套 ERP 页面模式，具体动作由业务阶段、主责系统、单据状态和用户权限共同决定；
- 第二期页面和数据扩展不得复制第一期已经存在的销售单、客户、合同、票款、库存和审计能力。

建设方案回答“建设什么、由谁负责、按什么规则流转”；详细设计回答“如何存储、如何进入页面、如何高效操作”。详细设计不得反向扩大建设范围。

## 5. 文档维护规则

1. 业务规则变化时，先修改对应阶段建设方案，再同步修改受影响的数据模型、商城映射、页面地图和交互规范；
2. 数据模型中的每个核心实体和约束必须标注业务依据与一期、二期适用范围；
3. 商城兼容逻辑只写入商城数据映射，不进入规范实体命名和核心业务规则；
4. 页面地图负责页面边界，交互规范负责页面内行为，两者不得重复维护业务规则正文；
5. 新增页面、实体或交互前必须能够追溯到建设方案中的业务能力；
6. 文档不保留“待定、可能、建议”等未确认结论；未确认事项先完成业务决策，再写入事实文档。
