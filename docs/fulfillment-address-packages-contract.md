# 履约收货地址与包裹执行合同

## 适用范围

手工供应商直发、仓库发货任务使用按收货地址分组的作业面。供应商 API 自动子单继续使用其冻结地址及来源观察流程；不得把整张采购的地址复制给单个 API 子单。收货、电子交付、服务履约保持原业务规则。

## 页面与操作

1. 履约办理页使用单栏。状态、当前处理人、进入时间、截止时间、办理说明、影响说明和付款提示合并至顶部；取消右侧办理状态卡片。
2. 每个分组显示收货人、电话、完整地址和物流登记状态。商品行显示该地址应发数量、本次发货数量及关联包裹。
3. 同一地址允许多商品合包、同一商品拆成多个包裹；每个包裹分别登记承运商、物流号及商品数量。禁止跨地址合包。
4. 搜索和折叠只改变展示，不删除录入。保存草稿允许缺少物流信息；先款条件不满足时允许保存草稿，禁止确认发货。
5. 部分发货须把未发商品的本次数量设为零或减少。本次各商品的包裹数量之和必须等于本次发货数量；全部为零禁止确认。
6. 同一任务最多100个地址、100个包裹商品关联，每个地址最多200条商品。数量最多6位小数，禁止负数及超出应发数量。

## 来源与持久化

- 地址来自生效销售版本或真实采购销售分配指向的采购版本行。分组身份由收货人、电话和地址的带密钥指纹生成；客户端只能提交服务端已给出的地址及真实发货行身份。
- `Delivery.packing` 保存本次分配、包裹和商品数量；`packing_addresses_encrypted` 加密保存地址快照。日志的 Debug 输出不得包含收货人、电话和地址。
- 更新和确认请求增加可选 `packing`，与 `tracking_entries` 互斥。旧字段不得覆盖已经按地址保存的草稿。确认手工任务必须使用地址包裹；API 自动子单保留原合同。
- 草稿带销售、采购生效版本标识。来源版本变化后禁止继续确认旧草稿，须核对来源并重新分配任务。禁止用当前地址覆盖历史正式发货记录。
- 旧正式记录继续显示原物流。旧草稿的物流号须由操作人确认地址后录入包裹，禁止自动猜测归属。历史部分草稿无法证明剩余地址数量时明确阻断确认，先核对来源安排并重新分配。

## 确认与后续流程

- 地址校验、来源版本锁、实际发货行拆分、剩余单据及任务创建、库存消费、付款门槛、正式状态、原任务完成、验收待办和审计使用同一事务执行器。任何失败不得留下部分成功结果。
- 正式发货行按地址拆开，同一销售商品发往不同地址时具有不同事实行身份。原草稿行软删除，新行号不得与原单行号重复。
- 未发数量生成新的发货草稿和履约任务；保留原采购销售分配、库存预占、未发地址及准确数量。仓发仅消耗本次数量对应的预占和库存。
- 发货结果、工作台发货详情、销售单交付概览和验收登记提供地址包裹查看入口，沿用 `delivery:detail` 权限。
- 验收按真实发货行计算可验收数量，只显示该行对应包裹；禁止把同商品其他地址的包裹归入该事实。验收冲回继续引用原验收分配的事实行。销售退货仍按销售稳定明细登记，退款仍按原资金与结算规则执行；本功能不把收货地址作为新的财务结算维度。
- 重复确认由原草稿状态和乐观锁拒绝；提交结果未知时沿用原结果查询流程，禁止自动重放确认。

## 上线与回滚

1. 先执行 `backend/scripts/migrations/20261104-delivery-address-packages.mongosh.js` 只读核对，再部署前后端配套版本。新增字段缺省为空，不回填历史地址，不新增索引。
2. 脚本只输出计数，不输出收件信息。存在包裹但缺少加密快照时停止上线，核实原记录。
3. 未产生任何地址快照时可以回退旧应用；产生地址草稿、剩余任务或正式包裹后，禁止直接回退会忽略这些字段的旧写入端。保留字段和事实，采用前向修复，或先停写并提供兼容读取与写入保护版本。
4. 禁止删除正式包裹、恢复软删除的草稿行或合并正式事实行来模拟回滚。迁移脚本及回滚核对必须由发布流程执行，本次开发验证不得连接真实数据库。

## 验收要求

- 两个地址、两个商品，分别完成合包、多包裹、部分发货、剩余任务再次全量发货；逐地址核对数量守恒。
- 校验跨地址商品、重复物流、超量、负数、未覆盖商品、过期来源、付款不足及重复确认均被拒绝。
- 保存后刷新仍保留未完整的包裹；搜索、折叠和编辑商品不丢失草稿。
- 正式详情和验收中，同一销售商品的两个地址只呈现各自包裹。
- 发布验收须单独确认真实事务失败回滚、并发改地址冲突、库存余额及预占变化、剩余待办生成、桌面及窄窗口布局。静态构建与纯规则测试不得代替上述验收。
