# 演示主数据合同

## 1. 使用范围

1. 功能入口为系统管理中的“演示主数据”。运行环境必须显式配置 `[demo] master_data = true`，请求必须通过既有 JWT、RBAC 和 `demo_master_data` 权限检查。
2. 仅在可清理的演示环境执行。生成、删除期间应停止对这批主数据及其单据的其他写入；本接口不提供跨请求的全局业务写入锁。
3. 主数据及其关联数据采用硬删除。删除后不可恢复；再次生成按当前 JSON 创建新记录及新 ID，不恢复旧业务单据。

## 2. 数据源与写入

| 文件 | 内容 |
| --- | --- |
| `backend/crates/erp-processes/src/demo_master_data/master-data.json` | 单位、品牌、分类、仓库、客户、供应商、商品及 SKU 的领域创建请求 |
| `backend/crates/erp-processes/src/demo_master_data/dev-foundation.json` | 公司、岗位账号、必要操作权限、部门、人员范围初始策略、审批链及默认责任规则 |
| `backend/crates/erp-processes/src/demo_master_data/offerings.json` | 每个演示 SKU 的供应商引用、供给价、税率、起订量、可供数量与有效期 |

1. JSON 通过 `include_str!` 随程序发布，修改后必须重新编译、发布。不得依赖进程工作目录中的外部 JSON 文件。
2. 每条主数据采用 `kind` 与 `data`。`data` 复用对应领域的创建请求；金额、税率和日期采用领域接口规定的字符串格式。
3. 业务编号或创建请求的 `idempotency_key` 为稳定种子键。已发布种子不得通过改键表示改名。
4. 商品的 `brand_id`、`category_id`、SKU 的 `base_unit_id` 在 JSON 中填写前置种子键，执行时替换为真实 ID。引用必须先定义，且种类一致。
5. 公司、采购维护人、仓储经办人分别使用 `$company`、`$supplier_maintainer`、`$warehouse_handler` 占位值，执行时解析为当前数据库的实际 ID。
6. 整份主数据清单必须先完成解析、领域字段校验、重复身份和引用校验。通过后按 JSON 顺序分批调用领域写入入口；禁止直接导入 BSON 业务文档。
7. 创建后在 `demo_master_records` 登记实际主键及主体、SKU 等关联 ID。未执行硬删除时，重复生成复用已有记录，并兼容恢复旧版本的软删除记录，不自动改名、不改已有账号密码、不覆盖已发布审批流程，也不替换已启用默认责任规则的负责人。
8. 同编号但未登记归属的字典、商品或仓库必须报冲突，不得自动纳入删除清单。若业务写入成功而登记清单失败，须先核对创建审计和真实 ID，再修复清单；不得仅凭名称认领数据。
9. 新增 JSON 内容时必须执行本合同第 5 节校验。登记存续期间，种子键与真实 ID 的绑定不得被后续写入替换；硬删除成功后移除登记，再次生成允许登记新 ID。
10. 岗位账号写入后补齐默认责任规则：采购账号为默认采购调度人，出纳为供应商付款默认负责人，开票人为销项开票默认负责人。某一层没有启用的默认规则时创建；已有启用规则时保留其负责人。停用规则不参与解析，也不阻止新建启用规则。这些规则不随演示主数据删除。
11. 演示商品维护人由 `dev-foundation.json` 的 `product_maintainer_account` 指定，当前为 `caigou`。创建时必须显式传入该账号 ID，业务组织取其有效主属组织；不得默认归给执行初始化的管理员。账号不存在或缺少有效主属组织时停止生成。
12. 重复生成时，只允许对已登记且实际 ID 一致的演示商品对齐维护人及业务组织。必须调用正式商品移交用例，执行目标资格、组织启用、操作人范围、版本及幂等校验并记录审计；两项均一致时不再移交。旧版软删除商品先恢复，再读取最新版本移交。移交失败须停止并返回错误，不得报告生成完成；已完成批次保留，修正后可重新生成。不得仅按商品编号认领未登记商品。
13. `product` 按[人员开通与访问配置合同](identity-access-workflow-contract.md#41-本人基础与旧配置)提供本人负责的基础范围。采购账号的 `list`、`detail`、`create`、`update` 分别检查动作资格；JavaScript 与 Rust 演示初始化对普通本人项跳过范围记录写入，公司、部门范围继续显式首次初始化。角色只提供动作权限，服务启动不得补写角色范围。既有人员范围及撤权决策必须保留；演示生成不得转换旧表达式、覆盖自定义配置或扩大到公司范围。

14. 基础准备前必须校验岗位与部门引用、全部 `PROCESS_REQUIRED` 类型覆盖、审批链非空及提交人与审批人分离。无需审批类型不得配置审批定义。岗位账号必须是可登录的后台账号。显式执行 `/foundation` 时，为每个演示账号创建或补齐 `role-demo-<登录名>` 专用角色，权限取当前岗位推荐模板与 `required_permissions` 的并集；审批岗位在同一专用角色内同时取得 `approval_instance:read` 与 `approval_instance:decide`。角色创建、补齐和账号追加绑定必须使用发起人的授权及正式审计事务；不得修改原有共享业务角色，不授予超管角色或全局通配权限。重复执行复用固定身份，权限已经覆盖且绑定存在时不写入；专用角色被删除、停用、改名或成为系统角色时拒绝自动修复。完成后重新验证全部岗位权限，失败须返回账号及具体动作。
15. 已发布审批链与演示规格不一致时，保留该版本并阻断基础准备。管理员必须核对并通过正式流程定义入口修正，再次生成；不得以删除业务数据替代审批配置。审批写命令键绑定定义 ID、锁版本或已有业务版本，禁止退役后重建时回放旧发布结果。
16. 人员范围只初始化 `configurable_actions` 中没有记录的动作。销售、采购、运营在有本人基础的业务使用本人范围；销售领导使用本部门及下级。采购的销售单读取、运营的商品读取使用 JSON 明确声明的公司范围。非本人基础目录及其余岗位按初始策略显式配置范围，仍须先具备动作权限；来源继承、审批任务及其他不可配置动作不写独立范围。已有空追加项、旧表达式、自定义范围或撤权不得覆盖。
17. 每个演示 SKU 必须声明一条初始供给。执行商品批次时先按登记 ID 解析供应商和 SKU，以采购身份调用正式供给创建流程，再调用正式商品上架入口，并使用销售开单共用的精确 SKU 资格查询核对当前可售性；停用、失效或停供导致资格缺失时返回错误。所有新供给为手工来源，不建立外部连接或写入外部凭据。供给归采购维护；商品价格、供应商能力、合同有效期及供给可用性仍受领域规则约束。
18. 卡券种子必须只有一个 SKU，且 SKU 编号等于商品编号。执行时必须使用正式卡券原子创建入口，同时生成商品、唯一 SKU 与卡券扩展修订，不得仅创建普通商品代替卡券档案。
19. 重复生成补齐供给并将已登记商品上架；不改写已存在供给的人工修订、价格或可供状态。供给幂等键包含当前 SKU 和供应商真实 ID，主数据硬删除重建后不得回放旧身份。供给业务记录、修订、可供投影沿既有关联图清理；供给命令回执保留，不将回执计入当前有效供给。
20. 客户、供应商、仓库缺失前置条件，或客户/供应商负责人对齐失败时，当前批次必须返回错误，不得把跳过提示视为完成。已完成独立事务保持已提交状态；修正原因后从失败游标重试，或从零重新生成。

### 2.1 已有环境更新

1. 按[人员开通与访问配置合同](identity-access-workflow-contract.md)执行普通岗位人员范围迁移预览及审核，在切换新版本前完成所需人员配置。迁移阻断必须逐项处理；不得以启动时补写角色范围代替迁移。有效内建超级管理员固定拥有全公司范围，无需通过迁移或补写人员记录取得商品、供应商等业务范围；此规则不改变演示主数据的岗位责任归属。
2. 使用具备演示数据生成及商品移交权限的管理员，在“演示主数据”页面再次执行“生成演示主数据”，等待全部批次完成。不得通过先删除再生成处理商品可见性。
3. 使用 `caigou` 刷新商品列表，核对演示商品的维护人为采购账号。若仍不可见，先检查角色是否授予 `product` 对应动作，再检查此账号各动作的人员范围与当前商品责任归属。具备动作资格且没有人员记录时，按商品当前维护人使用本人基础范围；旧记录保持原表达式，不自动叠加本人。既有停用、撤销或自定义配置由管理员核定后调整，生成接口不得自动覆盖。

### 2.2 演示执行顺序

1. 编译并重启目标环境的新后端；本地开发使用 `bash scripts/restart-backend.sh --build`。确认 `[demo] master_data = true`。
2. 以管理员进入“系统管理 → 演示主数据”，执行生成，先完成基础准备，再持续请求所有主数据批次。任一请求失败立即停止，不得展示“全部流程已就绪”。接口直接调用时，必须先执行 `POST /admin/demo-master-data/foundation`，再从 `cursor=0` 开始生成至 `done=true`。
3. 当前清单为 102 条主数据：6 个单位、8 个品牌、13 个分类、6 个仓库、24 个客户、18 个供应商、27 个商品/SKU；另准备 27 条供给、10 个岗位账号和 12 类审批定义。数量代表初始化清单，不代表已有业务单据或库存余额。
4. 使用 `xiaoshou` 开单，`caigou` 承担采购与电子/服务履约，`cangchu` 承担实物收发与库存；销售领导 `lisiyong`、运营 `yunying` 和财务总监 `caiwu` 按审批链审批。`fukuan` 提交回款、退款、冲正并登记付款；`kaipiao` 执行开票。`caiwu` 不得提交需要自己审批的资金单。新建账号初始密码为 `123456`；已有密码保留。
5. 先选演示客户、商品和供给，再按正常界面创建业务单据。合同、合同附件、交付凭证、开票资料及本次交易金额由演示操作者按业务入口提供。初始化不预造审批通过记录、库存余额、票款或已完成任务。
6. 历史环境保留的人员范围可能限制可见性；默认责任规则和更具体的客户、供应商、SKU 规则可能把任务指派给其他人员。演示前必须核对当前范围及实际任务负责人，不得仅凭账号角色名判定可执行。`caiwu`、`fukuan`、`kaipiao` 的演示专用角色按 JSON 显式包含 `finance_ledger:read`；此授权仅在管理员执行演示初始化时补齐，不由服务启动恢复，也不扩大其他账号的角色权限。演示角色及账号绑定随账号保留，不随主数据删除。

| 演示流程 | 数据与操作要求 |
| --- | --- |
| 仓库发货、拆分履约、先款后货、库存查询、取消释放预占 | 使用 `DEMO-MD-SKU-01` 至 `24` 的实物；先完成采购收货取得库存，再销售仓发；分别执行部分分配、付款条件及取消分支 |
| 供应商直发 | 使用实物 SKU 的一件代发供给，由采购完成供应商直发及交付确认 |
| 电子交付 | 使用 `DEMO-MD-SKU-25`（虚拟）或 `DEMO-MD-P-27`（卡券）；供应商为 `DEMO-MD-SUP-17`，按界面登记演示兑换信息 |
| 线下服务履约 | 使用 `DEMO-MD-SKU-26`，供应商为 `DEMO-MD-SUP-18`；采购登记服务执行，销售完成客户验收 |
| 审批驳回、采购驳回、销售变更、采购变更 | 按当前单据类型绑定演示审批链，指定节点账号处理；变更必须从已经生效的原单发起 |
| 库存调整 | `cangchu` 在演示仓库提交调整，`caiwu` 审批成本影响 |
| 客户回款、客户退款、回款冲正 | `fukuan` 经办；按 JSON 审批链交由销售领导和/或财务总监审批；必须具备真实来源余额 |
| 供应商付款、供应商退款、付款冲正 | 采购审批通过后由付款任务负责人登记付款；退款/冲正由 `fukuan` 提交并按对应链审批 |
| 销售退货、采购退货 | 从已交付/已收货的来源行发起，按实际退回数量执行库存与应收应付处理 |
| 开票申请、销项开票、进项登记、红票 | 销售提交开票申请、总监审批、开票任务负责人开票；红票须关联已经登记的蓝票及合法来源 |
| 供给失效异常 | 在完成正向开单后停用或调整演示供给，验证新开单/后续执行阻断；重复生成不会覆盖人工供给状态 |

本清单覆盖当前手工业务流程的主数据前置条件。供应商真实 API、商城外部接入和真实附件存储需各自配置并单独验收；生成接口不声明外部系统可用。所有流程的浏览器执行与数据库事务验收必须另行记录，库单元测试不得替代。

## 3. 删除合同

1. `DELETE /admin/demo-master-data` 不接收 `purge` 开关。每批由后端清理关联数据及最多 8 条已登记主数据；旧版本 `removed=true` 的软删除记录也必须处理。
2. 清理根仅来自登记清单的实际客户、主体、供应商、仓库和 SKU ID。删除前补齐演示商品当前及历史 SKU ID；不按显示名称、编号前缀或关键词删除。
3. 业务关联由 `derived_graph.rs`、主数据专属子记录由 `master_graph.rs` 显式登记，数据库访问必须绑定拥有领域公开的 Repository。最终物理删除条件只能为业务 `id` 的精确集合；不得清空集合。
4. 关联范围覆盖图中登记的合同、选品、销售、采购、履约、退货、票款、供给及结算、库存、审批、待办、单据关系和附件关系。新增业务关联时必须同步登记仓储、外键和行为测试；不得假定未登记的新集合会自动清理。
5. 明细命中后必须继续定位父单据及其子记录。库存调整明细必须带出调整单主表、审批和待办。
6. 命中的记录包含非演示 SKU 时，必须在任何物理删除前返回错误。不得只删除混用单据中的部分商品行。
7. 关联遍历必须达到不再增长的状态；超过 128 轮时返回错误，禁止执行已收集部分的删除。
8. 登记读取、关联发现、混用校验、主数据与关联数据硬删除、残留校验、登记清理及成功审计必须处于同一个事务。任何步骤失败必须回滚当前批次；提交结果未知时沿用统一错误，不自动重放。
9. 删除后必须检查已收集 ID 及根 ID 重新发现的关联记录。存在残留时不得报告清理成功。
10. 主数据按依赖顺序硬删除，商品先于字典；成功后按种子键和实际 ID 移除对应登记。中断后再次调用从剩余登记继续。不同批次相互独立，整个分批操作不是一个总事务。多个已登记角色共享的主体须等最后一个角色删除时再清理。
11. 主数据专属的历史修订、SKU、客户归属、主体联系/地址/银行/税务资料、供应商能力/资质/评级、仓库策略、客户与供应商资料创建命令一并硬删除，避免重建时命中旧命令。岗位账号、部门、公司主体、权限、审批定义、默认采购责任规则、默认财务责任规则和审计保留。文件资产和 S3 对象保留，清理业务附件关系不代表销毁文件。
12. 主体、品牌、分类、单位被未登记主数据引用，或仓库策略引用非演示 SKU 时，必须在任何删除前拒绝当前批次。已登记主体成为公司主体时必须拒绝删除。

## 4. HTTP 合同

| 方法与路径 | 请求 | 结果 |
| --- | --- | --- |
| `GET /admin/demo-master-data` | 无 | 开关、JSON 计划数量、登记清单的有效数量和旧版软删除待清理数量 |
| `POST /admin/demo-master-data/foundation` | 无 | 基础岗位、审批和默认责任规则准备结果 |
| `POST /admin/demo-master-data` | `{ "cursor": 0 }` 起，后续使用 `next_cursor` | 本批创建、恢复、跳过数量及通知 |
| `DELETE /admin/demo-master-data` | 无 | 本批主数据删除数量、关联记录物理删除数量和 `done` |

`active`、`removed` 为登记清单状态，不是对所有业务集合的实时盘点。硬删除完成后两者均为零；`removed` 不累计硬删除历史。删除响应的 `removed` 为本批完成清理的主数据登记条数；`derived_removed` 为实际删除的关联记录条数，包含主数据子记录、历史修订和创建命令，不等于单据主表数量。前端持续请求至 `done=true`，任意错误立即停止并展示错误。
