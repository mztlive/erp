# 选品册与销售方案合同

## 1. 适用范围

本合同适用于销售选品册、客户公开选品页、个人提货券及选品结果导出。

1. 每本选品册绑定一家客户，创建时将当前认证操作人员保存为销售负责人，将其有效主属组织保存为业务组织；公开提交人不得成为内部销售负责人。
2. 商品来源为当前筛选或当前勾选。形态为单品或套餐，创建后不得切换来源类型、形态及提交方式。 当前筛选来源的 `pool_filter.price_kind` 与价格上下限一同保存，取值为 `dropship`、`bulk` 或 `market`，缺省为 `dropship`。准备与重新准备必须按该单一价格口径收集商品，禁止按另一价格替代；该条件不改变选品报价规则。
3. 选品只保存客户确认结果。提交生成销售方案，不创建销售单、审批、应收、履约或库存预占。
4. 商品、图片和报价以发布批次快照为准。公开页不得展示供应商编号、内部四价、采购成本或集采起订数量。

## 2. 提交方式

| 方式 | 客户操作 | 会话与方案 | 金额 |
| --- | --- | --- | --- |
| 按份采购 `BY_QUANTITY` | 选择商品或整套套餐，填写份数 | 同册共享一个会话，提交生成一份方案并结束整册选品 | 使用冻结报价计算数量和合计 |
| 商城兑换 `MALL_REDEEM` | 勾选商品或整套套餐，不填写份数 | 同册共享一个会话，提交生成一份方案并结束整册选品 | 不保存数量、行金额及采购合计 |
| 提货券 `PICKUP_VOUCHER` | 输入独立提货码，选择商品、填写数量，再填写本人收件信息 | 每码独立会话，每码最多生成一份个人方案 | 每人独立核算，合计不得超过该册每人额度 |

单品与套餐均支持提货券。套餐按整套选择，每份套餐包含每个成员商品一件；不同套餐中的相同商品须分别保留来源。

## 3. 创建、准备与发布

销售按以下顺序操作：

1. 在商品池选择客户、选品形态、提交方式及商品来源，设置 8 至 64 个字符的访问密码。创建表单不得提供销售人员或组织选择。服务端在创建事务内将当前认证操作人员绑定为销售负责人，并读取其唯一有效主属组织作为业务组织；请求不得指定或覆盖这两个归属字段。账号无效、缺少有效主属组织、组织停用或归属不在创建权限范围内时必须拒绝创建；缺少组织时提示维护组织成员。已有选品册及其方案归属不随本次规则调整改写。
2. 提货券模式必须填写大于零的每人额度和 1 至 1000 个提货码数量；其他方式不得填写这两个字段。
3. 套餐填写档位、目标金额、容差、期望套餐数和成员商品数。单品不填写档位。
4. 创建后由后台准备任务冻结商品池、报价和图片。任务失败时恢复可操作状态；不得发布不完整批次。
5. 销售核对准备结果，必要时移除陈列项或重新准备，再提交当前册版本和确认批次发布。勾选来源的调整必须展示商品名称和 SKU 业务编号，支持在公司商品池内搜索、分页、添加及移除；不可售的原来源必须显式提示并保留到用户移除，禁止静默删选或展示 UUID 文本编辑框。
6. 发布须重新校验精确 SKU 修订、启用、上架、一件代发报价及有效供给资格。资格变化时拒绝发布，销售重新准备后再确认。
7. 提货券发布时生成指定数量的独立提货码。销售通过“导出提货码”取得发放表，每人分发一个码，同时提供选品链接和密码。

链接有效期为发布后 30 天。换链使原链接立即失效，不延长原有效期。

列表响应必须返回当前有效且未移除的陈列数量 `display_count`，以及已关联方案的业务编号 `proposal_no`。未准备册显示 0，尚无关联方案显示“—”；普通方式已提交册提供方案入口。提货券的多份个人方案继续从个人明细读取。

套餐准备未产出陈列时必须区分金额或件数无匹配与组合主图生成失败。缺图失败提示需包含待补图商品名称和重新准备动作，不得只提示“未得到可交付套餐”；准备失败不得替换原批次。

## 4. 密码访问

1. 所有已生成选品册的公开商品、会话、提交、回执和图片均须通过密码访问验证。
2. 仍开放且未解锁的公开页只能返回锁定状态及填写密码所需的提交方式信息；已结束册返回空的结束状态。两者均不得返回商品、价格、选择、方案或收件信息。
3. 新建册必须设置密码。历史册缺少密码时保持锁定，销售在详情页使用“设置访问密码”补设后开放访问。
4. 密码保存带盐慢哈希；含密码的幂等命令指纹使用应用密钥派生的 HMAC，不得保存可直接猜测密码的无密钥快速哈希。管理端详情、提货码表及选品明细不得返回原密码或密码哈希。
5. 成功解锁签发最长 12 小时的访问凭证，且不得超过选品链接到期时间。凭证绑定本册、当前链接版本、当前密码和当前个人会话。
6. 修改密码、换链、撤销、关闭或到期后，原凭证不得继续读取商品、选择、回执或图片。
7. 解锁、读取、保存、提交和图片请求执行服务端限流；密码、提货码、访问凭证及地址不得写入日志。
8. 公开响应使用 `private, no-store`；公开图片不得进入共享缓存。
9. 密码维护与操作审计在同一事务中完成；审计仅记录册身份、动作及认证操作人，禁止保存密码、提货码、访问凭证或收件信息。

销售可在已生成册详情设置或更新密码。密码更新须提交当前册版本，保留已选内容、个人提货码和已生成方案。册处于准备中或仍关联活动准备任务时，服务端须拒绝密码维护，且不得修改密码、册版本或任务身份；销售须等待准备结束后再操作。

## 5. 个人提货券

领取人按以下顺序操作：

1. 打开选品链接，输入册密码及本人提货码。
2. 选择该册中的商品或套餐，填写 1 至 100000 的整数数量。页面显示本人额度、当前合计和剩余额度。
3. 保存或核对选择。超过额度时拒绝保存和提交；服务端按冻结报价重新计算，不接受浏览器提交的金额作为依据。
4. 核对商品后填写收件人、电话、省、市、区县及详细地址。所有字段必填，首尾空白须去除。
5. 电话允许 7 至 20 位数字和可选前导加号；姓名及省市区最长 64 字符，详细地址最长 256 字符。
6. 确认提交后查看本人回执。提交冻结本人的选择和收件信息，不能再次修改或再次领取额度。
7. 更换提货码时退出当前选品，再输入另一提货码。浏览器查询缓存及未完成请求必须按个人会话隔离。

服务端执行以下约束：

- 提货码由系统生成，使用随机高熵代码；查询使用哈希，管理端复制使用密文。不得接受用户自行指定的参与人身份创建额度。
- 一个码只能访问自己的选择、金额、地址和回执；同册另一人的记录不得出现在公开响应。
- 错误码、其他册的码及缺少码的请求均不得进入个人选品。
- 每次保存和最终提交均核验额度；拒绝时不改写已保存选择、会话版本或方案。
- 每人最多一份销售方案，由数据库同册同参与人唯一索引保证。重复提交返回原方案，不追加第二份方案。
- 一个人提交后只冻结个人会话，整册保持已发布，其他人可继续选品。销售关闭册后停止办理，已有方案和后台明细继续保留。
- 不同人的同时提交须各自产生独立方案；同一码的并发或重试不得重复生成方案。

## 6. 保存与提交合同

1. 保存提交完整选择集合及预期会话版本；禁止外册商品、重复陈列项、缺少数量或非法数量。
2. 版本冲突时整次拒绝，客户重新核对服务端结果后再操作；不得覆盖他人的更新。
3. 最终提交使用已保存会话版本。提货券提交同时携带完整收件信息，冻结到个人销售方案。
4. 一次提交在同一事务内创建方案表头、陈列明细和 SKU 明细，冻结会话并保存重试结果。任一步失败不得留下部分方案。
5. 保存与提交重试必须使用原请求键和原载荷。访问资格须在每次重试时按当前册事实重新校验。
6. 普通方式的提交冻结整册；提货券的提交仅冻结个人。不得以共享会话或册级重试记录串接不同提货人。
7. 多人保存或提交发生已明确回滚的瞬态事务冲突时，系统最多自动重试三次，每次重验当前访问资格并复用原请求。个人版本冲突及结果未知不得自动重放。

## 7. 管理端查询与导出

1. 密码维护复用选品册维护资格；提货码读取复用选品册复制链接资格；个人明细读取与导出复用选品册详情读取资格。
2. 各入口同时校验当前册的销售负责人、业务组织范围及客户访问资格，不得仅凭持有册 ID 读取记录。
3. 提货券详情显示每人额度、提货码总数、已提交人数、码办理状态及个人方案、商品和收件信息。
4. “导出提货码”生成 XLSX，每行一个码，包含提货码和选品状态，不包含密码。
5. “导出全部选品明细”读取本册所有已提交方案，生成 XLSX；每个人的每个 SKU 明细一行。
6. 明细列包含提货码、方案编号、提交时间、收件人、电话、省、市、区、详细地址、商品名称、规格、数量、单位、含税单价、行金额和个人合计。
7. 金额按十进制文本保存，电话及提货码按文本导出；用户文本不得成为电子表格公式。
8. 销售方案列表仅返回摘要，不得返回个人收件姓名、电话或地址。收件信息须经方案详情或选品册个人明细的读取资格校验后返回。

## 8. 从销售方案创建销售单

1. 按份采购 `BY_QUANTITY` 的单品与套餐方案提供“创建销售单”入口。操作人必须具有 `sales_order:create`、来源方案详情及客户读取资格。商城兑换、个人提货券方案不得使用此入口。
2. 点击入口只读取预填内容，不写销售单、不启动审批。开单页带入方案客户及全部 SKU 明细，保留冻结 SKU 修订、规格、单位、数量和含税单价。不同套餐的相同 SKU 保持独立行；报价按手动成交价带入，不得被当前参考价覆盖。
3. 来源客户和“实物与服务”业务性质固定。销售可调整商品、数量和成交价，并补齐福利场景、结算与开票条款、交付日期。来源方案明细不得随销售单编辑改变。
4. 开单方式沿用现有合同或凭证规则。关联合同必须属于方案客户；无合同时仍须上传 PDF 或图片凭证，方案来源不得替代开单凭证。税率、付款条件和交付日期不得从方案总额推断。
5. 保存草稿或提交时，服务端在销售创建事务内重验方案当前访问资格、客户一致性、业务性质、销售创建权限及 SKU 可售资格。方案冻结 SKU 修订已不可用于开单时拒绝保存，销售须重新选择有效商品。
6. 销售单保存服务端生成的 `selection_source`（方案身份与编号），在详情及草稿续编中提供来源链接。普通保存、后补合同和提交不得改写来源。历史销售单缺省无来源。
7. 创建复用销售开单的完整载荷与请求键，重复点击或结果未知重试不得重复建单。方案为可复用开单来源，不设置一方案一销售单限制；销售重新发起一次独立开单可创建另一张销售单。
8. 新增字段采用可选默认值，不新增集合或索引，不要求回填历史数据。回滚前停止新方案开单入口；已保存来源字段须保留，不得清除。

### 8.1 开单接口

| 方法与路径 | 合同 |
| --- | --- |
| `GET /admin/sales-orders/selection-proposals/{id}/basis` | 以销售创建权限进入，同时校验来源方案与客户访问资格；仅返回按份采购方案的客户、来源及 SKU 开单内容，不向公开回执暴露 SKU 内部引用 |
| `POST /admin/sales-orders` | 可选 `selection_proposal_id`；不接受客户端提供来源编号；沿用现有草稿、凭证、意图和请求键合同 |
| `GET /admin/sales-orders/{id}` | 返回可选 `selection_source`；普通销售单及历史记录为空 |

## 9. HTTP 接口

管理端主路径为 `/admin/sales-selection-books`；`/admin/sales-selection-booklets` 为兼容同义路径。

| 方法与路径后缀 | 请求 | 响应 |
| --- | --- | --- |
| `POST /` | 客户、形态、提交方式、商品来源、密码及请求键；不含负责人和组织 | 服务端绑定当前操作人员及其有效主属组织，返回准备中详情；旧客户端附带的归属字段忽略，不参与归属与请求指纹 |
| `POST /{id}/access-password` | 当前版本、请求键、新密码 | 更新后的册详情 |
| `GET /{id}/vouchers` | 当前账号和册身份 | 该册个人提货码及提交状态列表 |
| `GET /{id}/selection-details` | 当前账号和册身份 | 所有已提交个人方案、商品及收件快照列表 |

公开主路径为 `/public/selection/{token}`；`/public/sales-selections/{token}` 为兼容同义路径。

| 方法与路径后缀 | 访问合同 |
| --- | --- |
| `GET /`、`GET /receipt` | 开放册无有效访问凭证返回锁定页，有凭证只返回该会话内容；结束册返回空结束页 |
| `POST /unlock` | 请求 `password` 和可选 `voucher_code`；返回 `access_token` 及本人 `page` |
| `POST /session`、`PUT /session` | 请求头 `X-Selection-Access`，提交选择和预期版本 |
| `POST /submit` | 同上；提货券追加 `recipient` |
| `GET /images`、`GET /images/{asset_id}` | 图片 URL 携带 `access_token`，同时校验资产属于当前册 |

## 10. 迁移与上线执行

存量库上线前执行以下步骤，不得直接以新代码覆盖旧唯一索引：

1. 停止旧版 API 和准备 worker，完成数据库备份并确认恢复入口。
2. 对目标库运行 `backend/scripts/migrations/sales-selection-vouchers.js` 的默认 `check` 模式，核对重复会话、重复方案、提货码冲突、旧索引和缺密码册数量。
3. 使用 `ERP_SELECTION_MIGRATION_MODE=apply` 执行同一脚本：旧记录参与人统一为空字符串，建立同册同参与人唯一索引，再删除旧册级唯一索引。
4. 启动新版，验证旧册锁定、后台设置密码、普通方式提交及个人提货券办理。
5. 按职责对已发布历史册补设密码，再向客户分发新访问信息。

回滚前先关闭或撤销所有仍开放的公开链接，再停止新版 API 和 worker。仅在不存在提货券册、个人会话、个人方案及开放公开链接时允许脚本 `rollback`；存在个人业务数据时禁止退回只能容纳一册一方案的旧版。密码新增字段及已有方案不得随回滚删除，旧版不得重新开放已受密码保护的链接。

## 11. 验收

根目录 `e2e/tests/flow-27-selection-sharing.spec.ts` 必须覆盖：

- 普通和商城方式的密码解锁、错误密码、匿名商品及图片拒绝、刷新恢复及换链失效。
- 历史缺密码册默认锁定，销售补设密码后恢复访问。
- 多个独立码保存、选品和地址隔离，每人额度独立核验，超额拒绝且无写入副作用。
- 地址必填、个人自动生成方案、重复提交不重复创建，一个人提交后其他人仍可办理。
- 密码变更使旧授权失效，新密码保留原选择和个人回执。
- 不同参与人同时提交、后台完整明细与真实 XLSX 下载逐行核对。
- 公开页剩余额度使用精确十进制计算；方案列表不返回收件信息，已授权详情和明细保留收件快照。
- 套餐提货券按份数展开 SKU，同一 SKU 在不同套餐中保留来源，并在个人方案及 XLSX 中逐行核对。
- 同一码的两个客户端同时提交后只有一份个人方案；原命令重试返回该方案。
- 后端完成真实提交后中断浏览器响应，刷新恢复本人回执，并用原命令确认未重复生成方案。

库单元测试须覆盖创建请求不含归属字段时绑定认证操作人员及其组织、客户端伪造归属字段无效、服务端归属为空时拒绝创建，以及准备中及残留活动任务时的密码维护拒绝、拒绝前后册状态与任务身份不变、无活动任务时的正常密码维护。

E2E 使用隔离数据库、API 进程及上传前缀；源开发库只读复制。普通 Rust 验证限定库单元测试，不新增真实 MongoDB 集成测试。
