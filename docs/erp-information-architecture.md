# ERP 信息架构与作业流规范

本文定义 ERP 桌面端用户实际看到的导航、工作区分组、任务接力、命令入口和单据视图形态。

本文与既有文档的分工是明确的：

- [页面与导航地图](./erp-page-map.md) 是**页面登记册**，回答"每个业务对象在系统里有没有归宿、稳定编号和稳定路由是什么"。它的编号和路由规则继续有效，本文不修改其中任何一条。
- 本文是**信息架构**，回答"用户上班第一眼看什么、下一步去哪、108 个页面如何收敛到可用的导航"。
- [页面布局与交互规范](./erp-interaction-spec.md) 是**页面内行为**，回答"进入某个页面之后怎么操作"。

三者的关系是：登记册保证完备，信息架构保证可用，交互规范保证正确。

---

## 1. 问题与设计原则

### 1.1 直接落地页面登记册的后果

页面登记册共 108 个稳定页面编号，其中 64 个带菜单路径、44 个是上下文页面。按登记册直接生成导航会得到 **10 个一级菜单、64 个菜单叶子**，并且这 108 个页面中有 80 个（74%）是通用列表或详情。

这样的系统每个业务对象都能找到，但没有任何一条路径告诉用户"现在该做什么、做完去哪"。原因是菜单按**业务对象（名词）**组织，而人的工作按**任务（动词）**推进。

### 1.2 五条设计原则

1. **导航层与登记层分离。** 导航只暴露作业入口，登记册的完整性由路由、全局搜索和命令面板保证，不由菜单保证。
2. **一次导航跳转最多进入一个工作区。** 同一业务连续动作在工作区内用页签切换，不回到菜单重新寻路。
3. **每个正式动作完成后必须给出下一步的可执行入口。** 用户永远不需要自己回菜单找下一站。
4. **默认视图承载 80% 场景，其余能力按需展开。** 列表默认列、详情默认页签、筛选默认条件都按最高频场景设定。
5. **稳定路由不变。** 本文不新增、不改名、不重定向任何既有路由；工作区是导航层的分组呈现，页签切换即切换到该页面自身的稳定路由。

### 1.3 本文新增的页面

信息架构只新增两个页面，其余全部是既有页面的重新编排：

| 页面编号 | 页面 | 路由 | 首次启用 | 新增理由 |
| --- | --- | --- | --- | --- |
| `ERP-WK-005` | 我的单据 | `/my-documents` | 一期 | 登记册缺少"我发起的、尚未完成的工作"视图；用户提交后失去对自己单据的跟踪面 |
| `ERP-PUR-022` | 统一交付队列 | `/fulfillment` | 一期 | 交互规范 §9.5 已声明代发、电子交付和服务履约共用同一流程，登记册却拆成 3 个入口 |

两个编号按登记册第 1 章规则新增，不改作其他页面，不占用已有编号。

## 2. 导航契约

### 2.1 12 个工作区

```text
┌ 作业区 ──────────────────────────────────────┐
│  工作台        我今天要处理什么               │
│  我的单据      我发起的还没走完的             │
├ 业务区 ──────────────────────────────────────┤
│  销售          销售单、变更、验收、退货        │
│  采购          采购单、变更、退货              │
│  履约          交付队列、入库、出库、供应商订单 │
│  库存          余额、预占、流水、调整、仓库     │
│  财务          应收侧、应付侧、成本与纠错       │
│  卡券销售      卡券单、商城同步、消费与回填     │
├ 支撑区 ──────────────────────────────────────┤
│  主数据        客商、商品与供给                │
│  异常与对账    业务异常、接口错误、接口对账     │
│  经营分析      6 个分析页                      │
│  系统管理      权限、审计、导入、迁移、监控     │
└──────────────────────────────────────────────┘
```

**66 个菜单页面 → 12 个导航入口。** 110 个页面编号一个都不删除，44 个上下文页面继续从关联对象进入。

导航分三段并用分隔线区分：作业区常驻顶部且不可折叠，业务区按角色裁剪，支撑区默认折叠为一组。

### 2.3 页签规则

1. 页签切换执行真实路由跳转，浏览器前进后退、刷新和链接分享行为与直接访问该路由完全一致。
2. 每个页签独立保存筛选、排序、分页和滚动位置，规则沿用交互规范 §2.3。
3. 页签数超过 6 个时，低频页签收进"更多"下拉；哪些是低频由角色默认视图决定，不由页面顺序决定。
4. 无权限的页签不显示。工作区全部页签都无权限时，该工作区不进入导航。
5. 未启用阶段的页签不显示，沿用登记册第 2 章的阶段控制，不使用页面空态代替。

### 2.4 角色导航裁剪

## 3. 任务接力

### 3.1 问题

交互规范 §14.2 要求正式动作完成后展示"下游任务、下一责任人、查看结果入口"，但没有要求提供**下一步的可执行入口**。结果是每完成一步，用户都要自己回导航寻找下一个页面。

### 3.2 规则

每个正式动作的结果面板必须包含 `nextActions`：当前用户可以立即执行的后续动作，带预填上下文。规则如下：

1. `nextActions` 由服务端计算并随 `FormalActionResult` 返回，前端不推导。
2. 每项包含动作名、目标路由、预填参数、是否可执行、不可执行时的阻断原因和责任人。
3. 下一步责任人不是当前用户时，仍然显示该动作但禁用，并写明责任部门与责任人，不隐藏。
4. 结果面板中的下一步动作按钮使用具体业务动词，沿用交互规范 §15.1 第 1 条。
5. 用户点击下一步动作时，目标页面必须已带入来源单据、客户、明细和数量，不要求重新选择。

### 3.3 实物与服务履约链的接力表

| 完成的动作 | 下一步动作 | 目标 | 预填内容 |
| --- | --- | --- | --- |
| 销售单提交 | 无（等待采购确认） | — | 显示采购责任人和时限 |
| 采购二次确认通过 | 生成采购单草稿 | `/purchase-orders/new` | 供应商、明细、数量、成本、履约方式、来源销售单 |
| 采购单财务审核通过 | 登记供应商付款 | `/finance/supplier-payments` | 供应商、采购单、应付金额 |

| 采购入库过账 | 创建仓发出库 | `/inventory/shipments` | 来源销售单、有效预占、SKU、可出数量 |

### 3.5 任务内闭环

当任务的完成条件依赖尚未登记的从属事实时，必须在**当前任务上下文内**用侧栏完成登记，不要求用户离开任务。

适用场景固定为：

| 任务类型 | 侧栏内可登记的从属事实 |
| --- | --- |
| `CARD_FUNDS_REVIEW` | 客户回款、销项发票、核销分配 |
| `CARD_FUNDS_DELTA_REVIEW` | 反向核销、退款、冲正、红票 |
| `PURCHASE_ORDER_REVIEW` | 无（财务只审核或驳回） |
| `INVENTORY_ADJUSTMENT_REVIEW` | 实物依据附件 |
| `SUPPLIER_SETTLEMENT_REVIEW` | 差异确认、成本费用登记 |

规则：

1. 侧栏调用的是与独立页面完全相同的强类型命令，服务端校验、幂等和审计不因入口不同而变化。
2. 侧栏内的登记成功后，主任务面板立即刷新余额、差额和可提交状态，不要求手工刷新。
3. 任务租约在侧栏操作期间继续心跳续期，不因打开侧栏而释放。
4. 侧栏不承载正式审批决策本身，只承载该决策所依赖的事实登记。
5. 交互规范 §8.4 "复核面板不提供填写捷径"继续有效：侧栏登记的是正式事实，不是复核结论的快捷填写。

## 4. 命令面板

### 4.1 定位

交互规范 §2.2 和 §12 都写了 `⌘/Ctrl+K` 是"全局搜索与命令"，但从未定义"命令"的内容。命令面板是 12 个工作区之外覆盖全部 108 个页面的主要手段，必须落实。

### 4.2 结构

```text
┌ ⌘K ─────────────────────────────────────────────────────┐
│ 搜索或输入命令…                                          │
├──────────────────────────────────────────────────────────┤
│ 动作                                                     │
│   新建实物与服务销售单                        Alt+N      │
│   登记客户回款                                           │
│   导入客户                                               │
│ 前往                                                     │
│   财务 › 客户应收                                        │
│   库存 › 库存流水                                        │
│ 对象                                                     │
│   SO-20260731-001  XX公司  已生效                        │
│   XX有限公司  客户                                       │
└──────────────────────────────────────────────────────────┘
```

三组固定顺序为动作、前往、对象。

### 4.3 规则

1. **动作**和**前往**来自 `GET /context` 的 `commands`，登录后一次取得并在本地模糊匹配，输入过程零网络往返。
2. **对象**来自 `GET /search`，按交互规范 §4.2 的规则在停止输入后请求，不逐字符请求。
3. 命令清单按当前用户权限计算。无权限的动作和页面不出现在清单中，不显示为禁用项。
4. 命令面板中的动作不绕过任何确认层。正式动作命令只负责打开对应页面或确认层，不直接提交。
5. "前往"覆盖全部 66 个菜单页面，包括未在当前角色导航中显示的页面。这是导航裁剪不损失可达性的保证。
6. 搜索结果沿用交互规范 §2.2 的边界：不返回卡号、卡密、卡实例绑定手机号和连接密钥。
7. 最近使用的 5 条命令在空输入时置顶，按当前用户本地存储，不进入服务端。

### 4.4 必备命令清单

动作类命令至少覆盖：

| 命令 | 目标 |
| --- | --- |
| 新建实物与服务销售单 | `/sales-orders/new?businessType=GOODS_SERVICE` |
| 新建卡券销售单 | `/sales-orders/new?businessType=VOUCHER`（阶段未开放时不出现） |
| 新建采购单 | `/purchase-orders/new` |
| 登记客户回款 | `/finance/customer-receipts`，打开创建层 |
| 登记供应商付款 | `/finance/supplier-payments`，打开创建层 |
| 登记销项发票 | `/finance/sales-invoices`，打开创建层 |
| 登记进项发票 | `/finance/purchase-invoices`，打开创建层 |
| 创建采购入库 | `/inventory/receipts`，打开创建层 |
| 创建仓发出库 | `/inventory/shipments`，打开创建层 |
| 创建库存调整 | `/inventory/adjustments`，打开创建层 |
| 导入客户 / 供应商 / 商品 / 可销售项目 | `/system/imports`，预选导入对象 |
| 打开我的下一条待办 | 队列内下一条，直接领取 |

## 5. 单据视图与纸质投影

### 5.1 三种视图形态

正式单据详情提供三种视图，用同一份服务端数据渲染，在页头右上角切换：

| 视图 | 用途 | 默认场景 |
| --- | --- | --- |
| 结构视图 | 可操作。多轨状态、并行责任、页签分区、正式动作 | 详情页默认 |
| 单据视图 | 只读整体阅读。纸质排版、打印、导出 PDF、对外发送 | 审批与确认场景默认；发票、出入库单、结算单详情默认 |
| 对比视图 | 两个版本并排纸质投影，差异高亮 | 从版本时间轴进入 |

视图切换只改变呈现，不改变权限、状态和可执行动作。单据视图中的正式动作按钮保持在固定操作条，不散落在纸面内。

### 5.2 单据视图使用 `PaperDocument`

`components/business/paper-document.tsx` 已实现通用纸质投影，具备打印语义（`article`/`table`/`thead`/`footer`、`break-inside-avoid`、`print:` 变体）和不参与计算的纯排版约定。它是单据视图和对比视图的唯一实现。

固定使用位置：

| 页面编号 | 页面 | 单据视图的价值 |
| --- | --- | --- |
| `ERP-SAL-012` | 销售单详情 | 对客户发送、审批阅读、归档 |
| `ERP-PUR-011` | 采购单详情 | 对供应商发送、下单凭据 |
| `ERP-SAL-014` | 销售变更详情 | 变更前后并排对比 |
| `ERP-INV-021` | 采购入库详情 | 仓库现场打印核对 |
| `ERP-INV-023` | 仓发出库详情 | 随货单据打印 |
| `ERP-FIN-005` | 销项发票详情 | 票面还原 |
| `ERP-FIN-010` | 进项发票详情 | 票面还原 |
| `ERP-FIN-021` | 供应商结算详情 | 对供应商发送核对 |
| `ERP-WK-002` | 任务处理台左栏 | 审批人一眼读完整张单 |

### 5.3 审批处理台使用纸质左栏

交互规范 §7.1 的审批布局是"左侧单据摘要 + 右侧处理面板"。左栏固定使用 `PaperDocument`，右栏是决策面板：

```text
┌ 待采购二次确认：SO-20260731-001              第 3 / 18 条  ┐
├──────────────────────────────────┬─────────────────────────┤
│  ┌──────────────────────────┐    │ 本次处理                │
│  │      销售单              │    │ 供应分配子行            │
│  │  ────────────────        │    │ 供应商 / 成本 / 数量    │
│  │  需方 XX公司  供方 本公司 │    │ 交期 / 履约方式         │
│  │  ┌────┬────┬────┬─────┐  │    │                         │
│  │  │商品│数量│单价│金额 │  │    │ 毛利影响                │
│  │  └────┴────┴────┴─────┘  │    │ ○ 通过   ○ 驳回         │
│  │  合计 ¥…    签章         │    │                         │
│  └──────────────────────────┘    │                         │
├──────────────────────────────────┴─────────────────────────┤
│ [返回队列]                      [驳回] [通过并打开下一条]  │
└────────────────────────────────────────────────────────────┘
```

这样做的收益是明确的：审批人的任务是**读懂一张单并作决定**，纸质整体呈现比分散页签的读取成本低；同时给以表格为主的 ERP 提供视觉节奏变化。

### 5.4 布局约束

`PaperDocument` 的 `min-w-3xl`（768px）在 1440px 基准宽度下的可用空间需要明确：

| 场景 | 可用宽度 | 处理 |
| --- | --- | --- |
| 详情页单据视图，导航展开 | 1440 − 208 = 1232 | 纸张居中，最大 1024，两侧留白 |
| 详情页单据视图，导航折叠 | 1440 − 64 = 1376 | 纸张居中，最大 1024 |
| 审批处理台左栏 | 约 700 | **导航自动折叠至 64px**，左栏 ≥ 768，纸张按 768 渲染 |
| 对比视图并排 | 1232 | 导航自动折叠，两张纸各 ≥ 640，允许纸内横向滚动 |
| 打印 | A4 | 组件 `print:` 变体已处理，不额外覆盖 |

进入审批处理台和对比视图时自动折叠左侧导航，退出时恢复用户原设置。这是交互规范 §2.1"宽度不足时折叠左侧导航"的具体触发条件。

### 5.5 数据来源

单据视图不从详情响应里拼装。每个支持单据视图的正式单据提供统一投影端点，返回可直接喂给 `PaperDocument` 的标准结构，包含出具方、双方主体、单据信息、明细行、汇总、备注和签章。契约见 [浏览器 API 契约](./api/README.md) 的 `DocumentView`。

组件约定不变：`PaperDocument` 只排版服务端已确认的正式事实，不计算金额、税额、大小写金额、状态或签章结果。

## 6. 列表默认视图

### 6.1 问题

交互规范 §4.5 要求销售单列表"至少分别展示"6 个状态维度且每个都用文字、图标和颜色。在 1440px 下这些列各自只剩约 80px，业务必需的金额和日期列被挤出首屏。多维状态的价值在筛选和快速预览，不在常驻列。

### 6.2 默认列集

§4.5 的多维状态要求继续有效，但明确区分**默认列**与**可选列**。默认列固定为 8 列：

| 列 | 宽度档位 | 说明 |
| --- | --- | --- |
| 选择 | — | 固定左 |
| 单号 | `reference` | 固定左 |
| 客户 / 供应商 | `reference` | — |
| 含税金额 | `amount` | 右对齐，等宽数字 |
| 主状态 | `status` | 文字 + 图标 + 颜色 |
| **阻塞点** | `tracks` | 当前唯一卡住的轨道及原因摘要 |
| 我的主动作 | `status` | 固定右 |
| 行操作 | — | 固定右 |

可选列（默认关闭，保存视图可开启）：履约、回款、开票、商城协同、异常、负责人、合同、业务性质、主责系统、创建时间、更新时间。

### 6.3 阻塞点列

阻塞点是新增的派生展示列，把 6 个状态维度中**当前实际阻碍推进的那一个**提炼出来：

```text
阻塞点
待采购确认 · 王五 · 逾期 2 天
商城接收失败 · 运营 · 3 次重试
—
```

规则：

1. 阻塞点由服务端从 `actionBlockers` 和 `nextResponsibilities` 计算并返回，前端不推导。
2. 无阻塞时显示 `—`，不显示"正常"等无信息量的文案。
3. 存在多个并行阻塞时显示最早到期的一个，并标注还有几条，展开进快速预览。
4. 阻塞点不替代多维状态。完整 6 维状态在快速预览、详情页头和可选列中仍然完整展示。

### 6.4 其他列表的默认列

| 列表 | 默认列 |
| --- | --- |
| 采购单 | 单号、供应商、含税金额、主状态、阻塞点、付款进度、我的主动作 |
| 待交付队列 | 交付方式、来源销售单、客户、SKU 与数量、要求交期、阻塞点、我的主动作 |
| 客户应收 | 客户、往来主体、应收余额、账龄、逾期天数、复核状态、我的主动作 |
| 统一任务队列 | 任务类型、业务对象、客户/供应商、进入时间、截止时间、责任人、下一动作 |
| 库存余额 | 仓库、SKU、在库、预占、可用、待入库、待出库 |
| 业务异常 | 异常类型、原单、业务影响、责任人、截止时间、下一动作 |

## 7. 效率验收指标

交互规范 §21 的 15 条验收全部检查正确性，没有一条检查效率。以下指标是页面上线的补充门槛，与 §21 并列执行。

### 7.1 路径长度

| 场景 | 上限 |
| --- | --- |
| 登录到开始处理第一条待办 | 2 次点击 |
| 从任意页面回到"我的下一件事" | 1 次点击 |
| 履约链上完成一步到开始下一步 | 0 次导航（由任务接力提供） |
| 命令面板到任意页面 | 输入 ≤ 4 字符 + Enter |
| 从待办进入业务对象并返回原队列位置 | 2 次交互，筛选和滚动位置不丢失 |

### 7.2 任务耗时

在真实数据量下测量，含服务端响应：

| 场景 | 目标 |
| --- | --- |
| 审批一条采购二次确认（3 条明细，供应商已存在） | ≤ 40 秒 |
| 新建一张实物与服务销售单（3 行明细，客户与合同已存在） | ≤ 90 秒 |
| 新建一张卡券销售单（唯一明细） | ≤ 45 秒 |
| 登记一笔客户回款并完成对 2 张销售单的核销 | ≤ 60 秒 |
| 完成一条卡券票款复核（历史事实齐备） | ≤ 30 秒 |

### 7.3 响应时间

| 操作 | 目标 |
| --- | --- |
| 列表首屏（50 行，服务端分页） | ≤ 800ms |
| 列表翻页与排序 | ≤ 400ms，表头和筛选不闪烁 |
| 快速预览打开 | ≤ 200ms |
| 处理并打开下一条 | ≤ 400ms，含领取与租约 |
| 命令面板首次呈现 | ≤ 100ms，本地匹配零网络 |
| 详情页首屏骨架 | ≤ 300ms，次级区块可后到 |

### 7.4 键盘完成度

以下流程必须可以完全不使用鼠标完成，作为验收用例逐条演练：

1. 登录 → 工作台 → 领取一条采购二次确认 → 填写供应分配 → 通过并打开下一条。
2. `⌘K` → 新建销售单 → 选择客户与合同 → 粘贴 3 行明细 → 保存草稿 → 提交确认。
3. 列表 → 筛选 → 逐行浏览快速预览 → 打开详情 → 返回并恢复原位置。
4. 回款列表 → 新建回款 → 进入核销工作区 → 分配到 2 张应收 → 确认核销。

## 8. 视觉与密度

### 8.1 页面节奏

ERP 长时间使用的疲劳主要来自单一的表格密度。三类页面使用不同的视觉节奏：

| 页面类型 | 节奏 | 手段 |
| --- | --- | --- |
| 队列与列表 | 高密度、低装饰 | 36px 行高、等宽数字、状态用文字+图标、无卡片包裹 |
| 正式单据 | 中密度、有边界 | 结构视图分区留白；单据视图用纸张边界和居中留白 |
| 分析 | 低密度、有图形 | 指标区不堆卡片，趋势图与明细表各占一侧 |

### 8.2 固定约束

1. 数量、金额、税率、日期和单号统一使用等宽数字，便于纵向核对（交互规范 §19 已要求，此处确认为全局默认）。
2. 状态一律文字 + 图标 + 颜色三者齐备，任何位置都不允许只用颜色圆点。
3. 密度切换（紧凑 36px / 舒适 44px）是用户偏好，保存在个人视图中，不进入共享 URL。
4. 业务组件不接受任意颜色和任意像素尺寸参数，全部走 `app/globals.css` 的语义 token 和宽度档位。
5. 工作区页签、面包屑和页面标题三者不重复表达同一层级：面包屑显示"工作区 › 页面"，页面标题只显示当前对象。
