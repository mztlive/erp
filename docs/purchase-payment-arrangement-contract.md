# 采购付款安排衔接合同

## 1. 责任与边界

1. 采购最终审批通过后，系统必须在采购生效事务内，为采购经办人建立“采购付款待安排”任务。任务绑定采购单，责任人不得使用最终审批人代替。
2. 付款安排、付款申请审批、出纳实际付款分别记录。付款安排不得自动提交付款申请，不得授予出纳付款资格。
3. 工作台及采购详情必须提供“申请采购付款”入口，并带入当前采购单。采购仍须确认逐单金额、收款账户、希望付款日及说明；现有同供应商、同我方主体、同收款账户的合并规则继续执行。
4. 出纳的申请付款执行任务统一显示“待执行采购付款”。

## 2. 待办状态

| 事实 | 系统处理 |
| --- | --- |
| 已生效采购存在未申请余额 | 建立或保留采购经办人的付款安排任务 |
| 部分余额已申请 | 保留剩余余额的安排任务及已登记跟进日 |
| 剩余应付全部由有效申请覆盖 | 完成本轮安排任务；详情显示关联申请审批及付款进度 |
| 申请驳回、撤回或关闭未付部分 | 在释放占用的同一事务恢复安排；取消旧跟进日期，重新要求核对 |
| 来源销售变更阻断付款 | 保留未申请余额的跟进责任，禁止申请入口，显示采购依据处理提示 |
| 采购变更或退款调整应付 | 按最新应付及有效申请占用重算，不覆盖历史付款事实 |
| 应付结清或采购已终止 | 完成开放的付款安排任务 |

可申请余额等于剩余应付减去有效申请占用，不得将申请占用计入已付。任务开放唯一性使用采购单、任务类型及固定责任键保证；同一事实重复同步不得重复建任务。已有开放任务的合法转派责任和跟进时间必须保留，申请释放触发的重新提醒除外。

## 3. 跟进日期

1. 只有当前任务负责人且具有采购详情及付款申请提交权限的账号可以登记跟进日。
2. 跟进日期使用上海业务自然日，不得早于当天。登记后任务保持开放，由工作台现有到期、逾期筛选与日期展示承担提醒。
3. 跟进日期仅表示下次处理时间，不表示供应商账期、已对账或已获准付款。不得据此自动申请或付款。
4. 现结、预付款必须显示付款条件及可计算的履约前实付缺口；周期结算由采购按约定完成对账后申请。预付款后的尾款金额及日期必须另行确认。

## 4. 接口与并发

| 接口 | 权限与行为 |
| --- | --- |
| `GET /admin/purchase-orders/{id}/payment-arrangement` | 使用 `purchase_order:detail`，在同一事务验证采购范围并读取余额、任务和本采购在关联申请中的分配 |
| `POST /admin/purchase-orders/{id}/payment-follow-up` | 使用 `purchase_payment_request:submit`，另行验证采购详情范围、精确任务、当前负责人及版本 |

跟进请求必须提供 `task_id`、`expected_version`、`follow_up_date`、`idempotency_key`。任务更新、审计和独立命令回执必须原子提交。同键同载荷重试返回原成功结果，同键异载荷拒绝。版本变化、任务已结束、任务不属于该采购或非当前负责人时拒绝新写入。

关联申请仅返回本采购行的申请、已付、未付及关闭金额；完整申请详情仍执行原有全部来源授权。不可借采购详情扩展其他采购或银行账户的读取资格。

## 5. 发布与验证

1. 服务端与前端必须同时支持 `PURCHASE_PAYMENT_ARRANGEMENT`；先发布读取兼容能力，再开放新任务写入。已有该类型任务时不得直接回滚到无法解码该类型的后端。
2. 本次复用工作项、工作项命令回执及其现有索引，不新增集合或改写历史单据。新增任务类型和回执结果为增量扩展。
3. 新采购生效自动建立任务；已有采购在申请占用、释放、采购变更等同步事件发生时按事实补齐。发布操作不得默认批量修改历史数据。已有采购详情可直接使用付款申请入口。
4. 库单元验证必须覆盖可申请余额、全部占用、部分申请、释放恢复、结清、阻断、负责人、日期、精确任务身份与同键异载荷；采购生效编排验证必须覆盖任务步骤失败后停止后续写入。
5. 静态检查及库单元测试不替代真实数据库事务、浏览器点击或部署验收。不得以源码检查声明运行环境已生效。
