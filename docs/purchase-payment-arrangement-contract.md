# 采购付款安排衔接合同

## 1. 责任与边界

1. 采购最终审批通过后，系统必须在采购生效事务内，为采购经办人建立“采购付款待安排”任务。任务绑定采购单，责任人不得使用最终审批人代替。
2. 付款安排、逐单付款申请审批、资金执行及正式核销分别记录。付款安排不得自动提交付款申请，不得授予出纳或后台任务付款资格。供应商预存款充值审批不得替代订单付款申请审批。
3. 工作台及采购详情必须提供“申请采购付款”入口，并带入当前采购单。工作台付款安排任务与采购详情入口必须复用同一弹窗，在当前页面打开，固定当前采购单为唯一来源，不显示选单步骤、其他采购单或批量申请侧栏；采购须确认金额、收款账户、希望付款日及说明。提交结果在弹窗内展示，提交成功后刷新当前采购单、付款安排、关联申请记录和工作台状态，不跳转至付款申请页。工作台必须在申请弹窗关闭后，再根据服务端任务完成状态执行返回列表或进入下一项；部分金额申请后仍保留当前任务。当前采购单不可申请时必须说明并禁止提交，不得改选其他采购单。付款申请列表的批量入口继续执行同供应商、同我方主体、同收款账户的合并规则。
4. 出纳的申请付款执行任务统一显示“待执行采购付款”，并明确本次批准的执行方式。银行转账与供应商预存款必须分别冻结真实资金账户，不得因供应商支持余额支付而自动切换付款方式。

## 2. 待办状态

| 事实 | 系统处理 |
| --- | --- |
| 已生效采购存在未申请余额 | 建立或保留采购经办人的付款安排任务 |
| 部分余额已申请 | 保留剩余余额的安排任务及已登记跟进日 |
| 剩余应付全部由有效申请覆盖 | 完成本轮安排任务；详情显示关联申请审批及付款进度 |
| 申请驳回、撤回或关闭未付部分 | 在释放占用的同一事务恢复安排；取消旧跟进日期，重新要求核对 |
| 来源销售变更阻断付款 | 保留未申请余额的跟进责任，禁止申请入口，显示采购依据处理提示 |
| 采购变更或退款调整应付 | 按最新应付及有效申请占用重算，不覆盖历史付款事实 |
| 应付结清或采购已终止 | 完成开放的付款安排任务 |

可申请余额等于剩余应付减去有效申请占用，不得将申请占用计入已付。任务开放唯一性使用采购单、任务类型及固定责任键保证；同一事实重复同步不得重复建任务。已有开放任务的合法转派责任和跟进时间必须保留，申请释放触发的重新提醒除外。

## 3. 跟进日期

1. 只有当前任务负责人且具有采购详情及付款申请提交权限的账号可以登记跟进日。
2. 跟进日期使用上海业务自然日，不得早于当天。登记后任务保持开放，由工作台现有到期、逾期筛选与日期展示承担提醒。
3. 跟进日期仅表示下次处理时间，不表示供应商账期、已对账或已获准付款。不得据此自动申请或付款。
4. 普通银行付款的现结、预付款继续显示付款条件及可计算的履约前净实付缺口；周期结算由采购按约定完成对账后申请。使用供应商预存款时须分别显示资金保障缺口和净实付金额，执行第 6 节规定。预付款后的尾款金额及日期必须另行确认。

## 4. 接口与并发

| 接口 | 权限与行为 |
| --- | --- |
| `GET /admin/purchase-orders/{id}/payment-arrangement` | 使用 `purchase_order:detail`，在同一事务验证采购范围并读取余额、任务和本采购在关联申请中的分配 |
| `POST /admin/purchase-orders/{id}/payment-follow-up` | 使用 `purchase_payment_request:submit`，另行验证采购详情范围、精确任务、当前负责人及版本 |

跟进请求必须提供 `task_id`、`expected_version`、`follow_up_date`、`idempotency_key`。任务更新、审计和独立命令回执必须原子提交。同键同载荷重试返回原成功结果，同键异载荷拒绝。版本变化、任务已结束、任务不属于该采购或非当前负责人时拒绝新写入。

关联申请仅返回本采购行的申请、已付、未付及关闭金额；完整申请详情仍执行原有全部来源授权。不可借采购详情扩展其他采购或银行账户的读取资格。

## 5. 发布与验证

1. 服务端与前端必须同时支持 `PURCHASE_PAYMENT_ARRANGEMENT`；先发布读取兼容能力，再开放新任务写入。已有该类型任务时不得直接回滚到无法解码该类型的后端。
2. 本次复用工作项、工作项命令回执及其现有索引，不新增集合或改写历史单据。新增任务类型和回执结果为增量扩展。
3. 新采购生效自动建立任务；已有采购在申请占用、释放、采购变更等同步事件发生时按事实补齐。发布操作不得默认批量修改历史数据。已有采购详情可直接使用付款申请入口。
4. 库单元验证必须覆盖可申请余额、全部占用、部分申请、释放恢复、结清、阻断、负责人、日期、精确任务身份与同键异载荷；采购生效编排验证必须覆盖任务步骤失败后停止后续写入。
5. 静态检查及库单元测试不替代真实数据库事务、浏览器点击或部署验收。不得以源码检查声明运行环境已生效。

## 6. 供应商预存款执行

1. 付款申请必须明确选择银行转账或供应商预存款，并冻结执行方式及账户快照。预存款账户须同时匹配我方付款主体、供应商、外部资金账号和币种；账号属于其他主体、供应商或连接时拒绝。历史未记录执行方式的申请仅按原银行付款规则解释，不推断为预存款。
2. 充值必须经过独立申请、明确批准、真实银行付款登记和供应商到账核验。银行已付但供应商未到账时只保留在途证据，不增加可用余额。充值使用独立资金用途，不核销具体采购应付，不建立退款留抵；重复银行付款依据和重复到账身份不得再次入账。存量余额导入必须有独立核实依据，不得读取远端余额后直接补账。
3. 订单仍须通过原逐单付款申请审批。系统在同一事务内重验批准状态、批准版本、执行方式、账户归属、授权范围及额度，并同时锁定付款申请额度、账户余额和真实到账批次。一个执行组只允许一份有效覆盖；同操作号同载荷返回原结果，异载荷拒绝。银行、留抵和预存款不得重复消费同一批准额度。
4. 自动余额执行必须取得财务独立授权，明确账户、连接、采购范围、金额限额、有效期及版本。负责人池配置、充值批准、API 自动下单开关和账户余额均不构成该授权。未取得有效自动授权时，保留原指定财务执行任务，由具备权限的负责人办理，不得静默转为自动执行。
5. 资金占用不减少采购应付，不增加净已付，不完成付款执行任务。仅在真实到账、逐单批准、有效执行授权、执行组全额专属占用及供应商可执行条件均满足时，允许该执行组进入供应商创建或尚未发送的订单确认。普通付款继续按原净实付门槛判断；预存款资格不得改变原付款条件。
6. 真实扣款须匹配外部唯一交易、原占用、执行组及批准范围。在同一事务内减少账面余额、消耗真实充值批次和占用、登记预存款使用、形成以该使用为来源的正式应付核销，并同步付款申请及任务进度。原充值只统计一次银行现金支出；本次余额使用不得再生成一笔银行付款或重复计入现金支出。
7. 发生超批、部分匹配或无法解释的扣款时须先保留真实资金证据并限制新增使用，不得扩大批准额度或强行核销。创建、确认或取消可能已送达时保持原占用并调查；任务超时、授权撤销、关闭自动下单及代码回滚均不得作为直接释放依据。只有尚未发送，或已取得明确风险消解证据时，才允许释放未使用占用及对应申请额度。
8. 供应商取消与资金返还分别核实。账户返款只有实际到账后才恢复可用金额，须引用原使用及核销，累计冲回不得超过原已核销金额。预存款返款不生成银行现金退款或退款留抵；银行现金退款继续按既有独立流程办理。
9. 采购修订、地址、数量或批准费用变化后，旧执行预算和授权适用范围必须重新核验。已发送、结果未知、已发货或存在未决返款的执行，不得直接退役重排。预算、占用及正式实付分别展示，销售及采购进度仍由已经应用的业务事实汇总。
10. 发布前须完成账户、充值批次、占用、使用、核销和历史银行付款的核对；新增自动占用和供应商下单分别控制，初始均关闭。只有专项资金验收及受控真实联调通过后才允许放行。已有预存款使用核销时，不得回退到只能读取普通付款来源的版本，不得删除占用、流水或补造银行付款实现回退。
