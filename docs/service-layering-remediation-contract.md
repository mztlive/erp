## 1. 合同效力

1. 本文件是上述后端代码基线下 Service 分层剩余问题的执行清单；清单项状态默认为 `OPEN`。
2. `R` 类编号表示持久化事实、批量读取、精确查询、数据库分页、聚合或索引责任应归 Repository；`E` 类编号表示纯业务规则、状态机、值对象、DTO 合同、领域工厂或 ERP 无关流程规则应归 Entity/VO/DTO/BPM。
3. `S` 类编号表示已经确认的问题必须在 Service 边界内修复，不计入下沉数量；不得为减少 Service 代码而把授权、事务或跨聚合决策错误下沉。
4. 同一个业务事实或规则及其直接调用点组成一个责任簇，不按函数数、文件数或代码行重复计数。
5. 任何新增发现必须先补入本文件、分配稳定编号、优先级和验收标准，再进入实施；任何清单项只有满足第 5 节关闭条件后才能标记 `DONE`。
6. 本文件不得替代业务合同、审批合同、WorkItem 合同或数据模型；发生业务语义冲突时，必须先修订权威合同，禁止在重构中代替业务方选择新语义。

## 2. 强制分层边界

| 层级 | 必须拥有 | 禁止拥有 |
| --- | --- | --- |
| Repository | 持久化过滤、最小投影、批量/精确读取、数据库分页/排序/聚合、索引适配、调用方执行器下的原子写 primitive | 自行开启或提交事务；RBAC/DataScope；跨聚合业务决定；HTTP/Service View；外部调用 |
| Entity / VO / DTO | 无 I/O 的不变量、状态迁移、金额/数量守恒、稳定身份、输入形态、确定性构造与转换 | Repository、MongoDB、HTTP、全局时钟、全局 ID 生成器、密钥、外部网关 |
| BPM | ERP 无关的流程定义、图、运行状态、命令计划和中性事件 | `DocumentType`、权限、DataScope、WorkItem、业务动作、通知模板、MongoDB |
| Service | 用例编排、事务、RBAC/DataScope、跨聚合加载与决策、外部网关、审计/outbox、Repository 查询参数、响应 View 映射 | 重复实现可复用纯规则；逐行 N+1；无界内存分页/聚合；伪造持久化事实 |

下沉实施必须同时遵守以下条款：

1. Repository 方法必须接收调用方 `&mut dyn Executor`，不得新增 `_with_session` 双轨 API，不得拥有事务生命周期。
2. Repository 只返回实体、强类型事实或存储无关投影；不得返回 services DTO、HTTP View 或授权结论。
3. Entity/VO/DTO/BPM 方法必须是确定性的；时钟、ID 和外部事实由 Service 显式注入。原始密钥不得作为 Entity/VO/DTO/BPM 参数，也不得由其持有、记录或选择算法；HMAC、加密及其他密钥运算必须由 Service 或 crypto port 完成，并仅把强类型计算结果传入领域层。
4. 下沉后必须删除原 Service 私有 helper 或重复规则源；只增加一层转发不构成完成。
5. 查询优化不得改变软删除、当前指针、业务日期、稳定排序、首错、缺失事实、金额精度或事务可见性。
6. 资金、库存、任务唯一性、幂等和版本号问题必须同时验证并发约束；单次快照查询或纯规则不得被当作并发保护。

## 5. 单项关闭条件与统一门禁

每个 `R` 项关闭前必须同时满足：

1. Repository API 必须按事项类型覆盖全部适用合同维度：Exact/Exists 覆盖精确过滤、缺失与软删除；Batch 覆盖空输入、去重、缺项和稳定归组；Page 覆盖过滤、稳定排序、游标或页码、总数和边界页；Aggregation 覆盖空集合、分组、精度及与基准算法对拍；Index 覆盖迁移、重复值门禁、回滚和代表性 `explain`。不适用维度必须在关闭证据中标记 `N/A` 及理由。
2. Service 仅解释持久化事实并继续拥有事务、授权和跨聚合决定；原逐行/全量读取路径已删除。
3. 批量查询的数据库访问次数不随当前页或请求项数量线性增长；索引项必须提供 migration、重复值门禁、回滚方案和代表性 `explain`。
4. 需要事务视图的查询和写入使用同一个调用方 executor/session；失败时不得产生部分提交。

每个 `E` 项关闭前必须同时满足：

1. 规则必须按事项类型覆盖全部适用合同维度：Arithmetic 覆盖零值、正负值、精度、舍入、溢出和守恒；State 覆盖所有允许/禁止迁移、幂等、版本及失败原子性；Conversion/Identity 覆盖规范化、round-trip、非法形态、稳定编码和确定性；Policy/Collection 覆盖完整矩阵、空集、重复、顺序和边界。无关维度不得机械补测，并须在关闭证据中标记 `N/A`。
2. Service 中原规则、镜像 helper、字符串中转或二次解析已删除。
3. Entity/BPM 未新增 I/O、MongoDB、Service Error、HTTP DTO、全局 ID/时钟/密钥依赖。
4. 已持久化 wire code、hash、fingerprint、receipt、revision 或 JSON 形态变化时，必须提供兼容读取、迁移和回滚合同。

#### 6.6.3 Service 保留边界

| 责任 | 必须保留内容 | 禁止误下沉的风险 |
|---|---|---|
| 事务与一致性 | `with_transaction`、审计、CAS、唯一键冲突恢复、多集合原子写入；Inventory 过账的流水、余额和预占释放。 | Repository 或 Entity 不得自行开启局部事务；库存状态与流水不得分两次提交。 |
| RBAC 与任务 | Warehouse handler 账号有效性、RBAC 权限覆盖、actor-specific allowed actions；WorkItem 当前责任人、冻结主体版本、任务版本和精确对象身份。 | Repository 不得接收 `AuditActor` 或返回 allowed actions；实体不得查询账号、权限或 WorkItem。 |
| 跨聚合决定 | 采购预付款门槛、采购销售分配一致性；验收事实加载与销售行组织；结算来源完整性、订单/行/退款归属；结算确认形成应付及成本差额。 | Repository 只返回事实，不得代替 Service 作资金、库存或跨聚合授权决定；验收域仅下沉纯数量与进度规则。 |
| 外部编排 | 供应商 gateway 派发、result-unknown 承接、InboxMessage、IntegrationErrorTask、W26 正式任务及重试/补偿。 | 外部调用不得进入数据库事务；Entity 不得依赖 gateway 或集成消息设施。 |
| BPM 集成 | Fulfillment `NO_APPROVAL` 文档注册与绑定端口调用；库存审批启动、撤回、最终动作与 BPM/WorkItem 同事务编排。 | 领域实体只承载状态、快照和纯规则，不得选择流程定义、审批人或直接关闭任务。 |
| 响应投影 | 所有 `From<Entity> for *View`、详情/列表 view mapping、展示兜底、actor-specific blockers。 | Database crate 不得引用 services DTO；展示字段不得污染领域模型。 |

## 7. 强制执行顺序

### 7.1 第一阶段：P0 优先队列

下列问题构成 P0 优先队列，必须拆成符合第 7.3 节的多个独立、可回滚批次，并先于非依赖性的 P1/P2 调整完成：

1. 审批详情、历史、恢复选项及管理列表的对象读取权和 DataScope 必须先收敛；同 execution 的全部开放审批任务必须在同一事务正确关闭。
2. 所有列表伪造乐观锁版本、错误对象 ID、错误 total/cursor、导入终态被后续调用覆盖的问题必须先修复。
3. 商城事实后页漏读、退款/冲正/恢复累计、票款/库存/结算守恒、并发额度和幂等竞态必须先补行为锁定及真实 MongoDB 并发测试。
4. evidence substring 关联、命令指纹、内容 hash、receipt 和 queue context 必须先固定规范编码与历史兼容方案，再迁移规则所有权。
5. P0 项不得与大范围文件拆分、命名整理或无关功能混在同一批次。

### 7.2 单个责任簇的实施次序

每个责任簇必须按下列条件顺序执行；纯 R 簇不得为满足形式而新增 Entity，纯 E 簇不得为满足形式而新增 Repository：

1. 在原行为上补充直接回归测试；若当前行为已被本文件标记为缺陷，先写失败测试固定正确合同。
2. `步骤 2：领域`：事项包含 E 责任时，新增 Entity/VO/DTO/BPM 能力及纯单元测试，不接触事务或外部 I/O；纯 R/S 簇跳过并在关闭证据登记 `N/A`。
3. `步骤 3：仓储`：事项包含 R 责任时，新增最小事实查询、批量写 primitive、索引和 Repository 测试；所有 API 接收调用方 executor；纯 E/S 簇跳过并登记 `N/A`。
4. `步骤 4：服务与接口`：切换调用点、保留授权/事务/跨聚合编排并删除旧 helper；S 项直接在本步骤修复。
5. `步骤 5：后端集成测试`：对适用事项执行真实 MongoDB 集成、事务、并发、唯一性、索引 explain 和 HTTP 合同测试；不适用维度登记 `N/A` 及理由。
6. 全量门禁通过后，提交证据必须记录变更文件、定向测试、全量门禁、未执行的外部验收边界，再将状态改为 `DONE`。

### 7.3 批次边界

1. 一个实施批次只处理同一业务事实或强耦合的一组 Repository + Entity + Service 调用点；不得按文件大小机械拆分。
2. 资金累计查询与额度规则、正式版本构造与 next-version、列表事实与分页、WorkItem 工厂与唯一责任必须成组交付；只完成其中一层不得关闭事项。
3. 涉及共享冻结文件时，必须先按 `backend/AGENTS.md` 走独立地基修订；禁止在领域批次中顺手修改冻结文件。
4. 存在可执行 P0 时不得启动独立的 P1/P2 批次；仅允许把某个 P0 的直接前置 P1/P2 依赖纳入同一依赖链和可回滚批次，并在执行登记中说明。全部可执行 P0 关闭后，外部合同导致的 `BLOCKED` P0 不得迫使团队空转，但启动 P1/P2 前必须记录批准人，且任何批次不得固化该阻断项的未签署语义。纯命名、低频转换或测试适配器类 P2 不得抢占 P0。
5. 每个批次必须可独立回滚；索引、fingerprint/hash、receipt/wire code 变更必须同时提供前向迁移和回滚路径。
