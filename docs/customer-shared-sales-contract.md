# 客户多人负责与资料并发维护执行合同

## 1. 客户身份与负责关系

1. 同一企业共用一份客户档案，统一社会信用代码保持全局唯一。信用代码缺省时须按规范化法定名称查重；命中既有主体时须提示复用，不得自动建立第二份客户档案或自动取得其业务权限。
2. 一个客户允许多名有效负责销售。增加人员不得结束其他人员的负责关系；同一客户、人员、角色不得存在重叠有效期。
3. 负责关系按自然日左闭右开区间维护。结束关系须在同一事务内校验版本及操作权限，只允许缩短原有效期，不得延后原结束日。被移除的整个区间须连续由其他有效负责销售覆盖；原结束日为空时须覆盖至无限期，不得仅检查新结束日当天。
4. 人员分配须具有 `customer_assignment:create` 功能权限与目标客户更新范围；不得由普通客户资料保存修改名单。历史协作记录不得自动转为负责关系。
5. 客户表单、合同导入、供应商建档、主体建档及名称修订须在原写事务内先争用法定名称互斥记录，再查询名称或信用代码候选。名称使用实体规范化后的法定全称。并发冲突须回滚整个命令，不得在查重失败后继续创建。
6. 命中唯一、启用且未删除的外部企业主体，且尚无客户角色时，客户创建允许经用户明确确认复用。复用保留主体 ID、名称、简称、信用代码、已有修订、联系人、地址、税务资料和银行账户，只新增客户角色、首条负责关系及本次客户付款条件。已建客户、同名异码、同码异名、歧义、停用或删除的主体不得按此入口新增客户。

## 2. 资料共享与业务隔离

1. 客户列表不得向全员公开。普通销售只能查看已分配及既有历史读取资格覆盖的客户；团队和公司范围须由既有角色权限明确授予。有效负责销售在既有功能权限及个人范围内共用客户身份、联系人、地址和结算基础资料。敏感字段沿用独立查看与揭示权限。
2. 客户负责关系仅授予客户资料及关联建单所需的客户资格。合同、销售单、选品、票款、成本、毛利、附件和统计须分别执行所属资源授权，不得按共同客户扩大业务范围。
3. 合同须保存独立负责销售；范围条款复用既有客户范围配置，但须按合同自身责任映射，不得按客户 ID 放行。合同读取、筛选、导出、附件和选用均按合同责任或明确授权执行。客户名单变化不得交接合同。无法证明历史合同负责人的记录只允许有全公司合同范围的人员修改，既有合法历史参与仍按原合同读取规则执行；不得按当前客户名单猜测归属。
4. 销售单继续使用 `sales_owner_user_id` 和业务组织进行当前责任授权。首次生效归属快照只用于历史经营统计，不授予访问权。客户名单变化不得改写单据责任、待办或冻结业绩。
5. 客户中心的合同、销售、应收和经营质量须先按各自资源过滤，再分页和汇总。跨销售业务的回款、发票只返回允许的分配部分，不返回其他业务明细、整单金额或完整凭证。
6. 客户列表按客户身份去重并展示全部有效负责销售。销售业绩按单据计算一次；管理汇总不得因一个客户有多名销售而重复累计。

## 3. 并发保存

1. 客户资料保存须同时提交打开资料时的主体及客户版本，根记录、修订、从属资料、审计和命令结果在同一事务提交。版本冲突须返回 409，禁止使用旧表单覆盖最新资料。
2. 编辑期间固定初始版本及表单基线；后台刷新不得替换基线或清空未保存输入。
3. 冲突后保留全部本地输入，按当前权限读取最新资料，展示打开时、最新及本次输入的差异。读取失败时保留草稿并允许重试，不得显示伪造的服务器值。
4. 用户核对并明确选择需要保留的修改后，使用最新版本重新提交；再次冲突须重复核对。不得自动强制覆盖，不得把掩码值当明文写回。

## 4. 接口合同

1. 客户列表、客户详情及 `GET /admin/customer-profiles/{id}` 的客户行增加 `owners: [{ user_id, user_name }]`，返回全部当前有效且未删除的负责销售，并解析账号显示名。原单人负责人字段仅作兼容展示，客户端不得据此判断客户是否属于当前销售。
2. 客户负责关系继续通过 `POST /admin/customers/{id}/assignments` 维护。`assign` 增加人员，`end` 按 `assignment_id` 与 `version` 结束指定关系；两者均须填写调整原因，不得以增加人员命令隐式结束其他人员。
3. 合同共享名单通过 `PUT /admin/contracts/{id}/sales-access` 完整替换，须同时具有 `contract:update`、`customer_assignment:create` 功能权限及目标合同更新范围。请求格式如下：

```json
{
  "version": 1,
  "shared_sales_user_ids": ["sales-b"],
  "change_reason": "共享年度框架合同"
}
```

4. `version` 必须为打开名单时的合同版本；名单最多 100 人，空数组表示取消全部明确共享。人员须为有效账号；名单去重且排除合同负责人本人。请求不得指定或修改合同独立负责人。
5. 共享更新成功后返回合同详情，包含新的 `version`、`shared_sales_user_ids`；`owner_user_id` 与 `owner_user_name` 表示合同独立负责销售。合同列表的 `ownership_basis` 为 `contract_sales_owner`，负责人及组织筛选须据此执行。
6. 版本过期返回 409，非法版本、名单或调整原因返回 400，缺少权限返回 403；JSON 含未知字段或类型不符由请求提取器返回 422。失败不得写入名单或成功审计；客户端须保留未提交输入。
7. `POST /admin/customer-profiles` 接受 `reuse_existing_party: boolean`，省略等同 `false`。存在可复用主体但未确认时返回 409，提示勾选“复用已有企业资料”；确认后按第 1 节执行，不以本次请求覆盖已有主体基础资料。无候选时按完整请求新建。复用时校验主体版本并推进版本，返回已有名称修订及新的主体版本。该字段为 `true` 时纳入幂等指纹；客户修订接口禁止选择复用。
8. 客户资料冲突核对界面须依据最新详情的 `EDIT_CUSTOMER` 动作判断是否允许重新保存；权限丢失时保留草稿并禁止提交。

## 5. 发布与验收

1. 前后端须同批发布。部署前执行责任字段迁移检查，保留已有负责关系及全部历史版本。重复客户合并须独立核对，不在本次发布自动执行。
2. 历史合同迁移使用 `scripts/migrate-contract-sales-owners.js`；默认只读。显式指定逐合同核对的负责销售和期望版本后，方可执行本批原子迁移。禁止自动使用创建人或客户第一名成员回填。
3. 验收须覆盖多人同时有效、同人重复拒绝、单人结束及最后一人结束拒绝、跨销售读取拒绝、客户汇总去重、历史责任不变、并发保存拒绝、草稿保留和核对后重提。
4. 回滚多人负责功能前须暂停名单变更并核对多人成员；不得直接运行旧的换任命令处理多人名单。合同责任字段应保留，回滚不得恢复按共同客户开放合同的规则。
5. 主体领域索引初始化须预建 `party_identity_guards` 集合及 `_id` 唯一索引；`_id` 为规范化法定名称。该集合仅保存互斥计数，不回填既有主体、不合并历史重复数据。发布期间须停止旧版写入进程，再启动新版写入进程，禁止绕过互斥约束的旧、新写入入口混跑。
6. 回滚身份查重实现前须暂停所有主体创建及改名入口；互斥记录须保留，不得在写入期间删除或清空。旧版恢复写入前须另行提供同等并发唯一约束。并发建档的数据库验证须使用隔离环境，不得在生产库重放创建请求。
