# 采购责任规则与负责人池合同

## 1. 数据结构与维护

1. 每条规则由匹配条件、负责人池、分配策略和启停状态组成。每个匹配条件只允许一条未删除的启用规则。新增人员必须编辑现有规则的池，不得新增同条件启用规则。
2. 匹配类型包括 `INQUIRY`（询价）、`SKU`、`CATEGORY`、`PRODUCT_KIND`、`DEFAULT_DISPATCHER`（通用默认池）。询价和默认规则不得携带商品选择器。
3. `owner_user_ids` 保存 1 至 100 个具体后台账号，数组顺序即轮询顺序。保存时去除账号首尾空白，拒绝空账号、重复成员和空池。每条规则的成员独立维护，同一人可加入不同规则池。
4. `strategy` 当前只接受 `ROUND_ROBIN`（轮询）。未来策略必须在策略类型、选择实现、输入事实、前后端合同及验收用例中同时扩展；不得提前接受未实现的负载均衡策略或静默退回轮询。
5. 询价池成员须满足询价处理权限、可登录后台账号和主属组织要求；其他池沿用采购建单资格校验。实际创建询价任务时仍核验所有最终负责人的询价执行资格。
6. 配置变更只影响后续任务，不自动改变已有任务。池内移除人员不取消其已有任务或历史参与记录；现有手动改派不占池轮次。

7. 采购与财务复用共享负责人池校验、轮询策略、版本比较持久化机制及前端编辑控件；匹配条件、账号资格和轮次集合由各领域分别拥有。财务规则遵循 `docs/finance-responsibility-contract.md`。

## 2. 匹配规则

1. 询价提交、补充后重提、重询和采购新一轮报价优先匹配唯一启用的询价规则；存在该规则时，整单全部商品进入同一个询价池，不再按商品规则拆分负责人。
2. 未配置启用询价规则时，沿用原匹配链：SKU、当前分类逐级到父分类、商品类型、通用默认池。停用询价规则后按此链处理新的任务。
3. 普通采购任务不匹配询价规则，始终使用上述商品匹配链。销售单生效创建采购任务属于普通采购场景。
4. 每条商品只能命中一个规则。命中具体规则后不得再进入默认池；同层规则多命中、缺少最终规则、命中池为空或人员失效时，拒绝整个分派。
5. 在本单本次任务创建中，同一规则池只选择一名负责人，全部命中该池的商品使用此人。不同池可选择不同人员；相同人员负责的商品仍合并成一个任务。

## 3. 分配策略与轮次

1. 每个规则池单独保存最近成功分派的成员。初次分派取数组首人；后续取最近成员的下一人，末位之后回到首人。
2. 最近成员被移除后从当前数组首人继续；调整成员顺序后按当前数组定位下一人。服务重启不得重置已有位置。
3. 每个实际命中的池每次成功任务批次推进一次，未命中的池不推进。单成员池也使用同一分配与事务机制。
4. 预览、资格检查、保存草稿、手动改派、失败提交以及命令回执重放不推进轮次。预览结果不预占名额，实际提交必须重验。
5. 历史参与采购仍在本单当前命中的启用池中时，可以按询价原有权限和状态规则发起新一轮报价；下一轮选到其他成员不得单独撤销其发起资格。
6. 轮到的人员账号、权限或组织失效时阻止分派并提示维护配置，禁止静默略过或重新解释为负载均衡。

## 4. 事务与错误

1. `procurement_dispatch_rotation` 以规则 ID 作为 `_id`，记录 `last_owner_user_id` 与 `revision`。轮次写入和任务创建使用同一事务，后续步骤失败时一起回滚。
2. 同一池以版本比较保护并发分派；池配置维护更新该池并发版本但保留分配位置。不同池分别保存状态。
3. 并发冲突沿用统一冲突响应及请求编号，重试须重放整个原命令；提交结果未知时使用既有回执恢复，不得单独重放轮次写入。
4. 重复启用同条件规则提示“同一匹配条件只能启用一个负责人池，请编辑现有规则添加人员”。池内重复成员提示重复选择，不允许通过重复人员增加权重。

## 5. 接口

1. 创建与整项更新请求使用 `owner_user_ids`、`strategy`；停止接收旧的 `owner_user_id`。未知字段和未知策略必须拒绝。版本与原选择器字段保持原语义。
2. 列表返回 `owner_user_ids`、按同顺序排列的 `owner_names` 和 `strategy`。缺失账号姓名在对应位置返回 `null`，不得删除成员导致名单错位。人员筛选参数仍使用单个 `owner_user_id`，语义为池包含此人。
3. 解析预览请求可带 `purpose: inquiry | procurement`，缺省为 `procurement`。询价预览执行询价池优先和询价人员资格规则。分派结果仍返回本次实际选中的单个 `owner_user_id` 与命中规则 ID。
4. 前端在一条规则中多选负责人并展示分配方式；当前只提供“轮询”。刷新候选账号不得清空已选成员。

## 6. 发布、迁移与回滚

1. 发布前停止旧版写入，备份 `procurement_responsibility_rules` 和 `procurement_dispatch_rotation`。前后端同批发布，禁止新旧字段合同混用。
2. 新版启动先迁移旧规则再登记索引。旧单人字段转换为单元素 `owner_user_ids`，缺失策略填 `ROUND_ROBIN`，最后移除旧 `owner_user_id` 字段。
3. 多条启用默认规则按规则编号升序合并成员到首条规则，重复人员只保留首次出现位置。其余规则停用并记录 `migration_merged_into`，保留历史记录；所有默认规则选择器键统一为 `default_dispatcher`。
4. 合并先保存完整成员，再停用被合并规则，最后收敛选择器键。迁移中断可以重新执行，禁止丢失已合并成员。合并后超过 100 人时阻止启动，由管理员先维护旧配置。
5. 旧全局轮次通过 `last_rule_id` 反查最近成员，为新默认池初始化 `last_owner_user_id`。已有新池轮次用 `$setOnInsert` 保留。旧全局轮次记录不再参与分派。
6. 独立迁移入口为 `scripts/migrate-procurement-dispatch-rotation.js`；新版启动完成迁移后不必另行执行。原选择器唯一索引保留，增加池成员查询索引。
7. 回滚必须停止新版写入，恢复发布前备份的规则与轮转集合后切换旧版。上线后新增或调整的池须另行登记并人工转换；不得将多成员池任意压缩为一个人，不得让旧版读取 `INQUIRY` 规则或新字段合同。已创建业务任务不得随配置回滚删除。
8. 单元测试不替代真实数据库迁移、并发和回滚验收；未执行项目须在发布记录中明确标注。
