## 一、页面概述

统一待办队列是跨工作面（采购二次确认、卡券票款复核、回款核对、映射/同步异常、履约异常、合同补全、低毛利确认、重复任务清理）的集中处理入口。布局为「左队列列表 + 右任务详情」双栏，提供四种责任范围（我的待办/待领取/团队/已跳过）、族筛选、超期/今日到期筛选、关键字搜索、单任务连续处理（j/k 或按钮切换）、领取/跳过/转交/保存证据/完成等动作，动作结果与冲突处理均有成熟反馈组件支撑。

整体完成度较高：加载骨架、空态、错误态、版本冲突弹窗、键盘导航、读屏 aria-live 播报、草稿保留机制齐备。主要问题集中在**动作语义与文案契约**（按钮说一套做一套、状态误报）、**内部 ID / 枚举原值泄漏**与**误操作防护**三类。

## 二、易用性

**顺畅的部分：**

- 主路径「领取 → 处理 → 自动下一项」闭环清晰：待领取范围任务有「领取」Alert（`unified-task-queue-page.tsx:1028-1054`），完成/跳过/转交后 `advanceToNext` 自动打开下一条（:272-286）。
- 深链优先：URL `currentWorkItemId` 聚焦任务，W01 深链即使超出当前筛选也会置顶显示（:160-166），空态给出「回默认有效待办」出口（:1280-1303）。
- 键盘 j/k 切换 + 移动端「上一项/下一项」按钮双覆盖（:543-565, :912-934）。
- 有跳转页的任务（handlerHref）走专用业务页，文案按类型生成（如「去确认采购计划」`mock/work-items.ts:222`），符合术语表 §3.1。

**阻碍效率的问题：**

1. 「待领取」范围是用户捡任务的主场景，但未领取的 PENDING 任务在连续处理条上显示「操作已失效，请刷新后重新处理」并禁用处理按钮（见问题 P1-5）——用户第一眼会以为自己丢了权限，实际只是没领。
2. 处理完一项后，用户若想回队列本身，点「返回队列」实际跳去了今日工作台 `/workspace`（见 P1-3），连续处理循环被切断。
3. 转交动作无目标选择、无确认，一键转给固定人（见 P1-4），在待办中心场景是高风险动作却没有防护。
4. 无批量领取/批量跳过：待领取范围逐条领取，量大时效率低（P2-2）。
5. 「收敛到同类连续处理」是改变队列范围的模式开关，却藏在详情底部动作区之后（:1246-1275），不易发现，且领取后会自动收敛导致队列意外缩小（P2-11）。

## 三、信息密度

**总体平衡较好：**

- 队列条目用 `density="compact"`，只留任务类型、状态徽章、业务对象、往来方、截止与责任方（`audit-import.tsx:125-137`），原因/影响让位给右侧详情，取舍正确。
- 详情卡信息分级：摘要 dl 栅格 → 原因/影响 → 检查项 → 决策备注 → 动作区，视觉层次清楚。
- 权限收回时金额字段脱敏为 `•••`、敏感影响清除（`queries.ts:75-90`），合规细节到位。

**过密 / 过疏的问题：**

1. 详情尾部技术行 `版本 v1 · 完成动作 CONFIRM_PROCUREMENT_PLAN · 允许关闭（重复/误派）`（:1093-1098）直接渲染内部命令枚举，对用户是噪音（P1-2）。
2. 队列列表不展示优先级：紧急/高/普通任务在列表里仅靠排序区分，没有视觉标识；「紧急」任务与「普通」任务同款外观（P2-4）。
3. 动作区最多可同时出现 7 个按钮（保存证据/先跳过/转交/关闭重复/前往任务页面/退回说明/主按钮），且其中 3 个指向同一跳转（P2-1），视觉拥挤、主次不清。
4. 详情里优先级出现两处（标题徽章 :1010-1020 与摘要字段 `mock/work-items.ts` summaryFields），轻微重复。

## 四、交互合理性

**做得好的：**

- 加载态骨架屏、错误态重试按钮（:599-620）、空态分「已处理完 / 任务不在筛选结果中」两种语义，覆盖齐全。
- 版本冲突走 `ConflictResolutionDialog`，提供「重新加载 / 保留草稿 / 查看差异」三条出路，备注通过 `draftsRef` 跨任务保留（:188-199, :1329-1365）。
- 筛选器全部映射到 URL 参数，分享/回退可还原（`queue-url.ts`）；「清除筛选」一次性还原（:771-790）。
- 结果反馈 `FormalActionResult` 带结果编号与队列位置事实表（:794-817），闭环明确。

**问题集中在语义与防护：**

1. 无分页/虚拟滚动，队列超过卡片可视高度后仅 `overflow-y-auto`（:865），任务量大时定位困难（P2-3）。
2. 错误态只有「重试」一个按钮，无错误说明、无返回队列/工作台出口（:611-620），用户被卡在死胡同（P2-7）。
3. `searchDraft` 只在初始化时从 URL 取值（:131），浏览器后退导致 URL 变了输入框内容不同步（P2-6）。
4. `queueContextId` 参数被写入 URL 但页面无任何控件消费/清除它（:98-99, `queue-url.ts:54-55`），违反「URL 参数与界面控件一一对应」契约（P2-5）。
5. 关闭类任务（重复任务清理）在连续处理条上点击主按钮会**跳过确认框直接关闭**（:972-975），与详情卡底部按钮（走确认弹窗）行为不一致（P1-7）。

## 六、改进建议

**P1 优先修复（影响主流程信任度）：**

1. **文案契约类（P1-1/P1-2）**：详情卡「编号」改为业务单号（如 `销售单 · XS2026…` 已是业务对象，可直接用）；删除「完成动作」行；`onSaveEvidence`/`onCloseDuplicate` 结果描述改为业务说法（「已记录操作结果」「已关闭重复任务」）；确认弹窗 effects 改为自然语言（「将提交采购确认结论」）；mock 摘要字段「替代任务/关闭原因」改业务表达或删除。
2. **转交（P1-4）**：增加目标人选择器（可选列表 + 默认值）与 `FormalActionConfirmDialog` 级确认，明确「任务将转交 ×××」。
3. **状态语义（P1-5）**：`leaseStatus` 区分「本会话从未领取」与「领取后失效」；待领取范围未领取任务显示「任务待领取/待认领」而非「操作已失效」，「重新领取」仅在确曾领取过时出现。
4. **按钮语义（P1-3/P1-6/P1-8）**：「返回队列」改「返回工作台」或改跳 `/workspace/tasks`；非 handler 任务只保留一个「完成并打开下一条」主按钮，删除「完成当前项」；删除「退回说明」死按钮或改为弹窗说明「退回请在任务对应页面处理」。
5. **关闭任务（P1-7）**：处理条与详情卡统一走确认弹窗，关闭类任务明确显示「将关闭重复任务」后果。

**P2 建议：**

- 队列列表补优先级徽章（紧急红色高亮）；「收敛」开关移到筛选工具栏区并加提示；补批量领取入口（按筛选整批领取 + 影响预览）；列表量大时加分页或虚拟滚动；搜索框与 URL 双向同步；错误态补错误摘要与返回工作台链接；空态区分「无任务」与「已处理完」；`queueContextId` 从 URL 摘除或补控件。
