# UX 评审报告：导入与期初（/governance/imports）

> 评审日期：2026-08-05 ｜ 评审视角：产品经理 / UX ｜ 纯分析，未修改代码
> 覆盖代码：`erp-client/features/import-opening/*`（page/api/queries/types/url-state）、`components/business/audit-import.tsx`、`components/business/feedback.tsx`、`components/business/document.tsx`、`components/business/role-demo-bar.tsx`、`components/business/list.tsx`、`mock/import-opening.ts`、`docs/ui-glossary.md`
> 严重度口径：P0 = 阻断操作或术语表红线（发布阻断）｜P1 = 明显阻碍效率｜P2 = 体验瑕疵

---

## 一、页面概述

页面为「治理 → 导入与期初」（W18），两层结构：

- **批次列表**：环境 Tab（验证/生产）+ 指标条（待校验/待业务确认/执行中/失败或部分失败）+ 筛选（对象集合/状态/批次号搜索）+ 批次表。
- **批次详情**：单号头 + 身份摘要 + 六段流水线指示器 + 7 个 Tab（概览/文件与规则/试算与问题/责任确认/执行进度/结果/审计）+ 常驻「提交前检查」门禁卡。

整体是一个**批次查看/演示器**，数据由 session-mock 提供，带角色演示切换条。

---

## 二、易用性

### 顺畅的部分
- 列表 → 详情 → Tab 的导航链路清晰，URL 状态（批次、Tab、筛选、角色）全部进 URL，刷新可恢复，符合本项目契约。
- 六段流水线 + 阶段化 Tab 的「先校验后确认再应用」心智模型正确；空态文案（"结果尚未形成""暂无导入任务"）写得可预期。
- 生产环境有显著红色标识 + 提交前检查卡，高风险操作（生产应用）有明确门禁呈现。

### 主要断点
1. **没有「发起导入」的入口**。页面名是"导入"，但列表页没有任何新建/上传动作，详情页的上传-映射-校验阶段也只能靠「模拟：标记已上传（仅演示）」按钮推进（见问题 P1-1）。用户无法走通"上传模板→映射→校验→执行"的完整路径，页面实际是批次只读查看器。
2. **责任确认主操作不可达**。"确认本范围/退回修复"按钮没有 onClick，且所有 seed 的任务类型登记门禁均为 false，按钮永远禁用（见 P1-2）。
3. **问题修复路径只有"标签"没有"动作"**：问题表"修复方式"列标注"可在导入中修复"，但本页不存在任何修复控件；修复只存在于 RESULT 阶段的"打开修复批次"（见 P2-3）。
4. 模拟操作（标记上传/规则变化/打开修复）成功或失败均无 toast/结果条反馈，只能靠观察数据刷新猜测（见 P2-4）。

## 三、信息密度

### 过密 / 冗余
- **同一事实展示两遍**：DocumentHeader 状态条（环境/基准日/规则版本/当前阶段）与下方身份摘要卡（环境/期初基准日/导入规则版本/…）高度重复（P2-7）。
- 详情页常驻「提交前检查」卡 + 6 个 GateRow + 结果条，对已完成（RESULT）批次仍显示"检查已完成，可提交"，语义错位且占据大量纵向空间（P2-8）。
- 列表"责任确认"列显示"2/4 责任范围"，无单位说明，业务用户第一眼读不懂。

### 过疏 / 缺口
- 问题明细表**无分页控件**，查询写死 page:1、size:50（P1-3）；总数显示"共 30 条问题"，但第 51 条起不可见，且无任何提示。
- 文件资产只有名称/大小/到期，**没有下载或查看动作**，"下载前重鉴权"的说法没有对应控件（P2-5）。

### 错误信息可理解性
- `errorDetail` 本身是好的业务化中文（"实盘数量不能为负或空""行基准日 2026-07-15 与批次统一基准日不一致"），结合行号/列名可定位。
- 但"错误码"列直接把枚举原值（`CUSTOMER_NOT_FOUND` 等）渲染上屏，且筛选下拉同样显示 `代码 · 中文` 双写（P0-1），把可理解的中文说明稀释成技术码，属于术语表红线。

---

## 四、交互合理性

### 合理处
- 加载态：列表用 DataTable loading、详情用骨架屏，有"重试"错误态与"返回列表"兜底。
- 空态：各 Tab 空态均有"之后会出现什么"的预期说明。
- 生产环境显著确认标识、失效确认警示条（"禁止按旧版本提交应用"）的阻断呈现直观。
- 按钮语义总体是动作词（"返回批次列表""查看问题明细""责任确认""打开修复批次"）。

### 不合理处
- 问题表加载中渲染为空态："当前筛选下没有问题行" 在查询 pending 时即显示（P2-7）。
- 六段流水线指示器与业务阶段两套命名并存：步骤标签是共享组件的"上传/映射/校验/预览/提交/结果"，描述才带出"安全接收/结构校验/业务校验与试算/责任确认/后台应用/结果"；且 VALIDATE 阶段被映射到名为"映射"的步骤却描述为"结构校验"——同一流程两套语言（P2-1）。
- 三个模拟按钮把"机制"写进按钮名（"模拟：规则变化后确认失效"），且带"（仅演示）"后缀，属 G6 允许的演示标记，但放在主操作位会与真实业务按钮混淆（P2-4）。

## 六、改进建议

1. **补齐导入发起主链路（P1-1，最高优先）**：列表页加"新建导入批次"主按钮，进入含"模板下载 → 文件上传（拖拽+大小/格式校验）→ 字段映射 → 启动校验"的向导；若本期只做查看器，应把页面名收敛为"导入批次（查看）"并把"导入"动作入口明确标注为演示占位，避免误导。
2. **修复责任确认死按钮（P1-2）**：给"确认本范围/退回修复"接上真实 mutation 与成功/失败反馈；至少在演示模式下提供一个"任务类型已登记"的 seed 以展示可操作状态，或将按钮替换为"去待办队列处理"的跳转。
3. **清除术语表红线（P0 全部）**：错误码列/筛选改用 `ISSUE_CODE_LABEL` 中文；结果分区徽章去掉 code 或换中文；"待登记项/禁止项/阻断码"翻译为业务口径（如"确认任务与责任池尚未配置，联系系统管理员登记"）；`file_asset`、`issv-*`、`bj_*`、`trial=` 一律不上屏；审计 Tab 的"批次身份"删除或改为批次号。
4. **问题明细分页（P1-3）**：给 ImportIssueTable 接 DataTable 分页或"加载更多"，页码进 URL（与现有 url-state 一致）。
5. **信息去重（P2-7/8）**：身份摘要卡去掉与 DocumentHeader 重复的环境/规则版本项；"提交前检查"卡仅在 APPLY 之前阶段渲染，RESULT 阶段改为结果摘要。
