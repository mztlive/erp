## 1. 页面概述

- **页面标题**：执行信息（`page.tsx:7` metadata；面包屑「商城与发布 / 执行信息」`execution-projections-page.tsx:685-694`）。术语表已将「执行投影/销售单执行投影」翻译为「执行信息」，符合规范。
- **页面定位**：销售单执行信息（信息发送至商城）的只读监管台 + 轻操作台。核心能力：查看发送/确认状态（三轨：销售记录 → 信息发送 → 商城确认）、按风险排序的列表、指标筛选、单条查询结果 / 重试 / 升级到接口错误中心、批量查询/重试。
- **主要区域**：页头（刷新 + 批量入口）→ 边界提示 Alert → 结果反馈区 → 指标条（5 指标筛选）→ 工具栏（搜索 + 5 个筛选器）→ 批量选择条 → 列表（固定左/右列）→ 详情抽屉（5 Tab）→ 行预览抽屉 → 动作确认对话框。
- **协同子区**（`collaboration-card.tsx`）：销售单页「与商城对接」只读卡，展示三轨状态、当前推送摘要、推送到商城的内容、商城侧消费情况。

**总体印象**：页面信息架构清晰、风险优先排序（`api.ts:294-322`）与「结果未知不计入已确认」的保守语义贯穿全局，业务语言整体合规（投递→发送、投影→数据、幂等→原任务号均有落地）。主要问题集中在：个别 W 编号泄漏到按钮文案、分页条数控件失效、双语义按钮、批量上限无前置提示、多版本列概念负担、内部 ID 上屏。

## 2. 易用性

**做得好的**
- 顶部「非写者边界」Alert 一次讲清页面能做什么/不能做什么（`execution-projections-page.tsx:743-749`），用户进页即知这是只读监管台，避免到处找编辑入口。
- 默认视图「风险优先 · 全状态」+ 指标条前置，用户 3 秒内可定位到最需要处理的「失败/转人工」。
- 搜索占位「销售单号、执行编号、客户」（`:836`）为业务语言；筛选器选项全部中文（待发送/发送中/重试中/已确认/失败/转人工/结果未知）。
- 批量选择条明确说明「批量操作仅作用于显式选择，不含当前筛选全部」（`:973`），防止用户误把"筛选全部"当批量范围；空态自带「清除筛选」一键复位（`:1050-1071`）。
- 动作前确认对话框（`FormalActionConfirmDialog`）列出锁定字段、影响、下一责任部门（`workflow.tsx:283-300`），对「升级」「批量重试」这类不可逆操作交代清楚。

**主要障碍**
1. **行操作「W29」按钮（`execution-projections-page.tsx:567`）直接把工作面编号当文案**。术语表 §1.2 规则 6 与 §3.6 明确要求「用户提示写页面中文名，不写 W29」；同一页其他位置（结果卡片 `openWorkspaceLabel("W29")`、协同卡 `openWorkspaceLabel("W23")`）都正确译为「打开接口错误与对账中心」「打开执行信息」，唯独列表行按钮漏了翻译。用户（运营/财务）看到「W29」无法预判去向。
2. **「升级 / 打开接口错误中心」是双语义按钮**（`execution-projections-page.tsx:1214-1246`）：`allowedActions` 含 ESCALATE 且无任务时点击弹升级确认框；否则直接跳转错误中心。斜杠拼合的标签无法表达"这次点了会发生什么"，同款问题在确认框 toStatus「W29 待办」（`:1637`）继续出现。
3. **三列版本并存**：ERP版本 vN（`:361-368`）、数据版本 vN（`:369-379`）、商城已确认版 vN/尚未确认（`:428-439`）。三者都是 vN 数字形态，业务用户需要反复横向对照才能分清「ERP 侧版本、系统数据版本、商城确认版本」三个概念；对只关心"有没有发出去、商城确认没有"的用户属于概念负担。
4. 概念翻译个别残留：Alert 标题「非写者边界」（`:745`）是 DDD/架构词，用户读不懂"谁是写者"；「延迟」筛选（`:913-916`）是网络术语，页内详情用的是「等待 / SLA」（`:1333-1336`），同一概念两套词。

## 3. 信息密度

- **列表**：10 列 + 选择列，左钉销售单、右钉操作，中间 8 列（ERP版本/数据版本/来源/商城/接收状态/商城已确认版/最近尝试/失败原因）。信息偏密：三个版本列 + 接收状态列下还叠加「超过 SLA / 接近 SLA」小字（`:416-424`），一行要扫 4 处版本/状态信息。
- **操作列**：最多 6 个按钮（预览/打开/销售单/查询结果/重试/W29，`min-w-[11rem]` 内 flex-wrap，`:483-570`），按钮数量随状态变化行高不一致，视觉噪声大。
- **空态与页脚**处理得体：「结果未知不计入已确认」以页脚小字（`:1078-1081`）+ 指标 detail（「不含结果未知」）双重表达，密度克制。
- **详情抽屉**：三轨状态 + 概览/执行内容/发送历史/版本对应/差异与错误 5 Tab 组织合理，白名单内容网格 8 字段两栏，密度适中。
- **重复信息**：批量操作成功后，`FormalActionResult` 结果卡片（`:751-772`，facts 含 成功/跳过/失败/仍未知）与 `BackgroundJobProgress` 进度卡（`:774-800`，同样的 成功/跳过/仍未知/失败 + 快照 ID）**同时出现且数据重复**，同一次操作产生两块反馈卡片。

## 4. 交互合理性

- **加载/空/错误**：列表骨架屏（`:662-670`）与失败重试（`:672-681`）完整；详情抽屉有独立 pending/error 态（`:1106-1113`）。协同卡两处状态处理有缺陷：消费汇总查询失败时静默显示 `0.00 / 0 单`（`collaboration-card.tsx:274-296` 无 isError 分支），误导用户以为"商城确实没消费"；协同主查询失败（`data` 为 undefined）会落入「还没推给商城」空态分支（`:59-90`），把"查询失败"误报为"确实没推过"。
- **分页**：`pageSize` 硬编码 8（`:230`），`onPaginationChange` 只写 page 忽略 pageSize（`:1029-1031`），而 UI 却提供 `pageSizeOptions=[8,20,50]`（`:1035`）——用户切 20/50 会立即弹回 8。表格框架描述「每页 6–8 行」（`:1011`）反而与事实一致但与控件不符。**分页条数控件是摆设**。
- **批量**：上限 20 条（`api.ts:43`）只在超限后报错「批量上限 20 条（系统保守约束）」（`api.ts:816-818`），选中 21+ 项前无任何提示；页头（`:716-737`）与批量选择条（`:984-1004`）两处批量按钮入口重复且文案不一致（「批量查询」vs「批量查询结果」）。
- **预览/打开**：「预览」抽屉（`:1541-1598`）内容（三轨状态 + 白名单网格）与「打开」详情抽屉头部高度重叠，且预览要先点「查看详情」再进详情——两步才能看完整信息，两个入口边界模糊。
- **确认对话框**：取消按钮沿用默认「返回修改」（`workflow.tsx:216`，本页未覆盖 `cancelLabel`，`execution-projections-page.tsx:1600-1701`），查询结果/重试场景没有"修改"对象，语义错位；锁定字段里「数据修订 v3」（`:1644`）与页内「数据版本」用词不一致（术语表：投影修订 → 数据版本）。
- **反馈聚焦**：结果卡片 `focus()` 处理到位（`:305-309`）；aria-label 齐全（指标条、批量区、搜索、筛选器均有）。
- **数据版本字段**：执行内容网格「数据版本」直接渲染 `contentHash` 原文（`sha256:…`，`:1771`），哈希上屏属于实现细节，用户无法利用。

## 6. 改进建议（按优先级）

1. **P0：清掉所有 W 编号文案**。行按钮 `:567` 改「接口错误中心」（或按行状态区分为「去处理错误」），`:180`「W29 任务」→「错误中心任务」，`:1637`「W29 待办」→「错误中心待办」。页面全部改用 `openWorkspaceLabel` / `workspaceLabel` 族（`lib/ui-text.ts:148-157`）。
2. **修复分页**：将 `pageSize` 移入 URL 参数（如 `size`），`onPaginationChange` 同时写 page 与 pageSize；或在列表页去掉 20/50 选项、改为统一 8/页并同步改表格框架描述文案。
3. **拆开双语义按钮**：ESCALATE 可用时显示「升级到接口错误中心」；已有任务/版本差异时显示「去接口错误中心处理」。杜绝一个按钮两种行为。
4. **批量上限前置**：选择条 `:970-974` 追加「最多批量 20 条，超出部分请分批」提示，并在超过上限时禁用批量按钮而非等到提交才报错。
5. **版本列瘦身**：列表保留「接收状态」+「商城已确认版」两列即满足主流程；ERP版本/数据版本移入详情抽屉「概览」（已有 `:1304-1342` 同字段），列表只留一列版本作上下文。
6. **内部 ID 与哈希清零**：`selectionSnapshotId` 改「选择批次号」或业务序号；`contentHash` 改为「数据 vN」。
7. **统一反馈渠道**：批量操作后保留 `BackgroundJobProgress` 作为唯一进度反馈，`FormalActionResult` 仅承担失败/阻断场景，避免双卡重复。
8. **协同卡补错误态**：`consumptionQuery` 与主查询均补 isError 分支（显示「数据加载失败，请刷新」），不要静默 0 或误报空态。
9. **术语一致性**：「非写者边界」→「本页只读」；「延迟」→「等待时长」；「白名单字段」→「执行字段」；「数据修订」→「数据版本」；确认框 `cancelLabel="取消"`。

---

**结论**：页面骨架与业务语言整体完成度高，核心操作（查询结果/重试/升级）语义清晰；最优先修复 W 编号泄漏（P0），其次是分页控件失效与双语义按钮（P1），随后做版本列瘦身与批量上限前置提示。
