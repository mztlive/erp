# UX 评审报告：/finance/supplier-accounts（供应商往来）

> 评审日期：2026-08-05 ｜ 评审视角：产品经理 / UX
> 评审范围：`erp-client/features/supplier-payables/supplier-accounts-page.tsx`（1590 行）、`allocation-session.tsx`（868 行）、`queries.ts`、`types.ts`，以及 `mock/session-state.ts` W12 段与共享组件 `components/business/*`（workflow.tsx / feedback.tsx / page.tsx / list.tsx / values.tsx）

## 1. 页面概述

页面为财务"供应商往来"（W12）工作台，包含两层：

1. **台账列表层**（supplier-accounts-page.tsx）：4 个视图 Tab（应付台账 / 付款 / 进项发票 / 待核销）+ 5 个可点击指标卡（开放应付、已到期应付、待分配付款、待分配进项票、先款门禁待满足）+ 搜索/供应商/来源类型/状态筛选 + 行内操作（预览、核销付款、继续核销、冲正、红票）+ 应付详情预览抽屉 + 供应商选择 + 冲正/红票确认框 + 跨页深链（W08 采购单 / W09 履约来源）自动进入核销会话。
2. **核销会话层**（allocation-session.tsx）：同供应商待核销池（多选 + 逐项分配金额）+ 本次付款/进项发票登记表单 + 拟分配/拟未分配实时试算 + ValidationSummary 定位式校验 + FormalActionConfirmDialog 提交确认 + 结果状态机（成功/被拒/阻断/未知，含"按操作号查询"兜底）+ 草稿保存。

整体结构清晰，主路径（查看 → 核销 → 提交 → 回列表重查门禁）闭环完整，深链与 returnTo 跨页流程设计成熟，为页面主要亮点。

## 2. 易用性

**顺畅的部分：**

- 从应付行直接"核销付款"（supplier-accounts-page.tsx:404-423）→ 会话预选该应付并预填分配金额，路径最短。
- 从 W08/W09 深链进入自动打开付款会话并预选采购单应付（supplier-accounts-page.tsx:226-275），完成提交后"返回来源并重查门禁"（allocation-session.tsx:520-529），跨页业务闭环设计得好。
- 预览抽屉内可直接转"登记付款/登记进项发票"（supplier-accounts-page.tsx:1407-1443），上下文不丢失。
- 冲正/红票在单据行内直达，确认框说明"原单保留、追加反向记录"，符合财务纠错心智。

**阻碍效率的部分：**

- **核销金额双份输入**：从应付行发起"核销付款"时，系统自动把分配金额预填为该应付开放余额，但付款金额字段为空（allocation-session.tsx:163-169），用户必须再敲一遍相同数字；进项票场景还要再手填不含税/税额共 3 个数字。单目标核销是最高频场景，重复录入既慢又易错。
- **打开会话即报两条校验错误**：因付款金额初始为空，会话一打开就同时出现"金额必须为正数"和"拟分配合计超过本次记录金额"（allocation-session.tsx:247-264），用户还未操作就先看到一片红色。
- **筛选无法一键还原**：跨页深链带入的 `purchaseOrderId` 筛选在"清除筛选"里被漏掉（见问题 P1-2），用户可能误以为清除功能失效。

## 3. 信息密度

**合理的部分：**

- 指标卡聚合了 5 个关键数字（开放应付、逾期、待分配付款/票、门禁户数），覆盖财务日常看板需要，且点击可联动视图筛选（supplier-accounts-page.tsx:963-1021）。
- 表格 compact 密度下信息组织尚可；应付行把"供应商/来源"、"应付含税/开放"、"已付/收票"分层展示（supplier-accounts-page.tsx:314-430），预览抽屉提供金额与分配关系明细。

**问题：**

- **金额口径标注不一致**：应付列头"应付（含税）/ 开放"中"开放"口径未标（开放 = 含税应付 − 净已付，混合口径）；"已付 / 已收票"列的 `settledTotal`/`invoicedTotal` 是净额却不标"净"，而进项票视图却写"净已分配"（supplier-accounts-page.tsx:333-353, 578-585）。用户对比两列会算不对账。
- 银行引用在列表只有打码值（supplier-accounts-page.tsx:465），`allowFullBankReveal` 字段未用于提供查看入口，核对银行流水时无法确认。
- 指标与视图缺少供应商维度的小计；筛选某供应商后列表仍是单笔行，没有该供应商应付汇总。

## 4. 交互合理性

**做得好的：**

- 提交确认层完备：FormalActionConfirmDialog 展示状态变化、锁定字段、影响、不可逆项（allocation-session.tsx:840-865），符合"正式动作先确认"规范。
- 结果状态机完备：成功/阻断/未知均有明确展示；"未知"提供"按操作号查询最终结果"（allocation-session.tsx:496-510），配合幂等键防重复提交，风险兜底好。
- 校验提示可点击定位到核销池（ValidationSummary 定位逻辑，feedback.tsx:549-558），分配超开放余额等业务校验在提交前拦截。
- 供应商锁定、跨供应商拒绝、混合来源策略提示在会话内都有说明（allocation-session.tsx:427, 776-783）。
- 列表加载有骨架屏、失败有明确"失败时不展示 0 元结论"的错误态（supplier-accounts-page.tsx:741-774），空态/无权限/无数据范围均有区分（778-809, 1165-1196）。

**问题（详见问题清单）：**

- 演示控件（模拟结果不确定/重复发票/并发版本冲突/策略缺失/收回权限）直接暴露在业务主路径上（supplier-accounts-page.tsx:1132-1162, allocation-session.tsx:787-814），非演示角色也可能误触发。
- 预览抽屉把"加载失败"与"未找到"合并显示为"未找到应付详情"（supplier-accounts-page.tsx:1446-1448），网络错误时误导用户。
- 阻断结果文案承诺"可切换到进项发票视图继续核销"（allocation-session.tsx:511-515），但页面上没有对应的切换按钮。

## 6. 改进建议

**高优先（对应 P1）：**

1. **会话金额联动预填**：发起付款核销时，把"付款金额"默认预填为已选目标分配合计（或唯一预选目标的开放余额），并在用户改动分配时同步试算提示；消除双份输入与初始报错（P1-1、P2-1 一并解决）。
2. **"清除筛选"补全参数**：把 `purchaseOrderId`、`from`、`returnTo` 一并纳入清除逻辑，或提供"离开此采购单上下文"的显式入口（P1-2）。
3. **红票与发票字段防护**：红票号码为空时禁用提交并提示必填，删除时间戳回退逻辑；发票代码去掉预填演示值，改为空值 + placeholder（P1-3、P1-4）。
4. **补充三金额交叉校验**：校验 不含税 + 税额 = 含税（允许分位差），不一致时在 ValidationSummary 中报错（P1-5）。
5. **文案术语对齐**：`fromWorkspace` 显示改走 `workspaceLabel()`；结果文案把"服务端"改"系统"、把"门禁/过账"按术语表口径替换；策略标识不上屏，改为业务可读说明（P1-6/7/8、P2-6）。
6. **继续核销防降级**：待核销视图"继续核销"若未能解析出原单据，改为提示"未找到原付款/发票，请回到对应视图操作"或直接禁用，禁止静默进入新单登记（P1-9）。

**中低优先（对应 P2）：**

- 增加"全部分配"/"按开放余额填充"一键操作与全选勾选；
- 预览抽屉区分"加载失败（可重试）"与"不存在"两种状态；
- blocked 结果下补一个"去进项发票视图"的跳转按钮，兑现文案承诺；
- 统一各视图金额口径标注（净/含税/开放），列头说清楚；
- 未分配视图增加轨道（付款/进项票）筛选；
- 表格开放排序能力；
- 演示控件收敛为仅演示模式可见，并给禁用按钮补充原因说明（参照术语表只读角色文案模式）。

**页面亮点（建议保持）：**

- 深链 + returnTo + 完成后重查门禁的跨页闭环；
- 未知结果兜底（按操作号查询）+ 幂等防重复；
- 提交前 FormalActionConfirmDialog 的锁定字段/影响/不可逆说明；
- 错误态刻意不展示 0 元结论的数据诚信处理。
