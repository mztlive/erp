> 评审视角：产品经理 / UX ｜ 参考基线：`docs/ui-glossary.md`（v1.2）

## 1. 页面概述

W17「商城同步与映射」单页六视图（Tabs）：运行总览 / 同步任务 / 来源数据 / 映射任务 / 每日核对 / 历史。页头提供三个手动动作（立即增量、按单补拉、刷新），页面中部常驻演示控制卡（角色 / 阶段 / 策略开关 / 来源开关）。

主业务路径：
- **手动触发同步**：立即增量（表单含理由校验）→ 创建任务 → 跳转「同步任务」并选中新任务；
- **失败处理**：任务详情卡显示失败分类与影响摘要 → 管理员可「重试失败任务」；
- **映射异常处理**：来源白名单记录 ↔ ERP 候选 → 领取 → 填写确认依据 → 双重确认 → 解决后进入「重新归集」；
- **每日核对**：差异列表 → 按此单号补拉（快捷路径）。

整体结构清晰、主路径闭环完整，状态呈现依赖共享 `BusinessStatusBadge` / `FormalActionResult` / `FormalActionConfirmDialog`，一致性良好。主要问题集中在：**封存态语义未贯彻、URL 参数与界面控件脱节、以及一批内部 ID / 枚举原值 / W 编号泄漏上屏**（多处命中术语表禁用清单）。

## 2. 易用性

**顺畅的路径**：
- 触发同步有独立表单 + 理由校验 + 成功结果面板，成功后自动跳转任务视图并打开新任务（mall-sync-page.tsx:336-355、:361-380）；
- 失败任务的重试按钮只在 `allowedActions` 含 `RETRY_FAILED_JOB` 时渲染，且有前置禁用原因（:1351-1379）；
- 「先跳过」成功后自动游标移到下一项（:459-474）；
- 每日核对详情卡提供「按此单号补拉」快捷入口，自动预填单号（:1942-1957）；
- 来源不可用 / 策略未配置时，按钮禁用并带 title 解释（:536-546）。

**阻碍效率的问题**：
1. **运行中任务无进度反馈**：触发增量/补拉后新任务状态为 RUNNING，但「页/数据/错」恒为 0/0/0，页面无轮询、无自动刷新，用户只能手动点「刷新」才知道是否完成（:599-604、api.ts:695-708）。对「查看同步状态/进度」这一核心诉求，反馈是断档的。
2. **全局搜索框在大部分视图是摆设**：搜索框固定渲染（:1182-1203），但 `q` 只过滤来源数据与映射任务（api.ts:504-529），在「同步任务 / 每日核对 / 历史」视图输入毫无反应，也没有任何提示。占位文案「商城单号 / ERP 单号 / 任务号」暗示覆盖任务，实际不覆盖。
3. **指标卡点击产生无效 URL 参数**：「失败任务」「待重新归集」指标写入 `status=failed` / `mappingStatus=resolved`（api.ts:415、:440），页面从不消费这两个参数 → 点击后列表未过滤，用户看到的是「点了一个看似筛选的动作，结果没变」，还遗留隐形 URL 状态。
4. **确认映射与先跳过的后续路径不一致**：跳过会自动移入下一项，确认成功后进程条直接消失，也不自动定位下一项，用户需要自己回列表点下一行；连续处理（SequentialProcessBar）在解决后整体卸载，没有任何「下一项」入口（:459-474 vs :430-435、:1853-1876）。
5. **封存态可继续浏览/操作第一期数据**：切到「已封存」后数据接口仍返回第一期 jobs/snapshots/mapping 全量（api.ts:467-471 的 `effectiveView` 是恒等运算），映射确认动作与 `confirmMapping` 均不校验 stage —— 封存后业务角色仍可提交「确认映射」，与 banner「已封存：无第一期写动作」自相矛盾（:539、:257）。

## 3. 信息密度

**合理的部分**：
- 状态全部走 `BusinessStatusBadge`（列表/详情两档），成功/失败/警告一眼可辨；
- 映射详情左侧证据、右侧候选并排，grid 分区清晰；敏感字段打码（:1590）；
- 指标条与六个 Tab 联动高亮（MetricFilterItem active 态），导航性强。

**过疏 / 过密的问题**：
1. **任务表「页/数据/错」列头语义不明**（:587）：`12/148/2` 这种三连数字无列标题说明，且「数据」应指「条数」；列头加说明或改为「页 12 · 条 148 · 错 2」。
2. **任务详情缺少失败明细**：只有错误分类 + impactSummary（:1342-1346），部分失败任务哪几页失败不可见，无法支撑「处理失败项」的排查诉求。
3. **同步进度信息用原始 token 而非业务口径**：「当前同步进度」直接显示 `wm_20260801_090000` 这类内部水位值（:1254-1256），对用户无意义；应显示「数据更新于 08-01 09:00」这类业务时间。
4. **演示控制卡常驻**（:1054-1138）：四个演示开关占据页首大片纵向空间，对不关心演示的真实使用者是噪音；建议折叠为一行「演示」入口。
5. 空态覆盖基本齐全（映射任务/详情选择/核对无范围），但 overview「最近同步任务」与 history 为空时直接渲染空白（:1285-1300、:1982-1996）。

## 4. 交互合理性

**做得好的**：
- 加载骨架、查询失败 Alert + 重试按钮（:858-887）；
- 确认映射走 `FormalActionConfirmDialog` 双重确认，列出影响与不可撤回项（:2161-2177）；
- 表单校验（理由 ≥4 字、单号必填）与 mutation pending 禁用防重复提交；
- 「来源不可用」时提供「可安全重试既有失败」的下一步指引（:545）。

**问题**：
1. **重试失败任务后不刷新数据**：`retryJob.mutateAsync` 成功后只 setResult，未 `pageQuery.refetch()`（:1358-1375），新重试任务（含 jobNo-R1）不出现，用户必须再手动刷新；且该按钮无确认对话框、理由硬编码「安全重试部分失败分页」（:1361），存在误触风险（术语上「安全重试」也是禁用词的变体，见问题清单）。
2. **首次领取按钮文案「重新领取」**：unclaimed 状态下按钮直接叫「重新领取」（workflow.tsx:495，页面 :1874 接入），首次领取语义不符。
3. **admin 角色也渲染 SequentialProcessBar**：进程条含被禁用的「确认映射」按钮（因为 admin 不能确认），但没有解释，admin 用户看到一排点不动的按钮（:1853-1876；术语表 §7「不要摆一排禁用按钮」）。
4. **「确认映射」提交按钮禁用无原因提示**：未选候选时按钮 disabled，页面上没有任何「请先选择 ERP 候选」的提示，用户可能困惑（:1731-1735）。
5. 动作失败 Alert 不会自动消失，跨操作残留（:1234-1239），错误文案亦未统一「说下一步」。

## 6. 改进建议

**优先修复（P0 + P1）**：
1. **文案清零**：按术语表逐项替换 —— ① `external_identity_map` 改为业务口径；② `wi_*`/`eim_*` 待办与结果编号改用「来源单号 + 任务号」；③ `wm_*` 全部替换为 `formatDateTime` 业务时间；④ 错误码/枚举统一走中文映射（如 `blockerMessage` 已含中文，直接删掉 `code` 前缀渲染）；⑤ W23/W29 按钮改 `workspaceLabel()`。
2. **修复指标筛选**：在页面消费 `status`/`mappingStatus` 参数并落地到 jobs/mapping 过滤（或删掉 `targetFilter` 交给查询层），同时补「清除筛选」入口 —— 与 AGENTS 契约对齐。
3. **封存态闭环**：`confirmMapping`/`reapply` 增加 stage 校验；sealed 时非 history 视图给只读提示或强制跳转，去掉可点但无效的确认按钮。
4. **RUNNING 进度反馈**：任务详情对 RUNNING 任务做轮询（如 3-5s refetchInterval）或展示「上次成功同步时间」，避免进度断档。
5. **搜索范围收敛**：搜索框按当前视图提示可用范围，或让 `q` 同时过滤任务号列。

**体验打磨（P2）**：
- 确认成功后自动定位下一项（与「先跳过」行为对齐），或保留进程条并给出「下一项」按钮；
- 重试动作加确认对话框 + 成功后 refetch；领取按钮文案区分首领取/重领取；
- 演示控制卡折叠；「页/数据/错」列头加说明；封存 banner 去重；DataFreshness 时间口径统一。
