# UX 评审报告：集成错误任务详情页

- 页面：`/governance/integration-errors/errors/[taskId]`（集成错误任务详情，W29 接口错误与对账中心）
- 代码：`erp-client/features/integration-errors/integration-error-detail-page.tsx`（薄 wrapper，实际全部逻辑在 `integration-errors-page.tsx` 的 focusMode 分支）+ `queries.ts` / `types.ts` / `url-state.ts` / `api.ts` / `mock/integration-errors.ts` + `components/business/domain.tsx`（InterfaceErrorResolutionPanel）、`workflow.tsx`（SequentialProcessBar）、`feedback.tsx`（FormalActionResult）
- 评审角色：产品经理 / UX 视角；依据 `docs/ui-glossary.md`（术语表）与 `erp-client/AGENTS.md`（界面契约）

## 1. 页面概述

路由 wrapper `integration-error-detail-page.tsx:6-12` 仅传 `forcedTaskId` 给 `IntegrationErrorsPage`，页面以 **focusMode** 渲染：隐藏队列、筛选、指标跳转，聚焦单个任务，展示：

1. 页头（面包屑 + 集成更新时间）
2. 指标条（详情模式下仍显示，但点击无导航效果）
3. 返回队列 / 刷新当前任务按钮组
4. 连续处理条（第 n/m 条、领取状态、处理当前 / 下一项 / 重新领取）
5. 先跳过（保留队列）/ 跳过 快捷按钮
6. 任务卡片：分类徽章、环境/严重度/状态/资金影响、Fact 网格（滞留/责任/方向/原动作/原任务号/事件摘要/载荷摘要）、对账左右证据（差异类）、修复入口
7. 证据与尝试卡片：尝试历史、证据时间线、处理审计、已关联证据、解决证据策略
8. 接口错误处理面板（按错误类给指引与动作）
9. 处理动作卡片：全部可用动作 + 阻断原因 + 处理说明 + 直接对账（无任务）分支

页面目标用户：运维 / 客服 / 采购 / 财务（对账），核心诉求是「一眼看到这单是什么、错在哪、能不能点重试 / 跳过 / 解决」。

**总体印象**：信息架构完整、错误分类引导是亮点（每类错误都有"做什么 / 不做什么"的明确指引）；主要问题集中在**详情路由的取数与状态处理不完整**、**连续处理条按钮是空操作**、**终态动作无确认**、**内部 ID / 枚举原值多处上屏**。

## 2. 易用性

### 顺畅之处
- 详情页聚焦单任务，隐藏队列与筛选，干扰少；`goToItem` 前后台一致（`integration-errors-page.tsx:412-433`）。
- 「先跳过（保留队列）」/「跳过」按钮语义清晰地区分"暂缓处理"与"推进到下一项"（按钮文案层面）。
- 每类错误给出"下一步"指引（domain.tsx:1194-1257 的 guidance + 页内 Alert），例如结果未知 → 只允许查询原结果；映射错误 → 去修复映射。这是全页面做得最好的部分。
- 修复链接（repairLinks）直接跳到供应商商品库 / 商城同步 / API 连接，任务上下文（q 参数）已带入。
- 成功后结果横幅可聚焦、有"下一项"按钮（`feedback.tsx:716-767`），键盘路径可用。

### 受阻之处
1. **详情取数失败/任务不存在时无任何错误态**：详情数据来自独立的 `detailItemQuery`（`integration-errors-page.tsx:185-189`），但页面只在 `queueQuery` 上有 isPending/isError 分支（`:562-584`）。`detailItemQuery` 失败或返回 null（任务不存在/已删除）时，item 为 undefined，直接落到「未选择处理项 · 从左侧队列选择任务或差异」空态（`:1845-1851`）——而详情模式根本没有左侧队列，用户看到的是"无任务"且没有任何解释或重试入口，只能靠"返回队列"按钮自救。
2. **「刷新当前任务」按钮是假的**：`returnRefresh`（`:557-560`）只 `queueQuery.refetch()`，但详情模式下展示的 item 来自 `detailItemQuery`（`:191-194`）——点刷新，页面内容纹丝不动，按钮名与行为不符。
3. **页面顶部最重要的两个动作按钮是空操作**：「处理当前」的 onClick 只是把焦点移到标题上（`:1234-1236`），「下一项」在详情模式（items.length=1）下 `neighbor(1)` 恒为 null（`:1237-1240`），点了没反应；真正的处理动作（查询原结果/标记已解决）藏在第四、第五张卡片里。用户会自然先点顶部主按钮。
4. **终态动作零确认**：「标记已解决」「关闭重复」「确认无误」「确认有效差异」均为一次点击即执行（`:1701-1708`、`:1722-1728`、`:1760-1788`），且点击时系统会**自动伪造证据记录**（`handleResolve` 在缺证据时先用 `newKey("pol")` 生成证据引用再提交，`:754-785`；`handleDirectTerminal` 同理 `:824-828`）。对"已入账资金"或"差额 ¥510"的任务，误点即产生终结结论，无撤回。

## 3. 信息密度

### 过密之处
- 详情页一屏纵向堆叠 6 张卡片（任务卡片 → 证据与尝试 → 解决面板 → 处理动作），每张卡片信息量都不小；任务卡片内的 Fact 网格（滞留/责任/方向/原动作/原任务号/事件摘要/载荷摘要）与解决面板的"最近尝试/请求摘要/响应摘要/下次重试"高度重叠（`:1345-1382` vs domain.tsx:1356-1404），同一份尝试数据被渲染两遍。
- 徽章行密集：分类 + 环境 + 严重度 + 状态 + 资金影响 + 补偿未闭环最多 6 个徽章（`:1290-1309`）。
- 「证据与尝试」卡片里 尝试历史、证据时间线、处理审计 三段时间线并列，对普通用户（采购/财务）区分度低——"证据"与"处理"的审计条对非运维人员几乎不可读。

### 过疏之处
- **错误原因缺少一句"人话"总述**：页面没有"为什么错、影响什么、你需要做什么"的三行式摘要，用户要在 分类徽章 + 面板 guidance + 尝试历史 + 阻断原因 之间自行拼装结论。尝试历史里混着 `HTTP 504 · 无 body（已脱敏）`、`MAPPING_REQUIRED`、`DUPLICATE_IGNORED`、`SIGNATURE_INVALID` 等技术原值（`mock/integration-errors.ts:80/88/210/326`），对非研发用户不友好。
- 业务单上下文单薄：业务对象只有一行标题（如 `SO-SF-77120 · 供应商接单`），金额、收件人、商品等关键上下文全部打码或缺失——用户可能不得不跳去供应商订单页才能判断"这单要不要重试"。

### 人话程度（错误原因）
- 分类标签与指引（结果未知/参数映射错误/供应商业务拒绝…）是业务化的，good。
- 但以下字段仍是"机话"：错误码徽章 `RESULT_UNKNOWN`（`:1589`）；筛选摘要 `视图=mine · 模式=all · 环境=production`（api.ts:412-418 → 页 `:1077-1080`）；证据策略 `pol_result_unknown_potential@v2 · DISTINCT_REVIEWER`（`:1539-1546`）；替代任务输入框默认值 `wi_iet_orig_55102`（`:238`）。

## 4. 交互合理性

- **加载态**：队列 skeleton 覆盖整页（`:562-573`），但详情数据（detailItemQuery）pending 时先闪「未选择处理项」空态再出内容，有闪烁。错误态只有队列级兜底（`:575-584`），详情级无。
- **空态**：无任务时渲染「当前筛选项已处理完」（`:1125-1130`）或「未选择处理项」（`:1846-1850`），后者在详情模式语境错误（没有左侧队列可"选择"）。
- **操作反馈**：动作成功/失败有结果横幅 + Alert，有 aria-live；`lastResult` 会聚焦（`:407-410`）。但失败信息直接透传 API message（`:531`），个别是机话（见上）。
- **误操作防护**：动作有服务端门禁（blockers）和禁用态，这是好的；但**没有任何确认对话框**，且"标记已解决"点击一次实际可能连发 两次操作（先补证再解决，`:774-803`），用户无从知晓。
- **返回路径**：存在两条返回入口且状态保留不一致——页头「返回队列」保留 view+queueContextId（`:1066`），连续处理条「返回队列」只保留 view（`:1225-1233`），后者的 onBack 会丢掉 mode/environment/owner/q 等全部筛选。用户返回后可能发现队列"变了"。
- **按钮语义**：部分按钮与行为不符——「返回后刷新当前任务」实际是"立即刷新且不返回"（`:1438-1445`）；「处理当前」「下一项」空操作；「跳过」在详情模式点击后无任何可见变化（队列里它仍是 PENDING，焦点也不变，`:526-529` + focusMode 下 neighbor(1)=null）。
- **URL/控件契约**：AGENTS §5 要求"URL 参数与界面控件一一对应"。`forceUnknownOnce` 勾选框（`:1082-1090`）是唯一改变查询行为的控件，但它是个 **"模拟仍未知"的演示开关**，出现在正式界面中（术语表 §6 演示标记原则下也不应裸奔）；`sessionAutoNext` state 写入后仅被死代码消费（`:1079`）。

## 6. 改进建议

1. **补齐详情取数状态（P1-1，最高优先）**：为 `detailItemQuery` 增加 isError →「加载失败 + 重试」、null →「未找到该任务，可能已结束或链接失效」+ 返回队列按钮；加载中给详情骨架而非空态。同时把页面渲染门禁从 `queueQuery` 改为详情相关 query，消除空态闪烁。
2. **修「刷新当前任务」（P1-2）**：`returnRefresh` 中追加 `detailItemQuery.refetch()`（或直接 `queryClient.invalidateQueries(integrationErrorKeys.item(...))`），并在按钮 hover/点击时给"正在刷新…"反馈。
3. **重新接线连续处理条（P1-3）**：详情模式下「处理当前」应绑定当前错误类的**主动作**（结果未知→查询原结果；可重试→重新提交；映射错误→去修复），而非 focus 标题；「下一项」在无下一条时应禁用（或按 focusMode 隐藏，参考 W09 的 `showProcessNext` prop 先例）。按钮契约：说动作就做动作。
4. **终态动作加确认（P1-4）**：资金影响 ≠ 无 或 补偿未闭环 时，「标记已解决/关闭重复/确认无误/确认有效差异」前弹确认框，展示将写入的证据清单；把自动补证据改为显式——证据由用户经明确入口添加，或确认框内明示"系统将自动登记 X 证据"。
5. **替代任务改选择器（P1-5）**：关闭重复的替代任务改为从队列（同错误类 PENDING 任务）下拉选择，展示业务名（任务号 + 业务单），彻底移除 `wi_*` 输入；默认值不再预填。
6. **过一遍术语表（P1-6）**：错误码徽章改中文分类名（`classification.label`）；filterSummary 用 `VIEW_LABEL/MODE_LABEL/ENV_LABEL` 中文映射拼装；证据策略 Alert 改为「需要 外部案例结果、业务对象核验 · 需独立复核」，去掉 policyId 与 `DISTINCT_REVIEWER` 原值。按术语表 §5.2 的扫描命令（`rg "IN_PROGRESS|REPLAY_ACCEPTED|..."`）做回归。
7. **演示控件收进演示模式（P1-7）**：`forceUnknownOnce` 勾选框移入「演示模式」开关（术语表 G6 口径）或直接移除；它不应在正式界面里改变真实查询语义。
8. **去重与语义清理（P2）**：解决面板与处理动作卡合并为单一动作区（面板负责指引、动作卡负责执行，或去掉重复按钮）；统一一条返回路径（保留 view+queueContextId 语义，丢失的 q/owner 在返回时从 URL 补回）；「跳过」在详情模式改为禁用并给出 tooltip「回到队列使用」；删除死代码 `sessionAutoNext`；领取状态文案改用 `leaseText` 常量；空态文案按 focusMode 区分。
9. **人话摘要（体验上限项）**：卡片顶部增加一行三句式摘要：「这单：X 供应商下单结果未知 · 潜在资金影响 ¥N · 你只需先查原结果」。技术上来自 classification + fundsImpact + guidance，不新增数据。

---

### 结论

页面骨架与错误分类引导是 W29 的强项，但详情路由的**取数失败无兜底**、**顶部按钮空操作**、**终态零确认**、**内部标识上屏**四类问题叠加，会让真实用户（运维/财务）在"点重试/点解决"主路径上反复受阻或产生误操作。建议优先处理 P1-1 ~ P1-4，再做一次全页文案过表（P1-6）。
