## 一、页面概述

路由壳 `app/(workspace)/governance/history-backfill/[jobId]/page.tsx` 将 `jobId` 传入 `HistoryBackfillPage` 的 `routeJobId` 分支，由 `JobDetailView` 承载（history-backfill-page.tsx:274-287, 940-1471）。

页面自上而下结构：

1. 面包屑（治理 / 历史消费回填 / 任务号）+ 返回任务列表、刷新按钮
2. 演示角色切换条 + 「下次动作·结果未知」演示按钮
3. `DocumentHeader`：商城名标题、任务号、版本（`lv-*`）、处理状态、报告确认/商城/范围/下游功能四轨状态、动作区（校验来源/开始回填/续跑原任务/下载报告）
4. 若干 Alert（技术处理完成≠报告确认、覆盖不足阻断、处理动作阻断、下载结果、正式结果 banner）
5. `ImportStageIndicator` 六阶段指示器 + `BackgroundJobProgress` 后台进度卡 + `CostCoverageNotice` 成本覆盖卡 + 任务事实网格（发起人/时间/原任务标识/范围说明/履约说明）
6. 七个 section Tab（概览 / 记录结果 / 去重 / 未归集 / 成本口径 / 失败诊断 / 审计报告），Tab 状态写入 URL（`section`）
7. 开始回填、续跑两个 `FormalActionConfirmDialog` 确认弹窗

**总体判断**：深链、面包屑、Tab 深链、确认弹窗、阻断原因解释等骨架完整，业务化程度整体较高；主要问题集中在「状态与数字自相矛盾」「按钮与行为不一致」「内部字段/枚举/ID 上屏」「隐形过滤状态无控件」四类。

## 二、易用性

**做得好的**：列表页任务号/「打开」双入口深链可用（history-backfill-page.tsx:335-348, 432-444）；详情页 Tab 全部可深链（`section` 入 URL）；返回列表保留列表筛选状态（282-284）；无效 jobId 有错误态 + 返回列表按钮（992-1007）；START/RESUME 均有影响确认弹窗，且明确「不可回滚」后果（1418-1468）。

**主要缺口**：

1. **报告确认动作在 UI 中不存在**：后端契约在满足条件（COMPLETED + PENDING + 策略已配置 + 财务/管理员）时返回 `CONFIRM_REPORT` 动作（api.ts:358-367），但详情页所有按钮（1182-1226、2028-2036）均无确认入口，`runCommand` 动作类型也不含它（1049-1050）。「技术处理完成 → 报告确认 → 下游解锁」这一条主业务闭环在 UI 上是断的：审计报告页永远只能看到「未确认」提示，没有完成它的动作。
2. **明细固定取第 1 页 100 条且无分页**（966-976 固定 `page:1, pageSize:100`；1816-1824 的 `DataTable` 未接分页）：真实任务动辄数万条，「失败诊断」「未归集」「去重」各 Tab 只能看到前 100 条中筛出的子集，大任务的失败重试链路实际不可达。
3. **从列表带入的关键词 `q` 是隐形过滤**：详情查询消费 `urlState.q`（971），进入详情时 URL 状态整体继承（284），但详情页 `ItemFilters` 只有结果/记录类型/成本口径三个控件，没有任何 `q` 控件或清除入口（1473-1563）。用户从搜索列表点进详情后明细被悄悄过滤，无法察觉、无法取消——违反「URL 参数与界面控件一一对应」契约。
4. **失败诊断只有诊断、没有重试**：失败项单元格仅给「可续跑 / 需业务修复」文本（1768-1778），整单续跑按钮在页头（1202-1210），而逐项「重新归集」动作 `REATTRIBUTE` 在类型与 api 中完整存在（types.ts:78, api.ts:765-797）却没有任何 UI 入口，是死能力。
5. **深链错误态语义合并**：任务不存在与「无模块权限」共用同一个「任务不存在或无权查看」文案（992-1007），且「请…检查任务身份」措辞晦涩；此态下没有重试按钮（列表页错误态有重试，739-749）。

## 三、信息密度

**偏密的区域**：详情首屏自上而下堆叠 4 类警示（覆盖阻断 Alert、完成≠确认 Alert、处理动作阻断 Alert、正式结果 banner，1230-1275）+ 状态轨 + 阶段条 + 进度卡 + 成本卡 + 8 项事实网格，信息之间无视觉层级收敛，用户进入任务详情的第一屏是「一屏警示」。

**重复展示**：
- 进度卡五组数字（已处理/新增/去重/待归集/失败，1291-1301）与概览 Tab「结果记录」卡六组数字（1606-1629）几乎完全重复；
- `DocumentHeader` 的 meta（1138-1144）与状态轨「范围」条目（1163-1170）两次展示同一范围信息；
- 创建弹窗中「必需历史起点」与「回填起点（固定）」为同一值两行（841-848）。

**直接观感缺陷**：后台进度卡三个统计块（成功/跳过/失败）中的「失败」数值把「待归集」并入失败统计（1289 `failedCount + unattributedCount`），而同卡描述文字又分别列出「待归集 N · 失败 N」（1293-1297）——同一张卡片内出现两个互相矛盾的「失败」数字，是信息密度里最伤信任感的一处。

## 四、交互合理性

**不合理交互**：

1. **阻断动作却推进了任务状态**：点击「校验来源」时，若覆盖不足，api 先写入 overlay `processingStatus=VALIDATING`、推进锁版本（api.ts:550-556），再返回 BLOCKED（557-566）。用户看到「来源校验未通过」横幅，8 秒后轮询刷新页面状态变成「校验中」——被阻断的操作改变了状态，阻断横幅与任务徽章自相矛盾。
2. **「下载报告」不下载**：页头按钮（1211-1225）与报告页按钮（2028-2036）点击后都只设置一条提示文案，且两处提示内容还不一致（页头写 `reportId v版本 · 已记录审计`，报告页写 `Schema · 规则版本`）；「已记录审计」是虚构行为描述。按钮说动作、动作必须真实，这是明确的语义造假。
3. **运行中任务 8 秒轮询导致明细表整表闪烁**：`refetchInterval` 8s（queries.ts:42-46）把 `isFetching` 传给 `ItemsTable` 的 loading（1394-1399、1823），用户在「失败诊断/未归集」逐条查看时表格每 8 秒刷新一次。
4. **手动刷新按钮无加载反馈**（1099-1107）：点击后无 spinner、无禁用，配合轮询无法区分「点了没反应」。
5. **非管理员角色动作按钮整体消失**（1182-1226）：FINANCE/OPERATIONS 进详情时「校验来源/开始回填/续跑」凭空消失，无解释；仅有的一部分解释（ROLE_DENIED 阻断 Alert，1344-1357）又带着原始错误码前缀上屏。
6. **按钮语义总体清晰**（「开始回填」「续跑原任务」「校验来源」都是业务动作词），确认弹窗的锁定字段/影响/不可回滚结构（1418-1468）是示范级的——这一点与前面几项并存，说明问题不在基础能力而在一致性收口。

## 六、改进建议

1. **补齐报告确认闭环（P1-1，最高优先）**：详情页渲染 `CONFIRM_REPORT` 按钮（放在 DocumentHeader 动作区与审计报告页各一处），确认动作走 `FormalActionConfirmDialog`，文案对齐「确认报告」；与 `POLICY_NOT_CONFIGURED` 的「确认动作不可用」Badge 互斥出现。
2. **明细分页化并给 q 以控件**（P1-2/3）：详情明细接分页或「加载更多」（建议分页状态入 URL），或在明细区补一个带清除按钮的关键词输入框，删除 ItemFilters 中的「URL：…」说明文字。
3. **修正数字与状态一致性**（P1-4/5）：进度卡「失败」恢复为纯 failedCount，待归集单独一档或并入「跳过」并说明；校验来源被阻断时不得推进状态/锁版本。
4. **阶段指示器语义化**（P1-6）：为回填流水线提供专属六步标签（范围确认 / 来源校验 / 记录入库 / 归集评估 / 报告 / 完成），不要复用「上传/映射/预览/提交」导入词。
5. **文案过一遍术语表**（P1-7/8/9/10、P2-2/4/11/12）：替换所有枚举原值（走 `COST_BASIS_LABEL`、`FACT_TYPE_LABEL` 等既有映射）；去重证明列改为业务摘要（如「命中实时记录 · 订单号…」）；「原任务标识/原任务号」改为展示任务号本身；错误码不再前缀上屏；「下游功能」改为「后续流程：已可用 / 保持关闭」。
6. **按钮行为落实**（P1-11）：「下载报告」接真实下载（或明确标注「示例：报告文件生成中」），两处提示统一；「已记录审计」删去或仅在真实落审计后展示。
7. **轮询与加载体验**（P2-6/7）：轮询时仅更新进度卡/徽章，不刷新明细表；刷新按钮绑定 `isFetching` 态（spinner/disabled）。
8. **角色只读态**（P2-9）：参考 W09「👁 你只能查看…」模式，非管理员角色用一行说明替换动作区，而不是让按钮凭空消失。
9. **信息密度收敛**（P2-8/15）：压缩首屏 Alert 数量（合并同类阻断为一条）、消除进度卡与概览卡数字重复、创建弹窗去重同值字段。
10. **暴露 REATTRIBUTE 或移除**（P2-5）：未归集项给出「重新归集」逐项操作（复用 `FormalActionConfirmDialog`），否则从类型与 mock 中摘除，避免死能力。
