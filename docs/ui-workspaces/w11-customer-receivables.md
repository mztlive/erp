# W11 · 客户往来

> 状态：草稿
> 页面模式：M2 高密度查询列表 + M5 分摊/核销工作区
> 主要路由：`/finance/customer-accounts`
> 主要角色：财务；销售、销售经理和管理层按授权只读
> 最后更新：2026-08-01

## 1. 定位与目标

### 1.1 用户目标

- 财务以实际收款/开票往来主体为上下文，看清应收、回款、销项发票和待核销余额。
- 一次完成“登记实际到账 + 分配到同一往来主体的多笔应收”，或“登记销项发票 + 分配到同一往来主体的多个可开票对象”。
- 从销售单票款区带入当前应收，在同一 W11 核销会话处理后回到原销售单，不再寻找独立核销菜单。
- 对已过账事实发起退款、回款冲正或红票纠错，并保留原事实和全部反向关系。

### 1.2 业务目标

- 把应收、回款、销项发票保持为三类独立事实；资金核销和发票核销保持两条独立多对多关系。
- 以 `counterparty_party_id` 作为资金与发票核销的主体相等键；`customer_id` 仅表示企业客户经营归属，不替代实际结算主体。
- `receivable_account/entry`、回款分配和发票分配在事务内同步更新，提交成功后立即显示正式余额。
- 卡券与非卡券销售单复用同一套客户往来能力；卡券复核状态明确展示但不改变核销内核。

### 1.3 不在本工作面完成

- 不修改销售单、合同、客户归属或销售金额；应收来源变化由 W05 正式版本或变更事实驱动。
- 不把回款和发票合成一条“票款进度”，也不允许用回款替代发票或用发票替代回款。
- 不跨 `counterparty_party_id` 核销；同一企业客户存在多个结算主体时必须分会话处理。
- 不直接编辑已过账回款、已登记发票、应收分录或核销行；错误通过退款、冲正、红票和反向分配纠正。
- 不把普通收据、银行回单、付款凭证写成发票；它们只作为附件或证据。
- 不在 W11 完成卡券期初复核结论；复核任务在 W13，W11 只登记其所需的正式回款、发票和核销事实。

## 2. 用户、权限与数据范围

| 角色 | 默认入口 | 可见范围 | 主要动作 |
| --- | --- | --- | --- |
| 财务经办 | W11 | 授权组织/往来主体的应收、回款和销项发票 | 登记、分配、保存草稿、发起纠错 |
| 财务复核 | W02 财务纠错队列，可进入 W11 | 待复核纠错及其原事实 | 只读核对；正式复核在队列完成 |
| 销售/协作销售 | W05/W03 链入 | 本人负责或历史参与客户的销售单票款摘要 | 只读、催回款；不得登记或核销 |
| 销售经理 | W03/W15 链入 | 本团队客户的应收与回款进度 | 只读下钻 |
| 管理层 | W15 链入 | 授权公司范围汇总与必要明细 | 只读，不显示写入口 |

权限与范围规则：

- 无 W11 模块权限时隐藏导航；直接访问显示无权限页。
- 财务数据范围、往来主体和字段权限由服务端过滤；前端不得接收全量后隐藏。
- 有模块权限但无数据范围时显示“当前角色未配置客户往来范围”，不得用 0 元假装无应收。
- 银行引用、附件和往来主体银行资料属于敏感信息；默认掩码，揭示权限与时限由服务端给出，日志不得记录完整值。
- 有查看权但无登记/核销权时，事实可见，动作保留禁用并显示 `actionBlocker`。
- 财务纠错必须经办/复核分离；不能因为用户同时拥有两个角色就允许同一人复核自己的记录。
- 页面期间权限收回时清除敏感值、未提交附件引用和查询缓存，未保存输入按安全策略处理。

## 3. 入口、路由与任务页签

| 场景 | 入口 | URL / 页签行为 | 返回位置 |
| --- | --- | --- | --- |
| 侧栏进入 | 客户往来 | `/finance/customer-accounts?view=receivable`，聚焦固定 W11 列表页签 | 原页签保留 |
| 从销售单登记回款 | W05 票款子区 | 打开 W11 会话，携带往来主体、应收账户/分录和来源页签 ID | 完成/取消后回 W05 原票款入口 |
| 从客户中心进入 | W03 | 携带 `customerId`，仍由服务端返回其可见结算主体 | 返回 W03 保留客户上下文 |
| 从卡券复核登记事实 | W13 | 携带 `workItemId`、应收账户和队列返回上下文 | 完成后回 W13 当前项并刷新指纹 |
| 选择往来主体后登记 | W11 工具栏 | 创建稳定草稿会话 ID，在同一 W11 TaskTab 打开 M5 工作区 | 返回原列表筛选与行焦点 |
| 刷新/后退 | 任意列表或会话 | 列表筛选与稳定会话 ID 可恢复；敏感揭示状态不恢复 | 返回原视图 |

固定列表页签身份为 `workspace:customer-accounts:{viewerScopeId}`。核销会话身份为 `allocation:customer:{draftSessionId}`，标题为 `核销 · {往来主体简称}`。会话 ID 是草稿/交互身份，不是正式核销事实；正式身份由回款单、发票和追加式分配行构成。同一草稿不得打开多个并行编辑页签。

### 4.3 区域与视图规则

| 区域 / 视图 | 目的 | 规则 |
| --- | --- | --- |
| 应收台账 | 看销售单来源的开放应收和到期情况 | 只读派生；行展开显示分录，不提供“编辑应收” |
| 回款 | 看实际到账事实及其净有效分配 | 已过账行不可编辑；纠错从原事实发起 |
| 销项发票 | 看蓝/红票及其净有效分配 | 发票方向、蓝红类型和会计增减方向分别展示 |
| 待核销 | 聚合有有效剩余的已过账回款和已登记销项发票 | 回款与发票分区，不把两种余额相加 |
| detail 预览 | 列表内读完主体、来源、金额、分配和反向关系 | 正式单据采用 768px 双栏；重作业进入会话 |
| 核销工作区 | 登记事实并完成同主体多对多分配 | 回款和发票共用主体上下文但分轨提交 |

## 5. 展示内容与字段

### 5.1 应收台账

| 字段 | 用户文案 | 数据来源 | 口径 / 格式 | 权限规则 |
| --- | --- | --- | --- | --- |
| `counterpartyPartyName` | 往来主体 | `receivable_account.counterparty_party_id` 的授权投影 | 资金与发票核销的相等键 | 必须可见才能进入核销会话 |
| `customerName` | 经营归属客户 | `receivable_account.customer_id` | 仅经营归属，不作为核销相等键 | 销售数据范围控制 |
| `salesOrderNo` / `accountSeq` | 销售单 / 往来子账 | `receivable_account` | 结算主体纠错产生新子账时序号可追溯 | 按单据查看权 |
| `businessType` | 业务性质 | 销售版本投影 | 卡券 / 实物服务 | 只读 |
| `grossTotal` | 应收总额 | 事务内同步汇总 | 含税人民币，服务端返回 | 金额权限 |
| `settledTotal` / `openTotal` | 已核销回款 / 开放应收 | 净有效 `receipt_allocation` 汇总 | `APPLY - REVERSE`，前端不重算 | 金额权限 |
| `invoicedTotal` / `openInvoiceableTotal` | 净已开票 / 剩余可开票 | 净有效销项票分配汇总 | 回款进度与此无关 | 金额权限 |
| `dueDate` | 到期日 | `receivable_entry` | 自然日；逾期状态由服务端返回 | 可见 |
| `status` | 未结 / 部分结清 / 已结清 | `receivable_account.status` | 不能用开票状态推断 | 可见 |
| `reviewStatus` | 卡券票款复核 | `receivable_account.review_status` 查询缓存 + 有效复核链结论 | 不适用 / 期初待复核 / 已复核 / 同步差额待复核 | 有复核查看权时显示 |

应收 detail 还需展示不可变分录：类型、增加/减少方向、正数含税金额、到期日、来源事实/版本、入账时间和 `receivable_entry_offset` 冲减关系。同步金额或销售变更只追加差额，不覆盖原分录和既有回款/发票。

### 5.2 回款与核销

| 字段 | 用户文案 | 数据来源 / 口径 |
| --- | --- | --- |
| `receiptNo` | 回款单号 | `customer_receipt.receipt_no`，正式形成后唯一 |
| `counterpartyPartyName` | 实际付款往来主体 | 必须与目标应收子账主体相等 |
| `receivedAt` | 实际到账时间 | 业务发生时间；与 ERP 记录时间分别展示 |
| `amount` | 到账金额 | 正数含税金额 |
| `bankReference` / attachment | 银行流水 / 回单 | 敏感值掩码；普通回单不是发票 |
| `allocatedTotal` / `unallocatedAmount` | 净已分配 / 未分配 | 服务端按有效 `APPLY - REVERSE` 返回；前端不从当前页求和 |
| `status` | 草稿 / 已过账 / 已冲正 | 原回款保留；冲正表示存在反向事实 |
| 分配明细 | 销售单、应收分录、序号、动作、金额、时间、反向来源 | `receipt_allocation` 追加式事实 |

### 5.3 销项发票与核销

| 字段 | 用户文案 | 数据来源 / 口径 |
| --- | --- | --- |
| `invoiceCode` / `invoiceNo` | 发票代码 / 号码 | 有代码时方向+规范化代码+号码唯一；数电票按方向+号码唯一 |
| `invoiceKind` | 蓝票 / 红票 | `invoice_kind`；红票关联原蓝票 |
| `invoiceDate` | 开票日期 | 业务日期 |
| `gross/net/taxAmount` | 含税 / 不含税 / 税额 | 服务端已确认金额；前端只格式化 |
| `roundingAdjustmentAmount/reason` | 发票尾差 / 原因 | 独立记录，不反改销售单价 |
| `allocatedTotal` / `unallocatedAmount` | 净已分配 / 未分配 | 服务端按有效分配返回，资金分配不参与 |
| 分配明细 | 销售单、应收子账、含税/不含税/税额、动作、反向来源 | `sales_invoice_allocation` |

## 6. 搜索、筛选、排序与默认视图

| 能力 | 默认值 | URL 状态 | 行为 |
| --- | --- | --- | --- |
| 视图 | `receivable` | `view` | 切换时保留往来主体和单号筛选 |
| 往来主体 | 全部有权主体 | `counterpartyId` | 核销会话创建后锁定，不允许中途换主体 |
| 经营客户 | 全部 | `customerId` | 只过滤经营归属，不改变核销相等规则 |
| 单号搜索 | 空 | `q` | 销售单、回款单、发票号的服务端搜索 |
| 状态 | 开放优先 | `status` | 可选未结、部分结清、已结清等服务端枚举 |
| 到期 | 全部开放 | `due` | 未到期 / 今日到期 / 已逾期由服务端判定 |
| 复核状态 | 全部 | `reviewStatus` | 卡券待复核、同步差额待复核可下钻 W13 |
| 排序 | 到期日升序、单号 | `sort` | 逾期风险可作为 Saved View，不覆盖用户显式排序 |

- 列表使用服务端分页和稳定 row ID；金额列右对齐，身份列和主动作列固定。
- 1440×900 下工具栏、分页和指标同时存在时至少露出 6–8 条有效行。
- 导出基于服务端冻结的当前权限/筛选快照，不能由前端遍历分页拼接。
- 核销池只查询当前 `counterparty_party_id` 的开放对象；即使搜索命中同名客户的其它主体也不返回。

## 7. 操作契约

| 操作 | 入口 | 权限 / 前置条件 | 确认 | 成功结果 | 失败恢复 |
| --- | --- | --- | --- | --- | --- |
| 登记回款并核销 | 页头、主体行、W05/W13 | 有登记权；实际主体已确定；表单和分配满足服务端策略 | 正式提交确认 | 形成回款单与有效分配，固定显示单号、金额、未分配余额和返回入口 | 保留草稿；冲突后刷新双侧余额；结果未知查询原操作 |
| 对已有回款继续核销 | 回款/待核销行 | 回款已过账且存在有效余额 | 正式提交确认 | 追加 `APPLY` 分配，不改原行 | 超额或并发占用时保留选择并显示最新开放余额 |
| 登记销项发票并核销 | 页头、主体行、W05/W13 | 发票号码唯一校验；主体一致；金额合法 | 正式提交确认 | 形成独立发票及分配，显示票号和净剩余 | 重复票号定位已有发票；不创建副本 |
| 对已有发票继续核销 | 发票/待核销行 | 蓝票存在有效余额 | 正式提交确认 | 追加销项票 `APPLY` 分配 | 同上 |
| 保存会话草稿 | 核销工作区 | 草稿可写、租约有效 | 无 | 保存输入、附件引用和目标选择，不形成正式票款事实 | 本地输入保留；租约丢失时禁止正式提交 |
| 发起客户退款/回款冲正 | 原回款或应收 detail | 有纠错发起权和业务依据 | 确认影响范围 | 形成纠错草稿并进入财务复核，不改原事实 | 失败保留原因与附件；结果未知查询操作号 |
| 发起销项红票 | 原蓝票 detail | 有红票权限、原票存在有效可红冲分配 | 确认原票及金额 | 形成独立红票和必要反向分配 | 超额/并发时刷新原票有效余额 |
| 导出当前往来 | 列表工具栏 | `EXPORT`；范围、字段和主体均已授权 | 大范围时展示筛选、行数、金额口径和遮罩规则 | 创建服务端快照与后台任务，返回任务号和 7 天下载入口 | 任务失败可按原快照重试；不在浏览器拼全量数据 |

正式提交是否要求“未分配余额为 0”由服务端返回的提交策略决定；前端不得自行发明，也不得通过拆页规避。无论策略如何，未分配余额必须持续可见并在结果中明确说明。

## 8. 数据契约

### 8.1 查询

```ts
type CustomerAccountsQuery = {
  view: "receivable" | "receipt" | "sales_invoice" | "unallocated"
  counterpartyPartyId?: string
  customerId?: string
  q?: string
  status?: string[]
  due?: "not_due" | "due_today" | "overdue"
  reviewStatus?: string[]
  occurredFrom?: string
  occurredTo?: string
  cursor?: string
  pageSize: number
  sort: string[]
}
```

查询响应至少包含权限/数据范围版本、正式水位、稳定对象 ID、服务端总数、分页游标、金额币种与口径、`allowedActions/actionBlockers`。列表及核销池分别使用 TanStack Query；Query Key 必须包含用户、角色、权限版本、主体和全部筛选。

### 8.2 提交

回款提交至少包含：草稿 ID、往来主体、到账时间、正数含税金额、银行引用/附件、追加式目标分配、应收基线版本、请求幂等键。发票提交还包含方向、蓝/红类型、规范化号码字段、含税/不含税/税额、尾差及原因、原票引用（红票适用）。

服务端在一个事务或等价一致性机制中：

1. 规范化并校验主体、号码和权限；
2. 按稳定顺序锁定资金/发票、子账和目标分录；
3. 重算双侧有效余额，拒绝超额与跨主体分配；
4. 写正式事实和追加式分配；
5. 更新应收、回款和开票同步汇总；
6. 返回正式对象号、操作号、水位和下一步。

重复提交使用同一幂等键。超时或断网后保持当前输入和“结果待确认”，通过操作号查询最终结果；不得换新幂等键重复过账。

### 8.3 前端边界

- 金额、开放余额、净分配、逾期状态、复核有效性均使用服务端结果；前端只做输入辅助和格式化。
- 前端可在当前编辑草稿中显示“拟分配合计”，但它只是输入校验提示，不得作为正式已核销金额。
- 服务端返回的提交策略决定是否允许保留未分配余额；UI 不硬编码业务规则。
- 卡券同步差额只追加应收分录；W11 不修改既有回款、发票或已通过复核记录。
- 回款分配目标是 `receivable_entry`；销项票分配目标是 `receivable_account`，两者不可共用一套无类型 ID。

## 9. 页面状态矩阵

| 状态 | 页面表现 | 可执行动作 | 恢复方式 |
| --- | --- | --- | --- |
| 初载 | 指标、工具栏、表格或核销双栏等高 Skeleton | 应用壳导航可用 | 原位替换 |
| 刷新 | 保留旧金额并显示正式水位 | 可查看；提交前重校验 | 成功更新，失败可重试 |
| 空数据 | “当前范围尚无客户往来事实” | 有权时从销售单链入；清除筛选 | 正式应收形成后刷新 |
| 筛选无结果 | 保留筛选摘要 | 清除筛选 | 返回有权数据 |
| 无数据范围 | 不展示 0 元指标 | 查看角色/申请范围 | 范围更新后重查 |
| 查询失败且无缓存 | `BusinessFailureState`，不显示 0 元或已结清结论 | 重试、返回来源 | 查询恢复 |
| 失败有缓存 | 保留旧数据并标记查询时间 | 查看；正式提交前强制重查 | 重试成功 |
| 字段级隐藏 | 金额或银行字段掩码，布局稳定 | 其它有权操作 | 权限更新后重查 |
| 草稿保存中/失败 | 禁止重复保存，输入不丢 | 重试、复制安全摘要 | 恢复后保存 |
| 正式提交失败 | 靠近主动作展示业务错误，保留分配 | 修正、按同一草稿重试 | 服务端校验通过 |
| 版本冲突 | 展示哪些目标余额变化；不静默改用户分配 | 刷新并重新确认 | 用户接受新基线后提交 |
| 正式动作成功 | `FormalActionResult` 固定展示回款/发票号、分配、未分配余额、时间和下一步 | 返回 W05、继续核销 | 目标页重查正式余额 |
| 结果不确定 | 固定结果区显示操作号，不更新本地进度 | 查询最终结果、联系支持 | 服务端返回终态 |
| 后台导出 | `BackgroundJobProgress` 显示筛选快照、金额口径和任务号 | 查看任务 | 完成后下载；失败按原快照重试 |
| 权限收回/租约丢失 | 清除敏感值，保留允许保留的非敏感输入但禁止提交 | 返回列表 | 权限恢复后重新取数 |

## 12. 验收清单

- [ ] 应收、回款、销项发票在同一客户往来工作面可查，但事实和分配轨道明确分离。
- [ ] 从 W05 到登记回款并核销，再返回 W05 不超过一个任务页签会话且上下文不丢。
- [ ] 一笔回款可分配同主体多笔应收，一笔应收可由同主体多笔回款核销。
- [ ] 销项发票独立完成多对多分配，不受回款核销进度替代。
- [ ] 核销严格使用 `counterparty_party_id`；跨主体目标不会出现在池中且服务端再次拒绝。
- [ ] 所有余额和净分配由服务端返回；前端拟合计不冒充正式结果。
- [ ] 已过账事实和分配不可编辑/删除，退款、冲正和红票追加反向事实。
- [ ] 幂等、并发余额变化、重复发票、结果不确定和权限收回均有可恢复状态。
- [ ] 1440×900 列表露出 6–8 行；五档视口及键盘核销流程通过验收。
