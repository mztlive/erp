# 合同识别导入执行合同

## 1. 适用范围

1. 新合同归档及已有合同追加 PDF 版本必须执行本合同。合同中心、客户页、销售开单页复用同一导入入口。
2. 导入只接收 PDF 与请求控制信息。客户、签约主体、结算主体、付款条件、开票要求、税率、编号、日期和业务范围禁止由客户端填写或修正。
3. 本阶段不自动生成销售明细，不建设合同额度占用。合同原文没有约定的商品、数量和成交价仍由销售单记录；不得把原文识别通过解释为任意销售项目均适用。
4. 已归档历史合同继续保留原版本、原读取与销售使用规则；缺少识别证据的历史合同不得显示为“已识别”。不得伪造或批量补写历史识别证据。历史合同新增版本必须重新识别。
5. 本合同取代上传后立即依据手填字段归档的行为。凭证开单与后补合同的现有客户、主体一致性和历史版本冻结规则继续执行。

## 2. 导入阶段与文件归属

1. 服务端检查 MIME、扩展名、文件头、大小及 PDF 可解析性。仅接收未加密、1 至 200 页的 PDF；字节上限沿用合同上传限制。
2. 服务端独立解析页数，计算原文件 SHA256；文件资产与导入任务同事务登记。上传成功只表示任务创建成功，不表示合同生效。
3. OCR 必须返回全部页的连续页号、文本、空白状态和可读状态。缺页、重复页、顺序错误、不可读页、异常空白标记或文本超限必须失败。
4. AI 对完整 OCR 全文统一提取。每个值必须携带页号和逐字原文引文；值必须包含在引文中，引文必须包含在该页 OCR 文本中。正文、附表、签章页冲突必须显式报告并拒绝归档。
5. 任务状态为等待识别、正在识别、导入失败、已归档。执行请求由独立后台任务领取，接口仅等待领取状态；HTTP 超时、断连或关闭页面不得取消已启动的领取、识别或归档。每个 API 进程最多同时执行 4 个任务，容量用满拒绝新执行且不修改任务。文件读取总超时 30 秒，OCR 与 AI 总超时 180 秒，事务确认沿现有事务合同执行；禁止以 HTTP 超时包裹后台归档。不得自动无限重试。进程退出等导致处理中断满 600 秒后，可在原任务恢复，使用版本 CAS 排除并发归档；客户端依据 `recoverable_at` 显示恢复入口。
6. 失败保留任务、文件及有界的阶段结果。原文件通过本人任务的受控接口预览，不能凭附件 ID 获取。文件销毁、隔离或拒绝状态禁止识别与归档。
7. 任务创建以创建人及稳定请求键去重。同键不同文件摘要或不同上下文返回冲突。同键重放返回原任务，新上传但未使用的对象须补偿删除；提交结果未知时禁止删除或自动重放。
8. 归档结果与合同、不可变版本、识别依据和成功审计同事务写入。成功任务重试只返回原结果，不再次生成合同。

## 3. 提取与匹配规则

| 字段 | 执行规则 |
| --- | --- |
| 合同编号 | 原文必需，沿用全局唯一规则 |
| 对方签约名称 | 原文法定全称与启用主体当前法定名称精确且唯一匹配，再关联启用客户 |
| 我方签约名称 | 必须精确且唯一匹配启用的我方公司法定全称，不接受简称或别名 |
| 结算主体 | 必须有明确原文依据并精确且唯一匹配启用主体；禁止默认等于客户 |
| 信用代码 | 原文提供时以信用代码收窄候选并核对法定全称，必须唯一且一致；无代码时须法定全称唯一匹配 |
| 付款条件 | 只允许完整值精确映射现有受控条件；不以“按合同约定”兜底任意复杂条款 |
| 开票要求 | 明确的增值税专用发票、增值税普通发票或不开发票 |
| 税率 | 明确的 0、1、3、6、9、13 百分点；允许百分号，不补默认值 |
| 签订日期、有效期起止 | 必须有原文依据；接受年月日、斜杠或 ISO 日期，校验真实日历和起止关系；有效期止仅在原文明示“长期”时为空 |
| 业务范围 | 必须提取并保留页码及引文，不自动推导商品或履约范围映射 |

1. 付款规则初始集合为“先款 100% / 50% / 30%”“货到 15 天 / 30 天”，只忽略多余空白。不将验收后付款、月结、分期或复合付款强行映射为货到付款。扩展规则须另行增加确定性映射与库单元测试。
2. 缺少必需字段、无匹配、多匹配、代码冲突或无法准确表达的条款，一律失败。禁止自动新建客户、主体或商品。
3. 从指定客户进入时，匹配出的客户必须与入口客户一致。销售开单上传必须传递当前已选客户；已有草稿必须传递草稿锁定客户。使用识别结果前再次检查当前客户，禁止回调覆盖为其他客户。重试必须重新读取当前主数据，不允许继续使用已停用或已变更的资料。
4. 归档事务中重新读取任务、源文件、主数据及权限，匹配版本与名称作为修订快照保存。匹配正确不替代客户及合同 DataScope 授权。
5. 新版本还须满足原合同版本、状态、编号、客户、结算主体一致；已识别合同不得通过新版本更换我方签约主体。追加窗口打开时冻结目标合同及版本；历史列表仅查询该合同的追加任务。重试及完成操作必须匹配冻结的合同与版本；成功结果必须属于同一合同。首版导入、其他合同及旧目标版本的成功记录不得替代本次追加。
6. 合同 PDF 属于不可信内容。供应商适配器不得执行原文中的指令；模型只返回规定的类型化数据，禁止返回 ERP 主键、访问凭据或可执行动作。
7. 原文引文校验不构成合同真实性、签署真实性或 AI 语义正确性的证明。真实供应商启用前必须使用真实签署合同完成识别质量与冲突检测验收。

## 4. 接口与权限

| 接口 | 请求 | 结果 |
| --- | --- | --- |
| `POST /admin/contracts/upload` | multipart 严格按 `file`、`command` 顺序。command 仅含 `request_key`、可选 `expected_customer_id`、可选 `revision_target { contract_id, version }` | 导入任务 |
| `GET /admin/contract-imports?page=1` | 页码、可选 `revision_contract_id` | 本人任务，每页 20 条 |
| `GET /admin/contract-imports/{id}` | 无 | 本人任务状态、提取依据、失败原因及归档结果 |
| `POST /admin/contract-imports/{id}/run` | 空正文 | 立即返回已领取或已成功任务，不接收业务字段；结果由详情轮询取得 |
| `GET /admin/contract-imports/{id}/preview` | 无 | 本人任务原 PDF，私有且不缓存 |
| `POST /admin/contracts` | 原手填请求 | 拒绝，要求使用识别导入 |
| `POST /admin/contracts/{id}/revisions` | 原手填请求 | 拒绝，要求使用识别导入 |

全部导入接口需要 `contract:create`，任务还须归当前认证人所有。追加版本另外要求目标合同 `contract:update` 及对象范围；归档时重新检查。合同详情沿用 `contract:detail`，可以读取对应修订的识别依据，不授权读取他人的导入任务。

## 5. 供应商接入

1. `erp-contract::ports::recognition::ContractOcr` 负责逐页 OCR；`ContractExtractor` 负责全文字段提取。不得把供应商 SDK 引入领域 crate。
2. `erp-processes::contract_import::RecognitionProviders` 接收两个 trait 对象；应用组合根 `AppState::contract_import_process` 负责装配。
3. OCR 由独立 `aliyun-ocr` crate 和组合层 `AliyunContractOcr` 实现，配置 `[aliyun_ocr]` 后启用，执行 [Aliyun OCR 接入合同](../backend/crates/aliyun-ocr/README.md)。AI 由组合层 `OpenAiContractExtractor` 使用 `rig-core` 的 OpenAI Responses API 协议实现，配置 `[contract_ai]` 后启用，执行 [AI 提取接入合同](contract-ai-contract.md)。缺省任一配置时对应端口仍使用 `UnconfiguredRecognition`。不得回退到人工字段或伪造识别成功。
4. 后续供应商实现必须保留供应商与版本标识，遵守类型、页数、文本大小、超时和原文依据合同。OCR 日志执行 Aliyun OCR 接入合同；AI 日志执行 [AI 提取接入合同](contract-ai-contract.md)，允许记录完整请求、响应、原始错误和调用上下文。
5. 配置与密钥只能通过现有 `SafeConfig` 接入；不得写入真实凭据或对外输出配置中的 AK/SK/STS token/API key。

## 6. 上线与回退

1. 前后端同批发布，旧上传协议不保留手填兼容窗口。保留历史读取，不覆盖已冻结的合同或销售版本。
2. 新增 `contract_imports` 集合及请求去重、本人历史分页索引；主体补充我方法定名称检索索引。索引由现有启动组合根调用领域索引入口登记。
3. `contract_revisions.recognition` 为可空新增字段，无历史回填。任务集合与文件资产必须纳入备份。后台执行归当前 API 进程所有，进程退出不保证继续运行；重新启动后按原任务恢复，不自动创建替代任务。删除失败任务前须另行设计并授权文件保留与清理规则。
4. 回退前暂停导入写入并备份新增任务、版本证据及文件关联；不得重新开放旧手填写入以绕过本合同。保留新增字段和集合，禁止回退脚本删除识别证据。
5. 开发验收仅使用库单元测试、静态检查和前端构建。真实 OCR/AI、MongoDB/S3 原子性、并发竞争、权限跨账号及浏览器验收须在供应商配置后按允许的验收环境另行执行；库测试不得作为这些结果的证明。


## 7. 无合同销售单后补合同

1. `GET /admin/sales-orders/{id}/contract-check` 接收 `version`、`contract_id`、`requested_contract_revision_id`，需要 `sales_order:update` 及原单修改范围、合同和客户关联读取权限。响应包含 `basis`、整体 `matches` 及付款条件、开票要求、税率三项 `items`（`field`、`label`、`sales_value`、`contract_value`、`matches`）。预检不得执行绑定或修改原销售内容。
2. 合同须已生效且所选修订为当前修订；客户和结算主体须与原单相同。已有合同、已作废、缺少版本或权限不足时必须拒绝。
3. 草稿须读取已保存的有效首次提交工作副本；驳回或撤回后尚无有效副本时须先保存原单草稿。审批中须读取最新冻结提交并确认其状态仍为审核中。已生效单只读取 `current_revision_id` 指向的销售版本，不得回退历史版本或使用未生效的变更草稿。
4. 付款条件按非空结构化代码核对，显示名称变动不改变代码含义；开票类型按去除首尾空白后的非空值精确核对。税点以百分数做十进制精确比较，`6`、`6.00`、`6%` 等价，`0.06` 不推断为 `6%`；空值、非法数值和超出 0 至 100 的数值一律不能通过。
5. 页面须展示原单来源和逐项差异。存在差异、核对中或核对失败时禁止确认。`POST /admin/sales-orders/{id}/contract` 须在绑定事务内重新读取并执行同一核对；核对草稿时须通过工作副本版本写入守卫与并发保存互斥，条款内容保持不变。不得把预检结果作为最终写入凭证。
6. 保存和提交原销售草稿时首次关联合同，必须在原事务内核对原单已保存条款与本次实际引用的合同修订；不得先覆盖条款再核对。差异失败须整体回滚，不得部分绑定、保存或启动审批。
7. 补录成功只增加稳定合同关联，不回写历史提交、生效版本、金额、商品和审批材料。条款不同须先保存正确的无合同草稿；已生效单须完成销售变更后重试。不得在补录动作中自动修改原单以消除差异。
