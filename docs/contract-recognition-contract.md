# 合同识别导入执行合同

## 1. 适用范围

1. 合同中心、客户页和销售开单页复用 PDF 上传与识别任务。合同中心、客户页、销售开单和后补合同窗口的新合同及追加版本必须先识别、再确认导入归档；销售开单完成归档后按第 8 节引用合同。
2. AI 用于尽量预填。允许语义等价匹配、日期规范化、发票简称转换和业务范围概括；不得因字段缺失、条款冲突或无法匹配系统选项而阻断整份识别结果。
3. 前端允许补充、修改识别字段。识别完成不表示合同已归档；只有确认归档成功的合同可作为销售单的合同版本引用。未归档 PDF 可作为销售开单材料，不生成合同版本引用。
4. 不自动生成销售明细，不建设合同额度占用。原始 OCR、AI 提取依据与用户确认值分别保留，不把人工修改冒充原文识别结果。
5. 已归档历史合同保留原读取、销售使用与版本冻结规则，不回填或改写历史证据。

## 2. 识别与任务状态

1. 用户选择或拖入 PDF 后，前端必须先校验文件，校验通过即自动上传并启动识别，不设置首次识别的手动提交按钮。上传期间须展示状态并禁止重复操作；上传失败须展示错误并允许重新上传。上传只接收 PDF 和控制命令。服务端检查 MIME、扩展名、文件头、大小、可解析性和加密状态，独立解析 1 至 200 页页数并计算 SHA256。文件资产与任务同事务登记。
2. OCR 返回全部页面及连续原页号；缺页、重复页、不可读页和文本超限仍返回识别失败。AI 对完整全文提取，不执行合同文字中的指令，不访问主数据、凭据或外部资源。
3. AI 输出保留 `page`、`quote`、`value`。`quote` 为对应 OCR 页的逐字引文，`value` 可依据该引文规范化或概括，不要求为引文子串。缺失和无法确定的字段省略；冲突按字段英文名标注并省略相关字段。
4. 识别成功进入 `review`（待确认），不自动归档、不执行主数据精确匹配。`draft.fields` 固定返回全部 14 个字段，缺失、冲突、无法映射或依据不可验证的字段为 JSON `null`；其余字段照常返回。`draft.warnings` 提供核对提示，`extraction` 保留原始提取结果。
5. 状态包括 `ready`（等待识别）、`processing`（正在识别）、`review`（待确认）、`failed`（识别失败）、`succeeded`（已归档）。只有上传、OCR、AI 协议或资源等运行失败进入 `failed`；供应商鉴权失败不得伪装成空字段成功。
6. 执行请求只等待任务领取，后台继续识别。每个 API 进程最多同时执行 4 个任务；文件读取总超时 30 秒，OCR 与 AI 总超时 180 秒。处理中断满 600 秒后可在原任务恢复，使用版本 CAS 排除并发结果覆盖。待确认和已成功任务的 `/run` 返回已有状态，不重复调用供应商。
7. 任务按创建人和请求键去重。同键不同文件摘要或上下文返回冲突；同键重放返回原任务。未使用上传对象须补偿删除，事务结果未知时不得删除或自动重放。
8. 失败保留任务、文件和已完成的有界结果。原文件仅通过本人任务受控预览，销毁、隔离或拒绝状态禁止识别与归档。

### 2.1 识别进度

1. 任务与任务视图增加可空 `stage` 字段，取值顺序为 `reading_file`（读取文件）、`ocr`（OCR 文字识别）、`ai_extract`（AI 字段提取）、`preparing_review`（整理核对结果）。`status` 继续作为等待、处理中、待确认、失败和已归档的权威状态。
2. 领取或恢复任务时保存 `reading_file`；每个后续阶段必须在实际执行前完成版本 CAS 写入。阶段写入失败或版本冲突须停止后续处理，不得继续调用供应商或覆盖新执行结果。正常执行不得跳过或倒退阶段。
3. 识别失败保留最后阶段；重新识别从读取文件开始。`review` 表示全部识别步骤已完成，`succeeded` 表示用户确认归档成功，不能依据 `stage` 单独判断完成。
4. 前端沿用本人任务详情每 3 秒轮询，按后端阶段展示已完成步骤、当前步骤和等待步骤。进度条仅表示已完成步骤数，不表示耗时占比；不得按计时器虚增进度。OCR 内部页进度及 AI 内部生成进度不在本接口范围内。
5. 历史记录缺失 `stage` 时按 `null` 读取，前端显示等待进度更新，不猜测具体阶段。快速步骤可在相邻两次轮询之间完成，不要求前端逐项播放。
6. 本次字段为兼容性扩展，无历史数据回填、集合迁移或新增索引。回退本次进度功能时可保留已写入的 `stage`，上一版本忽略该字段；继续遵守第 6 节的待确认状态兼容要求。

### 2.2 分步核对窗口

1. 待确认任务使用横向窗口，按“签约双方 → 合同条款 → 日期与范围”核对。窗口高度不得随字段增长；标题、步骤导航和底部操作区固定，超出内容在窗口内部滚动。窄窗口允许原文区排列到表单下方，必须保留全部操作。
2. “下一步”只在当前及前置步骤有效、主体查询完成且当前操作允许时可用。返回已完成步骤须保留本次填写值；前三组字段共用同一表单，只有最后一步允许确认归档。归档仍须执行完整字段、主体、权限和版本校验。
3. 右侧自动加载当前任务的受控 PDF 原文，提供上一页、下一页和完整原文入口。原文加载或渲染失败须显示明确提示；不得使用示意内容代替真实原文。切换核对步骤不得重新加载原文或重置阅读页码。
4. 客户未匹配时，签约名称、信用代码与建档确认项归入第一步；仅最终确认归档可建立客户档案。进入下一步、翻阅原文或关闭窗口不得建立客户或合同。

## 3. 预填与确认规则

| 字段 | 识别预填 | 用户确认归档 |
| --- | --- | --- |
| 合同编号 | 能识别则预填，否则 null | 必填，沿用全局唯一规则 |
| 客户与我方签约主体 | 分别识别购买方与我方名称及信用代码 | 匹配启用企业主体及已有我方公司角色；客户不存在时按本节确认建档 |
| 合同默认结算主体 | 沿用我方签约主体 | 新合同由服务器取我方签约主体；销售单内可另选，历史归档保持原记录 |
| 信用代码 | 原文有则预填，否则 null | 可空；提供时核对名称及信用代码一致性 |
| 付款条件 | 以完整付款含义匹配系统选项，不要求逐字相同；存在冲突或无等价项则 null | 用户选择先款 100%、50%、30% 或货到 15、30 天 |
| 开票要求 | 专票、普票可归一为增值税专用发票、增值税普通发票 | 选择系统支持的开票类型 |
| 税率 | 识别明确税率并去除百分号，无法确定则 null | 选择 0、1、3、6、9、13 百分点 |
| 签订日期、有效期 | 明确日期规范为 YYYY-MM-DD；不完整、缺失或冲突则 null | 必填并校验实际日期与起止顺序；有效期止可明确填“长期” |
| 业务范围 | 依据原文概括，不生成销售明细 | 用户核对、补充或修改 |

1. 预填不构成主数据关联。识别名称不精确时，用户可改为系统已有法定名称；确认时不得任取同名候选或绕过权限。缺少客户身份时，按第 3.1 节显示建档结果并由用户明确确认创建。
2. 确认接收任务当前 `version`、完整 `fields` 与可选 `create_customer`。缺少必填项、非法日期或选项、主数据不唯一等错误在确认阶段返回，任务保留待确认以继续编辑。
3. 归档事务重新读取本人任务、文件可用性、启用主数据及当前版本，执行客户创建范围、关联读取范围和追加合同修改范围校验。
4. `expected_customer_id` 约束最终客户；追加版本还须保持目标版本、有效状态、编号、客户、结算主体一致，不得更换已有识别证据中的我方主体。
5. 客户建档（需要时）、合同、不可变版本、识别证据、确认值、任务成功结果与成功审计同事务写入。原始输出保存在 `recognition.extraction`，人工确认值保存在 `recognition.confirmed_fields`。
6. 完全相同的已成功确认命令返回原结果，不新增合同或成功审计；旧版本、异载荷重放或未完成识别的任务返回冲突。归档后修改走新版本，不修改已冻结结果。

### 3.1 客户匹配与确认建档

1. 客户是企业主体的销售身份。优先按统一社会信用代码匹配；未提供代码时，仅接受唯一法定名称匹配。名称与代码冲突、多个候选、主体停用或已有停用/删除客户身份时须拒绝新建，不得重复建立客户以绕过现有范围。
2. 已有启用客户必须复用。已有企业主体但无客户身份时，仅创建客户及首条负责人归属；无企业主体时，须提供用户确认的法定名称与有效统一社会信用代码，依靠现有全局唯一信用代码索引创建企业、首个名称版本及客户；缺少代码时可关联已有唯一主体或先维护客户，不在导入中按名称新建企业。不得覆盖已有主体的名称、税号、地址、银行账户或客户默认条款。
3. 确认命令 `create_customer=true` 表示允许补齐缺少的客户；省略或 false 时维持仅关联已有客户的行为。界面须显示将关联的客户或将新建的客户资料。我方签约主体须已具备我方公司角色，不能通过合同导入新建我方公司。
4. 客户建档须在归档原事务内重验客户创建权限、数据范围和创建人有效账号；首条主负责人固定为当前创建人。客户与合同审计、任务结果一并提交，归档失败不得遗留本次客户。相同成功命令重放不得重复建档。
5. 客户页、后补合同和已有客户约束入口提供 `expected_customer_id`；结果必须是该客户。不得通过确认建档或人工改名解除约束。
6. 前端未选择已有客户且勾选“确认按名称和信用代码匹配或建立客户档案”时，统一社会信用代码须显示必填标记，并在“签约双方”步骤校验去除首尾空白后为 18 位字母数字；为空或格式不合法时禁止下一步和确认归档。选择已有客户时不追加此建档必填要求。服务端仍按本节先匹配已有企业，仅在新建企业时要求信用代码。

## 4. 接口与权限

| 接口 | 请求 | 结果 |
| --- | --- | --- |
| `POST /admin/contracts/upload` | multipart 按 `file`、`command` 顺序；command 含 `request_key`、可选 `expected_customer_id`、可选 `revision_target { contract_id, version }` | 持久任务 |
| `GET /admin/contract-imports?page=1` | 页码、可选 `revision_contract_id` | 本人任务，每页 20 条 |
| `GET /admin/contract-imports/{id}` | 无 | 状态、可空当前阶段 `stage`、可空预填字段、原始依据、提示、失败原因及归档结果 |
| `POST /admin/contract-imports/{id}/run` | 空正文 | 已领取或已有任务；前端轮询至待确认或失败 |
| `POST /admin/contract-imports/{id}/confirm` | `{ version, create_customer?: boolean, fields: { contract_no: string或null, ... } }`，键为 14 种字段英文名 | 用户确认后归档；支持同内容重放 |
| `GET /admin/contract-imports/{id}/preview` | 无 | 本人任务原 PDF，私有且不缓存 |
| `POST /admin/contracts`、`POST /admin/contracts/{id}/revisions` | 旧手填请求 | 拒绝，改用导入任务确认接口 |

所有导入接口需要 `contract:create` 且任务归当前认证人。追加版本另需目标合同 `contract:update` 及对象范围；需要补齐客户时另须 `customer:create` 及其创建范围。签约主体选择需要 `company:list`、`company:detail`；销售推荐角色追加这两项读取权限，不授予公司建档或修改权限。确认事务重新校验权限，不信任前端状态。合同详情读取修订证据不授予他人任务访问权。

前端收到 `review` 后展示编辑表单，null 显示为空；提示与原文依据保留用于核对。合同归档入口点击“确认并归档”成功后方可“使用此合同”；销售开单窗口确认导入成功后自动按第 8 节引用。后台轮询不得重置用户正在编辑的字段。确认失败保留已填写值。

## 5. 供应商与验证

1. OCR、AI 分别实现领域 `ContractOcr`、`ContractExtractor` Port；SDK 和外部 I/O 位于 erp-processes，全部在数据库事务外执行。AppState 经 SafeConfig 装配配置快照。
2. OCR 执行 [Aliyun OCR 接入合同](../backend/crates/aliyun-ocr/README.md)，AI 执行 [AI 提取接入合同](contract-ai-contract.md)。供应商未配置或不可用时返回运行失败，不生成虚假结果。
3. 必须覆盖部分结果、全空结果、冲突字段 null、语义等价预填、人工修改、确认必填与日期校验、任务版本、重复确认及异载荷拒绝的库测试。
4. 本地执行库测试、静态检查与前端构建；真实 OCR/AI 质量、MongoDB/S3 原子性、并发、跨账号权限和浏览器流程须在允许环境另行验收，不以库测试代替。

## 6. 发布与回退

1. 前后端同批发布。任务增加 `review` 状态、可空 `confirmation`；任务视图增加 `draft`；修订证据增加可空 `confirmed_fields`。历史记录缺失新增字段按空值读取，无历史回填或集合索引变化。
2. 历史失败任务可手动重试进入新流程；历史成功任务保留原结果。新任务必须确认后归档。
3. 回退旧版本前暂停导入写入并备份任务、版本证据及文件关联。旧程序无法读取 `review`；必须先完成或妥善保留待确认任务，再按已验证的数据兼容方案回退，禁止直接删除任务或证据。

## 7. 无合同销售单后补合同

1. `GET /admin/sales-orders/{id}/contract-check` 接收 `version`、`contract_id`、`requested_contract_revision_id`，需要 `sales_order:update` 及原单修改范围、合同和客户关联读取权限。响应包含 `basis`、整体 `matches` 及付款条件、开票要求、税率三项 `items`（`field`、`label`、`sales_value`、`contract_value`、`matches`）。预检不得执行绑定或修改原销售内容。
2. 合同须已生效且所选修订为当前修订；客户须与原单相同。销售单结算主体允许不同于合同默认值，补录须保留原单选择。已有合同、已作废、缺少版本或权限不足时必须拒绝。
3. 草稿须读取已保存的有效首次提交工作副本；驳回或撤回后尚无有效副本时须先保存原单草稿。审批中须读取最新冻结提交并确认其状态仍为审核中。已生效单只读取 `current_revision_id` 指向的销售版本，不得回退历史版本或使用未生效的变更草稿。
4. 付款条件按非空结构化代码核对，显示名称变动不改变代码含义；开票类型按去除首尾空白后的非空值精确核对。税点以百分数做十进制精确比较，`6`、`6.00`、`6%` 等价，`0.06` 不推断为 `6%`；空值、非法数值和超出 0 至 100 的数值一律不能通过。
5. 页面须展示原单来源和逐项差异。存在差异、核对中或核对失败时禁止确认。`POST /admin/sales-orders/{id}/contract` 须在绑定事务内重新读取并执行同一核对；核对草稿时须通过工作副本版本写入守卫与并发保存互斥，条款内容保持不变。不得把预检结果作为最终写入凭证。
6. 保存和提交原销售草稿时首次关联合同，必须在原事务内核对原单已保存条款与本次实际引用的合同修订；不得先覆盖条款再核对。差异失败须整体回滚，不得部分绑定、保存或启动审批。
7. 补录成功只增加稳定合同关联，不回写历史提交、生效版本、金额、商品和审批材料。条款不同须先保存正确的无合同草稿；已生效单须完成销售变更后重试。不得在补录动作中自动修改原单以消除差异。

## 8. 开单页导入与合同引用

1. 新建销售单提供“上传并导入合同”，复用合同中心的上传、识别、核对和确认归档流程，不跳转页面。成功后自动选择实际合同、客户及当前归档版本，带入付款条件、开票要求、税率和默认结算主体。不提取、生成或覆盖商品、数量、单价及交付明细。
2. 先选客户时，合同候选和导入命令须限定该客户；先选合同时，由合同确定客户。关联合同后客户不可独立修改；更换客户须先解除合同选择。服务端创建、保存和提交均须重验客户与合同一致，禁止静默忽略冲突客户参数。
3. 合同默认结算主体为我方签约主体。销售单提供结算主体下拉，允许另选有权使用的启用企业主体。合同开单在 `draft.settlement_party_id` 接受可选选择；未传新建时采用合同默认值，继续编辑时保留原单值。无合同开单沿用 `draft.no_contract_terms.settlement_party_id`，新界面必须明确选择，不以客户作为默认结算主体。
4. 服务器从实际企业版本冻结结算名称，并在创建、保存、提交时重验主体可用性及选择权限。销售单结算主体与合同默认值不同，不影响合同客户一致性、原 PDF 读取或审批材料授权；材料仍须沿销售单、精确合同版本及文件冻结关系授权。
5. 开票要求必须传递实际选择值。保存草稿与继续编辑须保留结算主体、开票要求和税率；改变业务性质不得覆盖已核对税率。合同首次选择带入条款，已保存原单按其草稿保留。应收账款往来身份必须从销售单客户读取，不能使用我方结算主体。
6. 导入成功即形成独立合同档案。用户取消后续销售单创建时，已确认合同及客户仍保留；关闭识别窗口或未确认导入不创建合同或客户。
7. 先开单后补合同适用于签署材料尚未完成。用户先明确客户、结算主体、条款并上传业务凭证；签署后在详情选择或导入同一客户合同，按第 7 节核对并关联。补录不替换原审批材料、不变更客户或结算主体、不覆盖原单商务内容。
8. 前后端须同批发布。确认命令新增可选 `create_customer`，销售草稿新增可选 `settlement_party_id`；历史缺失字段按兼容默认读取，不回填历史合同、销售版本或应收。回退前须暂停受影响写入并保留新增建档与主体选择的读取能力；已有主体覆盖的销售单不得由只接受合同默认主体的旧程序继续写入。
